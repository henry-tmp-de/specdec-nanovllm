## 0. 摘要（先看这五条）

1. **结论：是 bug，不是「截断的固有代价」。**
   在**同一个位置、同一条轨迹**上把「引擎实际用的 draft 分布 q_eng」和
   「按引擎自己声明的窗口重算一遍的 q_ideal」放在一起比：
   `P=0, M=5` 时 **TV(q_eng, q_ideal) = 0.685**（引擎的 KV **不是**它声明的那扇窗口）；
   而 `P=2, M=5` 时只有 **0.056**。⇒ 代价不在「窗口小」，在「环里存的东西 ≠ 声明的窗口」。

2. **★ 决定性判据（把「滑动」与「截断」解耦）**：
   `q_ideal` 就是「同样截断、但窗口起点不漂移」的那一档。它在引擎自己的轨迹上给出

   | 口径（8K / B=1 / out=128） | TV(p,q) → α |
   |---|---:|
   | 引擎实际（P=0,M=5） | 0.644 → **α 0.356** |
   | **同样截断、缓存一致（q_ideal）** | 0.389 → **α 0.611** |
   | target 被截断本身的影响 `TV(p_eng,p_win)` | 0.081 |

   ⇒ **截断只值 0.04**（0.65→0.61），**崩掉的 0.25 全来自缓存与声明不一致**。

3. **根因（指到行）**：`model_runner._run_draft_prefill_window` 把尾部窗口
   **一次性**按 `b0 = w.b0(end-1)`（`nanovllm/engine/model_runner.py:673`）写下，
   chunk 里**所有**位置都编码了同一个起点；而解码期 `DraftWindow.b0`
   （`nanovllm/spec_decode/draft_proposer.py:177-179`）的
   `max(valid_from//bs, pos//bs − M + 1)` 在序列**跨进新块**时把起点**前进一格**。
   ⇒ 环里被保留的那几个块，仍然编码着「读端已经声明丢掉的那一块」的上下文。
   逐位置 KV 对拍证实：把参考前向的窗口起点换成 prefill 那个（6912 而不是 7168），
   层 14/27 的 `max|ΔK|` 从 **10–38 → 0.5–7.5**（KV 本身量级 ≈ 40）。

4. **修法（默认关、老路径一行没删）**：新增 `spec_draft_win_align`（`nanovllm/config.py`）。
   开启后 prefill 对齐到**第一个生成位置**所在块的 `b0(end)`，并把它当解码期窗口下界的**地板**
   （`Sequence.draft_win_start`）。修复后 **TV(q_eng, q_ideal) 0.685 → 0.016**。

5. **★ 修前/修后 α（8K / B=4 / out=256 / k=6 / max_num_seqs=4，引擎内确定性仪器）**

   | | α_step（确定性） | accept_rate | tokens/轮 |
   |---|---:|---:|---:|
   | `m5` 修复前 | **0.345** | 0.100 | 1.60 |
   | `m5` 修复后 | **0.642** | 0.310 | 2.87 |
   | （参考）普通投机 `w0` | 0.655 | 0.672 | — |

   ⇒ **修复把「滑窗掉 44%」变成「基本持平」**；剩下的差（0.642 vs 0.655）才是真正的截断代价。

## 2. 排查过程：每一步排除了什么（★ 这一段是资产）

### 2.1 先排「是不是我把参考算错了」—— 同一套方法跑 `w0`

`scripts/slide_probe.py` 在 `DraftModelProposer.propose_batch` **之前**（引擎自己的前向
还没跑、环还没被写）做一次**纯 local-causal 重算**：把「引擎即将读的那扇窗口的 token」
喂给同一个 draft 模型（`set_context(True, ...)` + 临时把 `k_cache/v_cache` 摘成空张量，
从而走本地 k/v、**不写任何 cache**），拿最后一位的 logits 当 `q_ideal`，与引擎
`out_logits[:,0]` 直接比。

- **对照 `w0`（window=0，全上下文）**：`TV(q_eng, q_ideal) = 0.0 ~ 0.04`、`max|Δlogit| ≤ 0.5`
  ⇒ 探针本身没问题（paged decode 与 local-causal 的差别只有 ULP 量级）。
- **`p2m5`**：`TV(q_eng, q_ideal) = 0.045`（用**声明口径** head+tail 当参考）。
- **`m5`（P=0）**：`TV(q_eng, q_ideal) = 0.510 ~ 0.685`，`max|Δlogit|` 到 20 以上。
  ⇒ **同一个探针、同一套口径，只有 P=0 崩**。

### 2.2 排除「是截断造成的」—— 决定性解耦实验

`q_ideal` 这一档的语义就是：**可见窗口与引擎完全一样（同样截断），但窗口起点不漂移、
KV 与声明一致**。于是同一条轨迹上：

```
TV(p_eng, q_eng)      = 0.644   → 引擎 α 0.356
TV(p_eng, q_ideal)    = 0.389   → 若缓存一致，α 会是 0.611
TV(p_win, q_win)      = 0.269   → 连 target 也一起截断时：α 0.731
TV(p_eng, p_win)      = 0.081   → target 侧被截断的影响
```

★ **判据成立**：**不滑动（窗口起点不动）就不崩** ⇒ 是**滑动路径**的问题。
三条独立佐证：
1. 台账自己的 `p0m33`（窗口盖住全序列、环形缓冲从不回绕）α = 0.642 ≈ 普通投机；
2. 台账记的「第 1 轮 TV ≈ 0.23」**恰好等于**我们算出的理想值 `TV(p,q_ideal) = 0.26`；
3. 逐轮打点：**所有**被打到的轮次 `b0 = 28`（已经漂移过），而 prefill 写下的对齐是 `b0 = 27`。

### 2.3 排除「是几何/块表算错」—— 逐位置 KV 对拍

`scripts/slide_kv.py`：在某一轮的前向**之前**，按 `DraftWindow.slot(p)` 把引擎
`k_cache/v_cache` 里窗口内每个位置的槽位读出来，与「同一窗口重算一遍」的逐位置 `k/v` 比。

| 参考窗口起点 | 层 0（只依赖 token+RoPE） | 层 14 / 27（依赖上下文） |
|---|---|---|
| `REF_START = 7168`（读端声明） | **0.0000（逐位相同）** | max\|ΔK\| = 10.8–34.0，256/256 个位置都差 |
| `REF_START = 6912`（**prefill 的对齐**） | 0.0000 | max\|ΔK\| 掉到 **0.5–7.5** |

★★ **两条结论同时拿到**：
- **层 0 逐位相同 ⇒ 环里的 token 与位置是对的**（没有覆盖、没有错位、没有串请求）；
- **层 ≥1 只有在用 prefill 的起点重算时才对上 ⇒ 环里那些块的「上下文起点」是 prefill 的
  6912，而读端声明的是 7168。**

⇒ 台账 §2.7.2 排除掉的「写入时的 KV 被写坏」是对的；**没被排除的是「写的时候用的上下文」**。

### 2.4 排除「是敏感度不够/参考太苛刻」—— 扰动敏感度对照

把「多一块（256 token）前置上下文」这个扰动**单独**加在同一个干净窗口上：
`TV(q_ideal, q_ideal+1块)` ≈ **0.14–0.22**（P=0/P=2 都差不多）。
而引擎实际偏离 `TV(q_eng, q_ideal) = 0.685`（P=0）——
**引擎的偏离比「多一块上下文」还大**（因为除了老块带着旧起点，新块自己的 KV 又是在这批
带污染的老 key 上算出来的，误差会往下传）。
⇒ 不是探针苛刻，是引擎确实偏得更多。

## 3. 根因（机制）

一块环形缓冲里同时存在两种「对齐」：

```
draft 上下文 = 序列开头 P 块（常驻） + 最近 M 块（环，绝对块号 b → ring[b % M]）

写（prefill，一次成型）   b0_write = w.b0(end - 1)                 ← 对齐到 prompt 最后一位
写（decode，每步一格）    b0_write = max(vf, pos//bs - M + 1)      ← 对齐到当前位置
读（decode）              b0_read  = max(vf, pos//bs - M + 1)
```

`ctx = 8192`、`bs = 256`、`M = 5` 时：

1. prefill 写 `[27*256, 8192)` = 块 **27..31**，全部按起点块 27 的上下文；
2. 解码第一步（查询位置 8191）`b0 = max(27, 31−4) = 27` —— **与 prefill 同对齐** ⇒ 一致
   （这正是台账记的「第 1 轮 α 正常」）；
3. 一旦查询进入块 32（位置 ≥ 8192），`b0 = max(28, 32−4) = 28`，读端**声明**「只看
   `[7168, now)`」——**但环里保留的 28..31 号块是「带着 6912..7167 那一段上下文」写出来的**；
   而 27 号块的槽位此刻已经被 32 号块覆盖掉了（环只有 5 格），**没法再把它算回去**。
4. ⇒ 读端声明的可见区间与 key 的表示**不是同一个上下文**，草稿分布整段偏移。

**这不是「少读几个 token」的问题**（那只要值 0.04），而是**读到的 key 带着读端已声明不要的
上下文**。它天然是「轮次级」的：只在窗口起点漂移发生的那一步（+ 之后每一步）出现。
`P=0` 时模型没有 attention sink，对这种偏移极度敏感；`P≥1` 时常驻段把敏感度压下去，
所以表现为「加 P 就修好了」——**P 轴真正在修的，是这个对齐漂移**（与台账 §2.7.1「P 轴真正在修的是『滑动』」一致，
本轮把它隔离出来了）。

## 4. 修法（默认关、可关、老路径一行没删）

| 文件 | 改动 |
|---|---|
| `nanovllm/config.py` | 新增 `spec_draft_win_align: bool = False`（默认 False = 老行为） |
| `nanovllm/engine/sequence.py` | 新增字段 `self.draft_win_start = 0`（加性、默认 0） |
| `nanovllm/engine/model_runner.py` `_run_draft_prefill_window` | 开启时 `b0 = w.b0(end)`（对齐到**第一个生成位置**所在块）并记下 `seq.draft_win_start = b0*bs`；**关闭时走原来那句 `b0 = w.b0(end - 1)`，一个字没改** |
| `nanovllm/engine/model_runner.py` `_draft_request` | 开启时 `valid_from = max(valid_from, seq.draft_win_start)`（解码期窗口下界地板）；关闭时该行不执行 |

**原理**：让「写下环里那些块时的起点」和「解码期读它们时声明的起点」是**同一个对齐**。
代价是窗口最多少一个块（`end` 不是块边界时两者本来就相等，所以只在
`end % bs == 0` 这一刀上生效），换来的是「环里的内容 = 声明的窗口」。

★ 诚实的边界：这个修法**修的是第一次漂移**。序列再往前走、窗口起点再次前进一格时，
同一个问题会再次出现（那时需要「漂移时重算保留下来的那几个块」或「每条序列多给一格环」，
见 §6 挂账）。本实验的条件（ctx=8192 + out=256 ⇒ 最多到块 33）内不会二次漂移。

## 6. 没查清 / 挂账

| 项 | 状态 |
|---|---|
| **第二次及以后的漂移** | ★ **未修**。本轮只把「第一次漂移」对齐了。序列跨进块 33 之后会再次出现同类偏差。**修法候选**：①漂移发生时重算保留的那几块（≈一次 1024-token draft 前向 / 256 生成 token）；②每条序列的环多给一格（`(P+M+1)×max_num_seqs` 块），让起点可以晚一格前进。**两条都没实现、没测。** |
| **为什么 P≥1 能把敏感度压下去** | ★ **未隔离**。KV 偏差在 `p2m5` 上**同样存在**（层 14/27 逐位置差，量级与 `m5` 相当），但 `TV(q_eng,q_ideal)` 只有 0.045。机制猜测是「常驻段当 attention sink 吸收注意力质量」（本轮**没做** attention 权重可视化，也没有「只留前 4 个 token」的对照）。 |
| **「理想窗口」到底该怎么定义** | 本轮的 `q_ideal` = 「把这扇窗口当自足序列重算」。另一种可选语义是真流式滑窗（每个位置用它自己的 W 长窗口）。**这一段没有定论**，也**没测**另一种。 |
| **`P=0` 修好后还需不需要 P** | 本轮测到「同样截断、缓存一致」时 P=0 与 P=2 的理想 α 差不多（0.611 vs 0.587）。这只在 8K/B=1/out=128 一格上测过，**不足以推翻 P7-D 的 P 轴结论**（自由生成口径、25 格网格）。**需要重跑 P7-D 的网格（带 ALIGN=1）才能回答「P 是不是只在补这个 bug」。没做。** |
| **B=4 下的加速比** | 本轮只报了 α 与 tokens/轮，**没有重测 TTFT / tok-s**。修复会不会改变「滑窗的容量/速度账」**没测**。 |
| **`spec_draft_win_align` 与其他开关的交互** | 只和 `spec_draft_window` / `spec_draft_head_blocks` 组合测过（m5 / p2m5 / w0）。与 INT8 量化、分块 prefill（P13）**没测**。 |
