## 0. 怎么读这份台账（★ 先看这一节，否则数字会混用）

这个项目踩过好几次「数字口径混用」的坑，所以每条都标了口径。四个维度必须一起看：

| 维度 | 取值 |
|---|---|
| **算力口径** | `纯 kernel 时间`（torch.profiler 的 device time）≠ `墙钟`（含 Python dispatch / kernel launch / 同步） |
| **负载** | `batch` / `输入长度` / `输出长度` / `k`(投机候选数) |
| **负载文本** | `合成池化素材`（接受率被抬高到 0.95–0.99）≠ `自然长文/代码`（接受率 0.74–0.84） |
| **对照** | 跟 `U`（target-only 普通解码）比？还是跟 `C`（我们自己的旧投机实现）比？ |

**★ 最容易被误用的一条**：投机相关的加速比**高度依赖接受率**。合成素材上能到 1.19×，
把接受率按自然文本的水平还原后只有 **0.897×**。所以凡是投机加速比，**必须连报接受率**。

**硬件与软件**：RTX 3090（sm_86，24 GB，显存带宽规格 936 GB/s / 实测流式天花板 842 GB/s）·
Qwen3-4B（target）+ Qwen3-0.6B（draft）· BF16 · temperature=1.0 · torch 2.10.0+cu128 · triton 3.6.0 · flash-attn 2.8.3

## 1. 约束地图（先看这个，它决定了哪些方向有量）

**普通 decode 的 GPU 时间分解**（B=1、ctx=4096、CUDA Graph 开、64 个 decode step）：

| 类别 | 占 device 时间 | 说明 |
|---|---:|---|
| **GEMM / 线性层** | **79.27%** | batch=1 时是**纯权重流式**：8 GB 权重 / 10.5 ms = **763 GB/s = 3090 峰值带宽的 81%**，基本跑满 |
| attention | 9.24% | 随 ctx 上升：**8.12% / 9.24% / 14.68%** @ ctx 1024/4096/8192 |
| elementwise / norm / rope | 8.37% | Sampler 已被 torch.compile 融合成 1 个 kernel |
| 采样 / KV 写入 / memcpy / 其他 | 合计 ~3% | 采样仅 **0.81%** |

**prefill**：B=4 的 TTFT 是 B=1 的 **4.09 倍**（完全线性、不摊薄），反推 ≈65 TFLOPS，
**贴着 3090 的 bf16 峰值（约 71）→ 没有空间**。

**三条直接推论**（后面所有决策都建立在这上面）：
1. **decode 想显著变快，只能让权重变小**（量化）。不动权重，那 79% 是墙。
2. **prefill 没空间** → 「长 prompt 堵住 decode」只能靠**调度**解决，不能靠优化 prefill。
3. **吞吐的杠杆是并发**：B=1→B=4 时 U 的效率涨 **3.6 倍**（0.082 → 0.295 token/ms），
   而 B=4 时算力只用掉峰值的三十分之一 → **远没饱和**。

## 2. 优化清单

### 2.1 投机解码：把「实现正确但更慢」翻成真正加速

| | |
|---|---|
| **做了什么** | 在 nano-vllm 上实现线性链投机解码（draft 模型自回归猜 k 个候选 → target 一次前向验证 → 拒绝采样接受前缀 → 回滚）。**查出并修掉 5 个静默 bug** |
| **效果** | 相对**不开投机的普通解码**：baseline 82.3 → draft k=6 **132.5 tok/s = 1.61×**。**把符号翻正的是 CUDA Graph 而不是算法**：同一配置不拍图时只有 **20.8 tok/s = 0.68×**，每步产出几乎没变（3.77 → 3.82 个 token），变的只有 per-step 固定开销 |
| **条件** | 单条 256 token 生成的**自然代码 prompt**、B=1、graph on |
| **证据** | `scripts/bench_spec.py`；5 个 bug 的构造性证据见 `README.md` 第二节 |
| **★ 简历可写** | 「在 nano-vllm 上实现线性链投机解码，单请求吞吐 **+61%**；定位出瓶颈是 per-step 固定开销而非算法效率（不拍图时反而慢 32%），据此用 CUDA Graph 把符号翻正」 |

|---|---|
| **做了什么** | 给 draft 前向（bs=1、每步 1 token）与验证前向（bs=1、query 恒 1+k、varlen）**各拍一张静态形状的图**；形状不匹配自动退回 eager |

### 2.3 手写 paged decode attention（Triton + CUDA 两版）

| | |
|---|---|
| **做了什么** | 三版递进的 Triton 实现（v1 每(序列,q头)一 program → v2 按 kv 头分组共享 K/V → **v3 split-K**），再用 **Ampere 深度**重写 CUDA 版：`mma.sync` + `ldmatrix` + **`cp.async` 三级流水** + XOR swizzle |
| **效果** | 纯 kernel：v1 **192 µs** → v2 112 µs → **v3 31.4 µs**；CUDA 版 **25.87 µs / 648 GB/s = 实测带宽天花板的 77%**。<br>**vs flash-attn（41.2 µs / 410 GB/s / 48.7%）= Triton v3 快 1.31×、CUDA 完整调用快 1.47×** |
| **条件** | ctx=4096、B=1、Qwen3-4B 配置（GQA 32:8、head_dim 128）、bf16、随机数据 |
| **证据** | `nanovllm/kernels/README.md`；`scripts/bench_paged_decode.py`、`bench_cuda_paged_decode.py`、`prof_paged_decode.py` |
| **关键阶梯** | `cp.async` 三级流水一步值 **1.43×**（36.91 → 25.87 µs）；这个在 Triton 里改 `num_stages` 毫无反应 |
| **★ 简历可写** | 「手写 paged decode attention：Triton 三版递进到 **523 GB/s（62% 天花板）**，再用 CUDA `mma.sync`+`cp.async` 三级流水重写到 **648 GB/s（77%）**，比 flash-attn 快 **1.31–1.47×**；占用率仅 8% 却跑出 77% 带宽，证明 `cp.async` 把在途访存请求数与 warp 数解耦」 |

### 2.4 ★ 阶段 0：四项正确性修复（`df6e15f` `27a290d` `368303f` `1591bdf`）

**无性能收益**，但修掉了会让长上下文结论全部失效的缺陷。**这一节的价值在"发现了什么"，不在"快了多少"。**

| 修什么 | 后果（修复前） | 证据 |
|---|---|---|
| **前缀缓存哈希契约** | **prompt ≥384 或恰好 256 token → `IndexError` 崩溃**；128–383 把**半满块**当满块登记（静默污染）；且**从未登记过合法的 block 0**（缓存实际失效） | GPU 实测边界表：修复后 255/256/257/383/384/385/1024/2048/4096/8192 全通；修复前 256/384/512 崩 |
| 吞吐计数 | 用 `1+last_accepted` 计数，与实际交付 token 数不符 | 新口径严格等于 `len(output_tokens)` |
| 温度广播 | `_softmax_with_temp` 把长度 B 的温度塞进 vocab 维 | B=1 时字节等价（不影响基准），为批量铺路 |
| 门控快照 | `spec_enabled()` 读会随 `popleft()` 变短的队列长度 → 同轮内决定不一致；`spec_k` 有两份副本会漂移 | 副本偏小会导致往未分配槽位写 KV |

测试：**37 → 115 项**（纯 CPU，全过）。

**★ 简历可写** | 「发现并修复前缀缓存的进度契约缺陷——修复前 **prompt ≥384 token 直接崩溃**，
意味着此前所有引擎级长上下文结论都无效；修复后 4096/8192 token 首次跑通。累计 7 个静默 bug（不报错、只静默出错）」

### 2.5 ★ P6：批量投机（`18d345b` `1c1d907`）

| | |
|---|---|
| **做了什么** | ① **批量 draft**：同一候选位置把 B 条请求**一起**前向（k 个位置仍顺序，因候选自回归）；② 按精确 B∈{1,2,4} 捕获 draft 图；③ **按 `(B,k)` 捕获验证图**（query = B·(k+1)）；④ 每请求的 draft KV 水位与补齐 |
| **为什么需要** | 原来 draft 是**逐请求串行**（B=4、k=6 → 每轮 **24 次**独立前向，每次重读 1.2 GB 草稿权重），且验证图只有单请求形状 → **B>1 整个验证退回 eager** |
| **效果（B=4 / 4K / k=6 / 输出 256，output tok/s）** | 普通解码 U **169.9** · 改之前 C **131.2** · +批量 draft S1 **176.0** · +验证图 S2 **201.8** |
| **消融** | **S1/C = 1.34×**（批量 draft 的独立贡献）· **S2/S1 = 1.15×**（验证图的独立贡献）· **S2/C = 1.54×** · **C/U 0.77 → S2/U 1.19** |
| **结构证据** | 验证图 **37/37 全命中、0 退回**（改前是命中 3–7、退回 48–72）；draft 前向/轮从 24 → 6 |
| **附带修掉的第 3 个静默 bug** | 全接受时 draft KV 有位**从没写过且永不回头补**，污染**累积**。对照实验：关补齐 vs 开补齐 → 接受率 **0.866 → 0.987**、同负载 **152.3 → 201.8 tok/s（×1.32）**，而补齐只多 ~1 次批量前向/轮 |
| **其他档** | B=2/4K：**S2/U = 1.45×**（最漂亮的一档）· B=1：**无变化**（116.68 → 116.76，没有东西可批）· B=4/1K：**0.93×U 仍略输** · B=4/4K/k=2：**0.88×U 仍略输** |
| **★ 边界（必须一起写）** | ① **那个 1.19× 依赖接受率**：本负载 α≈0.99，把接受率还原到 0.87 → **152.3 tok/s = 0.897×U，仍低于普通解码**。自然代码 prompt 的 α 只有 0.745–0.842，那一档大概在 0.9× 附近。② **代价**：加载草稿把主模型可用 KV 容量从 **88832 → 45312 token（−49%）**，TTFT 也变差 |
| **★ 简历可写** | 「把投机解码从单请求扩展到批量：定位出两处随 batch 线性增长的开销（草稿逐请求串行 = 每轮 24 次前向；验证图只有单请求形状导致 B>1 全程退回 eager），重构为批量草稿 + 按 (B,k) 捕获验证图。**同接受率下吞吐 +54%，B=4 从 0.77× 翻到 1.19×**，验证图命中率 0→100%」 |

### 2.6 ★ P7-A：前缀缓存命中触发的「全量草稿补齐」（`548e099`）

| | |
|---|---|
| **做了什么** | 量化后发现：前缀缓存命中时草稿侧水位被判为无效 → 触发**全量补齐**。正确修法不是「假设 target 命中 = draft 有效」（那会静默输出垃圾），而是给草稿做**它自己的**块级 KV 有效性追踪（`Block.draft_hash` / `mark_draft_valid` / `draft_valid_cached_blocks`，只认连续前缀） |
| **量化（修复前，4 条请求共享 4096-token 前缀）** | 补齐 **16660–16665 个 token**；**单个 decode step 要 17.31–17.44 秒**；占端到端墙钟 **85%** |
| **效果** | 补齐 16665 → **22–31 token（−99.8%）**；吞吐 **12.53 → 76.63 tok/s（6.1×）** |
| **最关键的一句** | 参照「冷缓存（无前缀复用）」**45.5 tok/s**：<br>**修复前，前缀缓存是净亏的（12.5 < 45.5）——命中了比不命中还慢 3.6 倍；修复后是净赚（76.6 > 45.5，1.68×）** |
| **正确性证据（正反两面）** | 复用路径输出 == 全量补齐路径输出，**3/3 输出 md5 完全一致**；负对照 NEG（target 命中但 draft 没写过）仍正确回退；★ **承重性反证 NEGX**（朴素修法跳过守卫直读脏 KV）→ **接受率 0.9 崩到 0.175–0.470、logits argmax 一致率 0.333**，证明那道守卫真在挡东西 |
| **★ 简历可写** | 「发现前缀缓存存在**负优化**：命中长前缀时会触发一次全量草稿补齐，**单个 decode step 阻塞 17.3 秒、占端到端 85%**。用草稿侧的块级 KV 有效性追踪修复后补齐降到 22 token、吞吐 **6.1×**，前缀缓存从净亏翻成净赚 1.68×；并用**承重性反证**（绕过守卫则接受率崩到 0.175）证明该守卫不可省」 |

### 2.7 ★ P7-B/C：草稿滑窗 + 解耦草稿分配（`285cd68`→`c705603`，`f35c205` `920705f`）

| | |
|---|---|
| **做了什么** | ① **草稿只保留最近 W 个 token 的 KV**（块级环形缓冲，`b0 = max(valid_from//bs, p//bs−M+1, 0)`，块表旋转成递增以保因果正确，RoPE 用绝对位置）；② **解耦草稿的显存分配**：原来草稿**共用主模型的块号**（`Sequence.block_table`），导致块数必须相等、无法缩小；解耦后草稿有自己的独立编号 |
| **修掉的 3 个静默 bug** | ① `clip_gap_to_window` **块对齐方向反了** → 补齐 token 落错位、覆盖环里正确的 KV；② `valid_from = max(wvf, 补齐起点)` → 窗口被砍成约 1 个块、**与 M 无关**；③ ★ **补齐那一趟前向硬传 `valid_from=base`** → **那个前向的可见上下文从 1031 个 token 被砍到 7 个**，而它恰是草稿下一步最需要的 → **每轮全接受就往环里写一格坏 KV**。逐次前向对拍定位到**第 7 次前向**（ctx 1031 vs 7） |
| **效果①：容量** | target 可用容量 **45312 → 67840~78848 token（+50% ~ +74%）**；草稿池 **4.84 GB → 0.22–1.75 GB**。*（KV 总预算固定 ~11.06 GiB，省的是「切法」不是「总量」）* |
| **效果②：W ≥ 上下文时（本实验 W ≥ 1280）** | 接受率与全上下文**逐位相同**（226 次草稿前向 logits 0/226 不同、候选 0/34、验证 0/34、输出 md5 相同）；每轮耗时 **0.78–0.86×**；吞吐 **+23.0%（合成素材）/ +9.7%（自然长文）** |
| **效果③：W < 上下文时** | **W=512/1024 亏 34%–65%** → 明确不成立。W=256 看负载且**不稳健**（合成素材 −63%，自然长文 +23% 但 5 组里 2 组为负）→ **不能宣布成立** |
| **效果④：解耦草稿分配本身** | 每轮耗时 **0.79–0.86×**、吞吐 **+16~21%**，且**逐位相同、零接受率代价**、**与窗口大小解耦**（隔离实验：W=1280 不截断上下文时加速照样出现） |
| **口径结论（关键）** | 账是 **「轮数（由接受率决定） × 每轮耗时」** 两笔。只截一点点上下文时省得不够多、亏最狠；完全不截时纯赚约 20% |
| **⚠️ 归因未钉死** | 那 +20% **不是**来自「读的 key 变少」（ctx 逐条相同，已否）、**也不是**来自块表宽度（已否）。隔离实验同时改变了整套 KV 的分配布局，**具体环节尚未隔离**。文档里**不要写「来自滑窗省上下文」或「连续块」** |
| **★ 简历可写** | 「给草稿模型实现滑动窗口 KV（块级环形缓冲）并解耦其显存分配：**target 可用容量 +50~74%**；窗口不小于上下文时接受率**逐位不变**、每轮耗时 **0.8×**；解耦分配单独带来 **+16~21% 吞吐且零精度代价**。过程中用逐次前向逐位对拍定位并修掉 3 个静默 bug（含一个『补齐前向上下文被砍到 7 个 token』）」 |

### 2.9 逐字节等价性验证（P7 严格层）

```
spec_draft_window=0（默认档） vs 基线 1c1d907：
  226 次草稿前向 → 0 条不同（连块表与 slot 都比）
   34 次 propose   → 0 条不同
   34 次验证前向   → 0 条不同
  前 6 次 draft 前向 logits  max|Δ| = 0.00000000
  out_md5 相同
```

**方法**：把基线版本单独放一份，用**同一个**对拍脚本指过去跑，比每次前向的 `(tokens, positions, ctx, block_table, slot) + logits 的 bitwise md5`。

**★ 一条最有说服力的反向证据**：**拿旧测试文件跑修好的代码，它恰好挂在把 bug 钉住的那条断言上**（41 过 1 挂）—— 直接证明那个测试当时是把**错误行为当正确行为**钉住的。

### 2.10 ★ Q1：INT8 权重量化（只量化 draft 的 FFN）—— **未达门槛，如实记录**

**做了什么**：对称 per-channel 量化草稿（Qwen3-0.6B）的 FFN（gate/up/down，84 个模块），
配一版**融合反量化**的 GEMM（"先解压再算"会变成读 1B+写 2B+读 2B = 5B/参数，比原来更糟）。
**target 一个字节没动。** 配置开关控制，默认走原路径。
详细开发记录：`W8A16量化-开发记录.md`。

**Phase 0 闸门：通过，并给出本项目最强的一条证据**

★ GEMM 时间在 `B=1/4 × ctx=1K/4K` 四种组合下是 **10.46 / 10.52 / 10.65 / 10.70 ms —— 只差 2.3%**
→ 直接证明 decode 的 GEMM 是**纯权重流式**，与 batch 多大、上下文多长几乎无关。

代理实验（4B / 1.7B / 0.6B，权重 8.045 / 3.441 / 1.192 GB）：
`tok/s` 比 = 1 / 2.06 / 3.73，明显偏离权重比 1 / 2.34 / 6.75 —— 但**偏离已完全归因**
（① KV 流量不随权重缩水；② 每步约 **1.2 ms** 固定开销）。
关键在有效带宽：**权重缩小 6.75 倍，GEMM 带宽只掉 10%**（765 / 778 / 686 GB/s）
→ **字节节省几乎 1:1 变成时间节省**。

Amdahl 上界（假设去量化免费）：`B=1/1K` **1.60×** · `B=1/4K` 1.59× · `B=4/1K` 1.53× · `B=4/4K` 1.42×。

**精度：逐模块消融 + 噪声地板**（wikitext-2，122760 token，每次只量化一类）

| 配置 | ΔPPL% | 两半分歧（噪声地板） | 占线性层字节 |
|---|---:|---|---:|
| gate_proj | +0.155 | [0.105, 0.204] | 14.8% |
| up_proj | **−0.078** | [−0.059, −0.096] | 14.8% |
| down_proj | +0.228 | [0.254, 0.203] | 14.8% |
| **只 FFN（本方案）** | **+0.316** | [0.317, 0.316] | **44.3%** |
| 只 attention | +0.132 | [0.198, 0.066] | 29.6% |
| 全量化 | +0.471 | [0.589, 0.353] | 73.9% |

**性能（配对、交替、含空转噪声地板）** —— 用**每轮耗时**（tok/s 被轮数随机性淹没 ±10~20%）

| 负载 | ms/轮 bf16→int8 | **配对比值** | int8 更快 | 噪声地板 |
|---|---|---:|---:|---:|
| 合成 B=1/1K | 37.721→36.180 | **0.9591** | 9/9 | 0.60% |
| 合成 B=1/4K | 43.096→41.528 | **0.9634** | 9/9 | 0.26% |
| 自然 B=1/1K | 34.863→33.211 | 0.9548 | 9/9 | 4.04% |
| 自然 B=1/4K | 39.178→37.758 | 0.9638 | 9/9 | 4.40% |
| 合成 B=4 | 13.440→12.747 / 19.144→18.684 | 0.9519 / 0.9760 | 11/12 | **43–61%** ⚠️ |

合计 **40/42 配对一致**（符号检验 p≈1e-10）；**B=1 18/18 全胜；B=4 分辨不出**（噪声地板 43–61%）。

**★ 明确回答：没达到事前门槛（`B=1/4K ≥ +20%`），实测 +3.8% ~ +4.7%（B=1）。**
机制解释：draft FFN 只占 draft 权重 **44.3%**，draft 只占一轮权重流量 **47%** → 一轮总字节只降 **9.9%**；
再乘草稿前向的带宽效率折损（见下）→ 每轮 ≈ **−3.5%**，与实测吻合。
**性能上不划算。** 它的真实价值是**「量化草稿不破无损性」的示范** —— target 未动，
「相对 BF16 target 无损」严格成立，口径一个字不用改。

★ **接受率不变**：引擎只有 384 样本（SE 2.2%）分不出，改用恒等式 `α = 1 − TV(p,q)`
在 **12,282** 个 wikitext 位置上算 → **Δα = −0.00251 ± 0.00349，不显著**。

★ **显存是负的**：权重 −0.245 GB，但 **KV 池 174 → 171 块（−1.7%）**。
排查中抓到一个真 bug：split-K 的 `[SPLIT_K,M,N]` fp32 scratch 在 warmup 的 prefill（M 很大）
会分掉 200 MB+，把 peak 顶高 **1.285 GB** → 曾让 KV 池少 **11** 块；限制 split-K 只在 `M≤64` 用后回到 −3 块。
**剩下 3 块未归因，如实挂账。**

**★★ 两条反直觉的发现（都推翻了事前假设）**

1. **「FFN 比 attention 更耐量化」不成立。**

   | | draft（0.6B） | target（4B） |
   |---|---:|---:|
   | 只量化 FFN | **+0.316%** | **+0.637%** |
   | 只量化 attention | **+0.132%** | **−0.183%**（负值即噪声） |

   **attention 反而更耐量化。** 事前"只量化 FFN 因为 FFN 损害小"这个切法**既漏掉了更耐量化的 attention，
   又包含了最敏感的首尾层 —— 切错了维度。**

2. **「`down_proj` 最敏感」只在 0.6B 上成立。**
   draft 上它 +0.228%（三类里最高）；**4B 上它最不敏感**（+0.122% < gate +0.213 / up +0.269）。
   → **敏感度排序是模型相关的，不能跨模型外推。**

**★★ 两个新机会（本次测量挖出来的）**

- **机会 A：按「层位置」切，而不是按「FFN / attention」切。**
  draft 的 FFN 按位置拆：**前 4 层 +0.304% / 中间 20 层 +0.021% / 后 4 层 −0.002%**
  （三段和 +0.325 ≈ 整块实测 +0.316，**可加性成立**）。
  → **量化中间 20 层（71% 的层）代价几乎为零。** 这条对 **target 更重要**（上界 1.42–1.60×）。
- **机会 B：draft 前向只有 55.2% 的带宽效率。**
  draft 单次前向 **2563.6 µs / 1.192 GB = 465 GB/s = 实测天花板（842）的 55.2%**
  （对照 target 普通 decode：770 GB/s = **91.5%**）。拟合出**每步约 1.2 ms 固定开销**
  → 6 次草稿前向/轮 ≈ **7.2 ms ≈ 一轮（约 38 ms）的 19%**。
  **零精度代价、比量化那一刀更大**，且可能与「解耦草稿分配白拿 +20%」是**同一现象**。

**★ 方法（这一节本身就是资产）**

1. **逐模块消融**：每次**只量化一类**（q/k/v/o/gate/up/down 各一组），其余全部保持 BF16。
2. **★ 噪声地板**：同一配置在语料**两半**上各算一次 ΔPPL，用两半**分歧**当地板。
   这一步抓出了假效果 —— `up_proj` 报 **−0.078%**（字面即"量化让它变好了"），
   而两半分歧 [−0.059, −0.096] 说明整条落在噪声里。**没有地板就会把它当结论。**
3. **可加性检验**：位置维度三段和（+0.325）≈ 整块实测（+0.316）→ 证明分解有意义、不是交互作用。
4. **接受率不信任引擎的少量样本**：改用恒等式 `α = 1 − TV(p,q)` 在 12k 位置上算，
   避免把采样噪声当成"量化伤害了接受率"。
5. **在第二个模型上交叉验证**（4B）→ 才发现敏感度排序是模型相关的。

## 3. 测量成果（不是优化，但同样是简历资产）

| 测出什么 | 数字 | 为什么值钱 |
|---|---|---|
| **decode 成本分解** | GEMM 79.3% / attention 9.2% / elementwise 8.4% | **据此否掉了自己的第一条优化主线**（见 §4） |
| **权重流式已近硬件极限** | 763 GB/s = 3090 峰值带宽的 **81%** | 说明 decode 的 79% 没有免费空间，只有量化能动 |
| **Amdahl 的 f（attention 占比）** | 8.12% / 9.24% / 14.68% @ ctx 1024/4096/8192 | 直接给出 attention 优化的**上界** |

## 6. 已知边界与未测

**成立的条件**：
- 投机解码：batch=1（或很小）· 有接受率足够高的 draft（α 直接决定每步产出）· draft 与 target **词表相同**
- 滑窗：**窗口 ≥ 实际上下文长度**（本实验 `W ≥ ceil((L+OUT)/bs)·bs`）
- 批量投机：已覆盖精确 B∈{1,2,4}；B=3 等形状退回 eager（已记录原因）

**明确未测 / 没做**：
- **端到端统一验收**：各优化的数字散在不同轮次、口径不一，**从未在同一份代码、同一组负载上跑成一张消融表**（方案 §12.8 要的 `A vs U` / `S1 vs C` / `S2 vs S1` / `F vs U`）
- **并发-容量曲线**：B=4 时算力只用掉三十分之一，**吞吐上限未知**
- **长上下文（8K/16K）引擎级实测**：以前被那个崩溃 bug 挡着，修好后**还没测**
- warp specialization（试过，结果不对，修 4 轮停手）
- TMA / TMEM / 2-SM cluster（**sm_86 物理不支持**）
- ncu 硬件计数器（**机器上被禁**，`RmProfilingAdminOnly: 1` 且无 sudo）
- attention kernel 只用随机数据测过，**未接进引擎**

**挂账未定位**：
- 滑窗 M=2 反而比 M=1 和 M=4 都差（审计证明几何正确，机制未定位）
- 解耦分配那 +20% 的**具体环节**（已排除"读的 key 变少"与"表宽"）
