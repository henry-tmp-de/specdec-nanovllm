## 2.1 vLLM（区分 V0 / V1）

### (1) chunked prefill 是不是默认开启？从哪个版本开始？

**【结论 a】V0 时代默认关。** vLLM **v0.6.3**（2024-10-14）的
`vllm/config.py` → `SchedulerConfig.__init__(..., enable_chunked_prefill: bool = False)`。
**来源**：`raw.githubusercontent.com/vllm-project/vllm/v0.6.3/vllm/config.py` L964（默认值）、L941（docstring）。

**【结论 a2】它是从哪个版本开始"存在"的（opt-in 阶段）**（子 agent 从 release notes 核出）：
- **v0.4.0（2024-03-30）**："Progress in chunked prefill scheduler"（还没可用）
- **v0.4.1（2024-04-24）**："Progress towards chunked prefill scheduler"
- **v0.4.2（2024-05-05）**：★ "**Chunked prefill is ready for testing!** It improves inter-token latency in
  high load scenario" —— **opt-in，开关 `enable_chunked_prefill`**
- **v0.6.0（2024-09-04）**："Enable chunked prefill and prefix caching together"
⇒ 所以完整时间线是：**2024-05 起可 opt-in（V0）→ 2025-03 v0.8.0 起 V1 成为默认引擎（V1 里恒开）**。

**【结论 b】V1 里它被"默认打开"，且**演进过三次**（"无条件 True"只在 v0.8.0 成立）。**

| **v0.10.0**（2025-07-24） | 收窄为"**非 pooling 任务**才无条件 True"，注释改为 `# V1 always uses chunked prefills and prefix caching for non-pooling tasks.` |
| **v0.13.0（2025-12-19）起 → v0.31.0** | 改为**模型能力驱动**：`SchedulerConfig.enable_chunked_prefill: bool = True`（dataclass 默认），但 `EngineArgs...: bool \| None = None`，真正生效值由 `_set_default_chunked_prefill_and_prefix_caching_args()` 用 `model_config.is_chunked_prefill_supported` 决定；**用户仍可显式 `--enable-chunked-prefill` 覆盖**（对 generate 模型关掉会打 warning 但不报错） |

### (2) 调度策略是不是"decode 严格优先 + 剩余 token budget 填 prefill 块"？

**【结论】是。文档原话 + 源码结构都对得上。** 版本：v0.31.0。

**官方文档原话**（最直接的引用）：
> "With chunked prefill enabled, the scheduling policy **prioritizes decode requests**.
> It **batches all pending decode requests before scheduling any prefill** operations.
> When there are available tokens in the `max_num_batched_tokens` budget, it schedules pending prefills.
> **If a pending prefill request cannot fit into `max_num_batched_tokens`, it automatically chunks it.**"

**来源**：`https://docs.vllm.ai/en/latest/configuration/optimization.html`。

**源码结构**（v0.31.0 `vllm/v1/core/sched/scheduler.py`）：

```python
def schedule(self, throttle_prefills: bool = False) -> SchedulerOutput:
    ...
    token_budget = self.max_num_scheduled_tokens          # L582
    input_budget = self.scheduler_config.max_num_batched_tokens   # L585

    # First, schedule the RUNNING requests.               # L629
    while req_index < len(self.running) and token_budget > 0:      # L630
        ...
        num_new_tokens = (request.num_tokens_with_spec
                          + request.num_output_placeholders
                          - request.num_computed_tokens)            # L675
        if 0 < long_prefill_token_threshold < num_new_tokens:
            num_new_tokens = long_prefill_token_threshold           # L679
        num_new_tokens = min(num_new_tokens, token_budget,
                             input_budget - draft_slots)            # L681
        ...
        token_budget -= num_new_tokens                              # L825

    # then WAITING (new prefills) with whatever budget is left   # L885
    while token_budget > 0:
        request = request_queue.peek_request()                      # L896
        ...
        request_token_budget = min(token_budget, input_budget - draft_slots)  # L1073
        num_new_tokens = min(num_new_tokens, request_token_budget)  # L1123
        ...
        token_budget -= num_new_tokens                              # L1313
```

- **"decode 优先"** = 先跑 `self.running` 循环（在跑的请求），再跑 waiting 循环（新到 prefill）。
- **"剩余 budget 填 prefill 块"** = waiting 循环的条件就是 `token_budget > 0`，每个 prefill 请求拿 `min(该请求剩余, 剩余 budget)`。
- **chunk 就是这么来的**：一个 prefill 请求本步拿不满时，就只拿 budget 那一段 —— 源码里没有单独的 "chunk size" 参数。

**来源**：`.../v0.31.0/vllm/v1/core/sched/scheduler.py`（行号如上）。

**【结论·★ 一个容易踩错的概念】V1 的调度器里并没有"prefill 阶段/decode 阶段"这两个东西。**
源码开头的 NOTE 是 vLLM 作者 woosuk 写的：

> "**There's no "decoding phase" nor "prefill phase" in the scheduler.** Each request just has the
> `num_computed_tokens` and `num_tokens_with_spec`. … At each step, the scheduler tries to assign
> tokens to the requests so that each request's `num_computed_tokens` can catch up its
> `num_tokens_with_spec`. This is general enough to cover chunked prefills, prefix caching,
> speculative decoding, and the "jump decoding" optimization in the future."

**来源**：`.../v0.31.0/vllm/v1/core/sched/scheduler.py` L564-573。

⇒ 面试时**不要说** "vLLM V1 先调度 decode 再调度 prefill 块" 就完了；
说 "**V1 把 prefill/decode 统一成同一个抽象（每个请求欠多少 token 没算），decode 优先只是这个抽象下的自然结果**"，
会更接近源码事实。

### (3) 混合批怎么执行：拼一个批还是拆两个子批？attention 元数据怎么区分？

**【结论 V1（v0.31.0）】拼成**一个批**，做**一次**前向；attention 也是**一次 varlen 调用**，
靠每个请求自己的 `query_start_loc`/`seq_lens` 区分，**没有"两段"的概念**。**

V1 的 attention 元数据（`vllm/v1/attention/backends/flash_attn.py`）：

```python
@dataclass
class FlashAttentionMetadata:
    max_query_len: int
    query_start_loc: torch.Tensor          # L522
    seq_lens: torch.Tensor                 # L524
    block_table: torch.Tensor              # L525

    def build(self, common_attn_metadata, ...):
        max_query_len = common_attn_metadata.max_query_len      # L826
        query_start_loc = common_attn_metadata.query_start_loc  # L828
        seq_lens = common_attn_metadata.seq_lens                # L829
        block_table_tensor = common_attn_metadata.block_table_tensor  # L830
        ...
        query_lens = query_start_loc[1:] - query_start_loc[:-1]  # L885
        context_kv_lens = seq_lens - query_lens                  # L886
```

⇒ **一个混合批 = 一批"query 长度各不相同的请求"**：prefill 块的请求 query_len = chunk 大小，
decode 的请求 query_len = 1（投机解码时 = 1+k）。一次 `flash_attn_varlen_func` 全覆盖。
`block_table` 是每条请求各自的 KV 块表（prefill 块要读前缀缓存的 KV，decode 读自己的全部 KV），
**同一个张量、同一条路径** —— 不存在"给 prefill 段和 decode 段各一套 cu_seqlens"。

**来源**：`.../v0.31.0/vllm/v1/attention/backends/flash_attn.py` L521-525、L815-886。

---

**【结论 V0（v0.6.3，历史）】一次前向，但 attention 拆成两次核调用。**
V0 的 `FlashAttentionImpl` docstring 把批的排布写死在注释里：

```
If chunked prefill is enabled, prefill tokens and decode tokens can be
batched together in a flattened 1D query.

|<----- num_prefill_tokens ---->|<------- num_decode_tokens --------->|
|<-prefill_0->|...|<-prefill_N-1->|<--decode_0-->|...|<--decode_M-1-->|

Currently, cuda graph is disabled for chunked prefill, meaning there's no
padding between prefill and decode tokens.
```

前向里第一件事就是**按 `num_prefill_tokens` 切片，然后分两次调用**：

```python
# Query for decode. KV is not needed because it is already cached.
decode_query = query[num_prefill_tokens:]
# QKV for prefill.
query = query[:num_prefill_tokens]
key   = key[:num_prefill_tokens]
value = value[:num_prefill_tokens]

if prefill_meta := attn_metadata.prefill_metadata:
    ...
    prefill_output = flash_attn_varlen_func(
        q=query, k=key, v=value,
        cu_seqlens_q=prefill_meta.seq_start_loc,
        cu_seqlens_k=prefill_meta.seq_start_loc, ...)
    else:  # prefix-enabled（= 分块/命中前缀）
        prefill_output = flash_attn_varlen_func(
        q=query, k=key_cache, v=value_cache,
        cu_seqlens_q=prefill_meta.query_start_loc,
        cu_seqlens_k=prefill_meta.seq_start_loc,
        block_table=prefill_meta.block_tables, ...)

if decode_meta := attn_metadata.decode_metadata:
    decode_output = flash_attn_varlen_func(...)
```

**元数据怎么区分**：`FlashAttentionMetadata` 里存 `num_prefill_tokens` / `num_decode_tokens` / `num_prefills`，
并用两个 cached property 把**同一批 buffer 切成两份**：

```python
@property
def prefill_metadata(self):     # L152
    ... query_start_loc=self.query_start_loc[:self.num_prefills + 1], ...
@property
def decode_metadata(self):      # L186
    ... slot_mapping=self.slot_mapping[self.num_prefill_tokens:],
        query_start_loc=self.query_start_loc[self.num_prefills:] ...
```

**来源**：`.../v0.6.3/vllm/attention/backends/flash_attn.py` L480-500（布局注释）、L650-720（切分与两次调用）、L120-215（元数据属性）。

> ★ 这一段对我们特别有用：**我们的 `prepare_prefill` 用的正是 V0 这套 `cu_seqlens_k > cu_seqlens_q ⇒ block_tables 走 paged 路径`**（见 `docs/P12混合调度-开发记录.md §3.0`）。
> 所以 **vLLM V0 才是我们真正的"血亲"**，V1 已经是另一套设计了。

### (4) ★ CUDA Graph 怎么办（本调研的重点）

**【结论 1】vLLM V1（v0.31.0）的默认模式是 `FULL_AND_PIECEWISE`。**
源码 `vllm/config/compilation.py`（枚举与默认值）：

```python
class CUDAGraphMode(enum.Enum):
    NONE = 0
    PIECEWISE = 1
    FULL = 2
    FULL_DECODE_ONLY = (FULL, NONE)
    FULL_AND_PIECEWISE = (FULL, PIECEWISE)
```

同一个文件里 `cudagraph_mode` 的 docstring（**直接回答"混合批还能不能吃图"**）：

> - NONE, no cudagraph capture.
> - PIECEWISE.
> - FULL.
> - FULL_DECODE_ONLY.
> - **FULL_AND_PIECEWISE. (v1 default)**
>
> **PIECEWISE mode build piecewise cudagraph only, keeping the cudagraph incompatible ops
> (i.e. some attention ops) outside the cudagraph** for general flexibility.
>
> **FULL mode**: Capture full cudagraph for all batches. Can be good for small models or workloads
> with small prompts; **not supported by many backends**.
>
> **FULL_DECODE_ONLY mode**: Capture full cudagraph for decode batches only.
> **Mixed prefill-decode batches are run without cudagraphs.**
>
> **FULL_AND_PIECEWISE mode: Capture full cudagraph for decode batches and piecewise cudagraph for
> prefill and mixed prefill-decode batches.** This is the most performant mode for most models and
> is the default.

**来源**：`.../v0.31.0/vllm/config/compilation.py` L53-63（枚举）、L607-637（docstring，逐字如上）。

**【结论 1b】官方文档有专门一页讲这个（比源码 docstring 更全，强烈建议面试前看这一页）：**
`https://docs.vllm.ai/en/latest/design/cuda_graphs.html`（源文件 `docs/design/cuda_graphs.md`，v0.31.0）。要点：
- **PIECEWISE 的定位**（原文）："a single-mode strategy (and past default). It is the most flexible:
  **attention or other CUDA Graphs-incompatible operations stay eager, everything else goes into CUDA Graphs.**
  Requires piecewise compilation."
- **引入动机**（原文）："Initial piecewise compilation was built to allow piecewise cudagraph capture,
  **excluding cudagraph-unsupported operations (mainly attention)** … Many attention backends also weren't ready
  for unified 'full' CUDA Graphs capture (**e.g., only FlashAttention 3 supports it currently**) or only support
  CUDA Graphs for pure decode batches."
- ★ **"嵌套 wrapper"设计**（原文）："We wrap a **FULL mode wrapper outside the entire model** …
  meanwhile, **each piecewise backend is wrapped via a `PIECEWISE` mode wrapper inside the compilation.** …
  Therefore, for a `FULL` runtime mode, it is safe to capture/replay a full CUDA Graph since the piecewise
  wrapper is not activated."
  ⇒ **这就是"decode 走 FULL、混合批走 piecewise"能共存而不打架的机制。**
- **派发优先级**（原文）："We basically search the existing keys following the priority:
  **`FULL` > `PIECEWISE` > `None`**"。
- **默认值补充**（原文）："If you're on v1 with piecewise compilation, we default to `FULL_AND_PIECEWISE` …
  (**for pooling models, it's still `PIECEWISE`**). Otherwise, e.g. if piecewise compilation unavailable,
  we default to `NONE`."

**【结论 1c】`FULL_AND_PIECEWISE` 成为默认是**哪个版本**：v0.11.0。**
release notes 原文："This release **turns on FULL_AND_PIECEWISE as the CUDA graph mode default**.
This should provide better out of the box performance for most models … while preserving compatibility with
existing models supporting only PIECEWISE mode."（对应 PR **#25444**）
落地代码：`vllm/config/__init__.py@v0.11.0` L359-376（V1 + PIECEWISE 编译级 ⇒ `FULL_AND_PIECEWISE`；
pooling / encoder-decoder ⇒ PIECEWISE；否则 NONE）。
v0.31.0 走的是 `optimization_level = OptimizationLevel.O2`（默认），O2 的配置里 `cudagraph_mode` 就是 `FULL_AND_PIECEWISE`
（`vllm/config/vllm.py@v0.31.0` L442 / L316 / L1802-1803）。

**【结论 1d】★ 真正的"能不能吃 FULL 图"开关是 `AttentionCGSupport`（不是 `attn_state`）。**
枚举值：`ALWAYS` / `UNIFORM_BATCH` / `UNIFORM_SINGLE_TOKEN_DECODE` / `NEVER`
（`vllm/v1/attention/backend.py@v0.31.0` L562-576）。**取所有 attention group 里的最小值**，
不兼容时自动降级（mixed 不支持 → FULL_AND_PIECEWISE；decode full 不支持但 attention 在 splitting_ops → PIECEWISE；
否则 NONE）。**来源**：`vllm/config/compilation.py@v0.31.0` L1371-1465（`resolve_cudagraph_mode_and_sizes`）。

**官方给的"attention backend × 能不能 FULL"兼容表**（`docs/design/cuda_graphs.md@v0.31.0`，节选）：

| Attention backend | CG support | 官方注释 |
|---|---|---|
| FlashAttention **v2** | `UNIFORM_BATCH` | "Actually `ALWAYS` but workaround to fallback to `FULL_AND_PIECEWISE` for performance reason" |
| FlashAttention **v3** | **`ALWAYS`** | "has unified routine for both batches, so `FULL` mode is good" |
| Triton Attention | `ALWAYS` | — |
| FlashInfer | `UNIFORM_SINGLE_TOKEN_DECODE` | Blackwell TRTLLM 时升为 `UNIFORM_BATCH` |
| FlashMLA / FlashInferMLA / AITER FA | `UNIFORM_BATCH` | — |
| AITER MLA / CUTLASS MLA / Mamba | `UNIFORM_SINGLE_TOKEN_DECODE` | — |
| **未列出的 backend** | **`NEVER`** | — |

★ **代码里给出 FA2 为什么不是 ALWAYS 的真实原因**（`v1/attention/backends/flash_attn.py@v0.31.0` L605-623）：
FA2 的 `max_query_len=1` packed-GQA 特化让图**不能用于 mixed prefill-decode**，所以标 `UNIFORM_BATCH`。

★ 所以对"混合批下 decode 那部分还能不能吃到图"的**准确回答是**：

| 批的构成 | 走哪个模式 | decode 部分吃到什么图 |
|---|---|---|
| **纯 decode 批**（uniform decode） | **FULL** | 整张 FULL 图，attention 也在图里 |
| **prefill-only 批** | **PIECEWISE** | 不适用 |
| **混合批（decode + prefill 块）** | **PIECEWISE** | ★ **吃不到 FULL 图**。走 piecewise：图被**切成若干段**，**attention 这类"图不兼容算子"留在图外 eager 执行**，其余（GEMM/MLP/norm 等）按段 replay |
| 没有匹配的图（如 `num_tokens > max_cudagraph_capture_size`） | **NONE** | 整批 eager |

**【结论 2】"uniform decode" 是能不能吃 FULL 图的判据。**
运行时派发在 `vllm/v1/cudagraph_dispatcher.py`：

```python
def dispatch(self, num_tokens, uniform_decode=False, ...):
    ...
    if CUDAGraphMode.FULL in allowed_modes:
        batch_desc_to_check = batch_desc
        if batch_desc_to_check in self.cudagraph_keys[CUDAGraphMode.FULL]:
            return CUDAGraphMode.FULL, batch_desc_to_check        # 纯 decode → FULL
    if CUDAGraphMode.PIECEWISE in allowed_modes:
        batch_desc_to_check = replace(batch_desc, num_reqs=None, uniform=False)  # ← "放松"过的键
        if batch_desc_to_check in self.cudagraph_keys[CUDAGraphMode.PIECEWISE]:
            return CUDAGraphMode.PIECEWISE, batch_desc_to_check    # 其余 → PIECEWISE
    ...
    return CUDAGraphMode.NONE, BatchDescriptor(num_tokens)         # 兜底 → eager
```

- **`uniform=True` 只对纯 decode 批成立**（`uniform_decode_query_len = 1 + num_speculative_tokens`），
  所以 FULL 图的 key 集合只由 `_create_padded_batch_descriptor(bs, True, ...)` 生成。

  ★ **判据在 model runner 里，逐字如下**（v0.31.0 `vllm/v1/worker/gpu_model_runner.py` L3853-3871）：
  ```python
  def _is_uniform_decode(max_num_scheduled_tokens, uniform_decode_query_len,
                         num_tokens, num_reqs, force_uniform_decode=None) -> bool:
      """Checks if it's a decode batch with same amount scheduled tokens
      across all requests."""
      return (((max_num_scheduled_tokens == uniform_decode_query_len)
               and (num_tokens == max_num_scheduled_tokens * num_reqs))
              if force_uniform_decode is None else force_uniform_decode)
  ```
  ⇒ **要求"每条请求的 query 长度完全一致"**。混合批里 prefill 块的请求 query 长度 = chunk 大小、
  decode 的请求 = 1 ⇒ **不等 ⇒ `uniform_decode = False`** ⇒ 派发到 PIECEWISE（或 NONE）。
  这个布尔值随后被传进 `self.cudagraph_dispatcher.dispatch(..., uniform_decode=uniform_decode, ...)`（L3963）。
  **这就是"混合批吃不到 FULL 图"的完整证据链。**
- **PIECEWISE 的 key 是"放松"的**：`num_reqs=None, uniform=False` —— 即 piecewise 图**不要求形状精确**，
  这是个通用形状，所以混合批能命中。
- FULL 为什么必须精确：源码注释 "**FULL mode needs exact `num_reqs` because FA3's
  scheduler_metadata computation depends on it**"。

**来源**：`.../v0.31.0/vllm/v1/cudagraph_dispatcher.py`（`dispatch()`、`initialize_cudagraph_keys()`、`_create_padded_batch_descriptor()`）。

**【结论 3】full / piecewise / eager 各自适用什么。**（同 §4 source）
- `NONE`：`cudagraph_mode=NONE`、没初始化、`num_tokens > max_cudagraph_capture_size`、或后端不支持。
- `FULL`：**纯 decode 批**；对后端有要求（"not supported by many backends"），且 FA3 需要精确 num_reqs。
- `PIECEWISE`：**prefill 与混合批**；需要 `CompilationMode.VLLM_COMPILE` 且 attention 在 `splitting_ops` 里
  （dispatcher 里有 assert 强制）。
- `FULL_DECODE_ONLY`：**P/D 分离部署里的 decode 实例**专用（省显存），混合批干脆不用图。

**【结论 4 · V0 对比】** v0.6.3 的注释直接写：
> "Currently, **cuda graph is disabled for chunked prefill**, meaning there's no padding between prefill and decode tokens."

**来源**：`.../v0.6.3/vllm/attention/backends/flash_attn.py` L498-500。
⇒ **V0 时代混合批根本不吃图；V1 引入 piecewise 图，才让混合批"部分吃到图"。**
这是"V0→V1 在 CUDA graph 上的分水岭"。

### (5) 除"prefill 抢占/让路"外还有哪些机制？`--max-num-batched-tokens` 与 chunk 的关系？

**【结论 a】chunk 大小就是"剩余 token 预算"**，没有独立的 chunk 参数。
`max_num_batched_tokens`（SchedulerConfig，V1 默认按设备分档）就是每步的 token 预算；
`max_num_scheduled_tokens` 通常等于它（官方文档：`--max-num-scheduled-tokens` "This is usually equal to max_num_batched_tokens"）。

**官方文档给的调参方向（可直接背）**：
> "Smaller values (e.g., 2048) achieve better ITL because there are fewer prefills slowing down decodes.
> Higher values achieve better time to first token (TTFT)… For optimal throughput, we recommend setting
> `max_num_batched_tokens` > 8192 especially for smaller models on large GPUs.
> **If `max_num_batched_tokens` is the same as `max_model_len`, that's almost the equivalent to the V0
> default scheduling policy (except that it still prioritizes decodes).**"

**来源**：`https://docs.vllm.ai/en/latest/configuration/optimization.html`。

**V1 的默认值**（v0.9.0 `_set_default_args_v1`，按设备分档）：
- 显存 ≥ 70 GiB 且不是 A100：`LLM` 类 16384、OpenAI API server 8192；`max_num_seqs=1024`
- 其余：8192 / 2048；`max_num_seqs=256`

**来源**：`.../v0.9.0/vllm/engine/arg_utils.py` L1487-1500。

**【结论 b】抢占（preemption）在 V1 里只有一种：recompute。** 
`Scheduler._preempt_request()` 把请求放回 waiting 队列并 `request.num_computed_tokens = 0`
（**重算，不是换出**）：

```python
request.status = RequestStatus.PREEMPTED
request.num_computed_tokens = 0          # ← 重算
...
self.waiting.prepend_request(request)
```

**来源**：`.../v0.31.0/vllm/v1/core/sched/scheduler.py` L1538-1583。

**官方文档的同一句（可直接引）**：
> "In vLLM V1, the default preemption mode is **RECOMPUTE rather than SWAP**, as recomputation has lower
> overhead in the V1 architecture."

**来源**：`https://docs.vllm.ai/en/latest/configuration/optimization.html`。

V0 的 `preemption_mode` 是二选一（`Literal["swap","recompute"]`），v0.6.3 的 docstring 写着
"**We use recomputation by default since it incurs lower overhead than swapping**"，
**来源**：`.../v0.6.3/vllm/config.py` L946-950。
★ **`--preemption-mode` 从 v0.11.0 起消失**（v0.10.0 的 `vllm/config.py` 里还有
`preemption_mode: Optional[PreemptionMode] = None`、L2222/L2307；v0.11.0+ 的 `config/scheduler.py` grep 不到）。

**【结论 c】调度策略（policy）是可选的**：`--scheduling-policy`，choices `fcfs` / `priority`。
**来源**：`https://docs.vllm.ai/en/latest/configuration/engine_args.html`。V1 默认 `fcfs`
（v0.27.0 `vllm/config/scheduler.py`：`policy: SchedulerPolicy = "fcfs"`）。

**【结论 d】v0.31.0 新增了几个"准入/背压"性质的旋钮**（属于"除让路以外的机制"，面试可当加分项）：

| 字段（v0.31.0 `vllm/config/scheduler.py`） | 默认 | 作用 |
|---|---|---|
| `max_num_active_seqs: int \| None` | `None` | 限制**进入 RUNNING** 的请求数（不缩小 runner/图的容量），让 decode 批更小 |
| `max_num_queued_reqs: int \| None` | `None` | 限制在途（waiting+running）请求数，超了直接 **HTTP 503** 让客户端重试别的实例 |
| `max_num_queued_tokens: int \| None` | `None` | ★ **TTFT 的 QoS 阀门**：限制"处于 prefill 阶段的请求的 prompt token 总量"，超了 503。文档原话给了用法 —— "by setting it to `target_TTFT * prefill_throughput` you reject requests when the prefill backlog would exceed the latency target" |

**来源**：`.../v0.31.0/vllm/config/scheduler.py` L70-133（逐字为字段 docstring）。
⇒ ★ **这是在"调度"之外的另一条路：不解决阻塞，而是"挡在门外"（背压/拒绝）**，与我们和 vLLM 的批内做法都不同。

### (3) ★ overlap scheduler 是什么？和 chunked prefill 什么关系？

**【结论 a】存在，默认**开启**，开关是 `--disable-overlap-schedule`（默认 False ⇒ 开着）。**
源码 help 原文：
> "Disable the overlap scheduler, **which overlaps the CPU scheduler with GPU model worker**."

**来源**：`.../v0.5.21/python/sglang/srt/arg_groups/fields/schedule.py` L187-192。
`--enable-overlap-schedule` 仍存在但已是**废弃的 no-op**（help：`"'--enable-overlap-schedule' is deprecated.
It is enabled by default now. Please drop this argument."`）。

**它的 docstring 一句话定位**：`"A scheduler loop that overlaps the CPU processing and GPU computation."`
**来源**：`.../v0.5.21/python/sglang/srt/managers/scheduler.py` L1941-1942。

**【结论 a2】版本历史：v0.3.4 作为实验特性引入（opt-in），v0.3.6 翻转为默认开。**
- v0.3.2 及以前：`server_args.py` 中 0 处 `overlap`。
- **v0.3.4**：`enable_overlap_schedule: bool = False`（opt-in）。
- **v0.3.5**：首次启用会打警告："This is an experimental feature. Sampling penalizer、constrained
  decoding、embedding APIs are not supported and will lead to wrong results."
- **v0.3.6（2024-11-22）**：改为 `disable_overlap_schedule: bool = False` ⇒ **默认开**。

**【结论 b】机理（四条，全来自源码）**：

1. **双 CUDA stream**：调度准备跑在 `schedule_stream`（`scheduler.py` L1116），前向跑在 `forward_stream`；
   前向启动前 `forward_stream.wait_stream(self.schedule_stream)`（L4387）。
   反向用 `_apply_war_barrier()`（L1893-1904）—— 让下一次 `schedule_stream` 的写入等前向的
   shared-read 事件，避免读写冲突（可用 `SGLANG_FORCE_COARSE_WAR_BARRIER` 退化成粗粒度 `wait_stream`）。
2. **主循环顺序**（`event_loop_overlap()` L1941-2013）：每轮
   `ingest_requests` → `get_next_batch_to_run`（**CPU 组批**）→ `run_batch(batch)`（**GPU 异步发射**）→
   把 `(batch.copy(), batch_result)` 压进 `result_queue` → **然后才** `pop_and_process()` 处理**上一批**的结果。
   ⇒ **上一批的 CPU 结果处理与当前批的 GPU 前向在时间上重叠**（这才是"overlap"的本体）。
3. **对 CUDA graph 的影响**：overlap 下用 `record_batch_in_overlap()`（L4278-4291）把
   `(batch, 全字段快照)` 钉进双缓冲 `batch_record_buf = [None]*2`（L1669-1670），
   **防止 GPU tensor 被 torch GC 提前释放**；`_forward_isolation(batch, overlap=True)`（L4294+）
   让 `ScheduleBatch` 在一次前向内可回滚。批结果 copy 出来之后才处理。
4. **overlap 会被逐批临时关掉**：连续两个 prefill 批时禁用本批 overlap 以改善第一批 TTFT，
   由 `SGLANG_DISABLE_CONSECUTIVE_PREFILL_OVERLAP` 控制，**默认 False（即该优化默认不启用）**。

**【结论 c】与 chunked prefill 的关系：正交，不互为依赖。**
证据：`chunked_prefill_size` 与 `disable_overlap_schedule` 是两个独立字段；
`is_mixed_chunk = (chunked_prefill_size is not None and enable_mixed_chunk)`，
**不**依赖 overlap（`scheduler.py` L1327-1329）。两者被一起关掉都是有条件的、且都是**别的特性**引起的
（`pp_size>1` 强制关 overlap；embedding+sparse head；dllm；mamba auto）。

⚠️ **一条过时结论，别写进面稿**：`--enable-mixed-chunk` 强制关 overlap 的耦合**只存在于 v0.3.6 时代**
（当时 `server_args.py` 里有 "Overlap schedule is disabled because mixed-style chunked prefill is enabled."）。
**v0.5.21 全仓搜不到该字符串**，`overrides.py` 里也没有这条规则。

**【结论 d】`tp_worker_overlap_thread.py` 这条线已不存在**：该文件 v0.5.3 还有，**v0.5.4 起 404**；
overlap 逻辑已内联进 `scheduler.py` 的 `event_loop_overlap` + `overlap_utils.py`（`FutureMap`）。

### (4) radix cache 与 chunked prefill 怎么共存？

**【结论】两者默认都开，共存靠**三条**设计（v0.5.21）：**

1. ★ **chunk 边界对齐到 `page_size`，不是对齐到 radix 节点。**
   工具是 `RadixKey.page_aligned(page_size)`：`aligned_len = len(self) // page_size * page_size`（**向下取整**）。
   **来源**：`mem_cache/radix_cache.py` L146-150。
2. ★ **`page_size > 1` 时，末尾那个"不满一页"的部分只记在 `req.prefix_indices`、不进 radix tree**，
   用 `req.kv.cache_protected_len` 标出"树拥有的那一段"。源码注释原文：
   > "With page_size > 1 **the partial page sits in `req.prefix_indices` but not in the tree**;
   > `cache_protected_len` marks the tree-owned part … `req.prefix_indices` will be used in
   > `PrefillAdder::add_chunked_req` later"

   调用点：`scheduler.py` L3531-3535（`stash_chunked_request` → `maybe_cache_unfinished_req(req, tree_cache, chunked=True)`）。
3. ★ **`chunked=True` 的第二个作用：不给自己刚创建的节点刷 `hit_count`**（`_inc_hit_count(node, chunked)`：
   `if chunked: return`），避免 chunked 请求**自我抬权**把 lpm/dfs-weight 的排序搞偏。

**来源**：`mem_cache/radix_cache.py` L502-545（含 L526-536 注释）、L690-694、L704。

**【结论·★ 面试要点】命中前缀时，chunked prefill **只算未命中的部分**。**
待算长度 `cand_extend_input_len = len(req.full_untruncated_fill_ids) - len(req.prefix_indices)`，
即**总 prompt 减去已匹配前缀**（`prefix_indices` 含 device + host 各层缓存）；
随后 `req.set_extend_range(...)`，前向只跑这段区间。
**来源**：`schedule_policy.py` L1147-1149（`add_chunked_req`）、L1361-1364（`add_one_req`）；
辅助函数 `_uncached_len`（L490-494）注释直写 "all cache levels — device + host via hicache — counted as cached"。

**【结论】radix cache 被关掉时，chunked prefill 走 `ChunkCache` 而不是 `RadixCache`。**
`mem_cache/chunk_cache.py` docstring：`"Cache for chunked prefill, used when RadixCache is disabled."`。
`ChunkCache.disable` 恒为 `True`、`match_prefix` 返回空、`insert` 是 no-op
⇒ **关掉 radix cache 就没有前缀命中，chunked prefill 每次都从 0 算**。

**【结论】另一个相关但独立的 flag**：`--disable-chunked-prefix-cache`（默认 False），
help 原文 "Disable chunked prefix cache feature for deepseek, which should save overhead for short sequences."

### (5) ★★ SGLang 的 `prefill_decode_interval`：一个和"让路式"几乎同构的机制

**【结论】SGLang 有一个旋钮，语义就是"prefill 批之后先跑 N 轮 decode 再排下一个 prefill"——
和我们的 `spec_prefill_chunk_tokens` 让路逻辑是同一个形状。但它默认关。**

参数本体（help 原文）：
> "--prefill-decode-interval: **The number of decode rounds to run after a prefill batch before
> scheduling the next prefill.** By default, this is disabled except for profiled Qwen3-VL serving
> configurations on Hopper. In data-parallel attention mode, the interval is synchronized across all
> DP ranks. Set to 0 to disable."

**来源**：`.../v0.5.21/python/sglang/srt/arg_groups/fields/schedule.py` L56-62（默认 `None`）。

★ **默认值精确化**：`None` 统一解析为 **0（关闭）**；
**唯一会自动打开的配置是「大 Hopper 上的 Qwen3-VL」，被 override 设成 `22`**。
自动置 22 的条件（三个都要满足）：
`is_sm90_supported()`（Hopper）+ 显存 ≥ 60 GB + `model_type ∈ {"qwen3_vl", "qwen3_vl_moe"}`。
**来源**：默认解析 `arg_groups/validation_hook.py` L492-502（注释原文 "Leave Qwen3-VL Hopper free to pick 22;
everyone else stays disabled."）；override 在 `arg_groups/model_overrides/qwen3_vl.py` L17-31、L127-128。

实现（v0.5.21 `managers/scheduler.py`）：

```python
def init_chunked_prefill(self):
    self.chunked_prefill_size = get_schedule().chunked_prefill_size
    self.prefill_decode_interval = get_schedule().prefill_decode_interval or 0   # L1307
    self._prefill_decode_interval_remaining = 0                                  # L1308

def _should_defer_prefill(self) -> bool:                                         # L1351
    if self._prefill_decode_interval_remaining == 0:
        return False
    self._prefill_decode_interval_remaining -= 1
    return True

def _arm_prefill_decode_interval(self, batch) -> None:                           # L1358
    if self.prefill_decode_interval == 0 or batch is None:
        return
    is_extend = batch.is_extend_in_batch if self.require_mlp_sync else batch.forward_mode.is_extend()
    if is_extend:
        self._prefill_decode_interval_remaining = self.prefill_decode_interval
```

事件循环里，`_should_defer_prefill()` 为真时**直接不建新的 prefill 批**（`new_batch = None`），
于是这一步跑 decode；跑完一批后 `_arm_prefill_decode_interval(ret)` 重新上弦：

```python
elif self._should_defer_prefill():          # L3725
    new_batch = None
else:
    prefill_plan = self.get_new_batch_prefill(running_batch)
    new_batch = prefill_plan.batch_to_run
...
self._arm_prefill_decode_interval(ret)      # L3770
```

**来源**：`.../v0.5.21/python/sglang/srt/managers/scheduler.py` L1306-1375、L3723-3770。

⇒ **"prefill 批之后让 N 轮给 decode"在 SGLang 里是一个现成参数，默认值是 0（关）。**
这是本次调研里**与我们的实现最接近的行业机制**，也是 §3 对照的关键。

**【标注】"它按 chunk 边界让路"是**从代码路径推出的**（不是官方文档明文）**：
`get_new_batch_prefill` 也正是推进 `chunked_req` 下一个 chunk 的地方，被 defer 时它整轮不调用，
所以 in-flight 的 chunked 请求的下一个 chunk 也跟着延后；而每次 extend 批都会重新装填计数器
⇒ 长 prompt 切成 k 块时，**实际效果是每块之间插入 N 轮 decode**。
官方注释只写了 "The number of decode rounds to run after a prefill batch before scheduling the next prefill."
⇒ 面试时请说"**它的语义是 prefill 批之后让 N 轮 decode；在 chunked prefill 下等价于块间让路（这是我从代码推出的）**"。

### (6) ★ 混合批：SGLang 默认**不混**

**【结论】`--enable-mixed-chunk` 默认 **False**。**
字段 docstring 原文："**Enabling mixing prefill and decode in a batch when using chunked prefill.**"

**来源**：`.../v0.5.21/.../fields/schedule.py` L202-205（`enable_mixed_chunk: bool = False`）；
历史来源 `v0.4.6 server_args.py` L158。

调度器里对应 `self.is_mixed_chunk`（`scheduler.py` L1327-1328）：
```python
self.is_mixed_chunk = (
    self.chunked_prefill_size is not None and get_schedule().enable_mixed_chunk
)
```
关着的时候，事件循环是**"要么 prefill 批、要么 decode 批"二选一**；
开着的时候才会 `running_batch.merge_batch(new_batch)` 把 decode 与 prefill 块并成一个批。
（`scheduler.py` L3681、L3711 的 `merge_batch`；L3915/L4130 按 `self.is_mixed_chunk` 分支。）

★ **对我们极其有用的一条**：**"混合批"在 SGLang 里是一个**可选优化**，不是默认行为。**
所以"不混批"本身不是落后 —— 关键差异在于**我们连 let-decode-advance 的轮次都默认不给**（`spec_prefill_chunk_tokens=0`）。

**【结论】⚠️ 反例**：若显式传 `--chunked-prefill-size -1`（关 chunked prefill），
则即使 `--enable-mixed-chunk` 也**无效**（因为 `is_mixed_chunk` 依赖 `chunked_prefill_size is not None`）。

### 2.3.1 TensorRT-LLM

**【结论】两个术语都真实存在，而且是**两个不同层次**的东西（常被混淆）。**

**① in-flight batching（IFB）** —— 官方定义把三个词当同义词：
> "TensorRT LLM supports **in-flight batching** of requests (also known as **continuous batching** or
> **iteration-level batching**) for higher serving throughput. With this feature, **sequences in the
> context phase can be processed together with sequences in the generation phase**."

**② Chunked Context（a.k.a Chunked Prefill）** —— 官方独立一节：
> "## Chunked Context (a.k.a Chunked Prefill)
> The original behavior was to process all context tokens at once. However, this feature **splits the
> context into several chunks**. In this way, the context chunks can be batched with more tokens during
> the generation phase, which should increase overall throughput. Chunking contexts also removes
> constraints on input length. To enable this feature, the FMHA paged kv-cache also needs to be enabled.
> **Except for the last chunk, the size of each context chunk needs to be an integer multiple of the
> kv-cache block size.**"

**来源**：`https://github.com/NVIDIA/TensorRT-LLM/blob/main/docs/source/features/paged-attention-ifb-scheduler.md`
（2026-10 抓取）。

**【结论·区分】**
- **IFB = 批内混合"context 序列"与"generation 序列"**（= Orca 式 iteration-level scheduling）。
  解决的是"批里能不能既放 prefill 又放 decode"。
- **chunked context = 把**单条** context 切成块**（= SARATHI 式 chunked prefill）。
  解决的是"一条超长 prompt 一次吃下会顶爆 token 预算、阻塞 decode"。
- 两者可叠加：chunked context 的官方描述就是"让 context chunk 能和**更多 generation token** 拼进同一批"，
  前提正是 IFB 已在跑。

**【结论·版本时间线】**（官方 `docs/source/release-notes.md`）

| 版本 | 日期 | 原文 |
|---|---|---|
| v0.7.1 | 2023-12-27 | "fMHA support for **chunked attention** and paged kv cache"（kernel 层） |
| **v0.8.0** | **2024-02-29** | "**Chunked context support**" —— 功能首次进 release notes |
| v0.9.0 | 2024-04-16 | "context chunking to work with KV cache reuse" |
| v0.10.0 | 2024-06-05 | 引入 `ContextChunkingPolicy` |
| v0.11.0 | 2024-07-17 | `ModelRunnerCpp` 增加 `enable_chunked_context` |
| **v0.16.0** | **2024-12-24** | ★ "**[BREAKING CHANGE] Chunked context is enabled by default** when KV cache and paged context FMHA is enabled on non-RNN based models." |
| v0.17.0 | 2025-02-07 | 新 PyTorch workflow (`tensorrt_llm._torch`) 下 "chunked context (**default off**)" |
| v0.20.0 | 2025-06-19 | "Enabled chunked context for FlashInfer" |

但**是否与 vLLM 的 chunked prefill 同语义（同一次前向内混批）**，本轮**未逐句核实**（见 §5）。

### 2.3.2 TGI（Hugging Face Text Generation Inference）

**【结论】有 chunking，有专门文档页，叙事随 TGI v3 一起发布；但开关不叫 `--chunked-prefill`。**
官方文档页 `docs/source/conceptual/chunking.md`（标题 "**TGI v3 overview**"） 原文：
> "Performance leap: TGI processes **3x more tokens, 13x faster than vLLM** on long prompts. **Zero config!**"
> "On long prompts (200k+ tokens) conversation replies take **27.5s in vLLM**, while it takes only **2s in TGI**."
> 归因第 3 条："**Chunking Code**: Our chunking code enables finer control over compute resources…"

**来源**：`https://huggingface.co/docs/text-generation-inference/en/conceptual/chunking`。

**【结论】真正的旋钮是 `--max-batch-prefill-tokens`。** 对 `launcher/src/main.rs` 做 `chunk` 全串检索
**零命中** ⇒ **TGI 的 launcher 里没有任何以 chunk 命名的 CLI flag**。相关注释原文：
> "Limits the number of tokens for the prefill operation. Since this operation take the most memory and

### 2.3.3 分离式 / 解耦 prefill-decode（PD disaggregation）

#### DistServe
- **标题**：`DistServe: Disaggregating Prefill and Decoding for Goodput-optimized Large Language Model Serving`
- **作者**：Yinmin Zhong, Shengyu Liu, Junda Chen, Jianbo Hu, Yibo Zhu, Xuanzhe Liu, Xin Jin, Hao Zhang（北大 + UCSD）
- **编号/会议**：**arXiv 2401.09670**（2024-01-18），**OSDI 2024**（USENIX 页面已核）
- **核心思想（原文）**：
  > "DistServe assigns prefill and decoding computation to **different GPUs**, hence eliminating
  > prefill-decoding interferences. … co-optimizes the **resource allocation and parallelism strategy
  > tailored for each phase**. … **places the two phases according to the serving cluster's bandwidth**"
- **数字**："can serve **7.4x more requests** or **12.6x tighter SLO**"
- **对的问题是同一个吗**：原文第一句点明 colocatate 会 "lead to **strong prefill-decoding interferences**"，
  且 "**couples the resource allocation and parallelism plans for both phases**"。
  ⇒ **病根相同，治法不同**：它是"**把两阶段物理隔离到不同 GPU**"，不是"细粒度交错"。

#### Splitwise
- **标题**：`Splitwise: Efficient generative LLM inference using phase splitting`
- **作者**：Pratyush Patel, Esha Choukse, Chaojie Zhang, Aashaka Shah, Íñigo Goiri, Saeed Maleki, Ricardo Bianchini（Microsoft）
- **编号/会议**：**arXiv 2311.18677**（2023-11-30），**ISCA 2024**（DOI `10.1109/ISCA59077.2024.00019`）
- **核心思想（原文）**："splitting the two phases … **on to separate machines** … use **hardware that is
  well-suited for each phase** … requires **state transfer** … using the **fast back-plane interconnects**"
- **数字**："**1.4x higher throughput at 20% lower cost**… **2.35x more throughput** with the same cost"
- **与 chunked prefill 的差异（独特点）**：**异构硬件** —— prompt 阶段用高算力卡，token 生成阶段用
  **低功耗/低成本**卡。

#### Mooncake
- **标题**：`Mooncake: A KVCache-centric Disaggregated Architecture for LLM Serving`（arXiv 版）
- **作者**：Ruoyu Qin, Zheming Li, Weiran He, Mingxing Zhang, Yongwei Wu, Weimin Zheng, Xinran Xu（清华 + 月之暗面 Moonshot AI）
- **编号/会议**：**arXiv 2407.00079**（2024-06-24）；**FAST 2025**，获 **Erik Riedel Best Paper Award**
  （USENIX 正式标题为 `Mooncake: Trading More Storage for Less Computation — A KVCache-centric Architecture for Serving LLM Chatbot`）
- **核心思想（原文）**："**separates the prefill and decoding clusters** … leverages the **underutilized CPU,
  DRAM, and SSD resources** … to implement a **disaggregated cache of KVCache** … its **KVCache-centric
  scheduler** … a **prediction-based early rejection policy**"
- **数字**："up to a **525% increase in throughput**"；真实负载下 "**75% more requests**"
- **与 DistServe 的区别**：**DistServe 分离的是"算"，Mooncake 分离的是"算 + 存"**，并把 KV cache
  当成一等公民来调度（全局分布式 KV 池 + 跨请求前缀复用 + 过载早拒绝）。

#### ★ 三者共同点，以及 vLLM 官方对"它和 chunked prefill 是不是同一个问题"的定论

**vLLM 官方文档 `docs/features/disagg_prefill.md` 原文（这是我们能找到的最好答案）**：
> "**Disaggregated prefilling put prefill and decode phase of LLM inference inside different vLLM instances.**"
> "Without disaggregated prefilling, vLLM may insert some prefill jobs during the decoding of one request.
> This results in higher tail latency. Disaggregated prefilling helps you solve this issue and **control
> tail ITL**. **Chunked prefill with a proper chunk size also can achieve the same goal, but in practice
> it's hard to figure out the correct chunk size value. So disaggregated prefilling is a much more
> reliable way to control tail ITL.**"
> "!!! note **Disaggregated prefill DOES NOT improve throughput.**"

⇒ **面试可以说的定论**：**PD 分离与 chunked prefill 解决的是同一个问题（控 tail ITL、消解
prefill-decode 干扰），区别是"分离式不用调 chunk size、更可靠，但不提升吞吐；chunked prefill
保持同实例混批、直接提吞吐但要手工调 chunk size"。**

**【推测（标清）】**代价：每请求一次 KV 传输的网络开销、prefill 池单独配额导致的资源碎片、
跨实例调度复杂度；Mooncake 额外付出分布式 KV 存储的复杂度（换来跨请求复用收益）。

**【工业采用的最硬证据】** vLLM 主仓库 `mooncake` 命中 **88** 处（含
`docs/features/mooncake_connector_usage.md`、`vllm/distributed/kv_transfer/kv_connector/v1/mooncake/`、
`examples/disaggregated/mooncake_connector/`）。

**【标题】**
> **SARATHI: Efficient LLM Inference by Piggybacking Decodes with Chunked Prefills**

**【作者】** Amey Agrawal, Ashish Panwar, Jayashree Mohan, Nipun Kwatra, Bhargav S. Gulavani, Ramachandran Ramjee

**【编号 / 年份】** **arXiv:2308.16369**（cs.LG; cs.DC），v1 提交 **2023-08-31**，只有 v1、无后续版本。

**【单位】** **Microsoft Research India**（论文脚注写明其中一位作者 "Work done as intern at Microsoft Research India"）。
**【机构核实来源】** arXiv HTML 全文 + OpenAlex。

**【★ 发表状态：查不到正式会议】** arXiv abs 页**没有 Comments、没有 Journal-ref**；
OpenAlex 把它归为 `type: preprint`、venue = arXiv。
★ **网上流传的"SARATHI, MLSys 2024, 6:351–366"是讹传** —— MLSys 2024 那篇同名作者群论文是 **Vidur**
（LLM 推理仿真框架），不是 SARATHI。**面试里不要写"SARATHI 发表于 MLSys 2024"。**
（真正的正式发表版是后继工作 **Sarathi-Serve，OSDI 2024**，见 §2.5.1。）

**来源**：`https://arxiv.org/abs/2308.16369`（2026-10-12 抓取，标题/作者/提交历史逐字如上）。

**【术语（摘要原文）】**
> "SARATHI employs **chunked-prefills**, which splits a prefill request into equal sized chunks, and
> **decode-maximal batching**, which constructs a batch using **a single prefill chunk** and populates
> the remaining slots with decodes. During inference, the prefill chunk saturates GPU compute, while
> the decode requests **'piggyback'** and cost up to an order of magnitude less compared to a
> decode-only batch. Chunked-prefills allows constructing **multiple decode-maximal batches from a
> single prefill request**, maximizing coverage of decodes that can piggyback."

⇒ 两个术语要分清楚：**"chunked-prefills"**（分块）与 **"decode-maximal batching"**（满配 decode 的猪背批）。
"piggyback" 是标题里的说法。

**【★ 术语提醒】论文里**没有**出现缩写 "DMB"。** 全文检索 `DMB` **零命中**；论文始终把
`decode-maximal batching` 写全。**不要用这个缩写**（业界口语里可能有，但论文里没有）。
另外，论文 §4.3 的小节标题原文是 `4.3 Decode-Maximal Batching`，其子节标题 `Piggybacking decodes with prefills`
（原文 PDF 此处 LaTeX 编号错乱成 "3.1"，是论文自己的排版 bug）。

**【报告的收益（摘要原文数字）】**
> "For the LLaMA-13B model on A6000 GPU, SARATHI improves **decode throughput by up to 10x**, and
> accelerates **end-to-end throughput by up to 1.33x**. For LLaMa-33B on A100 GPU, we achieve
> **1.25x higher end-to-end-throughput** and **up to 4.25x higher decode throughput**. When used with
> pipeline parallelism on GPT-3, SARATHI reduces **bubbles by 6.29x**, resulting in an end-to-end
> throughput improvement of **1.91x**."

⇒ **收益量级一句话**：**吞吐 1.25x ~ 1.33x（端到端）、解码吞吐最多 10x；流水线气泡减少 6.29x。**
注意它的**主指标是吞吐与气泡（bubble）**，主要动机之一其实是 **pipeline parallelism 的微批不均衡**，
不只是"长 prompt 阻塞 decode"。

**【结论】正文明细（子 agent 从 arXiv HTML 全文核出，逐句定位）**

- **§5.1.1**：decode 提升区间 —— "our decode throughput improvement is still significant in all cases (**2.8×–10×**)"。
- **§5.1.2 Table 4「Peak throughput gains with Sarathi」**（chunk size = 256）：

  | 模型(GPU) | 序列长 | batch | P:D | decode 加速 | 吞吐增益 |
  |---|---|---|---|---|---|
  | LLaMA-13B (A6000) | 1K / 2K / 3K | 6 | 50:1 | 5.45× / 3.26× / 2.51× | **1.33×** / 1.26× / 1.22× |
  | LLaMA-33B (A100) | 1K / 2K / 3K | 10 / 5 / 3 | 28:1 / 63:1 / 127:1 | 3.83× / **4.25×** / 3.51× | 1.25× / 1.22× / 1.14× |

- **baseline 是什么**（§5.1）：把 prefill 与 decode **分开执行**的传统方式 ——
  "the baseline which executes the prefill and decode stages separately via **prefill-only and decode-only batches**"；
  §5.2 点名 **FasterTransformer** 就是这么部署的（"This is how popular frameworks like **FasterTransformer** deploy
  transformer models."）。另与 **Orca 的 iteration-level scheduling** 对比：Sarathi 三种序列长上的
  吞吐增益 1.27×/1.25×/1.23×，而 **Orca best-case 只有 1.11×**。
  ★ **vLLM / TGI 只是被引用为相关系统，不是它的实验 baseline。**
- **测的规模/硬件/workload**：单卡 LLaMA-13B on A6000、LLaMA-33B on A100；序列长 1K/2K/3K；
  P:D 比 1–200；chunk size 256/512。流水线并行实验用 **GPT-3 + 模拟环境**
  （"we report evaluations in a carefully simulated environment"），声称与真实
  64×A100 / 8 服务器 / InfiniBand 部署误差 <5%。

**【结论 · ★ 重要澄清】2023 这一版 SARATHI **没有报 ITL / tail latency 指标。**
它报的全是 **throughput**（decode throughput / end-to-end throughput / pipeline bubbles）。
**"chunked prefill 改善 ITL、控 tail latency"这套说法是后来 vLLM 文档与 Sarathi-Serve（OSDI'24）才明确作为卖点的**
（vLLM 文档原话："It improves inter-token latency (ITL) and generation decode because decode requests are prioritized."）。
⇒ ★ **面试里如果说"SARATHI 论文证明了 ITL 改善 X%"，属于张冠李戴。**

**【结论】它自己承认的局限（§6 Discussion）**
1. 只做 scheduling，**不优化 latency / 排队延迟 / 公平性**："real-world deployments need to optimize …
   simultaneously along multiple dimensions e.g., latency, queuing delays, fairness … Meeting these goals with
   Sarathi requires revisiting scheduling policies."
2. **不会选最优 chunk size**："we leave it to future work to explore how to pick an optimal chunk size"。
3. **假设过于简化**："we make a simplistic assumption in this paper that **each request in a batch has the same
   number of prefill and decode tokens**"。
4. **序列长只测到 3K**（超长序列 "may pose new challenges as the cost of attention grows quadratically"）。
5. **§5.4 自曝 chunk 代价**：chunk size = **64** 时，attention 有 **3×** 开销、整体 prefill 时间约 **5×**；
   256/512 才把 prefill 损失压到 20%/10% 以内。
   ★ **这条与我们在 `docs/P12混合调度-开发记录.md §4.1` 测到的"小 chunk 的 prefill 代价"是同一个现象**，
   可以互相印证（但**不要**在这里写我们的数字）。

**【与 vLLM 的关系（已核实，比"文档背书"精确得多）】**
- **RFC**：vLLM Issue **#3130「[RFC] Upstream Chunked Prefill」**（2024-03-01）正文引的正是
  2308.16369 + 2401.08671 两篇；并说明要把 **Anyscale 内部实现**上游。
- **但代码里已无痕迹**：对 vLLM 主仓库全库检索 —— `chunked_prefill` 命中 134 处，
  ★ **`sarathi` 命中 0 处**。即**当前 vLLM 代码与文档里都没有 "SARATHI" 字样**（只有那个 RFC issue 提过）。
- **一个失败的 PR**：**PR #3121「Add Sarathi-Serve support in vLLM」**（2024-02-29，由 Sarathi 作者之一提交）
  → **state=closed，merged=false（未合并）**。真正落地的是 **PR #3884「[Core][5/N] Fully working chunked
  prefill e2e」**（Anyscale，提交 2024-04-11 合并）。
⇒ **总结**：**"vLLM 的 chunked prefill 受 SARATHI 启发"有 RFC 背书，但"vLLM 实现了 SARATHI"是错的**
（照搬 Sarathi 调度器的 PR 没合进去）。

## 2.5 比"猪背"更新的做法（2024–2026）

> 下面每条都标了**信息强度**：`【一手】`= 打开过 arXiv abs 页/论文原文；`【二手】`= 只拿到搜索摘要，需复核。
> 所有 arXiv 编号与日期都逐个打开 `arxiv.org/abs/<id>` 核过（未用不稳的 export API）。

### 2.5.0 一句话坐标

"猪背"（2023）解决的是**批内怎么拼**。2024–2026 的后续分四条线：
**① 把拼法变成调度器 + 尾延迟约束**（Sarathi-Serve）；**② 把 chunk 变成优化变量**（FastGen / SLOs-Serve / PolyServe）；
**③ 换目标函数**（SLO goodput / 公平性，JITServe、Llumnix）；**④ 釜底抽薪——质疑"粗粒度两相"本身**（NanoFlow）；
再加两条**正交**线：**共享前缀**（Preble / Hydragen / ChunkAttention）与**复用/跳过 prefill**（CacheBlend / CachedAttention）。

### 2.5.1 Sarathi-Serve —— 最直接的接班人【一手】
- `Taming Throughput-Latency Tradeoff in LLM Inference with Sarathi-Serve`
- **arXiv 2403.02310**（2024-03-04），**OSDI 2024**；作者 Agrawal, Kedia, Panwar, Mohan, Kwatra, Gulavani, Tumanov, Ramjee
- 原文："introduces **chunked-prefills** … creates **stall-free schedules** that adds new requests in a batch
  **without pausing ongoing decodes**"
- 数字："**2.6x higher serving capacity** for Mistral-7B on single A100 … up to **3.7x** for Yi-34B on two A100
  as compared to **vLLM** … up to **5.6x** end-to-end serving capacity"（Falcon-180B + PP）
- **相对 chunked prefill 的增量**：把 2023 年的"批构造技巧"升级成**调度器** —— 给出 "stall-free" 的形式化、
  把 chunk size / token budget 变成 **TTFT ↔ 尾延迟**的可调旋钮、并**首次在尾延迟约束下对标 vLLM 报收益**。
- ★ **这正是"chunked prefill 改善 ITL / 控 tail latency"这个说法的真正出处**（不是 2023 那版 SARATHI）。

### 2.5.2 DeepSpeed-FastGen / Dynamic SplitFuse【一手】
- **arXiv 2401.08671**（2024-01-09），Microsoft DeepSpeed
- 原文：**"Dynamic SplitFuse"**，up to **2.3x higher effective throughput, 2x lower latency on average, and
  up to 3.7x lower (token-level) tail latency**, compared to vLLM
- **增量**：chunked prefill 是**固定大小**切块；SplitFuse **动态拆分** prompt 去填满固定 token 预算。
  ★ **这就是 vLLM 官方文档 related papers 里的第二篇**（见 §2.3.0）。

### 2.5.3 SLOs-Serve —— 把 chunk 当优化变量【一手】
- `SLOs-Serve: Optimized Serving of Multi-SLO LLMs`，**arXiv 2504.08784**（2025-04-05）
- 原文：用 **multi-SLO dynamic programming** 在 SLO 约束下持续优化 token 分配，
  "**exploring the full design space of chunked prefill**"（可联合投机解码）；per-GPU 容量 **2.2x on average**
- **增量**：chunk 大小从"超参"变成 **多阶段 SLO 下的 DP 优化变量**。

### 2.5.4 JITServe（原名 Tempo）—— 换目标函数【一手】
- **arXiv 2504.20068**：**v1（2025-04-24）标题是 `Tempo: Application-aware LLM Serving with Mixed SLO Requirements`**；
  **v2（2025-12-11）起改名为 `JITServe: SLO-aware LLM Serving with Imprecise Request Information`**
- 原文（现版）：最大化 **service goodput**（满足 SLO 的 token 数），用 **imprecise request information** 调度；
  结果 **1.4x–6.3x goodput** 提升，或 **28.5%–83.2% 资源节省**
- **增量**：chunked prefill 优化吞吐/ITL；JITServe 把目标改成"**满足 SLO 的有效服务量**"，并显式处理"响应长度未知"。
- ★ **引用注意**：说 "Tempo" 时要说清是 v1 的名字。

### 2.5.5 PolyServe —— 多 SLO 分桶 + 动态 chunk【二手，需复核】
- `PolyServe: Efficient Multi-SLO Serving at Scale`，**arXiv 2507.17769**（2025-07-17），UW + ByteDance
- 【二手】按 per-token latency 需求分桶到不同服务器子集；技法含 "request-wait-time-aware scheduling,
  **dynamic chunking**, **continuous chunked prefill prediction**"；报告 **1.23× goodput**
- ⚠️ **细节来自搜索摘要，未逐句核对原文**。它 related work 明确把 Sarathi-Serve/chunked prefill 当 baseline。

### 2.5.6 NanoFlow —— 釜底抽薪【一手】
- **arXiv 2408.12757**（2024-08-22）
- 原文："despite having memory-intensive components, **end-to-end LLM serving is compute bound** for most common
  workloads and LLMs. Alas, most existing serving engines fall short from optimal compute utilization, because the
  heterogeneous operations … are **executed sequentially** within a device"
- **增量**：不再把 serving 看成"prefill 块 + decode 块"两相粗粒度交错，而是切成极细的**操作流（nano-batch）**
  填满流水线。★ **这是对"chunked prefill 粒度设定"本身的质疑**，面试里可以作为"更前沿的思路"提一句。

### 2.5.7 Llumnix —— 跨实例重调度【一手】
- **arXiv 2406.03243**（2024-06-05），**OSDI '24**（arXiv Comments 原文 "To appear at OSDI '24"）
- 原文：**"runtime rescheduling across multiple model instances"**，含 KV cache 活迁移
- **增量**：不动"批内怎么拼"（chunked prefill 的地盘），而是加**跨实例的负载均衡/抢占** ——
  ★ **正好补上 SARATHI §6 自认的局限 1（排队延迟与公平性）**。
- 工业采用：vLLM 主仓库 `llumnix` **0 命中**（是独立项目）。

### 2.5.8 Preble —— 分布式前缀感知调度【一手】
- **arXiv 2407.00023**（2024-05-08），UCSD
- 原文："they are all confined to a **single-GPU optimization**, while production LLM serving systems are
  distributed by nature … the first **distributed** LLM serving platform that targets and optimizes for **prompt sharing**"
- **增量**：chunked prefill 处理"一条 prompt 太长"；Preble 处理"**多条请求共享同一前缀**"且**跨 GPU**。
  vLLM / SGLang 均未内置（各 0 命中）。

### 2.5.9 Hydragen / ChunkAttention —— 共享前缀的注意力实现【一手】
- `Hydragen: High-Throughput LLM Inference with Shared Prefixes`，**arXiv 2402.05099**（2024-02-07）
- `ChunkAttention: Efficient Self-Attention with Prefix-Aware KV Cache and Two-Phase Partition`，
  **arXiv 2402.15220**（2024-02-23），**ACL 2024**
- **增量**：**正交方向** —— 不动调度，而是**改 attention 实现**，让"大批请求共享 system prompt / few-shot 前缀"时
  decode 的 attention 不再退化。vLLM / SGLang 均未内置。

### 2.5.10 CacheBlend —— RAG 场景的非前缀 KV 复用【一手】
- **arXiv 2405.16444**（2024-05-26），UChicago
- 原文：复用的文本块 "are **not always the input prefix**"，所以预计算 KV 不能直接用（忽略了与前面文本的 cross-attention）
- **增量**：chunked prefill 省的是**算力时间**；CacheBlend **直接省掉整段 prefill**（快速融合多个文本块的 KV）。
  vLLM / SGLang 未内置。

### 2.5.11 CachedAttention（不要叫它 AttentionStore）—— 多轮对话 KV 复用【一手】
- **arXiv 2403.19708**（2024-03-23），**USENIX ATC 2024**
- 正式标题：`Cost-Efficient Large Language Model Serving for Multi-turn Conversations with CachedAttention`
- 原文：**CachedAttention** 实现**跨多轮对话复用 KV cache**（分层 KV 缓存系统）
- ⚠️ **"AttentionStore" 不是 arXiv 标题里的名字**；引用时写 **CachedAttention**。

### 2.5.12 再往后的分支【部分未核实】
- `AccelGen: Heterogeneous SLO-Guaranteed High-Throughput LLM Inference Serving for Diverse Applications`，
  **arXiv 2503.13737**（2025-03-17）—— **仅从搜索摘要获得，未核原文**。
- `semi-PD: Towards Efficient LLM Serving via Phase-Wise Disaggregated Computation and Unified Storage`，
  **arXiv 2504.19867**（2025-04-28）—— 标题与日期已核，**内容未读**；从标题看是 PD 分离与统一存储之间的折中。

### 2.5.13 ★ 这些"更新做法"和我们的关系（一句话）

> 我们要讲的故事（"让路 vs 猪背"）处在 **2.5.1 Sarathi-Serve 那条线**的分支上；
> **2.5.6 NanoFlow** 是对"粗粒度两相"的釜底抽薪式质疑，**2.5.7 Llumnix / 2.5.4 JITServe** 补的是公平性与 SLO ——
> 而这三个维度（细粒度、公平性、SLO）**恰好都是我们没做的**。
> 面试里主动说"我们知道这条线还在往哪走"，比只说"我们做了让路"更有说服力（但别把它们说成"已解决"）。

## 2.6 ★ 追加问题：多个长 prompt 同时到达时，主流引擎会不会让后面的长期等待？

（这一节是委托人临时追加的，用户直接问到，会进面试话术。**结论与常见印象不同，请重点看。**）

### 先给结论

> **会。** 默认配置下，**vLLM 与 SGLang 都倾向让"先到的那条超长 prompt"独占推进，
> 后面的请求（不管长还是短）要等它拼完。** 两家都提供了缓解旋钮，但**默认都是关的**。
>
> ★ **委托人"默认同时只推进一个 partial prefill"的印象，一半对一半错 —— 而这一点非常值得在面试里讲**：
>
> | 引擎 | 是否有"同时只推进 1 条 partial prefill"的机制？ | 机制 |
> |---|---|---|
> | **vLLM V0** | ★ **有**（`max_num_partial_prefills` 默认 **1**） | 显式配置项 |
> | **vLLM V1（当前）** | ★ **没有这个机制**（该配置被 V1 oracle 明确拒绝，v0.27.0 已删除） | 但**效果上仍然会等**：FCFS + 先到者吃满 token 预算（另一条完全不同的路径） |

**【结论 b2 · ★ 直接证实 "V0 默认只推进 1 条" 的源码，以及"为什么这么保守"的一手理由】**
V0 调度器里有一个专门的数据结构 `PartialPrefillMetadata`，它的**类 docstring 把设计意图写全了**——
这就是委托人要的"为什么保守"的**来源**（原文，v0.8.0 `vllm/core/scheduler.py` L330-424；
下面那段**代码**逐字取自 v0.9.0 `vllm/core/scheduler.py` L332-425，两版同构）：

> "When chunked prefill is enabled, we allow a certain number of seqs to be partially prefilled during each
> iteration. Having multiple partial prefills in flight allows us to minimize TTFT and **avoid decode starvation**
> in cases where **a single sequence group with a very large prompt blocks the queue for too many iterations**.
> The number of long prefill requests is limited so that **smaller requests may jump the queue in front of them**
> and get to the decode phase faster."

★ **注意**：这段 docstring 恰恰是在解释"**为什么需要允许多条**（默认 1 是"不启用这个特性"）"，
而不是"为什么限制成 1"。默认 1 的含义是：**这个"避免 decode starvation"的特性默认不开**。
配套的预算公式也在源码里：**N 条 partial prefill 时每条拿 `max_num_batched_tokens // N`**
（`partial_prefill_budget_lookup_list[i] = max_num_batched_tokens // i`；**N=1 ⇒ 一条吃掉整个预算**）。

它的核心一行就是**把并发 partial prefill 数夹到默认值**：

```python
class PartialPrefillMetadata:
    """..."""
    # The number of long prefill requests currently running
    long_prefills: int
    ...
    def can_schedule(self, seq_group: SequenceGroup) -> bool:
        """When concurrent partial prefills are enabled,
        we limit the number of long requests and only accept
        shorter requests from the queue while running them
        concurrently"""
        return not (seq_group.first_seq.get_num_new_tokens()
                    > self.scheduler_config.long_prefill_token_threshold
                    and self.long_prefills
                    >= self.scheduler_config.max_long_partial_prefills
                    and self.scheduler_config.max_num_partial_prefills > 1)
    ...
    @classmethod
    def from_queues(cls, running, waiting, scheduler_config):
        ...
        return PartialPrefillMetadata(
            schedulable_prefills=min(
                prefills, scheduler_config.max_num_partial_prefills),   # ★ 就是这一行
            long_prefills=long_prefills,
            scheduler_config=scheduler_config,
        )
```

★ **`schedulable_prefills = min(prefills, max_num_partial_prefills)`。默认 1 ⇒ 每次只允许 1 条 prefill 被调度。**
而且 `can_schedule()` 的最后那个条件 `max_num_partial_prefills > 1` 表明：
**"concurrent partial prefills" 这个特性在默认值 1 下是**不启用**的**。

**来源**：`.../v0.9.0/vllm/core/scheduler.py` L332-425（逐字如上）。

⇒ **解读（请逐条对照，别over-claim）**：
- 默认值 1 **确实是** `max_num_partial_prefills` 在 **V0** 里"同时最多几条序列处于部分 prefill"的上限。
- 在 **V1** 里这个上限**不是 1** —— 而是**没有这个机制**：V1 调度器按 token 预算推进，
  **一轮里可以同时推进多条 partial prefill**（见 (2)）。设 >1 会被 oracle 拒（回退 V0 或报错）。
- 所以"**vLLM 默认只推进一个 partial prefill，所以后面的要等**"这句话，
  **对 V0 成立，对 V1 不成立**（V1 的"等"是另一个机制造成的，见 (2)）。

**【结论 c】当前的公平性旋钮是 `long_prefill_token_threshold`，默认 0 = 关。**
官方文档（2026-10-12）逐字：

> "--long-prefill-token-threshold: For chunked prefill, a request is considered **long** if the prompt is
> longer than this number of tokens. **0 disables the cap (default).** **The cap is not applied when the
> request is the only one in the batch, since there is no other request for it to starve.** Default: 0"
>
> "--long-prefill-token-threshold-adaptive: **Floor the effective long prefill token threshold at a fair
> share of the token budget**: `max_num_batched_tokens` divided by the number of queued and running
> requests. Only applies when `long_prefill_token_threshold` is nonzero. Default: False"

**来源**：`https://docs.vllm.ai/en/latest/configuration/engine_args.html`（字段默认值另见
`.../v0.31.0/vllm/config/scheduler.py` L80、L87：`long_prefill_token_threshold: int = Field(default=0, ge=0)`、
`long_prefill_token_threshold_adaptive: bool = Field(default=False)`）。

源码里的注释把设计意图说得很清楚（v0.31.0 `scheduler.py` L611-618）：
```python

# starving other requests of the token budget. When it is the only
# request there is nobody to starve, so let it use the whole budget.
num_running, num_waiting = self.get_request_counts()
num_eligible_reqs = num_running + num_waiting

    self.scheduler_config.long_prefill_token_threshold
    if num_eligible_reqs > 1
    else 0

```

**⇒ 官方文档的措辞本身就在承认：不设这个 cap（默认）时，一条长 prefill 会 starve 其他请求。**

### (2) V1 默认到底会不会让后面的长 prompt 等？把机制说清楚

**V1 的调度顺序（v0.31.0 源码）**：
1. 先跑 `while req_index < len(self.running) and token_budget > 0` —— 所有**在跑**的请求（含正在分块的长 prefill）。
2. 再用剩下的 `token_budget` 跑 `while token_budget > 0` —— 从 waiting 队列取新请求。

```python
num_new_tokens = (request.num_tokens_with_spec
                  + request.num_output_placeholders
                  - request.num_computed_tokens)
if 0 < long_prefill_token_threshold < num_new_tokens:
    num_new_tokens = long_prefill_token_threshold
num_new_tokens = min(num_new_tokens, token_budget, input_budget - draft_slots)
```
**来源**：`.../v0.31.0/vllm/v1/core/sched/scheduler.py` L675-683。

**⇒ 推导**（这是**从源码直接读出来的，不是推测**，但请自己复核）：
- `long_prefill_token_threshold = 0`（默认）⇒ 那条长 prefill 一次拿 `min(自己剩余, token_budget)` = **整个预算**。
- `token_budget` 归零 ⇒ **waiting 循环根本没机会跑**，新到的请求（长或短）**这一步一条也进不来**。
- 下一步，那条长 prefill 已经在 `self.running` 里，**仍然排在 waiting 之前**，继续吃满预算。
- ⇒ **一条超长 prompt 会连着好几步独占整批，直到它自己拼完。后面的请求一直等。**
  （粗略地说，独占的步数 ≈ `ceil(prompt 长度 / max_num_batched_tokens)`。）

**【★★ 最强证据：官方 issue 里的生产数据】**
vLLM 官方 issue **#57413**（state=open，创建于 **2026-09-17**），标题：
> `[Feature]: Production evidence for restoring concurrent partial prefill limits
> (max_num_partial_prefills / max_concurrent_prefills) in V1 scheduler`

里面记录的场景与数字（作者自述）：

- **TTFT p95 冲到 76 秒**；`num_requests_waiting{reason="capacity"}` 持续 0–9
- 而 **`kv_cache_usage_perc < 40%`、`num_preemptions_total` 增量 = 0** ⇒ 瓶颈**不在显存、不在并发上限**，
  而在 **prefill 的调度准入**
- 作者**直接尝试** `--max-num-partial-prefills 4`，结果报 **`vllm: error: unrecognized arguments`**
  （★ 这就是"该参数在当前 vLLM 已不存在"的**运行期实证**）

**来源**：`https://github.com/vllm-project/vllm/issues/57413`。

### (3) V0 的 `_schedule_prefills` 遇到"装不下的序列"是 break 还是 continue？

**【结论】是 `break`（放弃整条循环），不是跳过它继续排后面。** v0.6.3 `vllm/core/scheduler.py`：

```python
while self._passed_delay(time.time()) and waiting_queue:
    seq_group = waiting_queue[0]                          # 只看队首
    ...
    prompt_limit = self._get_prompt_limit(seq_group)
    if num_new_tokens > prompt_limit:
        ... waiting_queue.popleft(); continue             # 超长 → 丢弃并 continue

    can_allocate = self.block_manager.can_allocate(seq_group, ...)
    if can_allocate == AllocStatus.LATER:
        break                                             # ← 装不下 ⇒ 整轮停
    elif can_allocate == AllocStatus.NEVER:
        ... waiting_queue.popleft(); continue             # 永久放不下 → 丢弃

    if (num_new_tokens == 0
            or not budget.can_schedule(num_new_tokens=num_new_tokens,
                                       num_new_seqs=num_new_seqs)):
        break                                             # ← 预算不够 ⇒ 整轮停
```
**来源**：`.../v0.6.3/vllm/core/scheduler.py` L845-950（`_schedule_prefills`）；v0.8.0 同构（L1032 起，
变量名改成 `num_new_tokens_uncached`）。

**【结论·★ 必须分开写：chunked prefill 开着时 V0 会怎样】**
- **chunked prefill 关**（V0 默认）：`num_new_tokens == num_prompt_tokens`，一个长 prompt 若超预算就**直接 `break`**
  → 后面全等（经典 head-of-line）。
- **chunked prefill 开**：`_get_num_new_tokens()` 会先把头请求**截断到剩余预算**
  （`num_new_tokens = min(num_new_tokens, remaining_token_budget)`；有 prefix caching 时按 block 对齐取整），
  所以头请求把预算吃干净 → 下一轮 `remaining_token_budget() == 0` → `can_schedule` 失败 → `break`。
  **结果同样是后面的长 prompt 全等**，只是头请求"边吃边走"。
  **来源**：`vllm/core/scheduler.py@v0.6.3` L1590-1640（`_get_num_new_tokens`）、L1090（`_schedule_chunked_prefill` 以 `enable_chunking=True` 调 `_schedule_prefills`）。

**【结论】V0 的优先级顺序官方写在 `_schedule_chunked_prefill` 的 docstring 里**（原文）：
> "This policy 1. schedule as many decoding requests as possible. 2. schedule chunked prefill requests that are
> not finished. 3. schedule swapped request. 4. schedule new prefill requests."

⇒ V0 的 prefill 队列是**严格的队首阻塞**：队首这条排不进去，后面的**全部一起等**（不会"越队"）。
这与 V1 的"预算驱动、逐条推进"是**两种不同**的行为。

**【结论】但 V1 也不是全 `break`**：v0.31.0 的 waiting 循环里还有一个 `skip_request()` 机制 ——
把"本轮排不进去"的请求放进 `step_skipped_waiting` / `step_skipped_kv_holding` 并 **`continue`**，
用于 KV connector / prefix replay / LoRA / streaming 等场景。
★ **但真正的"没预算了"仍然是 `break`**（`while token_budget > 0` + 内部 `num_new_tokens == 0 → break`）。
**来源**：`vllm/v1/core/sched/scheduler.py@v0.31.0` L873-903（`skip_request` 定义）、L1120-1130（`if num_new_tokens == 0: break`）。

**v0 → v1 在这点上的差异（本轮核实到的）**：
| | V0（v0.6.3 ~ v0.9.0） | V1（v0.13.0 ~ v0.31.0） |
|---|---|---|
| 同时推进几条 partial prefill | 由 `max_num_partial_prefills`（**默认 1**）限制 | **无此限制**，由 token 预算决定，可以多条 |
| 装不下的序列 | **`break`**（队首阻塞） | 逐条 `min(需求, 剩余预算)`，有预算就继续排下一条 |
| 会不会让后面的等 | **会**（队首阻塞 + 只允许 1 条 partial） | **也会**，但机制不同：先到的那条**吃满预算**，后面的进不来 |
| 公平性旋钮 | 无（除了那个上限本身） | `--long-prefill-token-threshold`（默认 0=关）、`--long-prefill-token-threshold-adaptive`（默认 False） |

### (4) SGLang 有没有对应参数？默认同时推进几条 partial prefill？

**【结论 ★】SGLang **没有** vLLM 那套 `max_num_partial_prefills` / `long_prefill_token_threshold`
（全仓 0 命中），但它**默认最多只推进 1 条 partial prefill** —— 靠的是**单槽设计**，不是配置项。**

**三重证据**（v0.5.21）：
1. `scheduler.py` L1325：`self.chunked_req = None` —— **单个 `Optional[Req]`，不是列表**。
2. `scheduler.py` L4076-4079：
   ```python
   if adder.new_chunked_req is not None:
       # Update chunked prefill
       assert self.chunked_req is None
       self.chunked_req = adder.new_chunked_req
   ```
3. `schedule_policy.py` L1511-1517 的源码注释原文：
   > `# Only one unfinished chunked request can be tracked.`

**【结论】但要区分"1 条 chunked"与"批里几条新请求"**：
`PrefillAdder` 在一次预算内可以放进**多条新请求 + 至多 1 条续跑的 chunk**。相关参数：
- `--max-prefill-tokens` 默认 **16384**（`fields/schedule.py` L67-77）
- `--prefill-max-requests` 默认 **None = 无限制**（`fields/schedule.py` L78-81）；
  预算检查在 `add_one_req` 开头（`schedule_policy.py` L1347-1349）
  ⇒ **这是与 vLLM 的一个实质差别：vLLM 的公平 cap 默认 0（不卡），SGLang 的 `chunked_prefill_size`
  默认是一个具体数字（2048~16384），所以 SGLang 天然给"单条长 prompt"设了上界。**
- `--prefill-max-requests` 是**较新**的参数：**v0.5.7（2026-01-01）才引入**（v0.5.6 及以前 0 命中）。

**【结论】装不下的那条 prefill 是 `break`，不是 `continue`。**
`scheduler.py` L4028-4056（`AddReqResult` 为 `NO_TOKEN` 时）：
```python
if res == AddReqResult.NO_TOKEN:
    if (self.enable_hierarchical_cache or self.enable_lmcache or ...):
        running_batch.batch_is_full = len(adder.can_run_list) > 0 or (not running_batch.is_empty())
    else:
        running_batch.batch_is_full = True
...
break
```
⇒ **预算耗尽 ⇒ `batch_is_full = True` + `break`，后面的请求本轮一个都不看，整体推到下一轮**
（这就是 SGLang 版"队头阻塞"的来源）。
循环里另有 `continue` 的分支，但都**不是**"装不下"，而是：LoRA 未加载、HiCache 预取未完成、
pooling mode 与已入批请求不一致 —— 那些是"跳过该请求继续看下一个"。

**来源**：`.../v0.5.21/python/sglang/srt/managers/scheduler.py` L4028-4056；
`AddReqResult` 定义 `schedule_policy.py` L607-610。

### (5) 有没有论文/实测讨论"N 条 partial prefill 同时在场的代价"？

# 3. ★ 与我们的实现的对照

> **本节不写我们的任何实测数字** —— 需要时说"见 `docs/优化报告.md §c.3`"或
> `docs/P12混合调度-开发记录.md §2`、`docs/P13调度与延迟-开发记录.md §4.2`。

## 3.1 我们做的是什么（代码事实，标源文件）

| 项 | 我们的做法 | 来源 |
|---|---|---|
| 开关 | `spec_prefill_chunk_tokens`，**默认 0 = 关**（= 老行为：prefill 排他） | `nanovllm/config.py` |
| 分块 | `budget = min(remaining, chunk)`；`seq.num_scheduled_tokens = min(num_tokens, budget)`；本步拼不完就 `_prefill_chunk_pending = True` 并**立刻 `break`** | `nanovllm/engine/scheduler.py` `schedule()` |
| **让路** | `yield_to_decode = chunk > 0 and _prefill_chunk_pending and bool(self.running)` ⇒ **这一整轮只跑 decode**；下一轮再继续 prefill | 同上 |
| 路径数 | ★ **一轮内只有一条执行路径**（要么全 prefill、要么全 decode），**不混路径** | 同上（注释明写）|
| 门控 | 没有可让路的解码请求时（`running` 空）**不分块**（分块只有代价没有收益） | 同上（P12） |
| CUDA Graph | decode 图按**精确 B** 捕获（`spec_graph_bs=(1,2,4)`）；`run_model()` 里 **`if is_prefill ... → eager`**，prefill 恒不走图 | `nanovllm/engine/model_runner.py` `run_model()`、`capture_*_cudagraph()` |

## 3.2 业界做的是什么（一句话）

**行业主流（vLLM V1）是"猪背"**：**同一个批里既有 decode tokens 也有 prefill chunk tokens，
一次前向跑完**，decode 与 prefill 共享一个 GPU kernel launch；
V1 用 **piecewise CUDA graph** 让混合批"部分吃到图"（attention 留在图外）。

**我们做的是"让路"**：**块与块之间让出一整轮给 decode**，一轮内不混任何两种执行路径。
（★ 有意思的对照：**SGLang 的 `--prefill-decode-interval` 是同一个思想的参数化版本**
—— "prefill 批之后先跑 N 轮 decode"，默认 0 = 关。见 §2.2 (5)。）

## 3.3 差异表：我们少拿到什么、省下什么

| 维度 | 猪背（vLLM V1 默认） | 让路（我们） | 我们少拿到 / 省下 |
|---|---|---|---|
| **decode 的推进** | 混合批里 **decode 每轮都能拿到 token** | 让路那一轮 decode 拿 token，**分块轮 decode 拿 0 个** | ★ **少拿到**：一条长 prefill 期间，decode 的 ITL 会出现"周期性的 0 推进格"。等价于"最大 ITL ≈ 一个 chunk 的墙钟 + 一个 decode 轮" |
| **尖刺能否压平** | 混合批下 ITL 尖刺 ≈ 混合轮墙钟（δ 很小） | 尖刺 = 一个 chunk 轮 + 一个 decode 轮 | ★ **少拿到**一个 decode 轮的绝对量（这是硬上界，见 `P12 §2`） |
| **CUDA Graph** | 混合批走 **piecewise**（attention 图外）；纯 decode 仍走 **FULL** | decode 批走 **FULL/精确 B 图**（形状不变）；分块轮是纯 prefill，**恒 eager** | ★ **省下**：混合批的形状逐轮不同、图退化的代价我们不用付。**我们每一条 decode 轮都是纯 decode，形状精确，图命中率不掉** |
| **实现复杂度 / 雷区** | 需要维护"两个子批的 KV 槽位/预算、`prepare_mixed`、后处理交付语义、图捕获重做" | 一轮只有一条路径 ⇒ 不需要这些 | ★ **省下**：`P12 §2.4` 列的 4 项代价（尤其"一轮内混两条执行路径"，本项目被同类 bug 坑过多次） |
| **KV / 预算的确定性** | 混合批形状不固定，KV 预算与后处理形状要按"混合"分叉 | 每轮形状确定（要么 prefill 要么 decode） | ★ **省下**：形状分支与归因难度 |
| **公平性（多个长 prompt）** | 见 §2.6：**默认也会让后面的等**（预算独占）；有 `--long-prefill-token-threshold` 可调 | 我们的让路逻辑**只解决"长 prefill 不堵 decode"**，**不解决"长 prefill 之间的公平"** | ★ **两家都没做**默认公平调度；这不是我们的短板，是行业共性 |
| **chunk 语义** | 「本步剩余预算」决定，**没有独立 chunk 参数**；`max_num_batched_tokens` 就是旋钮 | 独立参数 `spec_prefill_chunk_tokens`，且**有"无人可让路就不分块"的门控** | 我们多一个**显式旋钮 + 门控**（业界是隐含的） |

## 3.4 一句话概括我们的定位

> **我们和 vLLM V1 是同一个问题的两种解法**：vLLM 用"**同一批内并行**"（猪背 + piecewise 图），
> 我们用"**批与批之间串行**"（让路 + 保住精确形状的 FULL 图）。
> 我们**放弃了"decode 每一轮都推进"**（少拿到一个 decode 轮的尾部改善），
> **换来了"每轮形状确定、decode 图不被污染、一轮内不混路径"**（省下混合批的图退化与复杂度风险）。
> **SGLang 用 `--prefill-decode-interval` 提供了和我们同形状的旋钮，但默认关闭** ——
> 这说明"让路"是一个**业界认可但默认不启用**的设计点。

# 4. ★ 面试话术底稿（3–6 句，可直接背）

### 4.1 「你们的调度和 vLLM 有什么区别？」

> **标准版（约 6 句，背这段）**：

1. "我们和 vLLM 处理的是同一个问题——**一条长 prompt 的 prefill 会把正在解码的请求饿死**，
   国内的说法就是"长 prompt 阻塞 decode"；vLLM 的解法是 **chunked prefill**，
   把长 prefill 切成块，**把 decode token 和 prefill 块塞进同一个批里一次前向**，
   这个思路来自 **SARATHI（arXiv 2308.16369）**，术语叫 decode-maximal batching，也就是"猪背"。"
2. "我们在自己的引擎上做的是**另一种取舍：让路**——一条长 prompt 被切成块，
   **块与块之间让出一整轮给 decode**，所以一轮之内只有一条执行路径，
   要么全是 prefill、要么全是 decode，**从不混批**。"
3. "这么做的**代价**是：分块那一轮里 decode 请求拿到 0 个 token，
   所以 ITL 尖刺仍然是"一个 chunk 的墙钟 + 一个 decode 轮"，
   **比真混合多出一个 decode 轮的绝对量**——这是硬上界，我们量过（见 `docs/优化报告.md §c.3`），
   **结论是这笔收益不够大，所以主动不做**。"
4. "**换来的**是三件事：第一，**decode 那一轮的形状是精确的纯 decode 批**
   （batch size 只有 1/2/4 三种），**CUDA graph 的命中率不掉**；
   第二，不需要维护两个子批的 KV 槽位和后处理语义；第三，**
   我们项目里"一轮内混两条执行路径"已经被证明是失效高发区**，不让它进核心路径。"
5. "一个有意思的对照是：**SGLang 有一个 `--prefill-decode-interval` 参数，
   语义就是"prefill 批之后先跑 N 轮 decode"，和我们同形状，但它默认是 0、也就是关的**；
   **vLLM V1 的混合批走的是 piecewise CUDA graph，attention 被留在图外**。
   所以三家的差异本质上是在'图能不能保住'和'decode 每一轮推进不推进'之间选。"
6. "总结成一句：**vLLM 是"同一批内并行"，我们是"批与批之间串行"；
   我们放弃了一部分尾部改善，换确定性和图的完整性。**"

### 4.2 「为什么不用 CUDA graph 跑 prefill？」

> **4 句版**：

1. "**prefill 的批形状是不确定的**：一个 chunk 的 token 数是 `min(该请求剩余, 本步 token 预算)`，
   随每个请求、每一轮在变；CUDA graph 是按**静态形状**捕获并 replay 的，
   想把 prefill 放进去就得为很多形状各捕一张图，**图的数量和显存代价都不划算**。"
2. "**业界也是这么分的**：vLLM V1 的默认模式是 `FULL_AND_PIECEWISE`——
   **纯 decode 批用 FULL 图，prefill 与混合批用 piecewise 图，而 piecewise 恰恰是把 attention 这类
   图不兼容算子放到图外**；更早的 vLLM V0 源码里直接写着
   **"cuda graph is disabled for chunked prefill"**。"
3. "我们的引擎里 prefill 是**恒 eager** 的（`model_runner.run_model()` 里 `is_prefill` 直接走 eager），
   **而 decode 那一轮的 batch size 被限制在 1/2/4 三种精确形状**，所以 decode 的图命中率是稳的。"
4. "**一句话**：**prefill 是 compute-bound、且形状不固定，图收益小、捕获代价大；
   decode 是 memory-bound、形状固定，图收益大**——所以图留给 decode。"

### 4.3 「多个长 prompt 同时到达会怎样？」（见 §2.6，备用）

> **3 句版**：

1. "**默认配置下会互相堵**：vLLM V1 里，一条超长 prompt 每步会把 `max_num_batched_tokens`
   的预算吃满、`token_budget` 归零，**waiting 队列这一步一条都进不来**，
   而它自己一直在 `running` 里优先推进，所以要等它拼完——**这是从源码里读出来的，不是推测**；
   **而且有官方 issue #57413 的生产数据背书**：GLM MoE + 4×B200，prompt 中位数 10 万~18 万 token，
   TTFT p95 冲到 **76 秒**，而 KV 占用不到 40%、抢占次数为 0 —— 瓶颈就在 prefill 的准入调度。
   SGLang 也一样按 FCFS 排。"
2. "**vLLM 的公平性旋钮是 `--long-prefill-token-threshold`（默认 0 = 关）**，
   官方文档的原话是这个 cap"**防止一条长 prefill starve 其他请求**"，
   还有个 adaptive 版本把阈值**垫到"预算 ÷ 在场请求数"的公平份额**。"
3. "★ 这个'只推进一条'的印象其实**对两家有两套完全不同的机制**：
   **vLLM V0** 靠显式配置 `max_num_partial_prefills`（默认 1）—— 但**当前 V1 引擎已经没有它了**，
   它在 V1 里被标为不支持，**v0.27.0 已删除**，删除 PR 的原话是 'dead config … they have no consumer'；
   **SGLang** 则根本没有这个配置项，靠的是**代码结构上只有一个 `chunked_req` 槽**，
   源码注释原话 'Only one unfinished chunked request can be tracked.'。
   而且**整个 V0 引擎在 v0.11.0（2025-10）就被删干净了**（release notes 原话 "V1 is the only engine
   in the codebase now"），所以这个参数连"挂在 V0 上还能用"都不成立了 ——
   issue #57413 里有人实测 `--max-num-partial-prefills 4`，直接报 `vllm: error: unrecognized arguments`。
   所以**"默认只推进一条 partial prefill"这个说法，对 V0 和 SGLang 都对，唯独对当前 vLLM 不成立**。"
