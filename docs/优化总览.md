## 0. 一句话

在 nano-vllm（1385 行教学版 vLLM 复现）上做了三件事：
**把 per-step 固定开销压掉**、**用投机解码换算法**、**手写 paged attention 算子**。
过程中查出 **5 个真 bug**（2 个破坏无损性、1 个会让 CUDA 崩、1 个会无限生成）。

**测试条件**：RTX 3090、Qwen3-4B + Qwen3-0.6B、单条 256 token、
temperature=1.0、`enforce_eager=False`（除非特别说明）。

## 2. 优化一：per-step 固定开销治理（这是符号翻正的关键）

### 2.1 问题

上一轮的结论是「投机解码净亏损，因为 draft 多读了 2.2GB 权重」。**这个模型解释不了实测。**

```
4B 模型 fp16 权重 8 GB，3090 带宽 936 GB/s  →  读一遍只要 8.5 ms
实测每步 decode 却要 33.2 ms
```

多出来的 24 ms 跟权重一个字节的关系都没有。

### 2.2 定位（同一模型、同一次前向、只差一个开关）

| 配置 | 每步耗时 | tok/s | 折合带宽 |
|---|---:|---:|---:|
| `enforce_eager=True` | 33.2 ms | 30.6 | 26% |
| 开 CUDA Graph | **12.8 ms** | **79.6** | **66%** |

**差 2.6 倍，全是 kernel launch + Python dispatch。**

draft 侧更极端：0.6B 权重只有 1.2 GB（理论 1.3 ms 读完），
eager 下实测一次前向 **24.8 ms**（19 倍）。而 draft 要**串行跑 k 次**，这笔开销要乘以 k。

### 2.3 做法

给投机路径的两条前向**各拍一张静态形状的 CUDA graph**：

| 图 | 形状 | 收益 |
|---|---|---|
| draft 前向 | bs=1、每次 1 token | 24.8 ms → ~2 ms |
| 验证前向 | bs=1、query 恒 1+ k、varlen | 36 ms → ~14 ms |

验证前向走 varlen，`run_model` 里 `is_prefill=True` 会强制走 eager 分支，
**但它的形状是固定的**，所以照样能拍图。形状不匹配时自动退回 eager。
开关：`config.spec_cuda_graph`。

### 2.4 ★ 同一个规律在两层都出现

```
引擎层：eager 33.2ms/步 → CUDA graph 12.8ms/步     （固定开销吃掉 2.6×）
kernel 层：墙钟 76µs    → 纯 kernel 31.4µs          （启动开销吃掉 2.4×）
```

**「小尺寸下固定开销支配一切」** —— 同一个原理，两次都是 CUDA Graph 解决的。

## 3. 优化二：投机解码（线性链 + draft model）

### 3.1 结果

| 配置 | tok/s | 每步 token | 接受率 | 相对 baseline |
|---|---:|---:|---:|---:|
| baseline（开图） | 82.3 | 1.00 | — | 1.00× |
| draft k=2 | 116.9 | 2.15 | 0.65 | **1.42×** |
| draft k=6 | **132.5** | 3.82 | 0.77 | **1.61×** |
| *draft k=6（eager）* | *20.8* | *3.77* | *0.79* | ***0.68×*** |

**对照行才是重点**：每步产出几乎没变（3.77 → 3.82），**变的只有 per-step 固定开销**。
所以「把符号翻正的是 CUDA Graph，不是接受率，也不是算法」。

### 3.2 查出的 5 个 bug（都是「不报错、只是结果悄悄错」）

| | 问题 | 后果 | 证据 |
|---|---|---|---|
| **A** | draft 侧传概率，验证时又 softmax 一次 → q 被压成近似均匀分布（151936 词表上 max 只剩 1.2e-5） | **无损性破裂**：草稿 token 采自真分布 q、验证却用 q̃ | 构造 q≡p：传 logits 接受率 **1.0000** / TV 0.0032；传概率 **0.8895** / TV 0.1075（有偏，不随 N 收敛） |
| **B** | 候选对齐错位一位。验证送进去的 k+1 个 token 在位置 `len-1..len+k-1`，模型第 r 行是位置 `len+r` 的分布，所以候选 j 应对齐**第 j 行** | 接受率从应有的 **0.84 掉到 0.16** | 合成算例（target 各行峰不同、草稿逐行等于目标）：修复前 accepted=0、bonus 落在第 1 行的峰；修复后 accepted=3 |
| **C** | 全接受时把**已经算好的 bonus** 丢掉（那一行的分布本轮 forward 已经算出来了，且 scheduler 预留的槽位本来就是 1+k） | 每步只出 1 个 token，**必然比 baseline 慢** | k=1 修复前 `tok/step=1.0`（恒定）、修复后 1.561 |
| **D** | 终止判据用 `==` 而非 `>=`。一步落地多个 token 时完成数会**跳过** max_tokens（62→65） | **无限生成**（实测 300 步 / 572 token 不停） | `tests/test_scheduler_terminate.py` |
| **E** | 跨 block 少分配一块。所有写入路径写的是 `len-1..len+n-2`，公式按 `len..len+n-1` 算空位 | **CUDA 非法访存**（block_table 那一位是 -1，flash-attn 读第 -1 页） | `tests/test_block_alloc.py` |

> ⚠️ **D 和 E 都是「短测试测不出来」的典型**：D 要一步落地多个 token 才暴露，
> E 要序列长过 256 才暴露（64 token 的测试永远碰不到边界）。

### 3.3 draft 固有质量（独立于引擎的测量）

接受率有恒等式 **α = E[min(1,p/q)] = 1 − TV(p,q)**。
用 transformers 原生跑两个模型（绕开引擎，排除引擎算错上下文）：

| 指标 | 实测 |
|---|---:|
| 平均 TV 距离（0.6B vs 4B，60 个位置） | **0.1655** |
| argmax 一致率 | 86.7% |
| 理论接受率 α = 1 − TV | **0.8345** |

→ Qwen3-0.6B 给 4B 当 draft 是很好的组合，接受率上界 0.83。

## 4. 优化三：手写 paged decode attention

### 4.1 为什么做它

**上游原版**的 nano-vllm 里，「融合算子」全是 `torch.compile`，
手写 Triton kernel **只有 1 个**（`layers/attention.py` 的 `store_kvcache`），
attention 全靠 flash-attn。而「你写过什么算子、瓶颈是什么、效率如何」是高频门槛题。

> 核实过：本文档写作时，`grep -rn '@triton.jit' nanovllm/` 得到 5 处 ——
> 其中 1 处是上游的 `store_kvcache`，另外 4 处是本项目新增的
> （`kernels/paged_decode_attn.py` 的 v1 / v2 / v3-partial / v3-combine）。

### 4.2 Roofline 先定性

```
ctx=1024：KV 要搬 4.19 MB，要算 16.78 MFLOP  →  算术密度 4.0 FLOP/Byte
3090 的 roofline 拐点 ≈ 38 FLOP/Byte
```

**算术密度只有拐点的 1/10 → 铁定的访存瓶颈。**
所以优化只有两条路：**少搬字节**、**把带宽用满**。

⚠️ 参照系要用**实测天花板**：纯 copy 流式实测 **842 GB/s**（规格是 936）。

### 4.3 三步递进（每步的动因都来自上一步的数据）

| 版本 | 纯 kernel 时间 | 搬的字节 | 带宽 | 占 842 天花板 |
|---|---:|---:|---:|---:|
| v1 每 (序列,q头) 一个 program | 192 µs | 67.1 MB（**4× 冗余**） | 348 GB/s | 41% |
| v2 按 kv头 分组，4 个 q头 共用 K/V | 112 µs | 16.8 MB | 149 GB/s | **17.7%** |
| **v3 split-K** | **31.4 µs** | 16.8 MB | **523.8 GB/s** | **62.2%** |
| *（参照）flash-attn* | *41.2 µs* | *16.8 MB* | *410 GB/s* | *48.7%* |

**两次优化打的是两个不同的瓶颈**：
- **v1→v2 少搬字节**：v1 和 flash-attn 的实测带宽几乎一样（348 vs 410），却慢 4.6 倍
  → 说明 v1 不是带宽用不满，是**搬了 4 倍**（GQA 4:1，同一份 K/V 读 4 遍）
- **v2→v3 把带宽用满**：v2 搬得少了 4 倍却只快 1.7 倍，因为带宽掉到 **17.7%** ——
  它只启动 8 个 program，而 3090 有 82 个 SM。切开 context 后带宽回到 62.2%

### 4.4 CUDA 版（Ampere 深度）

用 `mma.sync` + `ldmatrix` + `cp.async` 三级流水 + swizzle 重写：

| | 纯 kernel | 带宽 | 占天花板 |
|---|---:|---:|---:|
| Triton v3 | 30.66 µs | 523.8 GB/s | 62.2% |
| **CUDA 版（融合归约）** | **28.01 µs** | — | — |
| └ 主 kernel 单独 | **25.87 µs** | **648 GB/s** | **77%** |
| 同访存路径的纯读取（把算全删掉） | 23.08 µs | 727 GB/s | 86.4% |
| 完全连续访存的纯读取 | ~20.9 µs | 801 GB/s | 95.2% |

**阶梯表（ctx=4096）**：

```
不用 cp.async → 双缓冲 → 三级流水     36.91 → 27.63 → 25.87 us   (1.43×)
combine 另起 kernel → threadfence 融合  28.27 → 28.03 us         (1.009×，几乎白干)
```

**`cp.async` 三级流水一步就值 1.43×** —— 而这个在 Triton 里改 `num_stages` 毫无反应，
因为编译器没把控制权给你。

### 4.5 ★ 两个被数据证伪的假设（我提的）

| 假设 | 怎么验 | 结果 |
|---|---|---|
| **`tl.dot` 要求 M≥16，GQA 比只有 4，75% 的 MMA 行白算** | ①只读探针（照搬访存路径，删掉 mma+softmax）：23.08 µs = **86.4% 天花板**，即**整个张量核+softmax+同步只值 2.79 µs（10.8%）**<br>②真写了 FFMA M=4 版（零 padding） | ❌ **反而慢 1.84 倍**（47.73 vs 25.87）。<br>原因：张量核的价值不在算力，在**免费做掉 head_dim 归约**；FFMA 要 5 步 butterfly、每 (位置,q头) 20 条 shuffle |
| **KV 访存模式太碎**（每位置读 256B、跳 1792B） | 64 个 program，两组各读满 33.6 MB：切片读 vs 连续读 | ❌ **只差 1.15×**（696 vs 801 GB/s）。DRAM 处理跨步读其实很好 |

### 4.6 占用率：8%，但带宽 77%

```
配置：splits=8 / block_n=64 / warps=4 / stages=3
动态 shared memory ≈ 98 KB/block（sm_86 上限 ~100 KB）
→ 每个 SM 只能塞 1 个 block → 4 个 warp，而 SM 支持 48 个 → 占用率 8.3%
```

**占用率 8% 却跑出 77% 带宽** —— 因为 `cp.async` 把「发访存请求」和「warp 数量」
解耦了：3 级流水让每个 CTA 随时有约 2 块 tile 在途（≈64KB 未完成请求），
**在途请求量（MLP）足够就够了，不需要靠堆 warp 来隐藏延迟**。
这也解释了为什么 Triton 里改 `num_warps` 完全没反应。

## 5. 无损性验证（三档，强度不同）

```bash
python tests/test_spec_decode.py              # 18 项，纯 CPU —— 主证据
python tests/test_scheduler_terminate.py      #  8 项，纯 CPU（bug D 回归）
python tests/test_block_alloc.py              # 11 项，纯 CPU（bug E 回归）
python scripts/check_draft_quality.py         # draft 固有质量
python scripts/check_lossless_engine.py       # 引擎级分布对比
```

**① 单元测试级（强证据 —— 主要靠这个）**
- `verify.py` 的无偏性：TV 随样本量收敛（N=40k → 400k，比值 2.91 vs 理论 3.16）
- 合成算例：`q ≡ p` 时必须全部接受（实测 **1.0000**）；候选 j 必须对齐第 j 行
- **和引擎、GPU、CUDA Graph 都无关**

**② draft 固有质量（独立于引擎）**：TV = 0.1655 → α 上界 0.8345

**③ 引擎级分布对比（中等强度）**

| | TV |
|---|---:|
| `TV(base, base2)` 基线噪声地板 | 0.5315 |
| `TV(draft, draft2)` 投机自己的地板 | **0.6325** |
| 跨组 base × draft 四个值 | 0.514 / 0.521 / 0.671 / 0.713 |

**跨组差异完全夹在两个噪声地板之间 → 没有发现系统性偏差。**

★ **必须给投机路径单独测一个地板**，不能只跟基线比：投机一步产出 3~4 个 token
（同一次前向、同一个上下文），序列自相关远强于逐 token 解码 → 有效样本量更小、
经验分布天然更散 —— 实测 `TV(draft,draft2)=0.63 > TV(base,base2)=0.53` 正好印证。
**拿 0.71 直接跟 0.53 比会得出「超出 34%、可能有偏」的错误结论。**

## 6. 方法论：三次被数据纠正

这部分比数字值钱 —— 面试问「你怎么定位问题」时讲这个。

### 6.1 墙钟 ≠ kernel 时间（差点得出完全相反的结论）

用「50 次连发 + CUDA 事件包住整段」测出 v3 = 76 µs、只到天花板 29%，
于是开始逐个排查 —— **四个假设全被证伪**（并行度、流水线、warp 数、访存布局）。

**「改什么都不动」本身就是最强的信号 —— 说明被测的根本不是 kernel。**

真相：v3 要启动**两个**内核，Triton 每次启动的 Python 开销 ~20 µs，
两次合计 **45.9 µs**，把 31.4 µs 的 kernel 整个盖住了。
用 `torch.profiler` 读 `self_device_time_total` 才发现。

### 6.2 差点被自己骗过去的数据

布局实验第一次跑出「两种布局一样快」，但**输出差异是 0.323608（应该 ~0）** ——
自检抓到是我在 v3 分支里把 stride 写死了，没用到按 layout 算出来的值。
**没有这个对拍，我就会得出「布局无关」这个完全错误的结论。**

同一类问题还有探针：第一版 `kvh` 写死成 0、第二版 8 个 program 全在扫全部位置
（8 倍冗余读），**两次都是「两组读的字节数其实不一样」**。

### 6.3 判据的精度不该超过被测量的分辨率

正确性判据一度写成「对 fp32 参照相对误差 < 5e-3」，结果 v2/v3 在 ctx=7 判 FAIL。
查下来**不是 kernel 错**：v2/v3 走 `tl.dot`（bf16 tensor core），
bf16 的天然精度下限就在 1e-2 绝对误差量级。

改成两个参照后反而更清楚：对 fp32 用 bf16 合理口径，**和 flash-attn 同口径对拍**
（同为 bf16，吻合到 2e-3 以内）。

## 7. 已知边界 / 没做的

**所有数字都限定在**：batch=1、单序列、ctx ≤ 4096、Qwen3-4B 配置、RTX 3090。

| 没做 / 没验证 | 说明 |
|---|---|
| **batch > 1** | 投机解码、attention kernel 全都没测并发。真实推理永远是 batch>1 |
| **ctx > 4096** | `config.py` 把 `max_model_len` 卡在 4096；Qwen3-4B 本身支持 40960 |
| **端到端数字** | **全部是 microbenchmark**，没有「引擎快了 X%」这种数 |
| **显存维度** | 没有峰值显存、并发上限、缓存命中率任何数据 |
| warp specialization | CUDA 版试过，能跑通但结果不对（ctx=1 复现、错位随机 → 竞态），修 4 轮停手；只读探针已证明其上限仅 ~2.8 µs |
| TMA / TMEM / 2-SM cluster | **sm_86 硬件不支持**（需要 Hopper/Blackwell） |
| ncu 硬件计数器 | **机器上被禁**（`RmProfilingAdminOnly: 1`，无 sudo）。roofline 的字节数是理论推算+时间反推，**不是硬件读数** |
| 真实模型权重 | attention kernel 只用随机数据测过 |
