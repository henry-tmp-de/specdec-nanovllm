## 1. 出发点

任务书给了两笔"已经量到/疑似"的账：

- **账①**：`model_runner.py` 里 `if self.draft_model is not None: self._run_draft_prefill(...)`
  **不看 `spec_k`** —— 只要进程加载了 draft，每次 prefill 都白跑一遍 0.6B。
  同进程探针（`docs/端到端验收.md` §6）实测 ctx=4096/B=1：**77.8 → 45.7 ms**。
  可疑点：0.6B 只有 4B 的 1/7 大，却吃掉 target prefill 的 **70%** 时间。
- **账②**：`scheduler.schedule()` 里 prefill 是**排他**的（`if scheduled_seqs: return ... True`）
  ⇒ 长 prompt 到场时，正在解码的请求**这一轮一个 token 都拿不到**。

任务书明确要求：**先测上界，一步都不许跳**，再按上界排序决定先做哪个。

## 2. 上界测量

### 2.0 探针设计（同进程多条件 + 真冷）

三张探针都沿用项目验证过的「**同进程多条件**」手法（把跨进程对比的噪声变成闭合归因）：

| 探针 | 条件 | 说明 |
|---|---|---|
| `p13_prefill_probe.py` | `with_draft` / `no_draft` / `window0` | 同一进程内翻转；**冷、热分开测** |
| `p13_itl_probe.py` | 3 条请求稳态解码 + 突来一条长 prompt | 量"解码请求那一轮"的 ITL 尖刺 |
| `p13_chunk_probe.py` | 逐轮打点 | 每轮的 (是否 prefill, 进了几个 token, 墙钟) |

**★「冷」必须是真的冷**：`docs/端到端验收.md` §6 的 77.8→45.7 ms 是**热前缀缓存**下测的
（同一批 prompt 反复跑 ⇒ 只剩未命中的尾巴 ≈ 1 个块）。本轮的冷档把
`BlockManager.hash_blocks` 打成 no-op **并把已有的哈希表清空** ⇒ 每个 prompt 都是完整 prefill。
（只打 no-op 不够：`_deallocate_block` 不删 `hash_to_block_id` 里的旧条目，上一个条件的热档
留下的缓存会被下一个条件的"冷"档命中 —— 这个坑本轮踩了两次，见 §2.5。）

### 2.1 账① 上界表（ctx 1K/4K/8K/16K）

**冷启动（真冷，完整 prompt）**，单位 ms：

| ctx | with_draft | no_draft | **draft prefill 代价** | 占比 |
|---|---:|---:|---:|---:|
| 1024 | 162.5 | 129.4 | **+33.1** | +25.6% |
| 4096 | 641.5 | 533.0 | **+108.5** | +20.4% |
| 8192 | 1464.7 | 1200.3 | **+264.4** | +22.0% |
| 16384 | 3761.1 | 3021.8 | **+739.2** | +24.5% |

**热缓存（只补未命中的尾巴 ≈ 1 个块 = 256 token）**：

| ctx | with_draft | no_draft | **draft prefill 代价** | 占比 |
|---|---:|---:|---:|---:|
| 1024 | 74.3 | 42.3 | **+31.9** | +75.4% |
| 4096 | 76.5 | 45.0 | **+31.5** | +70.0% |
| 8192 | 88.5 | 57.0 | **+31.5** | +55.2% |
| 16384 | 112.4 | 81.2 | **+31.2** | +38.4% |

**它到底在算什么（输入 token 数，探针直接打出来）**：

| 条件 | target prefill tokens | draft prefill tokens |
|---|---|---|
| 冷（full-context 路径） | ctx | **ctx（与 target 完全相同）** |
| 热（full-context 路径） | 256（尾巴） | **256（与 target 完全相同）** |
| 滑窗路径（W=4608） | 冷=ctx / 热=256 | **min(ctx, 4608)，冷热都是** |

⇒ **默认（full-context）路径下，draft 跑的就是 target 跑的那批 token，它没有"多干活"。**
⇒ **滑窗路径才是"多干活"的那条**：热态下 target 只跑 256，draft 却每次都把整个窗口
（4608）重算一遍 —— 因为 `_run_draft_prefill_window` 按 `token_ids` 重建窗口，
**不认前缀缓存**（复现了 `docs/端到端验收.md` §6 的结论）。

滑窗档热态实测：`with_draft` 76.6 / 156.8 / 186.6 / 212.4 ms vs `no_draft`
42.6 / 45.1 / 57.2 / 81.5 ms（1K/4K/8K/16K）⇒ **draft 一笔就要 +91 ~ +131 ms**，
**是 target 自己 prefill 的 2.0~3.5 倍**。

### 2.2 账② 上界表（3 条解码 + 突来一条长 prompt）

| ctx | 稳态解码轮 | 尖刺轮（无 draft） | **倍数** | 尖刺轮（有 draft） | **倍数** | 尖刺轮解码请求拿到几个 token |
|---|---:|---:|---:|---:|---:|---:|
| 1024 | 12.0 ms | 128.3 | **10.7×** | 159.9 | **13.3×** | **0** |
| 4096 | 12.1 ms | 532.4 | **44.2×** | 642.0 | **53.3×** | **0** |
| 8192 | 12.1 ms | 1199.7 | **99.4×** | 1467.2 | **120.8×** | **0** |
| 16384 | 12.1 ms | 2984.0 | **247.1×** | 3743.5 | **310.4×** | **0** |

两条结论：
- **尖刺倍数 10.7×~310×，远在方案 §6.3「只有 2–3 倍就收手」的停止线之上** ⇒ 混合调度**值得做**。
- **那一轮解码请求拿到的 token 数精确为 0** ⇒ 不是"变慢"，是**被完全饿死**（排他 prefill 的直接后果）。
- 尖刺高度 ≈ 那一次 **prefill 的墙钟**（与 §2.1 的冷档逐行吻合，误差 <10%，差的部分是
  3 条解码请求同时在跑）⇒ **改① 会把这个尖刺整体压低**（实测见 §5.4）。

### 2.3 ★ 归因：0.6B 凭什么吃掉 target 70% 的时间？

任务书的疑点是"0.6B 只有 1/7 大，却吃掉 70%"。数据给的答案**分两种状态，不是同一个数**：

- **热态**：target 只 prefill 尾巴（256 token，42~81 ms），而 draft 那一趟是**恒定的 ~31.5 ms**
  （**与 ctx 无关**）⇒ 在 1K/4K 上就显示成 **70%~75%**。
  ★ 这 31.5 ms 里几乎没有算力：0.6B 跑 256 token 只有 0.307 TFLOP，31.5 ms ⇒ **仅 9.8 TFLOPS**
  （峰值 71 的 **14%**），是**固定开销（kernel launch / 小 M 下的调度）支配**，不是计算。
- **冷态**：draft 与 target 跑同样多的 token，代价 **+20%~26%**。
  按"参数量 1/7"该是 ~15%，实测偏大，原因是**两模型的有效算力不同**：
  draft 约 26~45 TFLOPS，target 约 43~63 TFLOPS（长 ctx 下两者都掉），**draft 只做到 target 的 ~60%~73%**。

⇒ **所以"70%"是一个热态假象**：绝对代价只有 ~31.5 ms，是分母（target 尾巴 45 ms）太小把它放大成 70%。
**修法也因此不同**：热态那 31.5 ms 是固定开销（该问"能不能不做"），冷态那 20% 是真实算力（该问"能不能更省"）。
任务书里"它可能在做比 target 更多的活"这个猜测，**在默认路径上被否**（token 数完全相同），
**只在滑窗路径上成立**（每次重算整个窗口）。

### 2.4 账① 与账② 的连锁（任务书的担心，实测结论）

任务书担心"分块 prefill 会让 draft prefill 跑 N 遍"。实测：
- **full-context 路径不会**：`_run_draft_prefill` 复用的是 target 那一块的 `input_ids`，
  每块算一次，**总量与不分块相同**（§5.5 逐轮打点：2 块 × ~350 ms = 698 ms ≈ 不分块 648 ms）。
- **滑窗路径会**：它按 `token_ids` 重算整个窗口 ⇒ 每块都重算一遍 = N 倍。
  ⇒ 本轮**顺手加了守卫**：滑窗路径只在"这条序列本步把 prompt 拼完了"时才跑（§4.2）。

### 2.5 ★ 探针自身的三个 bug（都改了，写下来是因为它们是"静默错误"）

1. **冷档被热档污染**：第一版冷档只把 `hash_blocks` 打成 no-op，但**没清
   `hash_to_block_id`** —— 上一个条件的热档刚缓存过同一个 prompt，下一个条件的"冷"档就命中了它。
   症状：`no_draft` 的 `cold` 与 `warm` **逐行相等**（42.61 / 42.61）。
2. **不同 ctx 的 prompt 互为前缀**：第一版每个 ctx 都从 offset 0 起切 ⇒ 长 ctx 的 prompt
   天然命中短 ctx 已缓存的块。症状：ctx=8192 的 `with_draft` **比 no_draft 还快**（不可能）。
   改成"每个 ctx 一个互不重叠的固定起点"。
3. **第一个分块形状要付一次 torch.compile 编译钱**：分块档里**第一个块** 2055 ms、
   同一尺寸的**第二个块** 376 ms（§5.5 隔离实验：只与 `max_num_batched_tokens` 有关）。
   症状：分块档的尖刺看起来"变大 3 倍"。改法：预热必须用**最大 ctx**（用 1024 预热盖不住分块形状）。

★ 教训：**"冷/热"这种词不写清怎么保真，等于没有口径**；三次都是同一个模式 ——
**我以为在测 A，其实测的是"上一次运行的缓存"**。

## 3. 方向决策（哪个数字让我改的方向）

| 候选 | 上界（实测） | 风险 | 决策 |
|---|---|---|---|
| **① draft prefill（全上下文路径）** | 冷 +20~26%；热 +31.5 ms | 低（纯跳过） | **做**（只在"确定不投机"时） |
| **① draft prefill（滑窗路径热态）** | +91~131 ms，是 target prefill 的 2.0~3.5× | 中（**与滑窗模块耦合**） | **只做"别重复算"的守卫**，不重做缓存 |
| **② 长 prompt 堵 decode** | 尖刺 **10.7×~310×**，解码拿 0 token | 中（调度改动） | **做**（尖刺远超停止线） |

**停止条件判定**：方案 §6.3 说"尖刺只有 2–3 倍就收手"。实测 **10.7×~310×**，
**不触发停止条件** ⇒ ② 立项。这也是本项目 P1（attention）当年被否的反面：那次是上界不够（+3%），这次是上界很大。

**顺序**：任务书要求"先修①，因为分块会让 draft prefill 跑 N 遍"。
实测把这条**收窄**成"只有滑窗路径会跑 N 遍"（§2.4），所以在 ② 里加了滑窗守卫，而不是先做完整的①。

## 4. 改动（都默认关闭、老路径一行没删、可运行期翻转）

### 4.1 门控确定关着时，跳过 draft prefill

- `nanovllm/config.py`：新增 `spec_skip_draft_prefill_when_off: bool = False`。
- `nanovllm/engine/model_runner.py`：
  - 新增 `_draft_prefill_needed()`：默认（开关关）**恒 True**；打开后 `spec_k <= 0` 时返回 False。
  - `run()` 的 prefill 分支：`if self._draft_prefill_needed() and self._run_draft_prefill(...)`。
- **边界（诚实）**：只覆盖"**确定**不投机"的情形（`spec_k <= 0`）。
  `spec_batch_threshold` 那种按**解码批大小**判的门控，在 prefill 时刻还不知道未来解码批，
  **不猜**，仍然照跑。

### 4.2 分块 prefill + 在块之间让一轮给 decode

- `nanovllm/config.py`：新增 `spec_prefill_chunk_tokens: int = 0`（0 = 老行为）。
- `nanovllm/engine/scheduler.py` `schedule()`：
  - `budget = min(remaining, chunk)`；`seq.num_scheduled_tokens = min(num_tokens, budget)`，
    本步拼不完就置 `_prefill_chunk_pending`。
  - **★ 下一轮让路**：`yield_to_decode = chunk > 0 and _prefill_chunk_pending and bool(self.running)`
    ⇒ 这一轮**整轮跑 decode**，再下一轮继续 prefill。
  - ★ **一轮内仍然只有一种执行路径**（要么全是 prefill、要么全是 decode），
    **不混路径** —— 这个项目被"一轮内混路径"坑过 3 次（最典型：`spec_enabled` 门控快照 bug）。
  - `getattr` 兜底：部分 CPU 单测用 `Scheduler.__new__` 绕开 `__init__`（`tests/test_spec_gate.py`），
    不带这两个新字段。
- `nanovllm/engine/model_runner.py` `_run_draft_prefill()`：
  - **滑窗路径只在"全部序列本步都拼完"时才跑**（拦住 §2.4 的 N 倍重复计算）；
    全部拼完时走的是**原分支**，行为不变。

### 5.3 改动① 效果：draft prefill 代价被清零

同进程 ITL 探针，`SKIP_OFF=1`（打开跳过开关）+ `spec_k=0`：

| ctx | with_draft 尖刺 | no_draft 尖刺 | 差 |
|---|---:|---:|---:|
| 1024 | 128.5 | 128.7 | −0.2 ms |
| 4096 | 533.2 | 534.0 | −0.7 ms |
| 8192 | 1201.0 | 1201.3 | −0.3 ms |
| 16384 | 2996.0 | 3001.2 | −5.2 ms |

⇒ **四个 ctx 全部逐行相等（差 <0.2%）**：draft prefill 那笔开销被**完全去掉**。
对照基线（开关关）：159.9 / 642.0 / 1467.2 / 3743.5 ms ⇒ **省 31.4 / 108.8 / 266.2 / 747.5 ms（−17%~−20%）**。

### 5.4 改动② 效果（分块让路）：尖刺 **−44% ~ −81%**

`spec_prefill_chunk_tokens` 对同一场景（3 条解码 + 突来一条长 prompt）的影响：

**尖刺墙钟（ms）**

| ctx | 基线（不分块） | CHUNK=2048 | CHUNK=1024 | CHUNK=512 |
|---|---:|---:|---:|---:|
| 1024 | 159.9 | 161.1（未分块） | 160.1（未分块） | **99.2** |
| 4096 | 642.0 | 361.0 | 200.5 | **117.0** |
| 8192 | 1467.2 | 471.1 | 260.5 | **139.5** |
| 16384 | 3743.5 | 695.0 | 381.6 | **203.7** |

**尖刺倍数（尖刺 ÷ 稳态解码轮 12.1 ms）**

| ctx | 基线 | CHUNK=2048 | CHUNK=1024 | CHUNK=512 |
|---|---:|---:|---:|---:|
| 1024 | 13.3× | 13.4× | 13.3× | **8.2×** |
| 4096 | 53.3× | 29.9× | 16.7× | **9.7×** |
| 8192 | 120.8× | 39.1× | 21.6× | **11.6×** |
| 16384 | 310.4× | 57.5× | 31.6× | **16.9×** |

⇒ **CHUNK=512 把 16K 的尖刺从 310× 压到 16.9×（−95%）**；`no_draft` 同趋势（2984.0 → 156.8 ms）。
⇒ **尖刺 ≈ 一个 chunk 的 prefill 墙钟**，所以 chunk 越小尖刺越低、但轮数越多（16384/512 = 32 轮）。
**"尖刺 vs 轮数开销"的交点没扫**（§6 挂账）。

### 5.5 ★★ 分块让路的第一版是错的：同一个 chunk 被拼了 7 遍

第一版 `CHUNK=2048` 实测**尖刺反而变大 3 倍**（ctx=4096：642 → 2039 ms）。
逐轮打点（`p13_chunk_probe.py`）直接给出答案：

```
round 0  prefill  step_tokens=14336  target_fwd=14336  ms=2040.6   ← 一个 round 进了 14336 个 token！
round 2  prefill  step_tokens=2048   target_fwd=2048   ms= 373.3
```

**根因（是我自己的 bug）**：分块后那条序列本步拼不完，**没被 `popleft()`，还留在 `self.waiting[0]`**；
而 prefill 的 `while` 循环下一轮又取到**同一条**，把 `num_scheduled_tokens` 再覆盖一遍、再 `append` 一份。
于是 `scheduled_seqs` 里出现同一序列的多份副本，`prepare_prefill` 把这段 chunk **重复拼 N 遍**
（`max_num_batched_tokens=16640` 下 N=7 ⇒ 7×2048 = **14336**，与打点逐字吻合）。

**为什么原来没暴露**：原逻辑 `seq.num_scheduled_tokens = min(num_tokens, remaining)` 一定会把预算用光 ⇒
下一轮 `remaining == 0` 直接 break。是我引入的 `budget = min(remaining, chunk)` 让预算提前耗尽、
循环得以继续。而且**只有"预算充裕"的配置才暴露**：`max_num_batched_tokens=4352` 时
恰好被原来那句 `remaining < num_tokens and scheduled_seqs` 的守卫兜住（实测 4352 档一直是正常的 700 ms）。

**修法**：分块分支里 append 之后**立刻 `break`**（一条序列本步拼不完 ⇒ 本轮到此为止）。
修完逐轮打点：round 0 = 2048 token / 335.7 ms，round 2 = 2048 / 360.5 ms，**prefill 合计 696 ms ≈ 不分块的 648 ms**（没有 N 倍）。

⇒ **修好后**：251 项测试仍全过；逐字节对拍三组仍**完全一致**（§5.2 的 md5 一个字符没变）。

## 6. 没做 / 测不出 / 挂账

1. **滑窗路径热态那 2.0~3.5× 的浪费，只加了"别重复算"的守卫，没做根因修复。**
   真正的修法是给滑窗档做**它自己的**块级前缀缓存（现在只有 full-context 路径有
   `Block.draft_hash` / `draft_valid_cached_blocks`）。**这要动到滑窗的 KV 分配** ⇒
   属于任务书的"方向性变化"停止条件，**没有自作主张做**。
2. **`spec_batch_threshold` 那种门控没覆盖**（prefill 时刻不知道未来解码批大小），如实挂账。
3. **分块让路的代价只测了"prefill 总墙钟不涨"**（逐轮打点：696 vs 648 ms，+7%）；
   **吞吐 / 端到端 tok/s 的代价没测**。**待补**。
4. **chunk 大小的最优值没有扫完**：只测了 512 / 1024 / 2048，`256` 及更小会怎样未测。
   已知单调趋势是"越小尖刺越低、轮数越多"，交点没找。
5. **B=4 并发下的尖刺没测**（本轮只测了 3 条解码 + 1 条长 prompt）。
6. **分块 prefill 打开时，输出是否与不分块逐位相同【没测】**（预热/分块会改变 attention 的
   query 分组 ⇒ 浮点归约顺序变 ⇒ 极可能有 ULP 级差异）。本轮只验证了**默认路径（分块关）**
   的逐字节等价。**这条必须补**，否则不能宣布"无损"。
