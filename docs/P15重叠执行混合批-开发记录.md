## 0. 一句话结论（★ 连边界一起写）

**"混进同一个 step"本身一分钱不值（实测串行版三处收益都在噪声内、方向还不一致）；
值钱的是两条 CUDA stream 上的真重叠 —— 16K prefill 的第 1 块上藏起 93.4 ms，
第 14 块上升到 203.8 ms（上界的 93.1%）。**

★ **但 `§d.5` 给出的收益上界（12.1 ms/轮）是错的**：那个数只在"普通 decode（无投机）"下成立
（本轮逐值复核：**12.04 ms**）。本项目默认配置（`k=6` + draft 提议器）下一个解码轮实测
**220 ms**。⇒ **正确的上界是 `min(解码轮, prefill 块)`，不是"一个解码轮"。**

| | 微基准（直接量两个前向，`CTX=16384 / CHUNK=1024 / B=3 / k=6`，15 次中位数） |
|---|---|
| 只跑 decode 子批（含投机验证） | **220.2 ms** |
| 只跑 prefill 块（1024 token，第 1 块） | **171.4 ms** |
| 同 step、两个前向**串着跑** | **391.5 ms** = 220.2 + 171.4（残差 **−0.1 ms**） |
| 同 step、**两条 stream** | **298.1 ms** |
| ★ **重叠收益** | **93.4 ms = 上界（171.4）的 54.5%**；第 14 块上 **203.8 / 218.8 = 93.1%** |
| （参考）只跑 decode、**退回普通 decode** | **12.04 ms** ← 逐值复核了 §d.5 的"12.1 ms" |

★ 端到端：场景 A 解码 ITL 窗口 p50 **475 → 317 ms（−33.4%）**、长 prompt TTFT
**7524 → 5029 ms（−33.2%）**、稳态吞吐 **+8.9%**；而串行档三处都 ≈ 0。

## 1. 判据（开工前定死，避免事后凑结论）

| 判据 | 内容 | 怎么算过 |
|---|---|---|
| **J1** | 微基准里 `t(并发) < t(串行)`，且 `t(串行) ≈ t(decode)+t(prefill)` | 差值 > 噪声地板 |
| **J2** | ★ **串行版收益 ≈ 0**（与让路式在噪声内）| 端到端 ITL/TTFT 同口径对比 |
| **J3** | 并发不改变计算结果 | 同种子下 **串行 vs 并发逐 token 相同** |
| **J4** | 默认路径零影响 | CPU 回归 **361 → 404 项全过（FAIL=0）**，且 `overlap=false` 时逐值冻结 |
| **J5** | 图命中率不掉 | 纯 decode step 仍走 `run()`；混合 step 如实报 |

★ **停止线（方案里写好的）**：若"串行版"做完发现收益确实是 0、而"并发版"实现成本很高，
**停下回报**，不要为了"有个结果"硬做。→ 本轮**没触发**：并发版成本可控且收益为正。

### 2.2 为什么这样切

★ **"两条 stream 的并发编排"是一个独立概念，给了它自己的模块**（`mixed_batch.py`），
而不是往 `model_runner.run()` 里堆 `if mode == ...`。
`run()` 是纯 decode / 纯 prefill 的既有热路径，P15 **一行没动它**。

★ **改动全部局部化**（另一个 agent 同时在改 `scheduler.py` / `model_runner.py`）：
- `scheduler.py`：只改了 `if self.waiting and not yield_to_decode:` → `if self.waiting and (mixed or not yield_to_decode):`
  这一行守卫，以及 prefill 段末尾的 `if scheduled_seqs: return` 加了一个 `if mixed:` 前置分支。
  **prefill 的 while 循环体一个字符没动**（P14 要改的正是那个循环）。
- `model_runner.py`：prefill 分支整体搬进新方法 `_prefill_forward()`，`run()` 里只剩三行调用；
  新增的 `run_mixed()` 单独一个入口。**纯 decode 分支零改动。**

### 2.3 ★★ 关键设计：为什么重叠"能在不改热路径的前提下做到"

一个朴素想法是"把 decode 拆成发射段+采样段，两边都发射完再各自采样"。**不用这么做。**
关键认识是 **invariant I4**：

> 两条路径共享的只有【只读权重】与【全局 context 单例】（`utils/context.py`）。
> `Attention.forward` / `ParallelLMHead.forward` 都是在 **kernel 发射那一刻**读 `get_context()`；
> kernel 一旦发射，它与 Python 侧的 context 就解绑了。

⇒ 所以**发射顺序可以任意交错**，只要每次发射前把 context 设对。于是：

```
aux.wait_stream(cur)                       # 只插事件，不阻塞 Python
with torch.cuda.stream(aux):
    logits, temps = r._prefill_forward(seqs)   # ★ 只发射，不 .tolist()
dec = r.run(decode_seqs, False)            # 走当前流，内部照常吃图、照常 .tolist()
with torch.cuda.stream(aux):
    pf = r.sampler(logits, temps).tolist() # 采样推迟到 join 之后
cur.wait_stream(aux)
```

★ **唯一必须改的既有函数是 prefill 的采样点**：`run()` 原来在发射后立刻 `sampler(...).tolist()`，
那会同步当前流（= 在重叠开始前就把它取消掉）。所以把 prefill 拆成 `_prefill_forward()`（发射）
+ 调用方的采样。**老路径连着调两半 ⇒ 与拆分前逐字节一致。**

★ decode 侧**一行没改**：`run(seqs, False)` 里的 `.tolist()` 是**流作用域**的同步
（`Tensor.tolist()` → `cudaMemcpyAsync` + `cudaStreamSynchronize(current)`），
不会把 aux stream 上的 prefill 一起等掉。

### 2.4 aux stream 的两个细节

- **非阻塞**：PyTorch 建的 stream 默认带 `cudaStreamNonBlocking`，与**遗留默认流**之间
  **没有** CUDA 那种隐式同步 ⇒ 真并发。（如果用 `cudaStreamCreateWithFlags(0)` 就全废了。）
- **低优先级**：`Stream(priority=hi)`。prefill 是算力型长任务、decode 是带宽型短任务，
  空闲 SM 优先派给 decode —— 我们要的是"decode 不被 prefill 挡住"，不是反过来。

## 3. ★★ 不变量（写进注释、写进代码、写进测试）

这个项目被"一轮内混两条执行路径"坑过 **3 次**（最典型 `spec_enabled` 门控快照 bug，
复现见 `tests/test_spec_gate.py`）。P15 是**主动**往一轮里塞两条路径，所以把契约钉死：

| | 不变量 | 载体 |
|---|---|---|
| **I1** | 一个 step 里，任何序列**至多**出现在一条路径上 | `schedule()` 的 `_round_seqs` 守卫 + `_step_mixed()` 的 `assert` |
| **I2** | decode 子批走不走投机在**轮首取一次快照**、全轮一致 | 复用既有 `spec_enabled(active_B)` 契约，未改 |
| **I3** | 两条路径的 KV / 计数记账**各自独立**走 `postprocess` | `_step_mixed()` 里**两次** `postprocess` 调用 |
| **I4** | 共享的只有只读权重 + 全局 context 单例；context 必须在**各自 kernel 发射之前**设好 | `MixedForward._run_concurrent()` 的注释 + 发射顺序 |
| **I5** | 纯 decode step 必须走**老入口**、图照常命中 | `llm_engine.step()` 的类型分派；`run()` 零改动 |

★ **I1 是怎么被真正钉住的**（不是靠"小心一点"）：
prefill 段可能把一条序列从 `waiting` 推成 `RUNNING` 并 `append` 进 `self.running`；
decode 段的 `while ... popleft()` 若再取到它，就是**同一个 step 里该序列被调度两次** ——
这正是 P13「同一个 chunk 被拼 7 遍」那个真 bug 的**镜像**。守卫写成：

```python
seq = self.running.popleft()
if _round_seqs and seq in _round_seqs:      # I1
    self.running.append(seq)                # ★ 放回队尾（不能 continue —— 那会把它弄丢）
    break
```

测试 `tests/test_overlap_mixed.py §2` 专门覆盖了这一格（chunk 恰好在本轮拼完）。

## 4. ★ 测量方法（协调方硬性要求：串行 vs 并发必须同卡同时段交替）

**为什么这件事不能马虎**：本轮的效应量级是 **几十~几百 ms**，而"串行 vs 并发"的核心变量
只有"发到几条 stream"。如果三档分成三个进程、三个时间段跑，外部干扰（同机其他进程、
SM 时钟、显存温度）会和"重叠"混在一起**分不开**。

**做法**：
1. **只用 GPU 4 一张卡，全程串行**，用前 `nvidia-smi` 确认空卡；绝不碰别人的进程。
2. **三档放在同一个进程里、轮内交替**（`for run in range(RUNS): for mode in modes: ...`），
   每个条件重复 `RUNS≥3` 次，报**中位数 + 范围**，范围即噪声地板。
3. **微基准里四个条件逐个交替采样**（不是"先量完 A 再量 B"）。
4. 场景 A / B（延迟类）**一律串行测**，没有铺开到多卡。

**噪声地板实测**（深度扫描那一版的原始读数）：
- ★ 微基准里 `t(串行) − [t(decode)+t(prefill)]` 在 **4 个 prefill 深度**上是
  **−0.10 / −0.51 / −0.26 / +0.48 ms** —— 两个前向之间的固定开销，
  相对 390~600 ms 只有 **0.03%~0.1%**。**这就是这一轮的噪声地板。**
- 同一条件的 15 次重复范围：`decode_only 219.3~223.0`（±0.8%）、
  `prefill_only 170.3~244.4`（随深度增长）、`serial 390.6~466.9`、
  `concurrent 297.4~314.1`。
- 场景 A 的三档各 3 次重复：窗口 p50 `yield 474.3~476.2 / serial 498.4~499.1 /
  concurrent 311.8~321.9` —— ★ **并发与另外两档的范围完全不重叠**。
- ★ **本轮效应量（93.4 ms → 203.8 ms）是噪声地板（≤0.5 ms）的两个数量级** ⇒ 结论稳。

## 5. 结果

### 5.1 ★ 微基准（决定性的那一格）

脚本 `scripts/p15_overlap_micro.py`。直接调 `run_mixed`，把调度、postprocess、token 采样
全部排除在外，只留下"发射两个前向"这一件事。
四个条件（decode-only / prefill-only / serial / concurrent）**逐个交替采样**，各 15 次。

#### (a) 第一个 prefill 块（depth 0）上的四象限

| 条件 | 中位数 | 范围（15 次） |
|---|---|---|
| `decode_only`（3 条请求 × 1+k=7 个位置，含 draft 提议 + 验证） | **220.2 ms** | 219.4 ~ 223.0 |
| `prefill_only`（1024 token 的分片） | **171.4 ms** | 170.3 ~ 171.8 |
| `serial`（同 step、串着跑） | **391.5 ms** | 390.6 ~ 393.6 |
| `concurrent`（同 step、两条 stream） | **298.1 ms** | 297.4 ~ 300.1 |
| `decode_only_nospec`（退回普通 decode，B=3） | **12.04 ms** | 12.00 ~ 12.05* |

\* 去掉第一次调用的编译 outlier。**这个 12.04 ms 就是 `§d.5` 里写的"解码轮 = 12.1 ms"，
逐值复核通过。**

**读数**：
- **J1 过**：`serial − (decode + prefill) = −0.10 ms`（两个前向之间的固定开销，**0.03%**）；
  `concurrent` 比 `serial` **少 93.4 ms**，等于把 prefill 块（171.4 ms）藏起来 **54.5%**。
- **decode 在并发里被拖慢 77.9 ms**（220.2 → 298.1）—— 这是**资源竞争的真实代价**，
  也是为什么收益（93.4）小于理论上界（171.4）。
- ★★ **`§d.5` 的 12.1 ms 得到复核，但它不是本配置的上界。**

#### (b) ★★ 沿 prefill 深度扫描：上界到底是多少（本轮最值钱的一张表）

`prefill 块的成本随 seqlen_k 增长（第 i 块的 avg kv 长度 ≈ (i+1)·CHUNK/2）`，
而表格里每个数都是 **15 次重复的中位数**：

| prefill 深度（第几块） | `t_decode` | `t_prefill` | `t_serial` | `t_concurrent` | **重叠收益** | 上界 `min(dec,pf)` | 收益/上界 | 残差 |
|---|---|---|---|---|---|---|---|---|
| 0 | 220.2 | 171.4 | 391.5 | 298.1 | **93.4** | 171.4 | 0.545 | −0.10 |
| 5 | 220.4 | 242.9 | 462.8 | 306.8 | **156.0** | 220.4 | 0.708 | −0.51 |
| 10 | 219.0 | 319.2 | 537.9 | 338.9 | **199.1** | 219.0 | 0.909 | −0.26 |
| 14 | 218.8 | 381.4 | 600.7 | 396.9 | **203.8** | 218.8 | 0.931 | +0.48 |

★★ 三条结论：
1. **`serial = decode + prefill` 在四个深度上都成立**（残差 ≤ 0.5 ms）⇒ 串行那一档
   **确实一点重叠都没有**，它就是一个诚实的对照组。
2. **收益随块变大而单调逼近上界**：93 → 156 → 199 → 204 ms，
   占上界的 0.545 → 0.708 → **0.909 → 0.931**。
   块小的时候（171 ms）只能藏一半多；块一超过解码轮（220 ms）就被**饱和在解码轮**上 ——
   这正是"上界 = min(解码轮, prefill 块)"的实测形状。
3. ★ **换个算法看得更清楚：并发 step 里 decode 的【边际成本】** = `t_concurrent − t_prefill`
   = **126.7 → 63.9 → 19.7 → 15.5 ms**。
   块越大，解码越接近**免费**（第 14 块只多付 15.5 ms，而它单跑要 218.8 ms）。

★ **这张表也解释了场景 A**：16K prompt 的**平均**块远大于第 1 块
（avg kv 长度 ≈ 8K vs 第 1 块的 ≈ 2K），所以端到端能拿到的每轮节省
应当接近**整个解码轮（~220 ms）**，而不是第 1 块的 93 ms。

### 5.2 端到端三场景（★ 三档在同一进程内交替采样，每档 n=3）

原始数据：`docs/evidence/p15-20261013/scen{A,B,C}.log`；汇总脚本 `.../summarize.py`。
公共口径：`ctx=16384 / out=256 / k=6 / max_num_seqs=4 / CHUNK=1024 / TP=1 / GPU 4`，
自然长文（wikitext2），每档重复 3 次，报**中位数 + 范围**。

#### 场景 A：decode 饥饿（3 条短请求解码中，突来 1 条 16K 长 prompt）

| 指标 | `exclusive`（chunk=0，排他 prefill） | 让路式 `yield` | **P15-串行** | **P15-并发** |
|---|---|---|---|---|
| 长 prompt **TTFT (ms)** | 3756 [3747, 3758] | 7524 [7514, 7532] | 7529 [7529, 7531] | **5029 [5019, 5069]** |
| 解码 **ITL 窗口内 p50 (ms)** | —（不分块，无窗口） | 475.1 [474.3, 476.2] | 498.8 [498.4, 499.1] | **316.5 [311.8, 321.9]** |
| 解码 **ITL 窗口内 max (ms)** | — | 580.3 | 580.2 | **455.3** |
| 解码 **ITL 全程 p50 (ms)** | 217.0 | 217.5 | 216.8 | 217.0 |
| 解码 **ITL 全程 p99 (ms)** | 1089.8 [1014, 1125] | 570.4 [570, 574] | 581.5 [581, 584] | **409.3 [393, 416]** |
| 解码 **ITL 全程 max (ms)** | 3836.2 [3828, 3838] | 580.3 | 594.4 | **455.3** |
| wall (s) | 21.62 [18.7, 22.2] | 21.05 [19.9, 21.7] | 22.32 [22.1, 22.4] | **18.66 [18.5, 19.6]** |
| 混合 step 数 | 0 | 0 | **15** | **15** |

读数（三条）：
1. ★ **串行 ≈ 让路式**：窗口 p50 **+5.0%**、窗口 max **−0.0%**、TTFT **+0.07%**。
   ⇒ **"混进同一个 step"本身收益 ≈ 0** —— 这就是方案预测的那个 0，测出来了。
   （那 +5.0% 方向是**更差**，与"合并 step 多了 2 次 postprocess / 一次编排分发"一致，
   不足以读成任何收益。）
2. ★ **并发显著更好**：窗口 p50 **−33.4%**、p99 **−28.3%**、max **−21.5%**、
   长 prompt TTFT **−33.2%**、wall **−11.4%**。三档 3 次重复的范围**互不重叠**。
3. **`exclusive`（不分块）这幅参照图很重要**：长 prompt 的 TTFT 最好（3756 ms），
   但解码请求被饿死**整整 3.8 s**（ITL max = 3836 ms，p99 = 1090 ms）。
   分块把 p99 从 1090 → 570（救了延迟）、代价是 TTFT 从 3.8 → 7.5 s（差 2 倍）；
   **P15-并发把这两者同时拉回来**：p99 409（比让路式还好）且 TTFT 5.0 s（比让路式好 33%）。

#### 场景 B：prefill 公平（1 条解码中，3 条 16K 同时到达）

三条各自的 TTFT（ms，三次重复一共 9 个数，两个 run 的读数）：

| | 第 1 条 | 第 2 条 | 第 3 条 |
|---|---|---|---|
| 让路式 `yield` | 4800 / 4809 / 4812 | 9685 / 9711 / 9713 | 14582 / 14591 / 14599 |
| P15-串行 | 4805 / 4817 / 4814 | 9688 / 9759 / 9758 | 14550 / 14666 / 14666 |
| **P15-并发** | **4536 / 4538 / 4539** | **9158 / 9206 / 9124** | **13744 / 13795 / 13751** |

| 汇总 | 让路式 | P15-串行 | P15-并发 |
|---|---|---|---|
| TTFT **p50** (ms) | 9711 [9685, 9713] | 9758 [9688, 9759] *(**+0.5%**)* | **9158 [9124, 9206]** *(**−5.7%**)* |
| TTFT **p99** (ms) | 14493 [14485, 14501] | 14567 [14452, 14568] *(+0.5%)* | **13659 [13652, 13703]** *(−5.8%)* |
| 第 3 条完成时刻 e2e (ms) | ~14690 | ~14730 | **~13900** |
| wall (s) | 15.59 | 16.19 | 15.08 |

★★ **为什么这里只有 −5.7%？—— 恰好验证了"上界 = min(解码轮, prefill 块)"这个模型。**
场景 B 里只有 **1 条**解码请求 ⇒ 它的一个投机解码轮只有 **~32 ms**（B=1 时验证前向只有 1 行；
对照：B=3 时是 220 ms）。而 prefill 块是 ~530 ms。⇒ 每轮最多只能藏 32 ms。
实测量到的节省 = (9711 − 9158) / 16 块 ≈ **34.6 ms/块** —— 与 32 ms 的预测吻合。
**同一个"并发"机制、同一个 CHUNK，收益从 −33% 掉到 −5.7%，只因为被藏的那个前向变小了。**
这比任何论证都更能说明"收益 = 重叠量"而不是"混批"。

#### 场景 C：稳态吞吐（连续到达、无空闲）

12 条请求（1K/4K/8K prompt 混合，各 out=64），始终填满 `max_num_seqs=4`。

| | tok/s | wall (s) | 交付 token |
|---|---|---|---|
| 让路式 `yield` | 41.74 [40.62, 41.97] | 18.40 | 768 |
| P15-串行 | 42.46 [41.47, 42.52] *(**+1.7%**)* | 18.09 | 768 |
| **P15-并发** | **45.45 [44.97, 46.81]** *(**+8.9%**)* | **16.90** | 768 |

★ 串行的 +1.7% 落在两档范围**互相重叠**的区间里（40.62–41.97 vs 41.47–42.52），
按项目既有口径**只能读成"≈ 0，在噪声内"**，不能读成收益。

### 5.3 ★ 三档对照总表（回答"这一轮到底赚了多少"）

| 场景 | 主指标 | 让路式 | P15-串行 | P15-并发 | 串行 vs 让路式 | **并发 vs 让路式** |
|---|---|---|---|---|---|---|
| **A** decode 饥饿 | 解码 ITL 窗口 p50 | 475.1 ms | 498.8 ms | **316.5 ms** | **+5.0%（更差）** | **−33.4%** |
| | 解码 ITL 全程 p99 | 570.4 | 581.5 | **409.3** | +1.9% | **−28.3%** |
| | 长 prompt TTFT | 7524 | 7529 | **5029** | +0.07% | **−33.2%** |
| **B** prefill 公平 | 三条 TTFT p50 | 9711 | 9758 | **9158** | +0.5% | **−5.7%** |
| | 三条 TTFT p99 | 14493 | 14567 | **13659** | +0.5% | **−5.8%** |
| **C** 稳态吞吐 | 聚合 tok/s | 41.74 | 42.46 | **45.45** | +1.7%（噪声内） | **+8.9%** |

★ 一句话：**串行这一档三处都在噪声内、方向还不一致 ⇒ "混批"本身收益 0；
并发这一档三处一致为正、范围不重叠 ⇒ 收益全部来自重叠。**

### 5.4 ★ 正确性：重叠只改时间，不改结果（J3）

脚本 `scripts/p15_smoke.py`（证据 `docs/evidence/p15-20261013/smoke.log`）。

**做法**：同一个进程里跑三档（让路式 / 串行 / 并发），**每一档开头 `torch.manual_seed(同一个种子)`**。
两条混合路径的 host 侧 RNG 消费顺序**完全一样**（decode 的采样都发生在 prefill 采样之前，
无论 kernel 发到哪条 stream）⇒ 只要重叠没有改变任何计算，输出就该**逐 token 相同**。

```
[PASS] 串行 vs 并发：交付 token 序列逐 token 相同（3 条请求，各 [32, 32, 32] 个 token）
(参考) 让路式的交付 token 数 [32, 32, 32]，与并发相同: True
```

★ **这是"重叠只改时间、不改结果"的最强证据** —— 它比"对比 token 数"强得多，
也比"跑通不报错"强得多。（让路式档**不**参与逐 token 对比：它的投机轮次划分不同，
host 侧 RNG 消费顺序随之不同 ⇒ 采样结果本就应该不同，这不是 bug。）

同一个脚本里的墙钟也复现了主结论：`wall = 2.44 s（让路式）/ 2.40 s（串行）/ 2.07 s（并发）`
—— 串行 ≈ 让路式，并发 **−15%**。

### 5.5 ★ 图命中率有没有掉（J5）

脚本 `scripts/p15_graphprobe.py`（证据 `docs/evidence/p15-20261013/graphprobe*.log`）。

**纯 decode step：一行代码都没改，命中率不可能变。** 三条独立证据：
1. `git diff` 显示 `run()` 的 decode 分支、`run_verify()`、`run_verify_forward()`、
   `run_model()`、`capture_*_cudagraph()` **全部零改动** —— P15 只动了 prefill 分支
   （把它搬进 `_prefill_forward()`）。
2. `tests/test_overlap_mixed.py §4` 用脚本化 runner 锁住：**纯 decode step 调的是 `run()`，
   全程不会出现 `run_mixed`**。
3. `schedule()` 在"本轮没有待推进的 prefill 块"时返回老的两元组，
   `llm_engine.step()` 走的就是原来那几行。

**混合 step：** 实测（3 条解码 + 16K prompt，`CHUNK=1024`）：

| 配置 | 混合 step | 纯 step | 验证图命中 | 逐形状退回 |
|---|---|---|---|---|
| `spec_graph_bs=(1,2,4)`（**默认**） | 15 | 19 | 14 | `{shape_not_captured(B=3,k=6): 22}` |
| `spec_graph_bs=(1,2,3,4)` | 15 | 7 | 24 | **`{}`（0 次）** |

★★ 读数：**唯一观察到的退回是 `B=3 没被捕获`，而这是 `spec_graph_bs=(1,2,4)` 这个
既有配置决定的，不是 P15 引入的。** 把它加进捕获列表，退回立刻归零。
⇒ **混合 step 的 decode 侧走的是同一个 `run()`，图命中判据与纯 step 完全一致；
差别只在 batch 组成，不在代码路径。**
（★ 但这确实意味着：**默认配置下 3 条请求的混合 step 拿不到 B=3 的验证图** ——
这是既不修也不藏的既有边界，**如实报**。）

## 6. 带宽账（§d.5 前置条件 ③ 的复核）

§d.5 的估算：
```
decode ：带宽型（3 个 token / 12.1 ms ≈ 660 GB/s ≈ 峰值的 82%）+ SM 占用低
prefill：算力型（4B 模型读一遍 8 GB 权重 / 284 ms ≈ 28 GB/s ≈ 带宽的 3%）
⇒ 并发时带宽需求 ≈ 700 GB/s < 实测天花板 842 GB/s
```

★ **这条账的"decode 那一项"对本项目的默认配置不成立**，实测给出三处修正：

1. **"decode = 12.1 ms" 只在【普通 decode】下成立**（本轮逐值复核 12.04 ms）。
   一旦开投机（默认 `k=6` + draft 提议器），一个解码轮实测 **220 ms**。
   ⇒ §d.5 里"decode 已用 82% 带宽"这幅图**描述的不是默认配置的 decode**。
   ⚠️ **诚实边界：这个 220 ms 的内部拆解（draft 提议 vs 验证前向 vs CPU 侧开销）
   本轮【没有做 profiler 归因】** —— 只能说"它不是 12.1 ms"，不能说是哪一段吃掉的。
2. **两者确实在互相拖慢，而且拖慢量随 prefill 块变大而增长**（实测）：

   | prefill 深度 | decode 单跑 | 并发里的并发总时长 | decode 被拖慢 | prefill 被拖慢 |
   |---|---|---|---|---|
   | 0 | 220.2 | 298.1 | **+77.9** | — |
   | 5 | 220.4 | 306.8 | **+86.4** | — |
   | 10 | 219.0 | 338.9 | **+119.8** | — |
   | 14 | 218.8 | 396.9 | **+178.1** | — |

   ⇒ **"理论放得下"这句话要打个折**：并发不是免费的，
   `t_concurrent − t_prefill` = 126.7 → 63.9 → 19.7 → 15.5 ms，
   块越大、"多跑一个解码"的**边际成本**越小，但从来不是 0。
3. **净账仍然是正的**：每个深度上 `t_concurrent < t_serial`，
   而且 `t_serial = t_decode + t_prefill` 逐深度成立（残差 ≤ 0.5 ms）。
   ⇒ 重叠真的发生了，只是要付竞争税。

★ **没有做的**：没测 `nvidia-smi`/`dcgm` 意义上的实际 DRAM 带宽占用，
也没有用 `nsys` 看两条 stream 的时间线重叠比例。**"到底重叠了多少 %"这件事只有
墙钟证据（`t_concurrent` vs `t_serial`），没有时间线证据。**

## 7. 边界与没做的事（★ 没做就说没做）

1. **只测了 `CHUNK=1024`。** §d.5 提到 "C=256 时 decode 的 ITL 从 296 → 82 ms"。
   但那是**普通 decode** 的口径。本配置下解码轮 220 ms **大于**任何小块的墙钟
   ⇒ 上界由块决定；块越小、能藏的东西越少（但**被藏的比例**反而可能更高）。
   **没测 CHUNK=256/512**，只是给出了这个推理。
2. **只测了 `TP=1`。** 多卡下 `run_mixed` 要经 shm 分发，且两条路径的 NCCL 交互**没验证**。
3. **`max_num_seqs=4`**（与另一 agent 共用的口径）。batch 更大时解码轮会变长、
   上界会移动，**没测**。
4. **抢占（preempt）与混合 step 的交互只做了兜底、没做压测。**
   `schedule()` 里有一条兜底（decode 端一条都没排上就退回老形状），但没有构造
   "KV 正好不够、混合 step 里发生抢占"的用例。
5. **混合 step 里 decode 侧的投机接受率没单独统计。** 输出正确性由"串行 vs 并发逐 token 相同"
   覆盖（`scripts/p15_smoke.py`），但"混批会不会影响 α"没测。
6. **没做 `enforce_eager=True` 的对照**（那样 decode 也走 eager，重叠的收益结构会变）。
7. **吞吐场景 C 的 prompt 长度是我选的**（1K/4K/8K 混合），方案里只规定了 ctx=16384。
8. ★ **没有 profiler 证据**：那条 220 ms 的解码轮内部没有拆解，也没有用 `nsys`
   看两条 stream 的实际时间线重叠比例。重叠的**唯一证据是墙钟**
   （`t_concurrent < t_serial`，且 `t_serial = t_decode + t_prefill` 逐深度成立）。
9. ★ **默认 `spec_graph_bs=(1,2,4)` 下，3 条请求的混合 step 拿不到 B=3 的验证图**
   （实测退回 22 次）。这是**既有**边界（不是 P15 引入的），本轮**没改** ——
   改它属于动 `config` 默认值，会影响所有场景的口径。
10. **只有一个 prefill 块/轮**（P13 的"只推进队首"没动）。这是 P14 的地盘，
    不做越界改动。
