**名词先解释**（大白话）：

- **CUDA Graph（图）**：把一整个前向的 kernel 序列录下来，之后一次 replay 播放，省掉 Python 逐层发射 kernel 的开销。代价是**形状必须固定** —— 录的时候 batch 是 8，播的时候就只能塞 8。
- **capture size（捕获尺寸）**：录图时用过的 batch 大小列表。
- **padding（补齐）**：真实 batch 是 5，捕获表里只有 4 和 8，那就按 8 跑，多出来的 3 行是假的。多算了一点，但省下了"退回去逐层跑"的巨大开销。
- **slot_mapping**：每个 token 要写进 KV cache 的哪个槽位。
- **ragged（参差不齐）**：一批请求里，每条请求本轮要算的 token 数不一样。
- **uniform decode（齐整解码）**：一批请求里每条请求本轮 token 数完全一样（纯 decode 就是每条 1 个；投机验证就是每条 1+K 个）。

#### (b) 新机制 `num_speculative_tokens_per_batch_size`（当前 main 的答案）

`vllm/config/speculative.py:495`：

```python
num_speculative_tokens_per_batch_size: list[tuple[int, int, int]] | None = None
"""Batch-size schedule used to dynamically choose speculative-token count.
Each entry is ``(range_start, range_end, num_speculative_tokens)`` with an
inclusive batch-size range."""
```

默认 `None`（不启用）。**每条三元组是 `(起始 batch, 结束 batch, 用几个 draft token)`，闭区间。**

【文档】`docs/features/speculative_decoding/dynamic_speculative_decoding.md` 给了官方推荐配置：

```bash
--speculative-config '{
    "method": "eagle",
    "model": "yuhuili/EAGLE-LLaMA3.1-Instruct-8B",
    "num_speculative_tokens": 3,
    "num_speculative_tokens_per_batch_size": [
      [1, 64, 3],
      [65, 128, 1],
      [129, 512, 0]
    ]
  }'
```

文档原话解释：
- K=3 用在并发 [1, 64]
- K=1 用在并发 [65, 128]
- **K=0 用在并发 [129, 512]，即不产生 draft token**

**"为什么这么定"** —— 文档里写得很直白（这是全篇最值得引用的一段）：

> SD methods need to verify K tokens for each sequence during decoding. As BS increases, the effective BS becomes BS\*K which increases the compute requirement during verification. When this BS\*K goes beyond a critical BS then SD negatively impacts the decode speed (TPOT).

翻成大白话：**batch 大了以后，验证要算的 token 数是 BS×K，这个乘积超过某个临界点，投机就开始拖慢 decode**。所以他们的答案不是"关掉"，而是"把 K 降下去，降到 0 就是关掉"。

**校验逻辑**（`vllm/v1/spec_decode/dynamic/utils.py`）：

- `validate_and_normalize_dynamic_sd_schedule`：区间必须**非重叠且递增**，K ≥ 0，**第一个区间必须从 1 开始**（保证任何运行时 batch 都有定义）
- `build_dynamic_sd_schedule_lookup`：展开成 `dense_schedule[batch_size] → K` 的稠密查表，**区间之间的空隙用前一个区间的 K 顺延填**（例如 `[(1,16,3), (32,128,2)]` 里 17–31 会填 K=3），**尾部也用最后一个 K 顺延**
- 每次查表取 `min(vllm_num_speculative_tokens, K)` 做钳制

**调度侧怎么用**（`vllm/v1/core/sched/scheduler.py`）：

- `:307-313` 构造 `self.dynamic_sd_lookup`
- `:1564-1566` 每个调度步：`num_spec_tokens_to_schedule = self.dynamic_sd_lookup[len(num_scheduled_tokens)]`

**已知限制**（【文档】同一页）：

- 只测过 EAGLE / EAGLE-3 / DFlash
- **"Full Cudagraph only works with Model Runner V2. MRv1 only supports piece-wise cuda graph with this feature"** ← 这条对 Q5 极重要
- 不兼容 data parallel（DP rank 会选到不同的 K，导致集合通信发散/死锁），启用 DP 时**自动禁掉**并回退到静态 K

【源码】自动禁掉的具体位置：`vllm/config/vllm.py:1072-1076`，日志原文：

> "Dynamic speculative decoding is not supported with data parallelism because data-parallel ranks can select different speculative-token counts, causing DP divergence and deadlocks. Disabling num_speculative_tokens_per_batch_size and falling back to static num_speculative_tokens=%d."

#### (b) ★ draft 共享 target 的 embedding 和 LM head

### 2.3 Q4：CUDA Graph 的 padding 机制（★ 核心）

#### (a) 查表怎么建

`vllm/v1/cudagraph_dispatcher.py:71-96`，`_compute_bs_to_padded_graph_size`：

```python
self._bs_to_padded_graph_size: list[int] = [0] * (max_size + 1)
for end, start in zip(
    capture_sizes + [max_size + 1],
    [0] + capture_sizes,
):
    for bs in range(start, end):
        if bs == start:
            self._bs_to_padded_graph_size[bs] = start
        else:
            self._bs_to_padded_graph_size[bs] = end
```

**读法**：以 `capture_sizes = [1,2,4,8]`、`max_size = 8` 为例：

| 真实 bs | 映射到 | 说明 |
|---------|--------|------|
| 0, 1 | 1 | 0 也算 1 |
| 2 | 2 | **正好是捕获尺寸 → 映射到自己，零浪费** |
| 3 | 4 | 落在 2 和 4 之间 → 上取整到 4 |
| 4 | 4 | 正好 → 自己 |
| 5, 6, 7 | 8 | 落在 4 和 8 之间 → 上取整到 8 |
| 8 | 8 | 正好 → 自己 |

★ 注意这个设计：**正好命中捕获尺寸时不 padding**，只有落在缝隙里才向上补。所以捕获表越密，padding 浪费越小。

#### (b) 什么时候才真的退 eager

`vllm/v1/cudagraph_dispatcher.py:265-279`（`dispatch` 方法开头）：

```python
if (
    not self.keys_initialized
    or self.cudagraph_mode == CUDAGraphMode.NONE
    or max_size is None
    or num_tokens > max_size          # ← 只有这一个条件才退
    or allowed_modes <= {CUDAGraphMode.NONE}
):
    return CUDAGraphMode.NONE, BatchDescriptor(num_tokens)
```

【源码】**唯一的"形状不匹配就退"条件是 `num_tokens > max_size`（超过最大捕获尺寸）**。缝隙里的 batch 一律 padding 上取整，不退。

#### (d) ★ 投机场景专门加了什么

**第一处**：`vllm/config/compilation.py:1537` `adjust_cudagraph_sizes_for_spec_decode`：

```python
def adjust_cudagraph_sizes_for_spec_decode(self, uniform_decode_query_len: int):
    multiple_of = uniform_decode_query_len
    if not self.cudagraph_capture_sizes or multiple_of <= 1:
        return
    ...
    rounded_sizes = sorted(set(
        round_up(size, multiple_of)
        for size in self.cudagraph_capture_sizes
        if round_up(size, multiple_of) <= self.max_cudagraph_capture_size
    ))
    ...
    self.max_cudagraph_capture_size = rounded_sizes[-1]
    self.cudagraph_capture_sizes = rounded_sizes
```

调用条件（`:1497-1508`）：

```python
if (
    not use_v2_model_runner
    and cudagraph_mode.decode_mode() == CUDAGraphMode.FULL
    and uniform_decode_query_len > 1
):
    self.adjust_cudagraph_sizes_for_spec_decode(uniform_decode_query_len)
```

源码注释解释了原因：

> MRV1 adjusts cudagraph sizes to be a multiple of uniform_decode_query_len to avoid: https://github.com/vllm-project/vllm/issues/28207 and temp-fix: https://github.com/vllm-project/vllm/issues/28207#issuecomment-3504004536

★ **这就是关键**：投机时每条请求的 query 长度是 `1 + K`，而 FULL 图要求 `num_tokens_padded % (1+K) == 0`（`_create_padded_batch_descriptor` 里有 `assert num_tokens_padded % uniform_decode_query_len == 0`）。所以**捕获尺寸必须整体向上取整到 (1+K) 的倍数**，否则 padding 出来的形状没法整除，图里请求数算不对。

**第二处**：`uniform_decode_sizes` 按"请求数网格"追加（`vllm/config/vllm.py:2460-2508`）。源码注释讲清了为什么不能简单地把 token 网格延伸到大尺寸：

> The grid would not buy decode coverage anyway. Dispatch requires an exact multiple of decode_query_len, so a token-strided entry is only usable when it happens to be one; at query length 17 a captured 560 rounds to 561 and is rejected. Scaling a request-count grid keeps every entry usable and the count comparable to the non-speculative case.

翻成大白话：**query 长度 17 的时候，一个 token 步长的 560 会被上取整到 561，561 不是 17 的倍数 → 直接不可用**。所以必须改用"请求数网格 × query 长度"来生成。

具体网格（`vllm/config/vllm.py:2470-2477`）：

```python
def request_counts(max_reqs: int) -> list[int]:
    max_reqs = min(max_reqs, default_max_graph_size)
    counts = [n for n in (1, 2, 4) if n <= max_reqs]
    counts += list(range(8, min(max_reqs + 1, 256), 8))
    counts += list(range(256, max_reqs + 1, 16))
    return sorted(set(counts + [max_reqs]))
```

**第三处**：动态 K 时按"档"分别生成（`vllm/config/vllm.py:2478-2508`）。源码注释：

#### (a) `_pad_to_bucket`

```python
def _pad_to_bucket(raw_size: int, buckets: Sequence[int]) -> int:
    """Return the smallest buckets[i] >= raw_size.

    Caller's can_run_graph must reject raw_size > max(buckets) before
    reaching load_batch; this assertion makes the contract
    explicit (bisect_left returns len(buckets) when the value
    exceeds all buckets, which would otherwise IndexError below
    with no diagnostic).
    """
    assert raw_size <= buckets[-1], (
        f"size {raw_size} exceeds max captured bucket {buckets[-1]}; "
        f"can_run_graph should have rejected this batch"
    )
    index = bisect.bisect_left(buckets, raw_size)
    return buckets[index]
```

★ **跟 vLLM 是同一个思路**：`bisect_left` 向上取最近 bucket。区别是 SGLang 用**断言**把"超过最大 bucket"的责任推给调用方 `can_run_graph`（在更早的地方就拒绝了，不会走到这里）。

    """Pad to the captured slot count. The full-coverage variant (cap=None)
    keeps sum(verify_lens) == graph_num_tokens, so padding rows (or, with
    no padding rows, the last real row) can exceed the per-request verify
    window. Dense-layout consumers (mamba/KDA) must pass cap=N: rows are
    clamped to N and the layout no longer covers the tier's leftover
    tokens -- those collapse into the consumer's ghost slot. Real tokens
    map identically under both variants."""
    padded = PaddedToBucket.execute(
        verify_lens=self.verify_lens,
        graph_num_tokens=self.graph_num_tokens,
        bs=self.bs,
        padded_bs=padded_bs,
    )
    if cap is not None:
        padded = torch.clamp(padded, max=cap)
    return RaggedVerifyLayout._assemble_device(
        verify_lens=padded,
        graph_num_tokens=self.graph_num_tokens,
        total_verify_tokens=None if cap is not None else self.graph_num_tokens,

★ 注意 **cap=None 的"全覆盖变体"会把 `sum(verify_lens)` 撑到等于 `graph_num_tokens`** —— 也就是**把补齐的 token 塞进 padding 行（或没有 padding 行时塞进最后一行真实请求）**。这是有意的：这样 kernel 看到的 token 总数正好等于图 bucket，不需要额外分支。多出来的部分在 attention 里不会影响真实输出（因为它不在任何真实请求的 KV 范围里）。

**他们怎么做**（SGLang，`python/sglang/srt/arg_groups/cuda_graph_hook.py:500-532`）：

```
投机专用捕获表 = range(1,9,1) + range(10,33,2) + range(40,65,4) + range(72,257,8) + range(272,max+1,16)
                ↑ 1..8 每个都捕     ↑ 步长 2          ↑ 步长 4          ↑ 步长 8          ↑ 步长 16
```

**我们的差距**：

| 项 | 我们 | 行业做法 |
|----|------|----------|
| 捕获表 | `{1, 2, 4}` 三个 | 小 batch 段 1..8 全捕 |
| 匹配不上 | **退回 eager** | **向上取整 padding**，只有超过最大尺寸才退 eager |
| spec 专用表 | 无（和非 spec 共用） | **spec / 非 spec 两张不同的表** |

**可抄的具体动作**：

1. 把 `spec_graph_bs` 从 `{1,2,4}` 扩成 `{1,2,3,4,5,6,7,8}`（3090 单卡，8 张图的显存代价可接受）
2. 加一张 `bs → padded_bs` 查表（照抄 vLLM `_compute_bs_to_padded_graph_size` 的 12 行）：**正好命中就不 padding，落缝里就上取整**
3. 保留"超过最大尺寸退 eager"这一条（这一条是对的，行业也这么做）

**为什么这条最值钱**：我们实测 B=4/4K 时投机净亏 0.71×，一部分原因就是 batch 稍大就掉进 eager 回退（Python 逐层发射 kernel 的开销在 3090 上很显著）。**padding 到 8 比退 eager 划算得多**。

### 第二条：★ padding 行的四件套（slot / block_table / seq_lens / query_start_loc）

**他们怎么做**（vLLM，四个位置同时处理）：

| 位置 | 填什么 | 文件:行 |
|------|--------|---------|
| `slot_mapping` 尾部 | `-1`（`PAD_SLOT_ID`） | `vllm/v1/worker/gpu_model_runner.py:3899` |
| `block_table` 尾部 | `0`（`NULL_BLOCK_ID`，block 0 保留给 padding） | 同文件 `:2300` |
| `seq_lens` 尾部 | `0` | 同文件 `:~5693` |
| `query_start_loc` 尾部 | 填最后一个累计值（拍平，保证非递减） | 同文件 `:2028` / `:5696` |
| 另外 | `is_padding` bool mask 传进 forward context | `_prepare_padding_mask` `:3268` |

**-1 为什么安全**（这是整套的基石）：`vllm/v1/attention/ops/triton_reshape_and_cache_flash.py:65` 里 `if slot_idx < 0: return` —— **kernel 直接跳过，不写 KV**。

**我们的差距**：我们目前是"匹配不上退 eager"，**完全没有 padding 路径**，所以这四件套一个都没有。

**可抄的具体动作**：加 padding 时**必须同时做这四件事**，缺一个就会出静默 bug：

- 只填 `slot_mapping=-1` 忘了 `block_table` → attention 可能读到越界 block
- 只填 `slot_mapping=-1` 忘了 `seq_lens=0` → attention 会把 padding 行的 KV 当成真实上下文算进去
- 忘了 `query_start_loc` 拍平 → **FA 会因为非单调直接崩**（vLLM 源码注释明确写了 "as kernels like FlashAttention requires that"）

### 第三条：★ draft 和 target 共享 KV 池 + 权重

**他们怎么做**：

- **vLLM**（`vllm/v1/spec_decode/llm_base_proposer.py`）：
  - `:1689-1707` `validate_same_kv_cache_group` —— 断言所有 draft attention 层属于同一个 KV cache group
  - `:1711-1735` `initialize_attn_backend` —— `self.kv_cache_gid = gid`，**draft 直接用 target 那个 group 的 KV 池**
  - `:1400-1401` `_maybe_share_embeddings` + `_maybe_share_lm_head` —— **共享 target 的 embedding 和 LM head 权重**
- **SGLang**（`python/sglang/srt/mem_cache/unified_draft_pool.py:1-3`）：
  - `UnifiedKVPool` + `UnifiedDraftKVPool` —— draft 的 KV 是 target 那块物理 buffer 的 **strided view**，"same pages, same slot ids, same v2p table as the target -- one allocation, one free, one relocation"

**我们的差距**：我们的 draft 有**自己独立的 KV cache**，加载 draft 让主模型可用 KV 容量从 **88,832 掉到 45,312 token（-49%）**。

**可抄的具体动作**（按收益/风险排序）：

1. **权重共享（最容易、收益立竿见影）**：我们的 draft 是 Qwen3-0.6B，**如果它和 target 的 vocab / hidden 维度对得上，embedding + LM head 可以共享**。Qwen3-4B 的 vocab 是 151936 —— 两份 vocab 矩阵的浪费是可观的。注意 SGLang `eagle_worker_v2.py:252` 的约束：**共享要求 vocab 一致**。
2. **KV 池共享（中等难度）**：我们已经在给 draft 单独算 KV 池，改成"draft 复用 target 池 + 每请求多留 `1+K` 个槽位"（vLLM 的做法），能省掉整个独立池的开销。注意 vLLM 是**逻辑共用**（同一 group），SGLang 是**物理共用**（同一 buffer 的 view）—— 后者更难但更省。
3. **不管选哪条，都要按 `1 + K` 预留 KV**（vLLM `scheduler.py:347-358` 的 `_spec_decode_step_blocks`）—— 我们现在的 49% 损失里，有一部分是**预留策略不对**而不是真的不够。

**注意**：我们的 0.6B draft 参数量本身不大（KV 池按 28 层 × ... 算），49% 的容量损失说明**问题主要出在"独立池 + 池大小按 target 的公式算"这个组合上**，而不是 draft 本身真的需要那么多 KV。
