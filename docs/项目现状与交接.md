## 1. 约束地图（决定一切方向的实测底数）

**普通 decode 的 GPU 时间分解**（B=1、ctx=4096、CUDA Graph 开）：

| 类别 | 占 device 时间 | 说明 |
|---|---:|---|
| **GEMM / 线性层** | **79.27%** | batch=1 时是**纯权重流式**：8 GB / 10.5 ms = **763 GB/s = 3090 峰值带宽的 81%**，基本跑满 |
| attention | 9.24% | 随 ctx 上升：8.12% / 9.24% / 14.68% @ ctx 1024 / 4096 / 8192 |
| elementwise / norm / rope | 8.37% | |
| 采样 / KV 写入 / memcpy / 其他 | ~3% | 采样仅 **0.81%** |

**prefill** ≈ 65 TFLOPS，**贴着 3090 的 bf16 峰值（约 71）→ 没有空间**。

**三条推论**：
1. decode 想显著变快，**只能让权重变小**（量化）——那 79% 是墙；
2. prefill 没空间 → 「长 prompt 堵 decode」只能靠**调度**解决；
3. **吞吐的杠杆是并发**：B=1→B=4 时效率涨 3.6 倍，而 B=4 时算力只用掉峰值的三十分之一。

## 2. ★ 量化部分（本次重点）

### 2.1 为什么做它

上面的约束地图说得很直白：**decode 的 79% 是"每步必须把权重从显存读一遍"，而且已经贴着硬件带宽极限**。
所以 decode 想显著变快，**只有让权重变小这一条路**。attention 那条线上界实测只有 **+3%**（已否掉）。

### 2.2 走到这一步的路径（三次调整，都是被数据推着走的）

| 轮次 | 做什么 | 结果 |
|---|---|---|
| **Q1** | 量化 **草稿的 FFN**（gate/up/down，84 个模块） | 每轮 **−3.6% ~ −4.5%**，**未达门槛**（事前定的 ≥+20%）→ 如实报负结论 |
| **Q1.5** | 文献调研 | 推翻了两条假设（见 2.6） |
| **Q2** | 把范围扩到 **草稿的全部线性层**（q/k/v/o + gate/up/down） | 每轮 **−6.4% ~ −7.1%** —— **比 Q1 翻倍** |
| （取消） | 量化 **target** | 用户决定不做：**量化 target 会让普通解码也变快，从而削弱投机的相对优势**；而且 target 是"参考标准"，动它就要改写"无损"的口径 |

### 2.3 Q2 的结果（目前量化最好的结果）

**做了什么**：把 draft（Qwen3-0.6B）的**全部线性层**权重做 **8 位对称 per-channel 量化**（W8A16，
激活保持 BF16，**不需要校准** —— 文献证实 8 位下换方法没有差异），配一版**融合反量化**的 GEMM。
**target（Qwen3-4B）一个字节没动。**

★ **对 `nanovllm/` 是零生产代码改动** —— 复用上一轮交付的配置开关，换个 `quant_config.json` 就完成范围扩大。

| 负载 | 每轮耗时 bf16 → int8 | **配对比值** | 一致性 | 噪声地板 |
|---|---|---:|---:|---:|
| 自然长文 B=1/1K | 34.67 → 32.31 ms | **0.9293** | **9/9** | 2.47% |
| 自然长文 B=1/4K | 39.17 → 36.61 ms | **0.9328** | **9/9** | 1.36% |
| 合成素材 B=1/1K | 37.81 → 35.09 ms | **0.9277** | **9/9** | 5.93% |

### 2.3.1 ★★ 为什么量化之后显存反而占得更多？（重点展开）

**这是本项目最反直觉的一条负结论**：量化明明把权重从 8.68 GB 降到 8.28 GB（**省了 0.4 GB**），
但**可用的 KV 池反而少了 4 块**。必须讲清楚，否则"量化省显存"这句话会被误用。

#### ① 机制：省下的权重显存【不会自动】变成 KV 池

nano-vllm 的 KV 池不是"固定分配"，而是**把剩下的显存全吃掉**：

```
KV 池块数 ≈ ( 总显存 × 0.9 − used − peak + current ) / 每块字节

  total      = 卡的总显存（24 GB）
  used       = 【驱动级】占用（不是 PyTorch 缓存分配器管的那些）
  peak       = 加载/预热期间的【峰值】分配
  current    = 当前 PyTorch 已分配
```

**所以只要公式里另外三项里任何一项变大，权重省下来的钱就被吃掉。**
这是一条"零和"的账 —— 省下来的不等于你的。

#### ② 已确认的主因：split-K 的 fp32 scratch 把 `peak` 顶高了 1.285 GB ★

排查中发现一个**真 bug**（不是量化的锅，但只在量化路径上暴露）：

```
量化路径的 split-K 会把 [SPLIT_K, M, N] 的 fp32 scratch 全量分配
   → 在 warmup 的 prefill（M 很大）时能吃掉 200 MB+
   → 把 peak 顶高【1.285 GB】
   → 直接让 KV 池少了 【11 块】
```

**修法**：限制「split-K 只在 `M ≤ 64` 时使用」。
**效果：KV 池从 −11 块回到 −3 块**（找回了 8 块）。

**这一条是本次排查最大的收获** —— 它说明"显存变少"里**大部分是一个可修的实现问题**，不是量化的固有代价。

#### ③ 剩下约 0.16 ~ 0.19 GB 的"驱动级占用"：【未归因，两次复现都没找到来源】

```
Q1（只量化 FFN）： used 多出 0.16 GB → KV 池 174 → 171（−3 块）
Q2（全量线性层）： used 多出 0.19 GB → KV 池 174 → 170（−4 块）
```

**两次复现、数值稳定，但来源没找到。** 候选解释（**都是猜测，未验证，不要当结论写**）：

| 候选 | 为什么可能 | 为什么存疑 |
|---|---|---|
| **CUDA context 里多了量化 GEMM 的 kernel 模块** | 每个 Triton kernel 编译出的 cubin + 启动元数据都要驻留在 context 里，且 Triton 常为不同 shape 编多份；这类开销**只出现在 `nvidia-smi` 的 used 里、不出现在 `torch.cuda.memory_allocated()` 里** | 量级是否真有 0.16 GB 未测 |
| 量化路径调了不同的库、预留了更多 workspace | 换了 GEMM 实现就可能换 workspace 需求 | 未测 |
| 加载期的瞬时重叠（bf16 与 int8 权重同时存在）被算进 `peak` | 我们是"载入 bf16 → 在内存里量化 → 留 int8" | 若为真，量级应该远大于 0.16 GB，与实测不符 |
| 显存碎片化 / 分配顺序变化 | 分配尺寸变了，落址和碎片都变 | 未测 |

#### ④ 所以诚实的结论是

```
✅ 可以说：权重确实省了 0.4 GB
✅ 可以说：KV 池变少里【大部分（11 块里的 8 块）是一个可修的 split-K scratch bug】，已修
❌ 不能说："量化能省显存" —— 在当前这套预算口径下【净效果是负的（−4 块）】
❌ 不能把剩下的 0.16~0.19 GB 归因给某个具体机制 —— 【没查出来】
```

**要真正把显存挣回来，需要"直接加载预量化 checkpoint"**（省掉载入 bf16 再转换的过程），
**这一步没做**。

#### ⑤ 这条结论对外的写法

> 「量化让权重减少 0.4 GB，但 KV 池容量反而下降 2.3%——因为 KV 池是按
> `0.9×总显存 − 驱动级占用 − 峰值 + 当前分配` 算出来的**剩余量**，
> 权重省下的不会被自动继承。排查中发现并修复了一处 split-K 的 fp32 scratch
> 把峰值顶高 1.285 GB 的实现问题（找回了 8 个块）；**剩余约 0.19 GB 的驱动级占用
> 未能归因，如实挂账**。」

**★ 最有价值的一条结论**：

```
                  普通解码      投机      投机 ÷ 普通
draft BF16        77.9         109.8      1.411×
draft INT8        77.9         124.7      1.601×     ← 【变大了】
```

普通解码 **100% 是 target**（没动 ⇒ 一分不变），而投机一轮的权重流量里 **6/7 是 draft**（draft 跑 6 次）。
所以**量化 draft 让投机的相对优势变大**，与"量化 target"正好相反。

### 2.4 一个很漂亮的自查（可信度的来源）

用**同一把尺子**回头重跑 Q1 的 FFN 配置、复现了上一轮的数字；然后算「**每省 100 MB 换来多少 µs**」：

```
只量化 FFN：      87 / 96 µs
量化全部线性层：   89 / 96 µs      ← 两档完全一样
```

→ **证明这一刀就是"纯字节账"，没有别的隐藏机制。**

### 2.5 还没做的（量化的剩余空间）

```
① 草稿的 embedding / lm_head（占草稿权重 26%）还没量化
② 4 位（W4A16）—— 8 位这一档已到头（文献证实 ±0.005），要更大幅度必须下 4 位
   上界：B=1/4K 从 1.59× 提到 2.21×；代价：4 位真的需要 AWQ/GPTQ 那类校准
③ ★ 一个必须提防的坑：LLM.int8() 报告 hidden ≤2560 时朴素 int8 路径反而更慢（0.24~0.53×）
   我们的 4B 是 2560、草稿是 1024，都在区间内 —— 目前的"int8 存储 + 反量化融合"已绕开，改实现前必须先测
```

### 2.6 文献调研推翻了三条假设（已存 `docs/量化文献调研.md`）

| 假设 | 谁提的 | 结论 |
|---|---|---|
| "FFN 比 attention 损害小" | 用户 | ❌ 我们自己实测就否了（attn 反而更耐） |
| "我们的方法太粗糙，有方法空间" | 主 agent | ❌ **被否**。有论文**在 Qwen3-0.6B 本体上**测：RTN8 / g128-RTN8 / GPTQ8 / AWQ8 全部 ±0.005 内 —— **8 位下换方法没有差异** |
| "挑安全的层量化（中间 20 层）" | 双方共同 | ❌ **被否**。损伤是**弥散**的；**"把预算花在全局粒度上，比保护关键层好 21~52 个点"** |

**结论：8 位这一档已经到头了，没有优化空间。要更大的收益必须下 4 位。**

  · 两条负结论：显存是负的（KV 池 174→170 块）；B=4 测不出（噪声地板 58~60%）
  · 没做：草稿的 embedding/lm_head（占 26% 字节）；4 位量化；target 量化（用户决定不做）
  · 文献已确认：8 位下换方法无差异（±0.005）、损伤弥散不要挑层、全局粒度优于保护关键层
