### C1. CUDA Graph 把"实现正确但更慢"的投机解码翻正

- **一句话版**：在 nano-vllm 上实现线性链投机解码；定位出瓶颈是 **per-step 固定开销而非算法**，
  用 CUDA Graph 覆盖两条前向，单请求吞吐 **+61%**（**不拍图时反而慢 32%**）。
- **展开版**：
  "上一轮已经把投机解码实现对了（无损性单测全过），但速度是 **0.68×，净亏**。
  我先看'每步产出'有没有变 —— 每步 3.77 个 token 变成 3.82 个，**几乎没变**，
  说明算法没问题，问题在每步耗时（33.2 ms → 12.8 ms）。
  于是给 draft 前向和验证前向**各拍一张静态形状的 CUDA Graph**，
  单请求吞吐从 82.3 提到 132.5 tok/s。**把符号翻正的不是接受率，也不是算法，是 CUDA Graph。**"
- **量化结果**：普通 decode **30.6 → 79.6 tok/s（2.6×）**（每步 33.2 → 12.8 ms）；
  draft 前向 **24.8 ms → ~2 ms**；验证前向 **36 ms → ~14 ms**；
  单请求投机 **82.3 → 132.5 tok/s = 1.61×**。
  口径：**B=1、单条 256 token 的自然代码 prompt、k=6、α=0.77、`enforce_eager=False`**。
- **边界（必须一起说）**：
  - 这个 1.61× 是"**投机 + 拍图**"的联合结果，**不是投机单独的功劳**；
    同一配置**不拍图只有 0.68×**（20.8 tok/s）。
  - 加速比**强依赖接受率 α**，**必须连报**。α=0.77 才有 1.61×。
  - **B=1 的结论不能外推到 B=4**（见 C5、D 表）。
- **证据**：`scripts/bench_spec.py`；`README.md` §2；`HANDOVER.md` §4/§9；
  `docs/优化台账.md` §2.1/§2.2。

### C2. 手写 paged decode attention：Triton 三版递进 + CUDA 版赢过 flash-attn

- **一句话版**：手写 paged decode attention：Triton 三版递进到 **523 GB/s（实测带宽天花板的 62%）**，
  再用 CUDA `mma.sync` + `cp.async` 三级流水重写到 **648 GB/s（77%）**，
  比 flash-attn 快 **1.31–1.47×**。
- **展开版**：
  "先算 roofline 证明它是**纯访存瓶颈**（算术密度 4.0 FLOP/Byte，拐点 38）。
  然后三步走，每一步的动因都来自上一步的实测数据：
  v1 → v2 消掉 GQA 的 4× 冗余读；v2 → v3 用 split-K 把并行度从 8 个 program 提到 64 个。
  最后用 CUDA 重写，拿到 Triton 表达不了的两件事：**手写 shared memory 布局 + `cp.async` 三级流水**。
  `cp.async` 三级流水**一步就值 1.43×**，而这个在 Triton 里改 `num_stages` 毫无反应。
  **占用率只有 8% 却跑出 77% 带宽，说明 `cp.async` 把在途访存请求数和 warp 数解耦了。**"
- **量化结果**（**device time，不是墙钟**；ctx=4096、B=1、Qwen3-4B 配置）：

  | | 纯 kernel 时间 | 带宽 | 占实测天花板 842 |
  |---|---:|---:|---:|
  | Triton v1 | 191.4 µs | 86 GB/s | 10.3% |
  | Triton v2 | 111.2 µs | 150 GB/s | 17.8% |
  | **Triton v3** | **31.4 µs** | **523.8 GB/s** | **62.2%** |
  | flash-attn（对照） | 41.2 µs | 410 GB/s | 48.7% |
  | **CUDA 主 kernel（st3）** | **25.87 µs** | **648 GB/s** | **77.0%** |
  | **CUDA 完整调用（融合归约）** | **28.03 µs** | — | **1.09× vs Triton v3** |

  对 flash-attn：**Triton v3 快 1.31×**（主 kernel 31.4 vs 41.2）、**CUDA 完整调用快 1.47×**（28.01 vs 41.2）。
- **★ 边界（必须一起说）**：
  - **这个 kernel 没有接进引擎** —— 因为 Amdahl 上界只有 **+3%**（attention 只占 device 时间 8–9%），
    达不到自定门槛，**主动降级了这条主线**。别写成"引擎因此变快了"。
  - `25.87 µs` 是**主 kernel**，`28.01 µs` 是**完整调用**（含归约）——
    **不能拿 25.87 去跟 flash-attn 的完整调用比**。
  - 带宽分母是**实测流式天花板 842 GB/s**（纯 copy 512 MB 测出），不是规格值 936。
  - 所有时间都是 **`torch.profiler` 的 device time**；**本机 ncu 被禁**（无 sudo），
    拿不到 `dram__bytes_read`，**不要说成"ncu 量的"**。
  - sm_86 **物理不支持** TMA / TMEM / 2-SM cluster，只讲得了原理。
- **★ 附带两个"被自己的数据证伪的假设"**（面试很值钱）：
  1. "Triton 的 M 补到 16、GQA 只有 4，所以 75% 的 MMA 行白算" —— **错**。
     真写了个"正好算 4 行"的 FFMA 版，**反而慢 1.84 倍**（47.73 vs 25.87 µs）。
  2. **只读探针**（访存逐字节相同、mma 全删）跑 **23.08 µs / 727 GB/s / 86.4%** ⇒
     **整个张量核 + softmax + 同步加起来只值 2.79 µs（10.8%）** ⇒ warp specialization 是低价值目标，停手。
- **证据**：`nanovllm/kernels/README.md`；`scripts/bench_paged_decode.py`、`bench_cuda_paged_decode.py`、
  `sweep_cuda_paged_decode.py`；`nanovllm/kernels/paged_decode_attn_cuda.cu`（1,602 行）。

### C3. 端到端统一验收：一张可复算的消融表 + 把边界钉死

- **一句话版**：建立**端到端统一验收**：把 8 个优化档位在同一份代码、同一组负载、
  同一套口径（串行/单卡/自然长文/`runs=5`/含噪声地板）上跑成一张消融表，
  一条命令可重跑；跑出可复算的整体提升 **1.74×–5.82×**，并用**同一张表**把它的边界钉死。
- **展开版**：
  "项目最大的缺口是：各优化的数字散在不同轮次、口径不一（有的 B=1 有的 B=4；
  有的 device time 有的墙钟；接受率有的 0.84 有的 0.99），**互相不可比**。
  我把 `U → G → C → S1 → S2 → S4 → S5 → S6` 这条逐级加一项的阶梯放在同一把尺子上跑，
  写成一条命令可重跑。
  跑出来的结论有两面：整体提升 **1.74×–5.82×**；
  但**最大的一截来自 CUDA Graph（2.4–3.6×），不是投机** ——
  投机那一段单独看是 **1.60×（B=1/1K）→ 0.71×（B=4/4K，即 batch 大时净亏）**。
  此前流传的'B=4 提速 1.19×'**只在接受率≈0.99 的合成素材上成立**。"
- **量化结果**（`tok/s(maxB)`，自然长文，`runs=5`，噪声地板 0.05%–1.06%）：

  | 负载 | `U` 普通解码 | `G` +CUDA Graph | `S2` 默认投机 | `S6` 全优化 | **`U→S6`** | **`G→S6`（只算投机）** |
  |---|---:|---:|---:|---:|---:|---:|
  | B=1 / 1K | 21.7 | 79.2 | 121.4 | 126.5 | **5.82×** | 1.60× |
  | B=1 / 4K | 21.7 | 77.9 | 65.1 | 86.3 | **3.97×** | 1.11× |
  | B=4 / 1K | 100.7 | 289.1 | 257.5 | 279.2 | **2.77×** | **0.97×** |
  | B=4 / 4K | 100.9 | 245.1 | 166.4 | 175.1 | **1.74×** | **0.71×** |

  逐档边际：`U→G` **3.64 / 3.58 / 2.87 / 2.43×**（**全表最大的一刀**）；
  `C→S1` 批量 draft **1.86 / 1.56×**（只在 B>1）；`S1→S2` 验证图 **1.42 / 1.29×**（只在 B>1）；
  `S4→S5` draft int8 **1.05–1.33×**；`S5→S6` 直载 **1.000–1.004×（≈0）**。
- **★ 边界（必须一起说，三条）**：
  1. **提升的大头不是投机，是 CUDA Graph**（`G/U = 2.43–3.64×`）。
  2. **B=4 的自然长文下，整条投机栈比"普通解码 + 拍图"更慢**（`G→S6 = 0.71×`）。
     **投机优势随 batch 缩小是固有性质**（验证要付 `B·(k+1)` 的算力）。
  3. **`U` 这个零点本身带 ±4% 不确定度**（它是 eager、CPU-bound）⇒ `5.82×` 的分母不该当成精确值。
  4. **接受率是隐藏自变量**：自然长文 α 落在 **0.609–0.777**；ctx=1024（α≈0.77）是 1.60×，
     ctx=4096（α≈0.68）只有 1.11×。
- **★ 这张表还顺手挖出 6 条以前没记录过的事实**（都不需要新算法）：
  ragged tail 让"墙钟÷轮数"偏差可达 **1.6×**；`B=3` 没有图 ⇒ 整条 eager；
  `U` 的 TTFT 被 draft prefill 污染（纯 target 是 45.7 ms，表里是 77.8）；
  滑窗的 draft prefill 重算整个窗口、不认前缀缓存；`U` 作为基线带 ±4%；
  运行期关滑窗在 B=4 不等价。
- **证据**：`docs/端到端验收.md`；`scripts/acceptance_matrix.py`（一条命令重跑整张表）；
  原始日志 `docs/evidence/端到端验收-20261011/`。

### C4. 抓出十多个"静默 bug"（不报错、只悄悄出错）

- **一句话版**：在引擎里抓出**十多个静默 bug**（不报错、只悄悄出错），
  最重的一个让 **prompt ≥ 384 token 直接崩溃**、意味着此前所有长上下文结论都无效；
  每个 bug 都有**构造性证据 + 回归测试**，测试从 37 项涨到 **514 项**。
- **展开版**：
  "投机解码有一条硬性质：输出分布必须严格等于目标模型的分布。这些 bug 里有两个直接破坏它。
  最有代表性的两个：
  (1) **draft 侧传了概率、验证时又被 softmax 一次** —— 在 151936 词表上被压成近似均匀分布
  （真分布 max 0.597 → 二次 softmax 后 1.23e-05）。我构造了一个 `q ≡ p` 的算例
  （此时正确实现必须全部接受）：正确实现接受率 **1.0000**，原实现 **0.8895**。
  (2) **候选 j 被拿去和 target 第 j+1 行比**（整体错位一行）—— 接受率被从应有的 0.84 打到实测 0.16。
  现有的单测查不出来，因为所有多行用例的 target 各行都是**完全相同**的，索引偏移多少都没差异；
  我补的合成算例（各行峰不同）**第一次跑就暴露了**。
  另外还有一个**终止判据用 `==` 而不是 `>=`** 的 bug，让序列**无限生成** ——
  `max_tokens=64` 跑到 300 步 / 572 token 还没停，在 benchmark 里表现为'draft 模式一卡就是几百秒'。
  以及一个**前缀缓存的进度契约缺陷**，让 **prompt ≥384 token 直接崩** ——
  它意味着**此前所有引擎级长上下文结论都无效**。"
- **量化结果**：
  - 静默 bug 数量：README 第二节 5 个 + 台账 §2.4 / §2.5 / §2.7 / §2.10 与后续轮次共**十余个**。
  - 测试规模：**37 → 115 → 149 → 220 → 251 → 336 → 412 → 455 → 514 项**（纯 CPU；
    本机 py3.13 与服务器 venv py3.10 双跑一致）。
  - 边界表：修复前缀缓存契约后 **255/256/257/383/384/385/1024/2048/4096/8192 全通**；
    修复前 256/384/512 崩。
- **★ 边界**：这些 bug 的价值在"**发现了什么**"，**不在"快了多少"** ——
  阶段 0 的四项正确性修复**无性能收益**。别把它们写成"性能优化"。

### C5. 量化 draft（INT8，target 一个字节不动）—— 核心叙事：**量化 draft 让投机的相对优势变大**

- **一句话版**：给草稿模型做 W8A16 权重量化（融合反量化 GEMM，**不需要校准**），
  端到端 **+6.9% ~ +7.8%**，精度只 **+0.455% PPL**，**接受率不变**，
  且 **target 一个字节没动** ⇒「相对 BF16 target 无损」这句口径一个字都不用改。
- **展开版**：
  "第一刀只量化 draft 的 FFN，每轮只快 3.6%–4.5%，**没达到我事前定的 +20% 门槛**。
  我没有换方法，而是算了一笔字节账：FFN 只占 draft 权重 44.3%，draft 又只占一轮权重流量 47%
  ⇒ 一轮总字节只降 9.9%。**所以不是方向错，是剂量不够。**
  第二刀扩到 draft 的全部线性层（196 个模块），**对 `nanovllm/` 是零生产代码改动** ——
  换个 `quant_config.json` 就完成，因为上一轮的开关原样够用。
  结果是每轮 **−6.4% ~ −7.1%**，B=1 四档 **36/36 配对全胜**（符号检验 p≈1.5e-11）。
  **最有说服力的一条是内部一致性**：用同一把尺子回归重跑第一刀的配置，
  看'每 100 MB 省多少 µs'—— 两档**完全一样**（87/96 vs 89/96）⇒ 证明这就是纯字节账，没有别的机制。
  另外，**量化 draft 会放大投机的相对优势**（1.411× → 1.601×），
  因为投机一轮的权重流量里 6/7 是 draft —— 这和'量化 target'正好相反。"
- **量化结果**：

  | 项 | 数字 | 口径 |
  |---|---|---|
  | 每轮耗时 | **−6.4% ~ −7.1%** | B=1 四档 36/36 配对全胜，p≈1.5e-11 |
  | 端到端 tok/s | **+6.9% ~ +7.8%** | 接受率不变 ⇒ 就是 1/配对比值 |
  | 精度 | **+0.455% PPL** | wikitext-2，122,760 token |
  | 接受率 | **Δα = −0.00235 ± 0.00349（不显著）** | 恒等式 `α = 1 − TV(p,q)`，**12,282 个位置** |
  | 省下的字节 | draft 权重 1.192 → **0.752 GB**；线性层字节 **−36.9%** | — |
  | 投机/普通 | **1.411× → 1.601×** | 普通解码 100% 是 target，一分没变 |

- **★ 边界（必须一起说）**：
  1. **只量化 draft，target 一个字节不动。** 这是"无损"口径能一字不改的前提。
     **量化 target 会让普通解码也变快，从而削弱投机的相对优势**（实测 1.601× → 1.411×）——**没做**。
  2. **接受率不变**这个结论**不是**用引擎的少量样本得出的（引擎只有 384 样本，SE 2.2% 分不出），
     是用恒等式在 12k 位置上算的。**别写成"引擎实测接受率不变"。**
  3. **显存账曾经是负的**：量化后权重省了 0.4 GB，**但 KV 池 174 → 170 块（−2.3%）** ——
     后来由"构造期直载 int8"解决（见 C8）。**单独讲量化时不要声称省了显存。**
  4. **B=4 自然档分辨不出**（噪声地板 58%–60%）⇒ 这个收益只在 **B=1** 上被证明。
  5. **draft 的 embedding / lm_head 没量化**（占 draft 权重 26%）；**prefill 侧代价未测**。
- **★ 两条推翻事前假设的发现**（面试加分）：
  1. **"FFN 比 attention 更耐量化"不成立** —— 只量化 attention **+0.132%** vs 只量化 FFN **+0.316%**，
     **attention 反而更耐量化**；事前"只量化 FFN"这个切法**切错了维度**。
  2. **"`down_proj` 最敏感"只在 0.6B 上成立**；4B 上它最不敏感
     ⇒ **敏感度排序是模型相关的，不能跨模型外推。**
- **证据**：`docs/优化台账.md` §2.10/§2.11；`docs/W8A16量化-开发记录.md`；
  `scripts/eval_ppl.py`、`bench_draft_int8.py`、`bench_int8_gemm.py`、`check_quant_equiv.py`。

### C6. 修复前缀缓存的"负优化"：命中反而比不命中慢 3.6 倍

- **一句话版**：发现前缀缓存存在**负优化** —— 命中长前缀时会触发一次全量草稿补齐，
  **单个 decode step 阻塞 17.3 秒、占端到端墙钟 85%**；
  用草稿侧的块级 KV 有效性追踪修复后补齐降到 22 token、吞吐 **6.1×**，
  前缀缓存从**净亏翻成净赚 1.68×**。
- **展开版**：
  "4 条请求共享 4096-token 前缀时，单个 decode step 阻塞 **17.31 秒**、占端到端 **85%**，
  吞吐只有 12.53 tok/s —— 而**冷缓存（完全不命中）有 45.5 tok/s**。
  也就是说：**命中了比不命中还慢 3.6 倍，这个功能是负债。**
  根因是命中 target 的前缀缓存 ≠ draft 那把 KV 也有效，而当时的代码触发了全量补齐。
  **正确修法不是'假设有效'**（那会静默输出垃圾），而是给 draft 做**它自己的**块级有效性追踪。
  为了证明那道守卫真的在挡东西，我做了**承重性反证**：故意绕过它直读脏 KV ——
  接受率从 0.9 **崩到 0.175–0.470**、argmax 一致率 0.333。"
- **量化结果**：补齐 token **16660–16665 → 22–31（−99.8%）**；
  吞吐 **12.53 → 76.63 tok/s（6.1×）**；
  参照冷缓存 45.5 tok/s：**修复前净亏（12.5 < 45.5）→ 修复后净赚 1.68×（76.6 > 45.5）**；
  正确性：复用路径输出 == 全量补齐路径输出，**3/3 输出 md5 完全一致**。
- **★ 边界**：这个 6.1× 是**"把一个 bug 修掉"**带来的，**不是"我加了一个缓存"** ——
  缓存本来就在，是我们把它从负债修成了资产。别写成"我实现了一个前缀缓存"。
- **证据**：`docs/优化台账.md` §2.6；`nanovllm/engine/block_manager.py` 的
  `Block.draft_hash` / `mark_draft_valid` / `draft_valid_cached_blocks`。

### C7. 草稿滑窗 + 解耦显存分配

- **一句话版**：给草稿模型做**纯滑窗 KV**（只留最近 5 个块 = 1280 token，与序列总长无关）：
  草稿显存 **4.73 GiB → 0.55 GiB（−88%）**，主模型 KV 容量 **44,288 → 75,008 token（+69%）**，
  16K 下并发 **2 → 4 条**；首 token 延迟只贵 **0.3 ms**。
- **展开版**：
  "draft 和 target 原来**共用块号**，导致块数必须相等、无法缩小，
  target 可用容量被 draft 吃掉近一半。我做了两件事：
  ① 给草稿做**块级环形缓冲的滑动窗口**（只保留最近 M 块）；
  ② **解耦草稿的显存分配**，让它有自己的独立编号。
  有一条很干净的判据可以**先算后测**：`M × max_num_seqs < 普通投机的池块数（173）` 才省显存 ——
  四个实测点全部对上，连反面（M=65 时 target 池掉到 106 块、−39%）也测到了。
  **长上下文才是它的主场**：16K 下请求 4 并发时，普通投机**只能真正跑 2 条**（第 3、4 条排队到 TTFT 13.6 秒），
  滑窗能跑满 4 条。
  过程中我用**逐次前向逐位对拍**定位并修掉 3 个静默 bug，其中一个让补齐前向的可见上下文从 1031 个 token 被砍到 7 个。"
- **量化结果**（自然长文，`max_num_seqs=4`，`runs=5`）：

  | 项 | 滑窗（M=5） | 普通投机 |
  |---|---:|---:|
  | draft 池 | **20 块 / 0.55 GiB** | 173 块 / 4.73 GiB |
  | target 池 | **293 块 = 75,008 token（+69%）** | 173 块 = 44,288 token |
  | 并发 @8K / @16K | **8 / 4 条** | 5 / **2 条** |
  | α @8K / @16K | 0.6414 / 0.6165 | 0.6688 / 0.6559 |
  | TTFT @8K/B=1 | **91.41 ms（+0.3）** | 91.13 ms |

  **解耦分配本身**：每轮耗时 **0.79–0.86×**、吞吐 **+16~21%**，且**逐位相同、零接受率代价**。
- **★ 边界（必须一起说）**：
  1. **滑窗不是无损** —— 仍有 **4%–6% 的真实截断代价**（α 相对全上下文：8K −4.1%、16K −6.0%，
     5.6σ / 5.4σ）。**别写"无损"。**
  2. **"省显存"是有条件的**：判据 `M × max_num_seqs < 173`，**并发上限一高就翻负**。
  3. **"解耦分配那 +20%" 的具体环节至今未隔离**（已排除"读的 key 变少"和"块表宽度"）。
     **不要写"来自滑窗省上下文"或"连续块"。**
  4. **代价的另一面是 TTFT**：保住接受率的窗口 prefill 很贵（8K 下 W=8448 的 draft prefill 273.9 ms、
     占 prefill 82.8%，TTFT 90.9 → 336.9 ms）。**省显存不是免费的。**
  5. `realign` 与 INT8 / 分块 prefill 的**交互没测**。
- **★ 一条最漂亮的判断**（面试重点讲）：见 F 节的"我推翻了自己"第 1 条 ——
  「开头常驻段 P」的收益 **100% 来自它遮掩了一个 KV 对齐 bug**，修好后**效应反号**。
- **证据**：`docs/优化台账.md` §2.7 / §2.7.3；`docs/长上下文-滑窗容量.md`；
  `docs/P7-D开头常驻段-开发记录.md`；`docs/修复后重定位-开发记录.md`；
  `tests/test_draft_window*.py`、`test_draft_win_realign.py`。

### C8. 直载 int8：把量化的显存账从负翻正

- **一句话版**：量化后 KV 池反而变小（174 → 170 块）；用逐字节账目把设备已用量拆成
  `current + I + O`，实测**分配器之外的增量精确为 0**，改为**构造期直载 int8** 后
  **KV 池 170 → 180 块（+5.9%），并反超 BF16 基线的 174 块**。
- **展开版**：
  "量化让权重真省了 0.4 GB，但 **KV 池反而少了 4 块**，两次复现。
  我第一个猜测是'CUDA context 里多了量化 GEMM 的 kernel 模块'——
  **这个猜测被实测直接否掉**：我把预算时刻的设备已用量拆成三块
  （`current` 已分配、`I` 分配器内保留的空闲、`O` 分配器之外），
  三档的 `O` **逐字节全是 351,797,248，增量精确为 0**。
  损失全部是分配器内 `0.589 GiB` 的保留空闲，而且**恒等于 `inactive_split`**（不可回收的残块），
  `empty_cache()` 也还不回去。
  于是我改成**构造期直载**：整模型 bf16 从未在显存里存在过，逐层把那一层搬上卡算一次量化、算完即弃。
  `I` 从 679 MB 打到 82 MB，**KV 池 170 → 180 块，反超 BF16 基线**。
  因为收益全在 reserved 里，我用**同容量对照**（两档都锁 170 块）证明设备总占用仍低 0.564 GiB。"
- **量化结果**：KV 池 **170 → 180 块（+5.9%）**；`ΔO = 0`（逐字节）；`ΔI = +0.589 GiB`；
  直载 vs 就地（同容量）**−0.564 GiB**；直载权重与就地量化**逐位相同**（112/112 模块）；
  生成 md5 一致；**251 项 CPU 测试全过**；负数对照（真 int8 checkpoint 但不直载 → 必须报错）✅。
- **★ 边界**：
  1. **这一刀的速度收益是 0**（验收表 `S5→S6 = 1.000–1.004×`，落在噪声地板内）。
     **它换的是容量，不是速度。** 别写成"提速"。
  2. **target 侧没接直载**；`per_group` 粒度与 `TP>1` 被显式 assert 挡住（有意不做）。
  3. 直载路径下 `I` = 82 MB（比 BF16 基线的 47 MB 还多 **35 MB**）**来源未查清**；
     碎片的形成序列**没做 allocator snapshot 验证**。
- **证据**：`docs/优化台账.md` §2.12；`docs/显存归因排查报告-20261011.md`；
  `nanovllm/utils/loader.py` 的 `build_model_int8()`；`scripts/check_quant_direct_equiv.py`。

### C9. 调度：分块让路 + 重叠执行混合批（"排在一起" ≠ "同时跑"）

- **一句话版**：把长 prefill 切成块并让 decode 与之**真正并发执行**
  （decode 走 CUDA Graph、prefill 块走 eager，两条 stream），
  解码 ITL **−33.4%**、长 prompt TTFT **−33.2%**、稳态吞吐 **+8.9%** —— **两边都变好，不再是交换**。
- **展开版**：
  "长 prompt 到达时，正在解码的请求被**饿死整个 prefill 时长** —— 那一轮解码请求拿到的 token 数
  **精确为 0**，ITL 尖刺 **310 倍（3.8 秒）**，远超我们事先定的'只有 2–3 倍就收手'的停止线。
  第一版做**分块让路**：把长 prefill 切块、块之间让一整轮给解码，尖刺 **310× → 16.9×**。
  但它是**交换** —— 长 prompt 自己的 TTFT 从 3.7 秒翻倍到 7.5 秒。
  第二版做**重叠执行**：同一个 step 里 decode 走 CUDA Graph、prefill 块走 eager，用两条 stream 真正并发。
  实测 ITL −33%、TTFT −33%、吞吐 +8.9% —— **两边都变好**。因为 decode 是带宽型、prefill 是算力型，资源互补。
  关键是我把**串行版**也做了：`t_串行 = t_decode + t_prefill`，**残差 −0.1 ms** ——
  没有这个**零收益对照**，那个 −33% 就说不清是'重叠'的功劳还是'共批'的功劳。"
- **量化结果**（场景 A：3 条解码 + 突来 1 条 16K）：

  | 指标 | 独占（原始） | 让路式 | 串行共批 | **并发重叠** |
  |---|---:|---:|---:|---:|
  | 解码 ITL max | 3836 ms | 580 | 594 | **455** |
  | 解码 ITL 窗口 p50 | — | 475 | 499 | **317（−33.4%）** |
  | 长 prompt TTFT | **3756** | 7524 ❌ | 7529 ❌ | **5029（−33.2%）** |
  | 稳态吞吐 | 41.74 | 42.46 | 42.46 | **45.45（+8.9%）** |

  深度扫描：第 0 块省 **93.4 ms**（上界的 54.5%）→ 第 14 块省 **203.8 ms（93.1%）**。
- **★ 边界（必须一起说）**：
  1. **分块让路是一笔交换**：解码变好、**prefill 用户的 TTFT 翻倍**。别只报好处。
  2. **"排进同一个 step"本身收益是 0**（串行档实测 `t_串行 = t_decode + t_prefill`，残差 −0.1 ms）。
     **收益 100% 来自重叠，不来自混批。**
  3. **代价**：prefill 墙钟 **+11.5%**（C=1024）；**C≤512 有 p50 反向代价**
     （中位 ITL 12.2 → 60~76 ms）；并发时 decode 自己被拖慢 77.9 → 178.1 ms（净账仍为正）。
  4. **只在"有请求在解码 + 有 pending 块"时生效**；纯 decode step 图命中率不掉。
  5. **场景 B（只有 1 条解码 ⇒ 解码轮仅 32 ms）只 −5.7%** ——
     同一个机制、同一个 CHUNK，收益从 −33% 掉到 −5.7%，只因为被藏的那个前向变小了。
  6. 默认 `spec_graph_bs=(1,2,4)` 下 3 条请求拿不到 B=3 的验证图（既有配置边界）。
- **证据**：`docs/调度优化-迭代过程与思考方式.md`；`docs/P13调度与延迟-开发记录.md`；
  `docs/P15重叠执行混合批-开发记录.md`；`docs/evidence/p15-20261013/`；
  `nanovllm/engine/mixed_batch.py`（168 行，5 条显式不变量 I1–I5）；
  `tests/test_overlap_mixed.py`（43 项）。

### C11. P16：让投机路径的 CUDA Graph 支持"未精确捕获的 batch"

- **一句话版**：让投机路径的两张图支持**未精确捕获的 batch**（向上取整 + 空行补齐）：
  B=3 退回 eager **18~23 次 → 0**，B=3 的验证前向 **40.86 ms → 15.55 ms（2.63×）**，
  而**补 1 行只贵 0.04 ms（0.3%）**。
- **展开版**：
  "投机路径的两张 CUDA Graph 都是**精确匹配** batch 的，而捕获表只有 `(1,2,4)`，
  于是 B=3 的混合 step **整个退回 eager**。
  原版普通 decode 早就在用'向上取整 + 空行'绕开这个，投机路径当时没跟上。
  我照抄了桶选择，但**空行不是'什么都不做'，它会被真的算一遍** ——
  所以四个位置要同时处理：`slot_mapping=-1`（不写 KV）、`block_table=0`、`cu_seqlens_k=0`（读不到 key）、
  `input_ids/positions=0`，并且保证 `cu_seqlens` **单调不减**（flash-attn 的硬要求）。
  **空行的长度该给几，我做成了实验而不是照抄**：三种形状（`k=1` / `k=0` / `q=0,k=0`）
  互相对拍**逐位相同**、都不崩，于是采用 `k=0`（与 vLLM 对齐）。
  最后三条独立证据证明'默认关 = 老行为'，其中最强的一条是**精确桶上 `off ≡ on` 逐位相同** ——
  说明 padding 的代码完全没有扰动原有的精确匹配路径。"
- **量化结果**：

  | 项 | pad 关 | pad 开 |
  |---|---:|---:|
  | `shape_not_captured(B=3,k=6)` | 18~23 | **0** |
  | draft 前向退回 eager | 108~138 | **0** |
  | B=3 验证前向耗时 | **40.86 ms**（eager） | **15.55 ms**（补进 B=4 的图） |

  **补 1 行的 B=3（15.55 ms）与精确命中的 B=4（15.51 ms）只差 0.04 ms**；
  全量 CPU 测试 **514/514**。
- **★ 边界（必须一起说）**：
  1. **重档边界**：当批里混进一条 ~16K 的长序列时，验证前向变成 GPU 工作主导，
     图能省的固定开销**从 25 ms 缩到 ~2 ms**（B=3：eager 50.29 → 图 47.51，只有 **1.06×**）。
     **这不是 padding 造成的** —— 精确命中、`padded=0` 的 B=2 同样掉到 1.05×。
     即便如此，**补进图仍严格优于 eager**。
  2. **默认仍是 `(1,2,4)`**，没有改 —— 改默认会让"默认关"不再等于老行为。
  3. **桶配置 vs padding 二选一没定论**：扩到 `(1,2,3,4)` 也能把退回归零（零浪费命中）。
  4. **端到端 token 序列不一致这个对照不成立**（两档步数不同、随机采样），
     **既不能证有偏也不能证无偏**。
  5. draft 图的耗时**没单独测**。
- **证据**：`docs/P16图形状padding-开发记录.md`；`nanovllm/spec_decode/graph_pad.py`；
  `tests/test_graph_pad.py`（59 项）；`scripts/p16_graphpad_probe.py`、`p16_pad_variant_probe.py`。

### C12. 无损性验证体系（三档证据，别混着说）

- **一句话版**：建立三档无损性验证：用「**TV 距离随样本量收敛**」替代固定阈值，
  并**为投机路径单独测量噪声地板**（避免了把统计噪声误判为分布偏差）。
- **展开版**：
  "无损性有一条硬性质：输出分布必须严格等于目标模型的分布。
  我不设固定阈值，而是看 **TV 距离是否随样本量收敛到 0**：
  N=40,000 时平均 TV=0.00355，N=400,000 时 0.00122，比值 **2.91**（理论 3.16）⇒ 无偏。
  外加两个合成算例直接钉死对齐关系：`q ≡ p` 时必须全部接受（实测接受率 **1.0000**）；
  候选 `j` 必须对齐 target 第 `j` 行。
  第三档是引擎级分布对比，这里有个**方法论陷阱**：**必须给投机路径单独测一个噪声地板** ——
  投机一步产出 3~4 个 token（同一次前向、同一个上下文），序列自相关远强于逐 token 解码，
  有效样本量更小、经验分布天然更散。实测 `TV(draft,draft2)=0.63 > TV(base,base2)=0.53` 正好印证。
  拿跨组的 0.71 直接跟 0.53 比，会得出'超出 34%、可能有偏'的**错误结论**。"
- **量化结果**：N=40k → 400k 比值 **2.91**（理论 3.16）；`q ≡ p` 接受率 **1.0000**；
  draft 固有质量 TV = **0.1655 → α 理论上界 0.8345**；
  引擎级四轮各 4800 token：`TV(base,base2)=0.5315`、`TV(draft,draft2)=0.6325`、跨组 0.514–0.713。
- **★ 边界（必须一起说）**：
  1. **引擎级（第三档）是弱证据**：n=4800 时地板高达 0.5 量级，功效有限，
     **只能说"没发现偏差"，不能说"证明无偏"**。
  2. **分布级无损性从未做过统计检验** —— 已有的只有"逐字节等价"（P7-D 默认路径）+
     "机制上不破坏"（拒绝采样里 `min(1,p/q)` 与 `q` 无关，且 target 侧一个字节没动）。
     ★ **不要把"无损"写成实测结论。**
  3. **不能用低 temperature 做逐 token 对比**（`temperature=0.01` 会把分布压成 one-hot，p 恒为 1.0）；
     **随机采样下逐 token 对比没有意义**，要比 token 频率分布。
  4. GPU 精度确实影响逐 token 一致性（`max|Δlogit| ≈ 0.25`，30 个位置里约 1 次 argmax 不同 ≈ 3.3%），
     **"严格逐 token 一致"这个标准本身过严**。
- **证据**：`docs/优化台账.md` §2.8/§2.9；`tests/test_spec_decode.py`；
  `scripts/check_draft_quality.py`、`check_lossless_engine.py`。

### F2. ★ 三个"我推翻了自己"的故事（每个都能讲 3 分钟）

**① P 轴效应反号：一个 bug 伪装成了机制收益**

- **反馈**：给滑窗加"开头 P 块常驻"，测到它把接受率从 0.404 救到 0.704（**+71%**），
  于是被写进推荐配置 `(P=2, M=5)`。
- **判断**：以为这是"开头锚点"这个机制在起作用。
- **做了什么**：修掉滑窗的 KV 对齐 bug（尾部窗口起点漂移），然后**把整个
  `ALIGN × P × M × ctx` 网格重跑一遍**（32 格 × 3–9 遍，146 次进程）。
- **结果**：`ALIGN=0` 时 `Δ(P2−P0) = +0.2797`（**23.6σ**）；`ALIGN=1` 时 **−0.0188（3.0σ，P 反而更差）**。
  **效应反号** ⇒ P 的全部正收益 = 遮掩对齐 bug ⇒ **推荐配置从 2 个旋钮砍到 0 个**。
- **★ 教训**：判据不是"这项收益有多大"，而是"**把 bug 修掉之后，这个旋钮的效应还在不在**"。
  而且**修完必须问：这个机制还会在什么条件下复发？** —— 本题的答案：**每个块边界**
  （每 256 个生成 token），而且 `ctx` 恰好对齐到块边界时 `out=256` 根本碰不到它。

**② 收益上界算错了 18 倍**

- **反馈**：我把"重叠执行混合批"的收益上界钉成 **一个解码轮 = 12.1 ms**（占实测尾部 3.2%–10%），
  据此**排进"有依据地暂不做"**那一栏。
- **判断（★ 错判）**：我接受了这个上界，依据是"12.1 ms 是实测的"。
  **它确实是实测的，但实测的是普通 decode（`spec_k=0`），而基准场景写的是 `k=6`。**
- **做了什么**：不争，直接搭一个把调度/采样全排除掉的微基准，只量四件事：
  `t(decode)` / `t(prefill)` / `t(串行)` / `t(并发)`。跑之前先做一次**便宜的证伪**：
  把 `num_scheduled_tokens` 临时降到 1（退回普通 decode）再量一次 → **12.04 ms**（复核通过）。
- **结果**：同样的探针在 `k=6 + draft` 下量到 **220.2 ms（18 倍）**。
  修后上界 = `min(解码轮, prefill 块)`，实测每轮可省 **93.4 → 203.8 ms**（占上界 0.545 → 0.931）；
  端到端场景 A：ITL p50 **−33.4%**、TTFT **−33.2%**。
- **★ 教训**：**"收益上界的量级"比"收益是否正确"更容易错，而且更难被发现。**
  写"上界 = X ms"时，必须同时写下 X 是在**什么配置**下量的，并逐项核对
  （batch / k / 是否开投机 / ctx）。本轮对不上的地方正是 `k`。

**③ 假对照：测出"图跟 eager 一样快"**

- **反馈**：P16 第一版计时测出 B=3 的验证前向「图 39.8 ms、eager 39.7 ms —— **图没用**」。
- **判断（★ 差点当成结论写下来）**：以为"这个形状下 CUDA Graph 没收益"。
- **做了什么**：加了一条**独立的"对照组真的生效了吗"的证据** —— 打印
  `verify_graph_hits` / `verify_graph_fallbacks` 计数。
- **结果**：真因是计时循环没按每个 B 重设 `_verify_extra`，**两边都走了 eager**
  （`static_shape_mismatch`）。修好后真值是 **13.7 ~ 15.6 ms vs 40 ms（2.6~2.9×）**。
- **★ 教训**：**任何 A/B 耗时对照都要有一条独立的"对照组真的生效了吗"的证据。**
  同一个坑在 P16 里踩了两次：第一版 draft 对拍 max|Δ| 全是 22~27（看着像大 bug），
  真因是 `propose_batch` 每步采样候选、候选又写进 draft KV 供下一步读，
  **三次对照调用的随机数状态不同** ⇒ 第 2..k 步的输入 token 天然不同。
  复位 RNG + 只比第 0 个候选位置 + 加一条"同路径连调两次"的自洽性检查（实测 0.0）之后，
  数字才落到 0.16~0.22 的正常量级。
  **写对拍脚本时，"哪些量是确定的"必须先想清楚，否则量出来的是仪器的噪声。**

### F3. ★ 三个"我主动不做"的决策（和做了什么一样值钱）

**① 不做 P1：把自写 attention 接进引擎（上界 +3%）**

- 方案把它排为**第一条开发主线**（4–7 人天）。我先算上界：
  attention 占 device 时间 `f = 8.12% / 9.24% / 14.68%`（ctx 1024/4096/8192）；
  Amdahl `S = 1 / ((1−f) + f/s)`，代入我自写 kernel 的实测加速比 ⇒ **端到端上界 +10%、代入后只有 +3%**。
- ⇒ 达不到方案自定的 +5% 门槛 ⇒ **按方案 §6.3 停止条件降级**。
- ★ 这是这个项目**最值钱的一笔判断**：**用自己的测量否掉了自己方案里的第一条主线**。

**② 不做"真混合"（把 decode 与 prefill 塞进同一个 step 的形态本身）**

- 上界 = `min(解码轮, prefill 块)`；而**串行版实测收益为 0**（残差 −0.1 ms）。
- 代价：一轮内混两条执行路径 —— 而这个项目**被这个坑过 3 次**（最典型 `spec_enabled` 门控快照 bug，有回归测试）。
- 替代方案：**让路式分块 + 重叠执行**（一轮内仍只有一种路径，风险低得多），拿到 310× → 16.9× 和 −33.4%。
- ★ **"先做最便宜的等价物"**：在决定写混批之前，先问"有没有更便宜的旋钮"——
  **切块大小**这一个配置项就能把解码 ITL 从 296 ms 压到 82 ms（C=256），
  代价是 prefill 墙钟 +24.5%。**拧旋钮是可逆、可复算、零风险的。**

**③ 不做 P11（拒绝采样融合）与 P14（KV 量化）**

- **P11**：采样只占 device 时间 **0.81%** ⇒ 上限就这么多 ⇒ 不做。
- **P14 KV 量化**：我们**没有 KV 带宽瓶颈，只有容量问题**；
  而且翻面经数据，**172 道题里问 KV 量化的直接题 0 道**（G 桶的 8 道全是权重/激活量化）。
  ⇒ 8–12 人天的投入不值得。
- ★ **加一条**：**不做 target 量化** —— 它会让普通解码也变快，
  **削弱投机的相对优势**（实测 1.601× → 1.411×）。这是主动的选择，不是漏做。

## (g) 与行业对照：我知道自己在行业里的位置

> 依据 `docs/投机解码显存与图-行业调研.md`（2026-10-17 直读 vLLM / SGLang 最新 main 源码，
> 带 commit 号 + 文件行号，不是博客二手）。

### ★ 我们 P16 刚做的事，正是行业的标准做法

| 问题 | vLLM | SGLang | 我们 |
|---|---|---|---|
| 没精确捕获的 batch | `_compute_bs_to_padded_graph_size` 建 `bs → padded` 查表；**正好命中映射到自己（零浪费），落缝里才上取整** | `_pad_to_bucket` 用 `bisect_left` 向上取最近 bucket | **P16 做的就是这个**（`pick_bucket` 语义与 vLLM 完全一致） |
| 什么时候才退 eager | **只有 `num_tokens > max_size`** | 断言 `raw_size <= buckets[-1]`，责任推给调用方 | 一样（b > 所有桶时返回 None，退回 eager） |
| padding 行怎么保安全 | `slot_mapping=-1`（kernel 早退、完全不写 KV）+ `block_table=0`（NULL_BLOCK_ID）+ `seq_lens=0` + `query_start_loc` 拍平 | `out_cache_loc=0` 指向保留槽（写进一个会被丢弃的草稿槽）+ `seq_lens=1` | **四件套 + 单调不减**；★ 空行长度归零是**实测过的**，不是照抄 |

★ **一句话可以在面试里说**："我做完 P16 之后去读了 vLLM 和 SGLang 的源码，
发现**两家用的都是'向上取整 padding'而不是退 eager**，而且 padding 行的四件套处理跟我做的完全一致 ——
**我是先做出来、再在源码里找到同一个设计，这让我确认了自己在正确的路上。**"

### ★ 行业对"batch 大了投机就亏"的答案：**把 K 降下去，降到 0 就是关掉**

vLLM 官方推荐的动态配置：

```
并发 [1, 64]    → K = 3
并发 [65, 128]  → K = 1
并发 [129, 512] → K = 0     ← 不产生 draft token = 投机关闭
```

SGLang 的 `--speculative-adaptive` **默认配置**直接把大 batch 关掉：
`bs ≥ 64` 时 `candidate_steps = [0]`，**强制 0 步**。

**★ 而 vLLM 文档里那段解释，正是我们实测出来的规律**：

> "SD methods need to verify K tokens for each sequence during decoding.
> As BS increases, the effective BS becomes BS×K which increases the compute requirement during verification.
> When this BS×K goes beyond a critical BS then SD negatively impacts the decode speed (TPOT)."

**翻成大白话：batch 大了以后，验证要算的 token 数是 BS×K，这个乘积超过某个临界点，投机就开始拖慢 decode。**
—— 这正是我们验收表里 **`G→S6 = 0.71×`（B=4/4K）** 在行业里的说法。
**我们在自己的引擎上把这个临界点量化出来了。**

### ★ 我们和行业最大的差距：**省显存靠"KV 池与权重共享"，我们还没做**

| | 行业怎么做 | 我们 |
|---|---|---|
| **draft 的 KV 池** | **vLLM**：draft 的 attention 层被塞进**和 target 同一个 KV cache group**（`self.kv_cache_gid = gid`），**draft 复用 target 的 KV 池，不开独立池**。<br>**SGLang**：新的 `UnifiedKVPool` 把 draft 的 lane **融进 target 同一块物理 buffer** —— "same pages, same slot ids, same v2p table as the target"。 | ★ **我们有自己独立的 KV 池**，加载 draft 让 target 容量从 **88,832 → 45,312 token（−49%）** |
| **权重共享** | **vLLM**：`_maybe_share_embeddings` + `_maybe_share_lm_head` —— **把 target 的 embedding 和 LM head 权重共享给 draft**，省掉一份 `vocab × hidden` 的矩阵（Qwen3-4B 约 389M 参数、fp16 下约 780 MB） | **没做**（我们量化了 draft 的线性层，但没共享 vocab 矩阵） |
| **按 `1 + K` 预留 KV** | vLLM `scheduler.py` 的 `_spec_decode_step_blocks`：有投机时每条请求每步按 `1 + K + lookahead` 折成块预留 | **我们的 49% 损失里，有一部分是预留策略不对，而不是真的不够** |

**★ 一句可以在面试里说**："我读 vLLM 和 SGLang 源码时发现，**省显存的正解是让 draft 复用 target 的 KV 池
和 vocab 矩阵，而不是给 draft 开一个独立的池子** —— 我们现在的 −49% 容量损失，一部分就是这个原因。
**这是我从这个项目里带出来的、最明确的一个下一步方向。**"

### ★ 另一个可以直接抄的设计：spec 专用捕获表（小 batch 段更密）

SGLang 给投机场景**单独排了一张 CUDA Graph 捕获表**：

```
非投机： 1, 2, 4, 8, 12 | 16, 24, ..., 256（步长 8）| 272, ..., 496（步长 16）
投机  ： 1, 2, 3, 4, 5, 6, 7, 8（每个都捕）| 10, 12, ..., 32（步长 2）| 40, 44, ..., 64（步长 4）| ...
```

源码注释直接给了理由：`# Spec decoding case: less padding for smaller batch sizes`。

**大白话**：投机在小 batch 时才划算，所以小 batch 段是"主场"；
而 padding 会**多算**（batch 是 5 却按 8 跑，多算 3 条请求的 `1+K` 个 token），
投机本来就多算了 K 倍，再叠 padding 浪费，小 batch 的收益很容易被吃光。
**所以宁可多拍几张图（内存换时间），也要把小 batch 段做密。**

⇒ 我们的 `spec_graph_bs = (1,2,4)` 只有三个桶，**这正是 P16 要解决的场景**；
P16 实测也确认：**扩到 `(1,2,3,4)` 同样能把退回归零（零浪费命中）**，与 padding 是两条等价的路线。
