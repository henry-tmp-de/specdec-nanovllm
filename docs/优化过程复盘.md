> 本文档回答两个问题：**① 我们是怎么发现瓶颈的？② 拿到反馈之后是怎么迭代的？**

## 1. 方法论：我们是怎么找瓶颈的（可迁移套路）

这套顺序本身就是面试答案的骨架：

1. **先建"约束地图"，别先优化。** 用 `torch.profiler` 把 decode 的 **device time** 分解：
   `GEMM 79.27% / attention 9.24% / elementwise 8.37% / 采样 0.81%`（B=1、ctx=4096、图开）。
2. **用 Amdahl 算上界，上界不够就收手。** attention 占 8–9% ⇒ 上界 `S = 1/((1−f)+f/s)` → 代入自写 kernel
   的实测加速比 ⇒ **只有 +3%** ⇒ 直接降级整个方向。
3. **用微基准验证"是不是真到硬件极限了"。** 权重流式 **763 GB/s = 3090 峰值带宽的 81%**；
   prefill ≈ **65 TFLOPS**（峰值约 71）⇒ **两处都没有免费空间**。
4. **从约束反推该做什么。** 上面的地图直接给出三条推论：
   decode 想快**只能让权重变小**（量化）· prefill 没空间 ⇒ 长 prompt 堵 decode **只能靠调度** ·
   吞吐的杠杆是**并发**（B=1→4 效率涨 3.6×，而 B=4 时算力只用掉三十分之一）。
5. **每个数字都配"噪声地板"**（同一配置跑两遍，用分歧当地板）；主结果**配对/交替**、报**中位数 + 组间范围**、
   用**符号检验**下结论。
6. **等价性用"逐字节对拍"**（把基线单独放一份，用**同一个**对拍脚本指过去跑，比每次前向的
   `(tokens, positions, ctx, block_table, slot) + logits 的 bitwise md5`）。
7. **承重性反证**：故意绕过守卫/关掉补齐，看指标会不会崩 —— 崩了才证明那道守卫真在挡东西。
8. **一句话总结必须连边界一起写**（例："B=4 那个 1.19× 依赖接受率，还原后只有 0.897×"）。

## 2. 迭代年表（反馈 → 判断 → 行动 → 结果 → 下一个问题）

### [01] 方案排第一的主线，被我们自己的测量否掉
- **反馈**：任务书 §12 把"把自写 paged attention 接进引擎"排为**第一条开发主线**（4–7 人天）。
- **判断**：先测上界再投入 —— 上界不到方案自定的 +5% 门槛就按 §6.3 停止条件降级。
- **做了什么**：profiler 分解 device time；算 f；把自写 kernel 的实测加速比代进 Amdahl。
- **结果**：f = 8.12% / 9.24% / 14.68%（ctx 1024/4096/8192）⇒ 上界 +10%，**代入后只有 +3%** ⇒ **P1 降级**。
- **★ 下一个问题**：attention 是墙，那真正的墙在哪？→ **GEMM 79% 且已跑到峰值带宽 81%** ⇒
  decode 只剩"让权重变小"这一条路（→ 量化）；prefill 贴峰值 ⇒ 长 prompt 只能靠调度（→ P12）。
- **教训**：**用自己的测量否掉自己方案的第一条主线** —— 这是这个项目最值钱的一笔判断。

### [02] "实现正确但更慢" → 病根是固定开销 → CUDA Graph
- **反馈**：投机解码**实现是对的**（无损性单测全过），但 **0.68×、净亏**。
- **判断**：先看"每步产出"有没有变。若产出没变，问题就在固定开销，**不在算法**。
- **做了什么**：同一配置只翻 `enforce_eager` 开关对拍。
- **结果**：每步产出几乎没变（**3.77 → 3.82 个 token**），而每步耗时 **33.2 → 12.8 ms** ⇒
  把符号翻正的是 **CUDA Graph（6.4×）**，不是算法。给 draft 前向与验证前向各拍一张静态形状图 → **1.61×**。
- **★ 下一个问题**：既然固定开销支配一切，那"逐请求串行的 draft 前向"呢？→ 批量投机 `[05]`。
- **教训**：**性能问题先问"是算法还是开销"**，不要一上来怀疑算法。

### [03] 长上下文一测就崩 → 追出地基 bug → 此前结论全部失效
- **反馈**：`prompt ≥ 384` 或恰好 256 token 直接崩；256/384/512 全崩。
- **判断**：不是长上下文本身的问题，是**前缀缓存的进度契约**（`hash_blocks()` 的入参契约）算错了。
- **做了什么**：从契约查起；写边界表（255/256/257/383/384/385/1024/2048/4096/8192）复测。
- **结果**：修复前 256/384/512 崩、修复后全通。根因两条：**把半满块当满块登记**（静默污染）+
  **从未登记过合法的 block 0**（缓存实际失效）⇒ **此前所有引擎级长上下文结论都无效**。
- **★ 下一个问题**：既然缓存从来没真正生效过，那它现在是"没用"还是"**有害**"？→ `[04]`。
- **教训**：反馈里最值钱的不是"崩了"，而是**"崩了说明我之前那些不崩的结论其实没被检验过"**。

### [04] 前缀缓存是"负优化"：命中了反而比不命中慢 3.6 倍
- **反馈**：4 条请求共享 4096-token 前缀时，**单个 decode step 阻塞 17.3 秒、占端到端墙钟 85%**；
  吞吐 12.53 tok/s，而**冷缓存（不命中）有 45.5 tok/s**。
- **判断**：命中 target 的前缀缓存 ≠ draft 那把 KV 也有效；但**正确修法不是"假设有效"**（那会静默输出垃圾），
  而是给 draft 做**它自己的**块级有效性追踪。
- **做了什么**：给 `Block` 加 `draft_hash` / `mark_draft_valid` / `draft_valid_cached_blocks`（只认连续前缀）；
  并做**承重性反证** NEGX（绕过守卫直读脏 KV）。
- **结果**：补齐 16665 → **22 token（−99.8%）**；吞吐 **6.1×**；前缀缓存从**净亏翻成净赚 1.68×**。
  反证：绕过守卫后接受率从 0.9 **崩到 0.175–0.470**、argmax 一致率 0.333 ⇒ **守卫真在挡东西**。
- **★ 下一个问题**：draft 要维护一整套自己的 KV，把 target 可用容量砍掉 49% ⇒ 能不能只留最近的窗口？→ `[06]`。
- **教训**：**"加了一个功能"之前先测它到底是资产还是负债**；用**承重性反证**证明守卫不可省，比"我加了守卫"有力得多。

### [05] 批量投机：0.77× → 1.19×（★ 这个数字后来被自己的表推翻，见 `[09]`）
- **反馈**：B=4 时投机**输给普通解码**（C/U = 0.77）；结构证据是**验证图只有单请求形状 ⇒
  B>1 整条验证退回 eager**（命中 3–7、退回 48–72）；且 draft 逐请求串行 = **每轮 24 次独立前向**。
- **判断**：两处开销都随 batch **线性增长** ⇒ 批量 draft + 按 `(B,k)` 拍验证图。
- **结果**：`S2/C = 1.54×`；验证图 **37/37 全命中、0 退回**；draft 前向/轮 **24 → 6**；
  **B=4 从 0.77× 翻到 1.19×**。顺带修掉第 3 个静默 bug（全接受时 draft 有位**永不回头补**，
  接受率 0.866 → 0.987、同负载 ×1.32）。
- **★ 下一个问题**：这个 1.19× 依赖什么？→ 见 `[09]`：**依赖 α≈0.99 的合成素材**，还原接受率就掉回 0.897×。
- **教训**：**凡是投机相关的加速比，必须连报接受率**，否则这个数字不可迁移。

### [06] 滑窗 + 解耦分配：拿到 +16~21%，但**机制没钉死**（诚实挂账）
- **反馈**：draft 共用主模型块号 ⇒ **块数必须相等、无法缩小**；target 可用容量被 draft 吃掉近一半。
- **做了什么**：给 draft 做块级**环形缓冲滑窗**（`slot(p) = ring[(p//bs)%M]*bs + p%bs`）+ **解耦分配**；
  用逐次前向逐位对拍定位 3 个静默 bug（含一个"补齐那趟前向的可见上下文从 1031 被砍到 7"）。
- **结果**：`W ≥ 上下文` 时接受率与全上下文**逐位相同**（226 次前向 logits 0/226 不同）、每轮 0.78–0.86×；
  **解耦分配本身 +16~21%、零精度代价**。
- **★ 挂账（诚实）**：那 +20% **不是**来自"读的 key 变少"（ctx 逐条相同，**已否**）、
  **也不是**来自块表宽度（**已否**）——**具体环节尚未隔离**。
- **教训**：**拿到收益 ≠ 理解了收益**。归因没钉死就明确写"未隔离"，不要编一个机制出来。

### [07] 量化的第一刀不够 → 不是方向错，是**剂量不够** → 加剂量翻倍
- **反馈**：Q1 只量化 draft FFN ⇒ 每轮只 −3.6~4.5%，**未达事前定的 +20% 门槛**。
- **判断**：不是方法不行。算一笔字节账：FFN 只占 draft 权重 44.3%，draft 又只占一轮权重流量 47%
  ⇒ **一轮总字节只降 9.9%**。
- **做了什么**：扩到 draft 的**全部线性层**（196 个模块）；对 `nanovllm/` **零生产代码改动**
  （复用上一轮的开关，只换一个 `quant_config.json`）。
- **结果**：每轮 **−6.4~7.1%**（比 Q1 翻倍）；B=1 四档 **36/36 配对全胜**（符号检验 p≈1.5e-11）；
  精度代价只从 +0.337% 涨到 **+0.455%**（因为 **attention 比 FFN 更耐量化**），省下的字节 22.1% → **36.9%**。
- **★ 下一个问题**：收益为什么只有 7% 而不是估的 10%？→ 逐条对账："每 100 MB 省多少 µs"
  **两档完全一样**（87/96 vs 89/96）⇒ 证明这是**纯字节账**，没有别的机制，也就能外推。
- **教训**：**未达门槛要如实报**，并且**分清是"方向错"还是"剂量不够"** —— 后者加剂量就能救。

### [08] 量化露出"显存反而变多" → 先怀疑 kernel 模块 → 被逐字节账目否掉 → 构造期直载
- **反馈**：权重真省了 0.4 GB，但 **KV 池反而 174 → 170 块**；`used` 稳定多出 0.19 GB，两次复现。
- **判断（第一版，★ 错的）**：怀疑 CUDA context 里多了量化 GEMM 的 **kernel 模块** ——
  理由是"这类占用只出现在 `nvidia-smi` 的 `used` 里"。
- **做了什么**：① 先修掉一个真 bug（**split-K 的 fp32 scratch 顶高 peak**，找回 8 块）；
  ② 在**预算时刻**补打点，把 `used` 拆成 `current + I + O`（`I = reserved−current`，`O = used−reserved`）。
- **结果**：**`ΔO` 逐字节为 0**（三档 `O` 全是 351,797,248）⇒ **"kernel 模块"猜测被实测否掉**；
  `ΔI = +0.589 GiB` 且 **`I` 恒等于 `inactive_split`**（全是**不可回收的 split 残块**，
  warmup 头尾两次 `empty_cache()` 一分钱没还回去）。改**构造期直载 int8**（bf16 全程不上卡）⇒
  **KV 池 170 → 180 块，反超 BF16 基线的 174 块**；**同容量对照**证明设备总占用仍低 0.564 GiB。
- **★ 下一个问题**：多出来的容量换得来速度吗？→ `[10]`：**换不来，它只换容量**。
- **教训**：**最顺手的假设也要写成"可证伪的形式"再去测**。这次是靠把 `used` 拆成三块、
  拿到 O 精确为 0，才把那个"听起来很合理"的解释否掉的。

### [09] 招牌数字被自己的统一验收表推翻
- **反馈**：统一验收表跑出来 —— 滑窗**没有**复现台账的 +9.7%；**B=4/4K 时投机那一整条栈只有 0.71×**；
  招牌数字"B=4 从 0.77× 翻到 1.19×"**没有出现**。
- **判断**：不是谁算错了，是**口径不可迁移** —— 那个 1.19× 是在 **α≈0.99 的合成池化素材**上测的，
  而自然长文 α 只有 **0.61–0.78**。
- **结果**：真实边界是 **整体 1.74×–5.82×**，而且**最大的一截来自 CUDA Graph（2.4–3.6×）而非投机本身**；
  投机那一段单独看是 **1.60×（B=1/1K）→ 0.71×（B=4/4K，batch 大时净亏）**；`U` 零点本身还带 **±4%** 不确定度。
  同时**滑窗的容量收益也不是无条件的**：`滑窗省显存 ⟺ M × max_num_seqs < pool 块数(174)`，
  与上下文长短无关（两个实测点逐字节对上：并发 8 → target 197，并发 12 → 141）。
- **★ 下一个问题**：那下一步该打哪儿？→ 表里已给出判据：**在 B=4/ctx=4096 把 `G→S6` 从 0.71× 拉过 1.00×**，
  而不是再去动 B=1 那条贴着带宽上限的路。
- **教训**：**口径不一致的数字合集，等于没有数字。做完统一验收之后，以前所有"招牌数字"都要重新审一遍。**

### [10] 最新那一刀的边际收益掉进噪声 → 据此切去"整理"
- **反馈**：`S5→S6`（直载 int8）速度 = **1.000–1.004×**，落在噪声地板（0.05–1.06%）**之内**。
- **判断**：它**本来就该只换容量**（两档 int8 权重逐位相同，速度上不该有差别）——
  所以这个 1.000 恰恰是**"测量可信"的证据**，不是失败。
- **结果**：容量确实拿到了（滑窗组 target 141 → 152 块）；据此回答判断题：
  **新技术的边际收益已低于"把已有成果合成一组可复算数字"** ⇒ 把这一轮资源转向统一验收。
- **教训**：**"新功能没提速"不一定是坏消息** —— 要能判断它是"没效果"还是"测不出/本来就不该有效果"。
  它同时给出了**什么时候该从"加功能"切到"做整理"**的判据。

### [11] 统一验收里的两个污染源，被同进程探针钉死
- **反馈**：`U`（本该是 target-only 的零点）的 TTFT 在组与组之间差 **2.4 倍**（78.7 / 161.2 / 186.0 ms），
  而噪声地板只有 0.12–0.5%。
- **判断（第一版）**：怀疑 4 卡并行争用 —— **先把它排除掉**（同配置并行 vs 串行 TTFT 差 ≤3.2%）。
- **做了什么**：写**同一个进程里的三条件探针**（有 draft / 摘掉 draft / 有 draft 但窗口压回 0）。
- **结果**：真因是两处代码 —— ① `model_runner.py:705` 的
  `if self.draft_model is not None: self._run_draft_prefill(...)` **不看 `spec_k`** ⇒
  只要进程加载了 draft，prefill 就白跑一遍 0.6B（**77.8 → 45.7 ms**）；
  ② `_run_draft_prefill_window` **按 `token_ids` 重算整个窗口、不认前缀缓存**
  （压回 `window=0` → **77.5 ms ≈ 77.8 ms**，归因闭合）。
- **★ 下一个问题**：混合调度（P12）若把 prefill 切成 chunk，**这个 draft 前向就会被跑 N 遍** ⇒ 必须先解决。
- **教训**：**先排除最容易想到的解释（并行争用），再找真因**；**同进程多条件探针**是把
  "跨进程对比的噪声"变成"闭合归因"的关键手法。

### [12] ★★ 滑窗被自己的统一验收表判成"负的"——真因是我们为了一个**最后没用上**的对照，把 `max_num_seqs` 撑到了 12
- **看到了什么（反馈 / 现象 / 数字）**：`端到端验收.md` §8.3 的 `S2 → S4`（滑窗那一刀）=

  ⇒ 混合调度**不是**该被否掉的方向；而账① 的"70%"既然是热态计数，**修它的价值要按绝对值算（31.5 ms）**，

  分母是"整条 4K prompt"时是 6%，分母是"未命中的尾巴"时是 70% —— **百分比比绝对值更容易骗人**。
  另外：**"它在多干活吗"这个问题，用"把 token 数打出来"一行就能回答**，不需要任何推理。

### [14] 改动② 第一版"尖刺反而变大 3 倍" → 逐轮打点抓出是**我自己**埋的 bug
- **看到了什么（反馈 / 现象 / 数字）**：实现"分块 prefill + 块之间让一轮给 decode"之后，
  `CHUNK=2048` 实测尖刺 **反而变大**：ctx=4096 从 **642 → 2039 ms**（3 倍），ctx=16384 从 3744 → 4340 ms。
- **当时的判断（第一版，★ 错的）**：先怀疑是**测量伪影** —— torch.compile 对新的 chunk 形状
  付一次编译钱（我确实实测到"第一个块 2055 ms、同尺寸第二个块 376 ms"，且**只与
  `max_num_batched_tokens` 有关**）。★ 于是我把预热改成"用最大 ctx 预热分块形状" —— **没修好**。
- **做了什么**：不再猜，**给探针加逐轮打点**（每一轮：是否 prefill、`num_scheduled_tokens` 之和、
  target / draft 前向各吃多少 token、墙钟），跑单条长 prompt。
- **结果**：打点一行就把根因钉死 ——
  `round 0: step_tokens=14336`（**一个 round 进了 14336 个 token**）。
  根因是**我自己的 bug**：分块后那条序列本步拼不完，**没被 `popleft()`，还留在 `waiting[0]`**；
  `while` 循环下一轮又取到**同一条**，把 `num_scheduled_tokens` 再覆盖、再 `append` 一份 ⇒
  `scheduled_seqs` 里出现同一序列的多份副本，`prepare_prefill` 把这段 chunk **重复拼 7 遍**
  （7×2048 = 14336，**与打点逐字吻合**）。原逻辑不会踩：`min(num_tokens, remaining)` 一定把预算用光 ⇒
  下一轮 `remaining == 0` 直接 break；是我引入的 `budget = min(remaining, chunk)` 让循环得以继续。
  而且**只有"预算充裕"才暴露**（`max_num_batched_tokens=4352` 恰好被原来的守卫兜住，一直是正常的 700 ms）。
  **修法**：分块分支 append 后**立刻 `break`**。修完逐轮打点回到 2048 token / 335.7 ms，
  prefill 合计 **696 ms ≈ 不分块的 648 ms**；尖刺随之 **−44% ~ −81%**（16K：310× → 57.5×）。
- **★ 下一个问题是从哪儿冒出来的**：既然是"同一个 chunk 被拼 N 遍"，那**任何一种"预算充裕"的配置都会踩**
  （`max_num_batched_tokens` 默认就是 16384）—— 说明这类**循环不变量**（"同一条序列一轮只能被调度一次"）
  值得单独写一条 CPU 单测钉住。
- **值钱的方法论教训**：**"改了以后变慢"要先怀疑自己的改动，不要先怀疑测量。**
  我第一版把 3 倍变慢解释成 torch.compile 伪影，**方向就错了**（虽然那个伪影真实存在、也确实误导了我）。
  **逐轮打点（每一轮到底处理了几个 token）是把"变慢"定位到"变了什么"的最短路径** ——
  比任何推测都快，一行输出定案。

### [17] ★★ 接受率要"测硬"不是加样本、而是【换仪器】—— 但"换仪器"必须换成"测同一个量的仪器"
- **看到了什么（反馈 / 现象 / 数字）**：给 `(P=2, M=5)` 定标时，旧口径（自由生成统计接受率）
  被判定"噪声压过效应"：普通投机自己的 α 跨批次漂移 **±4~13%**（0.7814 vs 0.6911，两轮串行都复现 0.6911），
  同一棵树重复跑 3 遍 `out_md5` 都不同（上一轮 `[16]` 刚撞过）。
- **当时的判断**：把接受率换成**确定性仪器** —— 恒等式 `α = 1 − TV(p,q)`，
  在**固定上下文**上算，不发散、可复现、能堆样本量。**计划是"离线固定语料 + 按窗口语义重建 draft 上下文"。**
- **做了什么**：
  1. **离线固定上下文**（`scripts/det_alpha.py`）：wikitext 取 16 个窗口、每窗 2048 个位置
     （其中 256 个是"生成位"），按引擎的 `_run_draft_prefill_window` / `DraftWindow` 语义重建 draft 上下文，
     逐位置 `TV(target, draft)`。**跑出来是干净的**：`w0` 0.654、`m5` 0.621、`p2m5` 0.621。
  2. ★ **发现它和引擎对不上**：引擎里 `m5`（P=0）明显更差。于是**做第二条仪器** ——
     `scripts/engine_alpha.py`：直接 monkeypatch `nanovllm.spec_decode.verify.verify_batch`，
     拿**引擎自己**算出来的 `q`（draft logits）与 `p`（target logits）算 `1 − TV`
     （同一轮、同一位置、同一已确认前缀）。同一次运行里同时得到「确定性 α」和「项目一直用的 `accept_rate`」。
- **结果**：
  - ★ **两条独立仪器在三个配置上互相对得上（差 1–5%）**：8K/B=4 —— 普通投机 **0.655 / 0.672**、
    纯滑窗 **0.366 / 0.361**、`p2m5` **0.626 / 0.664**（前者=引擎内确定性 α，后者=项目原有 `accept_rate`）。
  - ★ **离线重建口径在 `P=0` 上偏乐观 0.25**（0.621 vs 0.366）。已定位到"**滑动**"而不是"窗口"：
    `P=0, M=33`（窗口盖住整条序列、**不滑动**）α 回到 **0.642** ≈ 普通投机；
    `P=0, M=5`（滑动）只有 0.366。**"离线重建"等价于"窗口不滑动"这个理想极限。**
  - **定标结论**：`(P=2, M=5)` 与普通投机**持平**（8K −1%~−4%、**16K +0.5%**），
    容量 +66%、16K 并发 2 条→4 条、TTFT 只贵 8 ms；
    ★ **16K 下不需要放大 M**（M=5/12/18/33 → 0.669/0.626/0.625/0.627）—— "16K 要放大窗口"那条直觉**只在 P=0 时成立**。
  - ★ 顺带纠了一条**口径误会**：项目原有的 `accept_rate`（`accept_mask.mean()`）
    **在数学上就是 per-position 的 α**（`E[accept_mask]=Σ_j α_j`，与拒绝采样的定义逐位对齐），
    **不是**"轮级接受长度"。所以它和确定性仪器本来就该相等 —— 本轮实测确实相等。
    真正会发散的是 `out_md5` / 轨迹类指标，**不是 α 本身**。
- **★ 下一个问题是从哪儿冒出来的**：
  1. **`P=0` 一滑就掉、`P≥1` 能修好 —— 为什么？** ★ **未定位**。已排除几何
     （引擎自报的 `ctx_len`/块表/token 集合与 `DraftWindow` 逐值一致，1600 组 CPU 对拍）与
     "窗口 prefill 写坏 KV"（快照引擎环里的 `v_cache`，`max|ΔV| = 0.0078` = bf16 舍入；
     换一个位置比就是 0.83~1.39）。已锁定范围：**第 1 轮正常、第 2 轮起崩**；**不滑就不崩**。
  2. **引擎内确定性 α 的 run-to-run 地板是 ±0.02**（`p2m5` 两次 0.626 / 0.651）——
     因为"上下文"仍然来自采样轨迹；而**离线固定上下文口径抖动为 0**。
     ⇒ 想真正"测硬"，得把**两者合起来用**：离线口径给无噪声的绝对值（但只对"不滑动"有效），
     引擎口径给真实路径的绝对值（但有 ±0.02 的轨迹地板）。
- **值钱的方法论教训**：**"换个更干净的仪器"这句话必须补一个限定 —— 换成"测同一个量的仪器"。**
  旧的 `accept_rate` 其实早就是那个量（只是用单样本估的，SE 大）；真正坏掉的是同一次运行里
  那些**轨迹类**指标（`out_md5`、tok/s）。而新仪器如果**自己重建了被测量的那个状态**
  （这里是"窗口的 KV 上下文"），它测的就是**一个理想化的近似系统**，不是引擎 ——
  **`P=0` 上差 0.25 就是这么来的。** 判据：**新仪器必须在"已知答案"的格子上先对一次**
  （本轮用的是 `P=0, M=33` 不滑动那一格，以及"窗口盖住全序列 ⇒ 分布必须与全上下文一致"的自检）。

### [18] ★★ "让路式分块已经能用旋钮压尖刺" ⇒ 真混合被自己的算术否掉（P1 式的"不做"）
- **看到了什么（反馈 / 现象 / 数字）**：P13 的让路式分块已把 16K 的 ITL 尖刺从 310× 压到 16.9×
  （C=512）。任务书要求正面回答"还有必要做真混合（一轮内同时跑 decode 与 prefill 两个子批）吗"，
  并给了判据：**先量让路式还剩多少绝对毫秒，再算真混合最多还能削掉多少**。
- **当时的判断**：直觉是"还能再压一个量级"。★ **被自己的测量否掉。**
- **做了什么**：用 `p12_sched_probe.py` 把尖刺**拆成两段**（一个 prefill 块轮 + 一个解码轮），
  在 C∈{256,512,1024,2048,不分块} 上逐格量，并跟"稳态解码轮"（B=3/B=4 都 ≈12.1 ms）对照。
- **结果**：
  - **尖刺 = T_pre(C) + T_dec**，实测差 3.4~17.7 ms（= 一个解码轮到一轮零头）。
  - ⇒ **真混合的绝对节省上界 = 一个解码轮 = 12.1 ms**（且这是 δ=0 的乐观界），
    占实测尾部：C=256 的 **4.1%**、C=512 的 **10.0%**、C=2048 的 **3.2%**。
  - ⇒ **而且"压尖刺"本来就是 chunk 大小一个旋钮**：T*=50/100/200/400 ms 分别对应
    C=128/256/512/1024，实测 51.3 / 82.3 / 170.7 / 296.5 ms。真混合不能把这条曲线
    整体下移超过 12.1 ms，**只是一次小幅 Pareto 平移，不是开/关**。
  - 代价：① 一轮内混两条执行路径（本项目踩过 3 次，最典型 `spec_enabled` 门控快照 bug）；
    ② decode 预算被分走；③ CUDA Graph 命中率下降（decode 是带宽 bound、prefill 是算力 bound，
    理论可重叠但混合批形状逐轮变、图退化成 eager）；④ 工作量不小。
- **★ 下一个问题是从哪儿冒出来的**：既然尖刺被拆成"块轮 + 解码轮"，那**小 chunk 是不是免费的**？
  ⇒ 量下去发现两个反向代价：(a) 吞吐（C=256 +24.5%、C=128 +70.4%）；
  (b) ★ **p50 也会被抬起来**（C≤512 时中位数 60~76 ms，C≥1024 才回到稳态 12.2 ms）。
  前者可以靠"没有解码请求时不切块"消掉，后者只能靠"别把 C 选太小"。
- **值钱的方法论教训**：**"还能再优化吗"这个问题的答案，往往不是"能/不能"，而是
  "上界是多少毫秒"。** 把 KPI 拆成"两个可直接测量的物理段"之后，上界自己就写出来了 ——
  这次是"一个解码轮"。**拆不动的东西才需要新架构；拆得动的东西只需要换个旋钮值。**

- **看到了什么（反馈 / 现象 / 数字）**：任务书点名要测"运行期把 `spec_k` 从 0 翻回正数时，

### [21] ★★★ `P=0` 滑窗"一滑就崩"被定位成【bug】而不是【截断的固有代价】—— 判据是把"滑动"与"截断"解耦

  3. **为什么 P≥1 能把敏感度压下去**：KV 偏差在 `p2m5` 上**同样存在、量级相当**，
     但 `TV(q_eng,q_ideal)` 只有 0.045 —— 机制未隔离（怀疑 attention sink 吸收质量，**没做权重可视化**）。
- **★ 值钱的方法论教训**：
  **"理想值"这个词有两个完全不同的意思**——"物理上不可达的上限"与"当前实现没做到的事"。
  `[17]` 把 `P=0` 的 0.621 读成了前者，于是把一个 bug 归因成了**固有代价**，
  还差点写进结论（"滑窗的质量代价来自截断"）。
  **分辨方法只有一个：把差异项解耦出来单独测** —— 这里就是"同样截断、但让窗口起点不漂移"。
  ★ 另一条：**换对照物要换到"能看见机制"的那一层**。同一个疑点，
  拿离线重算当对照只能证伪"写坏了值"；拿**引擎自己声明的窗口**当对照，才看得见"写的上下文不对"。

     修法（新增 `spec_draft_win_realign`，默认关）：**漂移发生时按新起点把这扇窗口重算一遍**
     （≤ M*bs 个 token 的 local-causal 前向）并推进地板 ⇒ 修后 α 回到 **0.6432 / 0.6322**。
     成本 **≤1%**（每 256 个生成 token 触发一次、每次 1280 token），**容量不变**。
  3. **把推荐配置整张表重测**：α（8K/16K）/ TTFT / draft 池 / target 池 / 并发，全部重跑。
- **结果**：
  - ★★ **P 轴没有独立价值，判决性证据是「效应反号」**：
    `ALIGN=0` 时 `Δ(P2−P0) = +0.2797 / +0.2200`（**23.6σ / 9.6σ**）；
    `ALIGN=1` 时 **−0.0188 / −0.0134（3.0σ / 2.1σ，P=2 反而更差）**。
    ⇒ **P 的全部正收益 = 遮掩对齐漂移**。**推荐配置从 `(P=2,M=5)` 砍成 `(P=0,M=5)`。**
  - ★ **修完之后真正的「截断代价」**：`(P=0,M=5)` 相对普通投机 **8K −4.1%（5.6σ）、16K −6.0%（5.4σ）**。
    ⇒ `[21]` 里「0.642 vs 0.655 ≈ 持平（−2%）」**偏乐观**（单遍运行 + 单遍基线）；重复多了之后**代价是真的**。
  - ★ **M 轴也「活过来了」**：`[15]` 的「M 从 3 加到 24 几乎白花钱」是 **P=0 + bug** 口径；
    修后 `M=5→12` 在 8K 上 **+0.0187（2.6σ）**。
  - ★ **一个反直觉的副产品**：旧推荐 `(P=2,M=5)` 的 α **没有被 bug 抬高**——恰恰相反，
    `ALIGN=0,P=2` 比 `ALIGN=1,P=2` **高 0.029**。因为 ALIGN 在「prompt 正好落在块边界」时
    把窗口缩小一个块，而 P=2 本来就能容错 ⇒ 对齐对它只有成本。
    **所以「P 在补 bug」的正确表述是：P 让「会崩的 P=0 那条路也能跑」，不是「让好配置更好」。**
  - **顺带赚到的两个数**：新推荐 **TTFT +0.3 ms（8K）**（旧推荐 +4.7 ms）、**draft 池 28 → 20 块**。
- **★ 下一个问题是从哪儿冒出来的**：
  1. **残留单轮尖刺**：修后仍有 **3/230 轮** `TV > 0.3`，机制解释为（算术与位置吻合、未做隔离实验）「**投机解码的写前量
     （`L−1 … L−1+k−1`）覆盖了环里最老那个块的槽位**，而读端的起点要等 `L−1` 自己跨块才前进」。
     代价 ~0.012 α。**候选修法**：把触发条件提前一个 `k`。**未做。**
  2. **`ALIGN=1` 对 P≥1 为什么是负收益**：机制已解释（少一个块的窗口），但**没做隔离实验钉死**。
  3. **旧配置那 +1.6%（8K）的零头**：最可能是「bug 让保留块多带一块上下文 + P 容错」白拿的，
     **没做「人为把窗口加宽一个块」的对照**。
- **★ 值钱的方法论教训（两条，都值得进面试答案）**：
  1. **「一个 bug 可以伪装成一项机制收益」。** 判据不是「这项收益有多大」，
     而是 **「把 bug 修掉之后，这个旋钮的效应还在不在」** —— 本轮就是**效应反号**（+0.28 → −0.019）。
     ★ **连带结论：凡是写着「推荐配置 / 参数旋钮 / 经验规则」的结论，只要它是在**已知 bug 未修**
     的状态下定标的，就必须在 bug 修完之后**整张重核一遍**。** 本轮如果只修 bug 不重核，
     会留下一份「推荐 `(P=2,M=5)`」的文档 —— 而那个配置的收益来源已经不存在了。
  2. **「修一个 bug」不等于「这类 bug 修完了」。** `[21]` 的修法只对齐了**第一次**漂移
     （`[21]` 自己也写了「只修第一次」），第二次漂移的代价 **−0.19 α** 和第一次一样大 ——
     是**同一类**、同一条路径、只差一个块边界。**修完必须问：「这个机制还会在什么条件下复发？」**
     本轮答：**每个块边界**（每 256 个生成 token）都会，而且 `ctx` 恰好对齐到块边界时
     `out=256` 根本碰不到它 ⇒ **只在「out≥257」或「prompt 不是块边界」时才暴露**。

### [23] ★★★ 「收益上界」写进方案时没人质疑它 —— 实测发现上界那一项抄错了配置（P15）

- **看到了什么（反馈 / 现象 / 数字）**：`docs/优化报告.md §d.5 方向 2` 把"重叠执行的混合批"
  的收益上界钉成 **一个解码轮 = 12.1 ms/轮（占尾部约 4%）**，并据此**排在有依据地暂不做**那一栏。
  但同一张表里的 296 / 284 ms 又是从 `[18]` 的"3 条解码"场景来的 —— **两个数字来自两个不同配置。**
- **当时的判断**（★ **错判，且是这一轮最值钱的那一条**）：我一开始也接受了"上界 12.1 ms"，
  准备把它当成"这轮做了也就是 4%"来做/来否。**依据是"12.1 ms 是实测的"** ——
  它确实是实测的，但**实测的是普通 decode（`spec_k=0`）**，而基准场景写的是 `k=6`。
- **做了什么**：不去争，**直接搭一个把调度/采样全排除掉的微基准**（`p15_overlap_micro.py`），
  只量四件事：`t(decode)` / `t(prefill)` / `t(串行)` / `t(并发)`。
  跑之前先做了一个**便宜的证伪**：把 `num_scheduled_tokens` 临时降到 1（退回普通 decode）
  再量一次 → **12.04 ms**。
- **结果**：
  - ★ **12.1 ms 被逐值复核通过 —— 但它不是本配置的解码轮。** 同样的探针在
    `k=6 + draft` 下量到 **220.2 ms（18 倍）**。⇒ 上界应当是 `min(解码轮, prefill 块)`。
  - **形状那一半被证实**：`t(串行) = t(decode) + t(prefill)` 在 4 个 prefill 深度上
    残差 **≤ 0.5 ms** ⇒ "混进同一个 step"确实一分钱不值。串行档端到端三处收益
    全在噪声内且方向不一致（A +5.0% / B +0.5% / C +1.7%）。
  - **并发档**：第 1 块省 93.4 ms（上界的 54.5%）→ 第 14 块省 **203.8 ms（93.1%）**。
    端到端：场景 A 解码 ITL 窗口 p50 **475 → 317 ms（−33.4%）**、长 prompt TTFT
    **7524 → 5029 ms**、稳态吞吐 **+8.9%**；场景 B（只有 1 条解码 ⇒ 解码轮仅 32 ms）
    只 **−5.7%** —— ★ **同一个机制、同一个 CHUNK，收益从 −33% 掉到 −5.7%，
    只因为被藏的那个前向变小了**；实测每块省 34.6 ms，与 32 ms 的预测吻合。
- **★ 下一个问题是从哪儿冒出来的**：
  1. ★ **220 ms 的解码轮内部没拆解**（draft 提议 / 验证前向 / CPU 侧开销各占多少）——
     没做 profiler 归因，所以**不敢说优化哪里能让它变小**，只能说"它不是 12.1 ms"。
  2. **默认 `spec_graph_bs=(1,2,4)` 下 3 条请求的混合 step 拿不到 B=3 的验证图**
     （实测退回 22 次，改成 `(1,2,3,4)` 后退回归零）。既有的，没改。
  3. **块大小这个旋钮与重叠不互斥**：块越小、能藏的比例越高、绝对量越小。
     `CHUNK=256` 没测，"P15 在哪个 CHUNK 上最优"是个**没做的组合题**。
  4. 抢占（KV 不够）与混合 step 的交互**只做了兜底、没做压测**。
- **★ 值钱的方法论教训（两条）**：
  1. **★★「收益上界的量级」比「收益是否正确」更容易错，而且更难被发现。**
     `[18]` 当年就是"靠算术否掉一个方向"的漂亮案例；这一轮同样是算术，
     却因为**上界那一项抄了另一个配置的实测值**而把量级算小了 18 倍。
     ★ **判据：写"上界 = X ms"时，必须同时写下 X 是在【什么配置】下量的，
     并检查它与本场景的配置逐项对得上（batch / k / 是否开投机 / ctx）。**
     本轮的对不上的地方正是 `k`：上界取的是 `k=0` 的读数，场景写的是 `k=6`。
  2. **★ 对照组的"预期为 0"必须真的测出来，而不是推出来。**
     `[18]` 已经把"混批 = 0"用算术论证得很干净，但**算术不是测量**。
     本轮把串行档做成一个**真的可执行、真的占资源**的实现跑了一遍，
     结果是"三处都在噪声内、方向还不一致" —— 这才叫"0 被测出来了"。
     而且这次测量顺手给出了**下一层的量**：可藏的东西 = `min(解码轮, prefill 块)`，
     四个深度上的比例 0.545 → 0.931 是一条**单调曲线**，比一个"12.1 ms"有用得多。
### [24] ★★ 任务书里"等 3 倍时间 ⇒ 变 1 倍"的算术，被"轮"这个字骗了 —— 轮数收益 ≠ 墙钟收益（P14）

- **看到了什么（反馈 / 现象 / 数字）**：`docs/优化报告.md` §d.5 方向 1 给了 P14 的任务：
  prefill 循环只看队首 ⇒ 3 条 16K 同时到达时"第 1/2/3 条分别在第 16/32/48 轮完成
  （**等 3 倍时间**）"；改成同轮多序列轮转后"三条都在第 16 轮完成，**总工作量一分不多**"。
- **当时的判断**：**接受这个算术**（判据是"总工作量不变 ⇒ 几乎免费"，外部还有三个生产
  issue 背书：SGLang #32549 / #35537、vLLM #57413）。★ **这一步的错在于：我把"轮"当成了

- **做了什么**：按时交付了机制（`PrefillRotation` + `spec_prefill_rotate`，默认关），

    2×2 分解：**池子的贡献 −55.4%，轮转的贡献另外 −17.3%** ——
    ★ **"把池子做大"比"改调度顺序"有效得多，而轮转只有在池子够用之后才开始有正收益。**
    ⇒ 一条优化"没用"的时候，先问**它被什么前置条件挡着**，很可能那个前置条件才是主因。
  - **代价侧**：轮转**不抬高 KV 峰值**（132 → 133 块）、**零抢占**（8 组全 0），
    但**场景 C 稳态吞吐 −12%**（1841.7 → 1620.2 tok/s；当档噪声地板 3.7%/8.0%）。
  - **不变量侧**：`tests/test_prefill_multiseq.py` 51 项断言 + 全量 **412/412**；
    跨树对拍 8 组配置默认路径**逐轮轨迹 md5 全等**。
- **★ 下一个问题是从哪儿冒出来的**：
  1. **−12% 吞吐差没归因**：手上有"总轮数几乎一样、每轮更贵"的痕迹，但**没有隔离实验**
     能把它分给「KV 准入把解码批压小」还是「prefill/decode 交替的节奏变了」。
  2. **N 的边界是配置事实**：`N_max = floor(池块数 / ceil(ctx/块大小))`（16K ⇒ 2）。
     日志里 **draft 全上下文缓存 ≈ 4.87 GiB ≈ 20~30 个 target 块** —— 开草稿滑窗
     能不能把 N 从 2 抬到 3？**本轮只记了线索，没做实验。**
  3. **等权轮转不是最优**：表里的"p50 变差"是这个策略的固有交换；
     加权的（"先到的多给点"）能不能同时改善 max 和 mean，**没测**。
- **★ 值钱的方法论教训（两条）**：
  1. **"轮数/步数"是调度器的**内部尺子**，一旦被优化的那个动作本身会改变"一轮多长"，
     它就不能当时间单位用。**任何"X 轮完成 ⇒ 快 N 倍"的推论，都必须再用墙钟复述一遍**，
     否则就是把自变量和因变量一起改了。
  2. **"等权公平"是一个 max↔mean 的交换，不是单向改善。** 报公平类优化时，
     必须同时给出**最大值改善**与**中位数代价**（本轮：max −16%、p50 +141%），
     否则"更公平"会被读成"更快"。★ 顺带一条：**外部 issue 的适用前提必须逐条核对**
     （那三个 issue 都是"KV 没满却在等"；我们 16K 场景 KV 已经 75%，前提不成立）。

| 任务书（§d.5 方向 1） | "3 条 16K 同时到达：第 1/2/3 条在第 16/32/48 轮完成（**等 3 倍时间**）；轮转后三条都在第 16 轮完成 ⇒ 数倍改善、几乎免费" | **P14 实测分两半**：① 按**轮数**完全成立（`[4,7,10]→[4,4,4]`、总 token 逐值相同）；② 按**墙钟**只有**最大 TTFT −16%（8K）/−30%（4K）**，而 **p50 反而 +141%** —— 轮转把"一轮"的工作量也放大了 N 倍（off 每轮 1 块 vs on 每轮 3 块），"第 16 轮"是另一根尺子；③ **16K × 3 条时被 KV 准入卡死**（池 174 块 ÷ 64 块/条 ⇒ N≤2），最大 TTFT 无改善，稳态吞吐 **−12%**（`[23]`）|
| 主 agent（P12 开头） | "让路式分块还能再压一个量级 ⇒ 真混合值得做" | **自己的算术否掉**：尖刺 = 块轮 + 解码轮，真混合的绝对上界 = **一个解码轮 = 12.1 ms**，占实测尾部 **4.1%~10.0%**；而"压尖刺"本来就是 chunk 一个旋钮 ⇒ **不做**（`[18]`） |
| 主 agent（P12 无损性第一版） | 用**生成的 token 序列**判"分块是否无损" | **同配置重复跑的对照否掉**：解码路径自己跨进程就不可复现（logits 差 20~29、argmax 翻 22/60 步），而 prefill **4/4 逐位相同** ⇒ 判据换成 prefill 的 logits（`[19]`） |
| 主 agent（P12 追 bug） | 翻转 `spec_k` 后接受率崩是 proposer 的 catchup 逻辑有问题 | **把水位打出来否掉**：翻转时 `draft_valid_len=8192`（= prompt 长度），而 draft 前向根本没跑 —— 是 `advance_draft_watermark` **盖了个没写过的章**（`[20]`） |
| 主 agent（P12 假设） | "小 chunk 只是把尾巴压低、代价是吞吐" | ★ **p50 也被抬起来**：C≤512 时解码请求的中位 ITL 从 12.2 ms 涨到 **60~76 ms**；只有 C≥1024 才回到稳态 ⇒ 规则里得多一条约束 |
| 台账 §2.7.1（推荐配置） | "`(P=2, M=5)` 是推荐配置；P 轴一行见效（P=0→2 相对 +71%）" | ★★ **32 格 × 3–9 遍的 `ALIGN` 网格**：P 的效应在对齐修好前后**反号**（+0.2797/23.6σ → −0.0188/3.0σ）⇒ **P 的全部收益来自遮掩对齐 bug**，推荐砍成 `(P=0,M=5)`（`[22]`） |
| 台账 §2.7 / `[15]` | "M 轴几乎没有拐点（3→24 只涨 0.106），『M 更大』是死区" | 那是 **P=0 + bug** 的口径；修后 `M=5→12` **+0.0187（2.6σ）**，M 重新有意义（`[22]`） |
| `[21]`（本轮之前那条） | 修完第一次漂移后 "`m5` 0.642 vs `w0` 0.655 ⇒ 截断只值 −2%，基本持平" | ★ **偏乐观**：单遍运行 + 单遍基线；7–9 遍重复后是 **−4.1%（5.6σ，8K）/ −6.0%（5.4σ，16K）**（`[22]`） |
| `[21]` 的修法本身 | "对齐修复把漂移问题解决了" | ★ **只解决了第一次**：序列每跨进一个新块就复发，代价同样是 **−0.19 α**（8K 0.644→0.458）；补 `spec_draft_win_realign` 后回到 0.643（`[22]`） |
| `[18]` / `§d.5 方向 2` | "重叠混批的收益上界 = **一个解码轮 = 12.1 ms**（占尾部 4%）⇒ 有依据地暂不做" | ★★ **上界那一项抄的是另一个配置的读数**：12.1 ms 是 **普通 decode（`spec_k=0`）** 的解码轮（P15 逐值复核 **12.04 ms**），而场景写的是 **`k=6`**。同探针在 `k=6 + draft` 下量到 **220.2 ms（18 倍）**。修后上界 = **`min(解码轮, prefill 块)`**，实测每轮可省 **93.4 → 203.8 ms**（占上界 0.545 → 0.931）；端到端场景 A ITL 窗口 p50 **−33.4%**、TTFT **−33.2%**（`[23]`） |
| `[18]` 的结论本身 | "混批 = 0，所以不值得做" | ★ **形状对、结论对、但只对了一半**：串行档实测确实 ≈ 0（A +5.0% / B +0.5% / C +1.7%，范围重叠、方向不一致），**但并发档三处一致为正** ⇒ **"混批本身 0" 与 "重叠值得做" 可以同时成立**（`[23]`） |

## 4. 面试问答速查（骨架）

| 会问什么 | 怎么答（一句话 + 一个数字） |
|---|---|
| **你怎么找瓶颈？** | 先建约束地图再优化：profiler 把 decode 的 device time 分解成 `GEMM 79.27% / attn 9.24% / elementwise 8.37%`；GEMM 已跑到 **763 GB/s = 峰值带宽 81%** ⇒ 只剩量化这一条路 |
| **你怎么决定该不该做？** | 先算 Amdahl 上界：attn 占 8–9% ⇒ 上界 **+3%** ⇒ 直接收手，把资源挪到批量执行 |
| **你怎么保证数字可信？** | 每个数配**噪声地板**；配对/交替测量 + 符号检验；**逐字节等价性对拍**（bitwise md5 比每步的 tokens/positions/block_table/slot）；**承重性反证**（绕过守卫则接受率 0.9 → 0.175） |
| **你踩过最大的坑？** | **口径混用**：`tok/s` 会被轮数随机性淹没 ±10~20%，所以主指标改用"每轮耗时 = 墙钟 ÷ 轮数"；以及**不能用大类占比给具体技术背书** |
| **什么时候收手？** | 两种：上界不够（P1 +3%）；边际收益掉进噪声（`S5→S6` = 1.000 ⇒ 转去做统一验收） |
| **你做过最反直觉的一件事？** | 量化让权重省了 0.4 GB，KV 池却**少了** 4 块 —— 最后定位到**分配器内不可回收的 split 残块**，改用构造期直载后 **170 → 180 块，反超 BF16 基线** |
| **你的结果有什么边界？** | 整体 1.74×–5.82×，但**大头是 CUDA Graph 而非投机**；投机那一段是 **1.60×（B=1/1K）→ 0.71×（B=4/4K，净亏）** |
| **讲一个失败的结论** | 滑窗拿到的 +16~21% **机制至今没隔离**（已排除"读的 key 变少"和"块表宽度"）——**拿到收益不等于理解了收益** |
| **讲一个「收益其实是 bug」的** | 「开头常驻段 P」曾是**推荐配置**（P=0→2 相对 +71%）；修掉对齐 bug 后 **P 的效应反号**（+0.28/23.6σ → −0.019/3.0σ）⇒ **旋钮的收益 100% 来自遮掩 bug**，推荐从 `(P=2,M=5)` 砍成 `(P=0,M=5)` |
| **你怎么发现「推荐配置」是错的** | 上一个 bug 修完后**把整张定标表重跑一遍**（32 格 × 3–9 遍、换掉会发散的仪器）；判据是 **「效应还在不在」**，不是「效应多大」 |
