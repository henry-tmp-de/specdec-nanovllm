# 性能优化的过程复盘（★ 面试弹药库）

> 为什么有这份文档：面试官**非常在乎"优化性能的整个流程"**，而不只是最终数字。
> 本文档回答两个问题：**① 我们是怎么发现瓶颈的？② 拿到反馈之后是怎么迭代的？**
>
> 三份文档分工（不要混）：
> | 文档 | 回答什么 |
> |---|---|
> | **`优化过程复盘.md`（本文）** | **过程**：怎么发现 → 怎么判断 → 怎么迭代 → 哪一步推翻了自己 |
> | `优化台账.md` | **结果**：每项优化的效果 / 口径 / 证据 / 边界（简历素材权威版） |

**收录判据（不追求全，追求关键）** —— 属于下面任何一类就**必须**记：

1. **改变了方向**的反馈（例：`[01]` attention 主线被否）
2. **推翻了自己先前结论**的反馈（例：`[08]` "kernel 模块"猜测被否）
3. **暴露"此前的结论其实无效"**的反馈（例：`[03]` 前缀缓存 bug 让所有长上下文结论作废）

6. 值钱的**方法论教训**（例：`[02]` 先问"是算法还是开销"）

## 1. 方法论：我们是怎么找瓶颈的（可迁移套路）

这套顺序本身就是面试答案的骨架：

1. **先建"约束地图"，别先优化。** 用 `torch.profiler` 把 decode 的 **device time** 分解：
   `GEMM 79.27% / attention 9.24% / elementwise 8.37% / 采样 0.81%`（B=1、ctx=4096、图开）。
2. **用 Amdahl 算上界，上界不够就收手。** attention 占 8–9% ⇒ 上界 `S = 1/((1−f)+f/s)` → 代入自写 kernel
   的实测加速比 ⇒ **只有 +3%** ⇒ 直接降级整个方向。
3. **用微基准验证"是不是真到硬件极限了"。** 权重流式 **763 GB/s = 3090 峰值带宽的 81%**；
   prefill ≈ **65 TFLOPS**（峰值约 71）⇒ **两处都没有免费空间**。
4. **从约束反推该做什么。** 上面的地图直接给出三条推论：
   decode 想快**只能让权重变小**（量化）· prefill 没空间 ⇒ 长 prompt 堵 decode **只能靠调度** ·
   吞吐的杠杆是**并发**（B=1→4 效率涨 3.6×，而 B=4 时算力只用掉三十分之一）。
5. **每个数字都配"噪声地板"**（同一配置跑两遍，用分歧当地板）；主结果**配对/交替**、报**中位数 + 组间范围**、
   用**符号检验**下结论。
6. **等价性用"逐字节对拍"**（把基线单独放一份，用**同一个**对拍脚本指过去跑，比每次前向的
   `(tokens, positions, ctx, block_table, slot) + logits 的 bitwise md5`）。
7. **承重性反证**：故意绕过守卫/关掉补齐，看指标会不会崩 —— 崩了才证明那道守卫真在挡东西。
8. **一句话总结必须连边界一起写**（例："B=4 那个 1.19× 依赖接受率，还原后只有 0.897×"）。

## 2. 迭代年表（反馈 → 判断 → 行动 → 结果 → 下一个问题）

### [01] 方案排第一的主线，被我们自己的测量否掉
- **反馈**：任务书 §12 把"把自写 paged attention 接进引擎"排为**第一条开发主线**（4–7 人天）。
- **判断**：先测上界再投入 —— 上界不到方案自定的 +5% 门槛就按 §6.3 停止条件降级。
- **做了什么**：profiler 分解 device time；算 f；把自写 kernel 的实测加速比代进 Amdahl。
- **结果**：f = 8.12% / 9.24% / 14.68%（ctx 1024/4096/8192）⇒ 上界 +10%，**代入后只有 +3%** ⇒ **P1 降级**。
- **★ 下一个问题**：attention 是墙，那真正的墙在哪？→ **GEMM 79% 且已跑到峰值带宽 81%** ⇒
  decode 只剩"让权重变小"这一条路（→ 量化）；prefill 贴峰值 ⇒ 长 prompt 只能靠调度（→ P12）。
- **教训**：**用自己的测量否掉自己方案的第一条主线** —— 这是这个项目最值钱的一笔判断。

### [02] "实现正确但更慢" → 病根是固定开销 → CUDA Graph
- **反馈**：投机解码**实现是对的**（无损性单测全过），但 **0.68×、净亏**。
- **判断**：先看"每步产出"有没有变。若产出没变，问题就在固定开销，**不在算法**。
- **做了什么**：同一配置只翻 `enforce_eager` 开关对拍。
- **结果**：每步产出几乎没变（**3.77 → 3.82 个 token**），而每步耗时 **33.2 → 12.8 ms** ⇒
  把符号翻正的是 **CUDA Graph（6.4×）**，不是算法。给 draft 前向与验证前向各拍一张静态形状图 → **1.61×**。
- **★ 下一个问题**：既然固定开销支配一切，那"逐请求串行的 draft 前向"呢？→ 批量投机 `[05]`。
- **教训**：**性能问题先问"是算法还是开销"**，不要一上来怀疑算法。

### [03] 长上下文一测就崩 → 追出地基 bug → 此前结论全部失效
- **反馈**：`prompt ≥ 384` 或恰好 256 token 直接崩；256/384/512 全崩。
- **判断**：不是长上下文本身的问题，是**前缀缓存的进度契约**（`hash_blocks()` 的入参契约）算错了。
- **做了什么**：从契约查起；写边界表（255/256/257/383/384/385/1024/2048/4096/8192）复测。
- **结果**：修复前 256/384/512 崩、修复后全通。根因两条：**把半满块当满块登记**（静默污染）+
  **从未登记过合法的 block 0**（缓存实际失效）⇒ **此前所有引擎级长上下文结论都无效**。
- **★ 下一个问题**：既然缓存从来没真正生效过，那它现在是"没用"还是"**有害**"？→ `[04]`。
- **教训**：反馈里最值钱的不是"崩了"，而是**"崩了说明我之前那些不崩的结论其实没被检验过"**。

### [04] 前缀缓存是"负优化"：命中了反而比不命中慢 3.6 倍
- **反馈**：4 条请求共享 4096-token 前缀时，**单个 decode step 阻塞 17.3 秒、占端到端墙钟 85%**；
  吞吐 12.53 tok/s，而**冷缓存（不命中）有 45.5 tok/s**。
- **判断**：命中 target 的前缀缓存 ≠ draft 那把 KV 也有效；但**正确修法不是"假设有效"**（那会静默输出垃圾），
  而是给 draft 做**它自己的**块级有效性追踪。
- **做了什么**：给 `Block` 加 `draft_hash` / `mark_draft_valid` / `draft_valid_cached_blocks`（只认连续前缀）；
  并做**承重性反证** NEGX（绕过守卫直读脏 KV）。
- **结果**：补齐 16665 → **22 token（−99.8%）**；吞吐 **6.1×**；前缀缓存从**净亏翻成净赚 1.68×**。
  反证：绕过守卫后接受率从 0.9 **崩到 0.175–0.470**、argmax 一致率 0.333 ⇒ **守卫真在挡东西**。
- **★ 下一个问题**：draft 要维护一整套自己的 KV，把 target 可用容量砍掉 49% ⇒ 能不能只留最近的窗口？→ `[06]`。
- **教训**：**"加了一个功能"之前先测它到底是资产还是负债**；用**承重性反证**证明守卫不可省，比"我加了守卫"有力得多。

### [05] 批量投机：0.77× → 1.19×（★ 这个数字后来被自己的表推翻，见 `[09]`）
- **反馈**：B=4 时投机**输给普通解码**（C/U = 0.77）；结构证据是**验证图只有单请求形状 ⇒
  B>1 整条验证退回 eager**（命中 3–7、退回 48–72）；且 draft 逐请求串行 = **每轮 24 次独立前向**。
- **判断**：两处开销都随 batch **线性增长** ⇒ 批量 draft + 按 `(B,k)` 拍验证图。
- **结果**：`S2/C = 1.54×`；验证图 **37/37 全命中、0 退回**；draft 前向/轮 **24 → 6**；
  **B=4 从 0.77× 翻到 1.19×**。顺带修掉第 3 个静默 bug（全接受时 draft 有位**永不回头补**，
  接受率 0.866 → 0.987、同负载 ×1.32）。
- **★ 下一个问题**：这个 1.19× 依赖什么？→ 见 `[09]`：**依赖 α≈0.99 的合成素材**，还原接受率就掉回 0.897×。
- **教训**：**凡是投机相关的加速比，必须连报接受率**，否则这个数字不可迁移。

### [06] 滑窗 + 解耦分配：拿到 +16~21%，但**机制没钉死**（诚实挂账）
- **反馈**：draft 共用主模型块号 ⇒ **块数必须相等、无法缩小**；target 可用容量被 draft 吃掉近一半。
- **做了什么**：给 draft 做块级**环形缓冲滑窗**（`slot(p) = ring[(p//bs)%M]*bs + p%bs`）+ **解耦分配**；
  用逐次前向逐位对拍定位 3 个静默 bug（含一个"补齐那趟前向的可见上下文从 1031 被砍到 7"）。
- **结果**：`W ≥ 上下文` 时接受率与全上下文**逐位相同**（226 次前向 logits 0/226 不同）、每轮 0.78–0.86×；
  **解耦分配本身 +16~21%、零精度代价**。
- **★ 挂账（诚实）**：那 +20% **不是**来自"读的 key 变少"（ctx 逐条相同，**已否**）、
  **也不是**来自块表宽度（**已否**）——**具体环节尚未隔离**。
- **教训**：**拿到收益 ≠ 理解了收益**。归因没钉死就明确写"未隔离"，不要编一个机制出来。

### [07] 量化的第一刀不够 → 不是方向错，是**剂量不够** → 加剂量翻倍
- **反馈**：Q1 只量化 draft FFN ⇒ 每轮只 −3.6~4.5%，**未达事前定的 +20% 门槛**。
- **判断**：不是方法不行。算一笔字节账：FFN 只占 draft 权重 44.3%，draft 又只占一轮权重流量 47%
  ⇒ **一轮总字节只降 9.9%**。
- **做了什么**：扩到 draft 的**全部线性层**（196 个模块）；对 `nanovllm/` **零生产代码改动**
  （复用上一轮的开关，只换一个 `quant_config.json`）。
- **结果**：每轮 **−6.4~7.1%**（比 Q1 翻倍）；B=1 四档 **36/36 配对全胜**（符号检验 p≈1.5e-11）；
  精度代价只从 +0.337% 涨到 **+0.455%**（因为 **attention 比 FFN 更耐量化**），省下的字节 22.1% → **36.9%**。
- **★ 下一个问题**：收益为什么只有 7% 而不是估的 10%？→ 逐条对账："每 100 MB 省多少 µs"
  **两档完全一样**（87/96 vs 89/96）⇒ 证明这是**纯字节账**，没有别的机制，也就能外推。
- **教训**：**未达门槛要如实报**，并且**分清是"方向错"还是"剂量不够"** —— 后者加剂量就能救。

### [08] 量化露出"显存反而变多" → 先怀疑 kernel 模块 → 被逐字节账目否掉 → 构造期直载
- **反馈**：权重真省了 0.4 GB，但 **KV 池反而 174 → 170 块**；`used` 稳定多出 0.19 GB，两次复现。
- **判断（第一版，★ 错的）**：怀疑 CUDA context 里多了量化 GEMM 的 **kernel 模块** ——
  理由是"这类占用只出现在 `nvidia-smi` 的 `used` 里"。
- **做了什么**：① 先修掉一个真 bug（**split-K 的 fp32 scratch 顶高 peak**，找回 8 块）；
  ② 在**预算时刻**补打点，把 `used` 拆成 `current + I + O`（`I = reserved−current`，`O = used−reserved`）。
- **结果**：**`ΔO` 逐字节为 0**（三档 `O` 全是 351,797,248）⇒ **"kernel 模块"猜测被实测否掉**；
  `ΔI = +0.589 GiB` 且 **`I` 恒等于 `inactive_split`**（全是**不可回收的 split 残块**，
  warmup 头尾两次 `empty_cache()` 一分钱没还回去）。改**构造期直载 int8**（bf16 全程不上卡）⇒
  **KV 池 170 → 180 块，反超 BF16 基线的 174 块**；**同容量对照**证明设备总占用仍低 0.564 GiB。
- **★ 下一个问题**：多出来的容量换得来速度吗？→ `[10]`：**换不来，它只换容量**。
- **教训**：**最顺手的假设也要写成"可证伪的形式"再去测**。这次是靠把 `used` 拆成三块、
  拿到 O 精确为 0，才把那个"听起来很合理"的解释否掉的。

### [09] 招牌数字被自己的统一验收表推翻
- **反馈**：统一验收表跑出来 —— 滑窗**没有**复现台账的 +9.7%；**B=4/4K 时投机那一整条栈只有 0.71×**；
  招牌数字"B=4 从 0.77× 翻到 1.19×"**没有出现**。
- **判断**：不是谁算错了，是**口径不可迁移** —— 那个 1.19× 是在 **α≈0.99 的合成池化素材**上测的，
  而自然长文 α 只有 **0.61–0.78**。
- **结果**：真实边界是 **整体 1.74×–5.82×**，而且**最大的一截来自 CUDA Graph（2.4–3.6×）而非投机本身**；
  投机那一段单独看是 **1.60×（B=1/1K）→ 0.71×（B=4/4K，batch 大时净亏）**；`U` 零点本身还带 **±4%** 不确定度。
  同时**滑窗的容量收益也不是无条件的**：`滑窗省显存 ⟺ M × max_num_seqs < pool 块数(174)`，
  与上下文长短无关（两个实测点逐字节对上：并发 8 → target 197，并发 12 → 141）。
- **★ 下一个问题**：那下一步该打哪儿？→ 表里已给出判据：**在 B=4/ctx=4096 把 `G→S6` 从 0.71× 拉过 1.00×**，
  而不是再去动 B=1 那条贴着带宽上限的路。
- **教训**：**口径不一致的数字合集，等于没有数字。做完统一验收之后，以前所有"招牌数字"都要重新审一遍。**

### [10] 最新那一刀的边际收益掉进噪声 → 据此切去"整理"
- **反馈**：`S5→S6`（直载 int8）速度 = **1.000–1.004×**，落在噪声地板（0.05–1.06%）**之内**。
- **判断**：它**本来就该只换容量**（两档 int8 权重逐位相同，速度上不该有差别）——
  所以这个 1.000 恰恰是**"测量可信"的证据**，不是失败。
- **结果**：容量确实拿到了（滑窗组 target 141 → 152 块）；据此回答判断题：
  **新技术的边际收益已低于"把已有成果合成一组可复算数字"** ⇒ 把这一轮资源转向统一验收。
- **教训**：**"新功能没提速"不一定是坏消息** —— 要能判断它是"没效果"还是"测不出/本来就不该有效果"。
  它同时给出了**什么时候该从"加功能"切到"做整理"**的判据。

### [11] 统一验收里的两个污染源，被同进程探针钉死
- **反馈**：`U`（本该是 target-only 的零点）的 TTFT 在组与组之间差 **2.4 倍**（78.7 / 161.2 / 186.0 ms），
  而噪声地板只有 0.12–0.5%。
- **判断（第一版）**：怀疑 4 卡并行争用 —— **先把它排除掉**（同配置并行 vs 串行 TTFT 差 ≤3.2%）。
- **做了什么**：写**同一个进程里的三条件探针**（有 draft / 摘掉 draft / 有 draft 但窗口压回 0）。
- **结果**：真因是两处代码 —— ① `model_runner.py:705` 的
  `if self.draft_model is not None: self._run_draft_prefill(...)` **不看 `spec_k`** ⇒
  只要进程加载了 draft，prefill 就白跑一遍 0.6B（**77.8 → 45.7 ms**）；
  ② `_run_draft_prefill_window` **按 `token_ids` 重算整个窗口、不认前缀缓存**
  （压回 `window=0` → **77.5 ms ≈ 77.8 ms**，归因闭合）。
- **★ 下一个问题**：混合调度（P12）若把 prefill 切成 chunk，**这个 draft 前向就会被跑 N 遍** ⇒ 必须先解决。
- **教训**：**先排除最容易想到的解释（并行争用），再找真因**；**同进程多条件探针**是把
  "跨进程对比的噪声"变成"闭合归因"的关键手法。

## 3. ★ 被我们自己推翻的结论清单（面试最值钱的一节）

**"我做过什么"不难讲；"我被数据打过脸、并且承认了"才是可信度的来源。**

| 谁提的 | 当时的假设 | 怎么被推翻 |
|---|---|---|
| 任务书 | P1 把自写 attention 接进引擎是**第一条主线** | f 只有 8–9% ⇒ Amdahl 上界 +10%、实测 **+3%** ⇒ 降级 |
| 用户 | "FFN 比 attention 更耐量化" | **我们自己实测就否了**：draft 只量化 attention **+0.132%** vs 只量化 FFN **+0.316%** |
| 主 agent | "我们的量化方法太粗糙，还有方法空间" | **文献**：有人在 **Qwen3-0.6B 本体**上测 RTN8 / g128-RTN8 / GPTQ8 / AWQ8 → **全部 ±0.005 内** ⇒ 8 位下换方法无差异 |
| 双方共同 | "挑安全的层量化（中间 20 层）" | **文献**：损伤是**弥散**的；"把预算花在全局粒度上比保护关键层好 21–52 个点" |

| 主 agent（文档） | "split-K 把 peak 顶高 **1.285 GB**" | 那是 `peak − current`；**真值是 0.531 GiB**（原始日志 10.250 → 9.719） |
| 主 agent（文档） | "`used` 是**驱动级**占用" | `used = total − free`，**包含** PyTorch 分配的保留空间 |
| 台账 | "B=4 提速 **1.19×**" | 只在 **α≈0.99 的合成素材**上成立；自然长文 **0.71×** |
| 台账 | "滑窗让 target 容量 **+50~74%**" | 只在 **`M × max_num_seqs` < pool 块数**时成立；并发一高就翻负 |

## 4. 面试问答速查（骨架）

| 会问什么 | 怎么答（一句话 + 一个数字） |
|---|---|
| **你怎么找瓶颈？** | 先建约束地图再优化：profiler 把 decode 的 device time 分解成 `GEMM 79.27% / attn 9.24% / elementwise 8.37%`；GEMM 已跑到 **763 GB/s = 峰值带宽 81%** ⇒ 只剩量化这一条路 |
| **你怎么决定该不该做？** | 先算 Amdahl 上界：attn 占 8–9% ⇒ 上界 **+3%** ⇒ 直接收手，把资源挪到批量执行 |
| **你怎么保证数字可信？** | 每个数配**噪声地板**；配对/交替测量 + 符号检验；**逐字节等价性对拍**（bitwise md5 比每步的 tokens/positions/block_table/slot）；**承重性反证**（绕过守卫则接受率 0.9 → 0.175） |
| **你踩过最大的坑？** | **口径混用**：`tok/s` 会被轮数随机性淹没 ±10~20%，所以主指标改用"每轮耗时 = 墙钟 ÷ 轮数"；以及**不能用大类占比给具体技术背书** |
| **什么时候收手？** | 两种：上界不够（P1 +3%）；边际收益掉进噪声（`S5→S6` = 1.000 ⇒ 转去做统一验收） |
| **你做过最反直觉的一件事？** | 量化让权重省了 0.4 GB，KV 池却**少了** 4 块 —— 最后定位到**分配器内不可回收的 split 残块**，改用构造期直载后 **170 → 180 块，反超 BF16 基线** |
| **你的结果有什么边界？** | 整体 1.74×–5.82×，但**大头是 CUDA Graph 而非投机**；投机那一段是 **1.60×（B=1/1K）→ 0.71×（B=4/4K，净亏）** |
| **讲一个失败的结论** | 滑窗拿到的 +16~21% **机制至今没隔离**（已排除"读的 key 变少"和"块表宽度"）——**拿到收益不等于理解了收益** |
