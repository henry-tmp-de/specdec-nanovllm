## 4. 表格怎么读：三个"每轮"口径 + 结构证据

### 4.1 三个"每轮"口径（★ 别只看第一个）

| 口径 | 定义 | 用途 |
|---|---|---|
| `ms/轮` | **墙钟 ÷ decode 轮数**（含 prefill 摊销） | 任务书字面口径 |
| `ms/轮(稳态)` | 各 decode 轮耗时的均值（**剔除 prefill**） | 去掉首 token 的那笔钱 |
| **`ms/轮(maxB)`** | **只在 active B = 最大 batch 的那些轮上取中位数** | **★ 去掉"收尾尾巴"** |

### 4.2 ★ 收尾尾巴（ragged tail）—— 一个必须先讲清的结构效应

`out=256` 的 4 条并发请求**落地速度不同**，先跑完的会退出，于是尾部出现 B=3 / B=2 / B=1。
而引擎的 draft 图 / 验证图**只按精确 B∈{1,2,4} 捕获**，**B=3 整条退回 eager**
（`ModelRunner._forward_group` / `run_verify_forward` 的 `shape_not_captured(B=3,k=6)`）。
于是尾部每一轮贵好几倍，`墙钟÷轮数` 被它拉高。

**这不是猜测，是逐轮记下来的**（表里 `rounds_by_B` 与 `verify_graph_fallbacks` 两列直接看得到）：

```
B=4/ctx=1024, S1：rounds_by_B={'1':4,'2':10,'3':39,'4':50}
                 verify_graph_fallbacks={'batch_verify_graph_off': 100}
   → 39 轮跑在 B=3（没有图）→ ms/轮 73.0，而 ms/轮(maxB) 只有 45.2
```

**所以：跨档比较一律读 `ms/轮(maxB)`；`ms/轮` 与 `tok/s` 只能当"这条尾巴也算进去"的端到端口径看。**
（尾巴在真实服务里是存在的，所以它不是"错的数字"；但它由采样轨迹决定，**不适合用来比较两个档**。）

### 4.3 `catchup_forwards`（= P7-A 修复生效的直接证据）

表里每一档都记了 `catchup_forwards`（每轮平均的"草稿补齐前向"次数）。
**所有投机档都是 0~1 次/轮**（只有"全接受"轮会补 1 个 token 的缺口）。
对照台账 §2.6 修复前的 **补齐 16660 token / 单步 17.31 s**，可以确认前缀缓存命中不再触发全量补齐。

### 4.4 接受率（★ 投机档必看）

自然长文的接受率落在 **0.609–0.777**（B=1/1K 最高，B=1/4K 最低）。
台账 §0 的警告在这里被实测复现：**同一套优化，接受率 0.78 时是加速，0.61 时接近打平。**

## 5. 并行 vs 串行（判据 (a)(b)）—— 实测过，结论：**采用串行**

### 5.1 为什么会有这个问题

引擎原来硬编码 `tcp://localhost:2333`，同一台机上只能跑一个实例。
我加了一个环境变量覆盖（`nanovllm/engine/model_runner.py` 的 `_RENDEZVOUS_PORT`，
`NANOVLLM_PORT`，**默认 `"2333"`，默认行为一行没改**），于是多个独立实例能铺到多张空卡上。

### 5.2 条件 (a)：墙钟真的加速了吗？—— **是**

同一份代码、同一组负载，两组数据：

| 组 | 并行（4 进程 / GPU 0-3） | 串行（1 进程 / GPU 0） |
|---|---:|---:|
| `win` | 365 s | 364 s |
| `win_int8` | 383 s | 384 s |
| `win_int8_direct` | 394 s | 385 s |
| `core` | 751 s | 768 s |
| **合计** | **751 s**（= 最长的那个组） | **1901 s**（= 四个组相加） |

→ **并行把总墙钟从 1901 s 压到 751 s，2.53×**。
拿不到 4× 是因为四个组**负载不均**：`core`（含 255 轮 × 4 cell 的 eager `U`）自己就要 751 s，
其它三个组各 ~380 s。四张卡跑"一个 751 s + 三个 380 s"只能压到 751 s 那一档。

★ 更关键的一行：**每个组自己的墙钟几乎不变**（365 vs 364、383 vs 384、394 vs 385、751 vs 768）。
也就是说 4 个进程同时跑**没有让任何一个组变慢**（±2%），
`CPU dispatch 争用 / 磁盘 I/O 争用 / 内存带宽` 这几项担心在这套负载上**没有兑现**。

### 5.3 条件 (b)：数字落在噪声地板之内吗？—— **投机档是，`U` 不是**

同一配置、并行 vs 串行的 `ms/轮(maxB)` 相对差：

| 档 | 差值的范围（4 个 cell） | 该档的噪声地板 |
|---|---|---|
| `G` / `C` / `S1` / `S2` | **−0.01% ~ +0.87%**（除 S1 两处 +2.7~3.0%） | 0.04% ~ 0.74% |
| `S4` / `S5` / `S6` | **−0.54% ~ +1.17%** | 0.14% ~ 0.69% |
| **`U`** | **−3.6% ~ +4.7%** | 0.10% ~ 0.74% |

★ **`U` 是唯一一个跨条件差异明显超出噪声地板的档**，原因很具体：**`U` 是 eager**，
它的每轮耗时**被主机侧 Python dispatch / kernel launch 主导**（`U` 的 `G` 对照恰好证明这一点：
`G/U` 每轮 0.28~0.43×，而两者算的是同一件事）。CPU 侧的抖动（频率、调度、页缓存）
会直接进 `U` 的墙钟，所以它的**跨进程/跨条件不确定性是 ±4% 量级**，
而拍图的档（G/C/S1/S2/S4/S5/S6）只有 <1%。

### 5.4 结论

- **(a) 成立、(b) 对除了 `U` 以外的所有档成立** → 并行"能用"，**但**：
  - 串行的四组数据**已经全齐**（`out/acc_serial/`、`out/acc_serial2/`），没有理由再把主表换成并行；
  - `U` 是这张表的"零点"，它的跨条件不确定性（±4%）是**系统性的**，
    合到并行条件里只会让"整体提升"的分母多一个 ±4% 的抖动；
  - 并行只对"缩短总墙钟"有利，对本表的**可比性**没有好处。
- **所以：主表采用【串行、单卡、单进程】的 `acc_serial*` 数据**；
  `out/accv3/`（第一版 4 卡并行）**只作对照，不混进正式表**。
- ★ 附带结论（有价值的负结论）：**`U` 作为基线本身就带 ±4% 的不确定度**，
  因为它是 eager、CPU-bound 的。任何"相对 U"的比值，分母都不该当成精确值。

## 6. 归因：`U` 的 TTFT 为什么在组与组之间差 2.4 倍？

**现象**（同一个 `U` 配置，B=1/ctx=4096，第一版并行数据的 TTFT）：core 78.7 ms / win 161.2 / win_int8 186.0。
当时自报噪声地板只有 0.12%~0.5%，所以这**不是噪声**。

### 6.1 先排除"并行争用"

用同一配置并行 vs 串行各测一遍，TTFT（ms）：

| 组 | B=1/1K | B=1/4K | B=4/1K | B=4/4K |
|---|---:|---:|---:|---:|
| core | 74.1 → 76.4 | 78.7 → 79.2 | 167.8 → 168.3 | 211.2 → 210.6 |
| win | 76.8 → 75.0 | **161.2 → 158.5** | 228.8 → 225.7 | 605.2 → 595.1 |
| win_int8 | 84.1 → 83.8 | **186.0 → 185.2** | 255.6 → 255.4 | 713.8 → 705.4 |

→ **并行与串行的 TTFT 差 ≤3.2%，组与组之间的 2.0~2.4× 差在两种条件下完全一样。**
**不是争用。** 是配置差异。

### 6.2 真正的原因（`scripts/acceptance_prefill_probe.py`，同进程内三个条件，ctx=4096）

| 组 | ① 有 draft（= 表里 `U`） | ② 摘掉 draft | ③ window 强制 0 |
|---|---:|---:|---:|
| core（window=0） B=1 | **77.8** | 45.7 | — |
| win（window=4608） B=1 | **158.0** | 45.8 | **77.5** |
| win_int8（window, int8） B=1 | **183.4** | 45.2 | 84.9 |
| core B=4 | **205.5** | 164.0 | — |
| win B=4 | **586.2** | 165.2 | **206.6** |
| win_int8 B=4 | **702.4** | 166.0 | 213.9 |

（同一次运行里 hook 报的 TTFT 与插桩测的 prefill 墙钟逐行吻合，差 <1% ⇒
**表里的 TTFT 就是 prefill 那一步**，口径没问题。）

**两条结论：**

1. ★ **`U` 不是"target-only"**：`ModelRunner.run()` 里
   `if self.draft_model is not None: self._run_draft_prefill(...)` **不看 `spec_k`** ——
   只要进程里加载了 draft 模型，prefill 就要多跑一遍 0.6B 前向。
   **摘掉 draft 后 ctx=4096/B=1 的 TTFT 从 77.8 → 45.7 ms（纯 target）。**
   （`U` 的 **decode 轮耗时不受影响** —— `U` 的 decode 路径根本不碰 draft；只有 TTFT 这一项被污染。）
2. ★ **滑窗档的 draft prefill 比全上下文贵 3.5×**（B=1：158.0 vs 77.8；B=4：586.2 vs 205.5）：
   `_run_draft_prefill_window` 是**按 `token_ids` 把整个窗口重算一遍**（`ids.extend(seq.token_ids[w0:end])`），
   **不认前缀缓存**；而全上下文路径只用 `prepare_prefill` 算出的"未命中尾巴"（这里只剩 1 个块）。
   同一进程里把 `spec_draft_window` 压回 0，TTFT 立刻回到 **77.5 ms ≈ core 的 77.8 ms** —— 归因闭合。

**所以这一条的正确读法是：滑窗档的 TTFT 列有实现上的额外代价，不是"滑窗本身慢"。**
它不影响 decode 的每轮耗时。

## 8. 整体提升（`U → S6`）与它的边界


### 8.1 主数字：`U → S6`（`tok/s(maxB)`，同 cell 内 U 与 S6 各自都在自己的进程里测）

| 负载 | `U` | `G` | `S2` | `S6` | **U → S6** | **G → S6（只算投机那一截）** |
|---|---:|---:|---:|---:|---:|---:|
| B=1 / ctx=1024 | 21.7 | 79.2 | 121.4 | 126.5 | **5.82×** | 1.60× |
| B=1 / ctx=4096 | 21.7 | 77.9 | 65.1 | 86.3 | **3.97×** | 1.11× |
| B=4 / ctx=1024 | 100.7 | 289.1 | 257.5 | 279.2 | **2.77×** | **0.97×** |
| B=4 / ctx=4096 | 100.9 | 245.1 | 166.4 | 175.1 | **1.74×** | **0.71×** |

**一句话：整体提升是 `1.74× ~ 5.82×`，取决于 batch 与输入长度 —— 只报一个数会被误读。**

### 8.2 ★ 这个数字的边界（必须一起写）

1. **提升的大头不是投机，是 CUDA Graph。** `G/U = 2.43~3.64×`。
2. ★★ **把「投机那一截」（`G → S6`）单独拎出来看：B=1 是 `1.11~1.60×`，B=4 是 `0.71~0.97×`
   —— 在 B=4 上，整条投机栈（含批量 draft、验证图、滑窗、int8）比
   「普通解码 + CUDA Graph」**更慢**。**投机优势随 batch 缩小是固有性质**（验证要付 `B·(k+1)` 的算力），
   本表用自然长文把它量化了：B=4/ctx=4096 时是 **0.71×**。
3. **接受率是这里的隐藏自变量**：自然长文的 α 落在 **0.609~0.777**。
   同一个 `G → S6`，ctx=1024（α≈0.77）是 1.60×，ctx=4096（α≈0.68）只有 1.11×。
   ★ 台账 §0 的警告（合成素材会把 α 抬到 0.95–0.99）在这里被实测复现：
   **表里任何加速比都必须和它那一行的 α 一起读。**
4. **`U` 这个零点本身带 ±4% 的不确定度**（它是 eager、CPU-bound；见 §5.3）。
   所以 `5.82×` 这类数字的分母不该被当成精确值。

### 8.3 逐档的边际贡献（看哪一刀值钱、哪一刀在噪声里）

| 这一刀 | 打在哪 | B=1/1K | B=1/4K | B=4/1K | B=4/4K | 读法 |
|---|---|---:|---:|---:|---:|---|
| `U → G` CUDA Graph | 压 per-step 固定开销 | **3.64×** | **3.58×** | **2.87×** | **2.43×** | ★ 全表最大的一刀；batch 越大越小，但**始终最大** |
| `G → C` 旧投机实现 | — | 1.53× | 0.84× | 0.34× | 0.34× | 只在 B=1/短上下文赢过"普通解码+图"；**B=4 亏 3 倍**（裸投机是净亏） |
| `C → S1` 批量 draft | 去掉 `B×k` 次单序列前向 | 1.00× | 1.00× | **1.86×** | **1.56×** | 只在 B>1 有价值（B=1 无处可批） |
| `S1 → S2` 验证图 | 去掉 B>1 的 eager 验证 | 1.00× | 1.00× | **1.42×** | **1.29×** | 同上，只在 B>1 有价值 |
| `S2 → S4` 滑窗+解耦分配 | — | 0.99× | 1.00× | 0.96× | 0.92× | ★ **本表没复现出正收益（见 §8.4）** |
| `S4 → S5` draft int8 全线性层 | 少读 36.9% 的 draft 字节 | 1.05× | 1.33×¹ | 1.13× | 1.14× | 有收益，但 B=1/4K 那一格混了轨迹差异¹ |
| `S5 → S6` 构造期直载 int8 | 把量化显存账翻正 | **1.002×** | **1.001×** | **1.004×** | **1.000×** | ★★ **速度上完全等于 0**（见 §8.5） |

不能当成纯速度比。

★ **跨进程的行**：`S4/S5/S6` 与 `S2` 不在同一个进程里（滑窗的池布局只能在 init 期定），
所以这三行的性价比是**跨进程比值**，带着 §5.3 量到的 ~1–2% 跨条件不确定度。
`U/G/C/S1/S2` 五个档是**同进程配对**（不确定度 <1%）。

### 8.4 ★ 滑窗（`S4`）在本表没有复现出正收益 —— 如实报

台账 §2.7 记的是「窗口 ≥ 上下文时：每轮 0.78–0.86×、吞吐 +9.7%（自然长文）」。
本表在自然长文 + `W=4608 ≥ ctx` 下**没有复现**：`S4/S2 = 0.92~1.00×`（每轮耗时 maxB 1.000/1.000/1.007/1.019）。

**差异的可能来源（未逐条验证，如实列出）：**
- 本表的窗口取 **`W=4608`**（`M=18` 块），台账那组实验的主点取 **`W=1280`**（`M=5`）。
  台账自己写了「表宽比 W=0 宽时会有 ~5e-4 的数值扰动」——本表 `M=18` 比全上下文所需的 5/17 块都宽，
  这个扰动足以让采样轨迹发散（实测 α 0.6376 vs 0.6755、输出 md5 不同），
  **于是 `S4` 与 `S2` 不是同一条轨迹，比值不再是"同一负载下更快的倍数"**。
- 本表的 `S4` 与 `S2` 是**跨进程**比较（滑窗必须在 init 期开）。
- 本表的 `max_num_seqs=12`（为了给 in-group 对照留块号空间，见 §7.4），台账那组是别的取值。

**结论：在本表的条件下，滑窗这一档的边际收益落在噪声/轨迹差异里，不能宣布为正。**
（这不是否掉台账 §2.7，而是说明它**依赖于窗口取值与轨迹**，换一组就没了。）

### ★ 8.4.1 后续补测：把"滑窗判负"这个读法纠正过来（2026-10-12）

本节那张 `S2 → S4 = 0.92~1.00×` 让"滑窗"看起来是负的。**这个读法是错的，已经被专项补测纠正**：

- **本节判负的直接原因不是滑窗，是 `max_num_seqs`。** 为了给 §7.4 那个**最后没有被采用**的
  组内 `S2` 对照留块号空间，滑窗组把 `max_num_seqs` 撑到 **12** ⇒ draft 私有池 **216 块**
  **白占约 4 GB** ⇒ 连「省显存」这件事本身都被吃掉了。**池子大小只该由真实并发决定。**
- **4K 是滑窗最没用的角落。** 容量账是 `滑窗省显存 ⟺ M × max_num_seqs < target 池块数(173)`，
  而 `M` 要盖住上下文才不损接受率 ⇒ **上下文越长、这条判据越容易满足、容量收益越大**。
- **长上下文的实测**（4 组各一进程、`max_num_seqs=4`、ctx 4K/8K/16K、B 1/2/4）：
  M=33 → target **206** 块（+19%）、M=18 → **252**（+46%）、M=5 → **293**（+69%）；
  ★ **16K 下请求 4 并发时普通投机只能真正跑 2 条**（排队到 TTFT **13.6 s**），只有 M=5 能跑满 4 条；
  ★ 且 `8K/B=1`、M=33 时**输出 md5 与普通投机逐字节相同**（零代价）。
  代价：M=33 在 8K 的 draft prefill 占 prefill **82.8%**、TTFT 3.7×。

**完整数据、口径、噪声地板、复算命令、边界：见 `docs/长上下文-滑窗容量.md`。**
本节 §8.4 的表格保留原样（它是当时那组配置的真实读数），但**不能再拿去论证"滑窗没用"**。

### 8.5 ★★ `S5 → S6` 的速度收益是 0.000 —— 最新那一刀只换了容量

四个 cell 的 `S6/S5` 在 `tok/s(maxB)` 上是 **1.000 / 1.001 / 1.004 / 1.002**，
`ms/轮(maxB)` 上是 **0.998 / 1.002 / 0.999 / 1.002**，全部落在噪声地板（0.14%~0.56%）**之内或边缘**。
**机制上讲得通**：两档产出的 `(int8 权重, scale)` 本来就是**逐位相同**的（台账 §2.12 已验证），
图、kernel、字节流量完全一样 —— 唯一被改的是**分配顺序**。

所以 P9 的收益是**容量**，不是速度：

| 配置 | target 可用块数 |
|---|---:|
| BF16 draft（`win` 组，max_num_seqs=12） | 141 |
| INT8 就地（`win_int8`） | **135**（−6 块 = 台账 §2.10/§2.11 那个负结论） |
| INT8 直载（`win_int8_direct`） | **152**（比就地 **+12.6%**，且**反超 BF16 基线 +11 块**） |

★ 在**没有滑窗**的口径（`max_num_seqs=8`，`out/acc_serial/`）下同一组数是
**197 / 191 / 208** —— 方向与幅度一致，与台账 §2.12 记的「170 → 180 块、反超 BF16 的 174」同构。

### 9.2 测不出 / 未定位的

- **滑窗那一刀的干净归因**：in-group `S2` 控制组在 B=1/ctx=1024 **逐位等同** core 的 `S2`（md5 相同 ✅），
  但在 B=1/ctx=4096、B=4/ctx=1024、B=4/ctx=4096 上 **`α` 明显偏离**（0.357/0.384 vs 0.676/0.634），
  输出 md5 也不同。**为什么运行期把 `spec_draft_window` 压回 0 在 B=4 下不等价 —— 未定位。**
  可以确定的只有：**这条"双向回退"在 B=4 下不是一条可以用来对比的路子**（默认路径不受影响，默认窗口就是 0）。
- **`B=4` 下 `S5/S4`（int8 的收益）是否被轨迹差异放大或掩盖**：α 不同（0.640 vs 0.605），
  所以 `1.13~1.14×` 里有多少是 int8、多少是"多落地了几个 token"——**混在一起，没拆开**。
- **`U` 的 ±4% 来源**：只归因到"它是 eager、CPU-bound"这一层；
  具体是 CPU 频率、调度还是别的 —— **没测**。
- **`_run_draft_prefill_window` 为什么不认前缀缓存**：这是 E1 现象的机制（它按 `token_ids` 重算整个窗口），
  但"这是不是有意的设计"——**没定**。
- **`RAGGED TAIL` 的量化影响**：只能给"逐轮 `rounds_by_B` + `verify_graph_fallbacks` 计数"这种结构证据，
  **不能**给出"如果 B=3 也拍图，B=4 那几个 cell 会变成多少"——**没测**。

### 9.3 ★ 正面回答那个判断题

> **现在再做一个新技术点的边际收益，是不是已经低于「把已有的优化 + bug 修复 + 一批测量
> 合成一组能被复算的数字」？**

**回答：是。而且本表本身就是这个结论的证据，不是感觉。**

数据依据（全部来自本表）：

1. **最新那一刀（P9 / `S6`）的速度边际收益是 `1.000~1.004×`**（§8.5），
   **落在噪声地板之内**。它的价值是容量（135 → 152 块），**不是速度**。
2. **阶梯上越靠后的刀越小**：`G = 2.4~3.6×`（旧）→ `S1 = 1.6~1.9×`（只在 B>1）→
   `S2 = 1.3~1.4×`（只在 B>1）→ `S4 ≈ 1.0×`（本表甚至略负）→ `S5 = 1.05~1.14×` → `S6 = 1.000×`。
   **最大的那个数（CUDA Graph）是最早做的那一项。**
3. **这张表改变了项目自己的结论口径**：
   - 台账里那个「B=4 从 0.77× 翻到 1.19×」在本负载（自然长文、α≈0.64）下**没有出现**：
     `S2/U = 1.65×`（B=4/4K）但 `S6/G = 0.71×` —— **投机整体在 B=4/4K 是净亏**；
   - 「整体提升」不是一个数，而是 **1.74×~5.82×**，**离开 cell 就没意义**。
   这些不是"新发现的技术点"，而是**把已有数字放到同一把尺子上之后才看得见的**。
4. **本表还顺手挖出 6 条以前没记录过的事实**（都不需要新算法）：
   ragged tail 让 `墙钟÷轮数` 偏差可达 1.6×（§4.2）；
   `B=3` 没有图 → 整条 eager；
   `U` 的 TTFT 被 draft prefill 污染、纯 target 是 45.7 ms 而表里是 77.8（§6）；
   滑窗的 draft prefill 重算整个窗口、不认前缀缓存（§6.2）；
   `U` 作为基线带 ±4% 的 CPU-bound 不确定度（§5.3）；
   运行期关滑窗在 B=4 不等价（§9.2）。
   **这六条里任何一条，都比"再做一项优化"更能改变对系统的判断。**

**所以：方案的重点应该放在「统一验收 + 把边界钉死」，而不是再开一条新技术线。**
如果一定要再开，判据应该是：**在 B=4/ctx=4096 这一格上，能把 `G → S6` 从 0.71× 拉过 1.00×** ——
也就是解决"batch 大时投机净亏"这件事，而不是再去动 B=1 那 79% 已经贴着带宽上限的 GEMM。
