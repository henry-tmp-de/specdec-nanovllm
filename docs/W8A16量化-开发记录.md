## Phase 0 · 上界测量（硬闸门）

### 0.0 口径

* **device 时间**（torch.profiler 的 `device_time`）≠ 墙钟。下面凡是"GEMM 时间"都是 device time。
* **decode tok/s** = `1/TPOT`（TokenDeliveryHook，按批交付计），**不含 prefill / 排队**；
  与台账里的 `wall tok/s`（总 token / 总墙钟）是两套口径，不要混。
* 权重字节数**按 storage 去重**：Qwen3 `tie_word_embeddings=True`，
  `named_parameters()` 会把 lm_head 与 embed_tokens 列两遍，直接求和会多算 0.78 GB。
* 每组计时 **5 次取中位数**，组间范围一并给出（本卡很稳，decode 的组间范围通常 <0.5%）。
* 时间（hook）与 profiler **分开跑**。
* 工具：`scripts/p0_weight_bw.py`；日志 `p0_Qwen3-4B.log` / `p0_Qwen3-1.7B.log` / `p0_Qwen3-0.6B.log`。

### 0.1 Amdahl 上界（用实测分解，不靠推算）

Qwen3-4B、graph on、B=1/4 × ctx=1024/4096、输出 256。**device 每步分解**：

| B | ctx | device ms/step | GEMM ms | GEMM% | attention ms | 其它 ms | 墙钟 TPOT ms |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 1024 | 12.198 | **10.458** | 85.7% | 1.069 | 0.671 | 12.588 |
| 1 | 4096 | 12.443 | **10.516** | 84.5% | 1.238 | 0.689 | 12.856 |
| 4 | 1024 | 13.306 | **10.647** | 80.0% | 1.958 | 0.701 | 13.849 |
| 4 | 4096 | 15.782 | **10.703** | 67.8% | 4.364 | 0.715 | 16.322 |

**★ 这张表里最重要的一列是 GEMM 那一列：10.46 / 10.52 / 10.65 / 10.70 ms —— 与 batch 和上下文长度几乎无关。**
batch 从 1 涨到 4、上下文从 1K 涨到 4K，GEMM 只涨 2.3%。这**直接证明 decode 的 GEMM 是纯权重流式**
（读一遍 8.045 GB 权重，与算多少条请求无关），而不是算力瓶颈。

**可量化字节的构成**（Qwen3-4B，36 层）：

| 部分 | 字节 | 每步是否流式 | 本方案是否量化 |
|---|---:|---|---|
| block 线性层（q/k/v/o/gate/up/down） | 7.26 GB | 是 | **是** |
| lm_head（与 embed_tokens **共享存储**） | 0.78 GB | 是（GEMM） | 否（见 §Phase 1） |
| **合计每步要读的权重** | **8.045 GB** | | |
| embedding gather（只读 B 行） | ~0 | 否 | — |

量化后每步权重 = 7.26/2 + 0.78 = **4.41 GB → 比值 0.548**。
（如果连 lm_head 也量化：4.02 GB → 0.500。只多 9%，代价是动输入/输出表示，本轮不做。）

**Amdahl 上界**：把 GEMM 时间按 0.548 缩放，非 GEMM 部分（含墙钟比 device 多出的那 ~0.4 ms
发行/启动开销）**完全不动**：

| B | ctx | 现值 ms | 上界（去量化免费，k=1） | 上界加速 | k=1.2 时 | k=1.3 时 |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 1024 | 12.588 | 7.861 | **1.601×** | 1.492× | 1.436× |
| 1 | 4096 | 12.856 | 8.105 | **1.586×** | 1.478× | 1.424× |
| 4 | 1024 | 13.849 | 9.036 | **1.533×** | 1.437× | 1.390× |
| 4 | 4096 | 16.322 | 11.472 | **1.423×** | 1.342× | 1.302× |

（k = 融合反量化相对"纯流式"的时间惩罚系数。k=1 是理想，k=1.2~1.3 是现实预期。）

**W4A16 的参照**（每参数 4bit + group128 的 0.0156 B ≈ 0.516 B，比值 0.258）：
每步权重 7.26×0.258+0.78 = 2.653 GB → 比值 0.330 →
B=1/4K 上界 **2.21×**（k=1）、1.88×（k=1.3），B=4/4K 1.90× / 1.66×。
**W4 的收益明显更大，但 4bit 必须要 GPTQ/AWQ 那类校准，工程量是本轮的 2–3 倍。**

### 0.2 ★ 小模型代理实验（决定性的那一个）

同一份代码、同一配置、只换模型。**权重字节比 vs decode 吞吐比**：

| 模型 | 权重 GB | B=1/4K decode tok/s | B=4/4K | 权重比(vs 4B) | tok/s 比 | GEMM 带宽 |
|---|---:|---:|---:|---:|---:|---:|
| Qwen3-4B | 8.045 | 77.78 | 61.27 | 1.000 | 1.000 | **765 GB/s** |
| Qwen3-1.7B | 3.441 | 160.51 | 108.73 | 2.338 | **2.064** | **778 GB/s** |
| Qwen3-0.6B | 1.192 | 290.25 | 161.19 | 6.749 | **3.732** | **686 GB/s** |

**★ 关键：看最后一列，不是看 tok/s 比。**

最后一行是「按权重字节算的 GEMM 有效带宽」= 权重字节 / GEMM 时间：

| 模型 | 权重 GB | GEMM ms/step（B=1→4, ctx 1K→4K） | GEMM 带宽 GB/s | 占实测天花板 842 |
|---|---:|---|---:|---:|
| Qwen3-4B | 8.045 | 10.458 → 10.703（+2.3%） | 752 – 769 | 89 – 91% |
| Qwen3-1.7B | 3.441 | 4.421 → 4.763（+7.7%） | 722 – 778 | 86 – 92% |
| Qwen3-0.6B | 1.192 | 1.737 → 1.884（+8.5%） | 633 – 686 | 75 – 81% |

**读法**：权重流式带宽**基本与 batch、上下文无关**（同一个模型内部四条几乎重合）。
权重规模缩小 **6.75 倍**（8.0 GB → 1.2 GB）后，带宽只掉 **10%**（765 → 686 GB/s）。
⇒ 把权重砍半（8.0 → 4.4 GB）时，带宽损失远小于 10%（因为 4.4 GB 仍在"大"那一侧），
**字节的节省几乎 1:1 变成 GEMM 时间的节省**。这就是"字节省得下来、时间也省得下来"的直接证据。

**那为什么 tok/s 比（3.732）明显小于权重比（6.749）？** 两个原因，都能量化，而且**都不在可量化项里**：

1. **KV 流量不缩水**。B=1/4K 时 0.6B 的 KV 要读 470 MB，占它总流量（1.66 GB）的 28%；
   4B 的 KV 只有 604 MB，占 7%。量化权重不影响这部分。
2. **每步有一块固定的非 GEMM 开销**。用 `t = (W + KV)/BW + T0` 拟合三个点：
   **BW ≈ 742 GB/s、T0 ≈ 1.2 ms/步**。对 4B（12.86 ms/步）T0 只占 9%，
   对 0.6B（3.45 ms/步）T0 占 35%。
   **T0 恰好就是 Amdahl 里被排除掉的那部分**（attention + elementwise + 采样 + 发行开销），
   所以它**不削弱 §0.1 的上界**，只是解释了代理实验的表面偏离。

**结论**：代理实验的表面偏离（比值 3.73 而不是 6.75）**已被完全归因**，
且归因到的两项都已计在 §0.1 的 Amdahl 之外。**闸门通过。**

### 0.3 值不值得做的判断

* **上界**：W8A16 在 B=1/4K **+58.6%**、B=4/4K **+42.3%**（k=1）；按现实的 k=1.2 打折后
  仍有 **+47.8% / +34.2%**。相对事前选定的 **"+20% 且困惑度退化 <1%"** 门槛，**空间充足**。
* **代价**：prefill 仍走 BF16 算力路径、还要多一层反量化 → **TTFT 大概率小幅回退**，
  必须与收益同报（不掩饰）。
* **风险**：真正的风险不是上界，而是**融合反量化 kernel 能不能把 int8 也流到 ~90% 带宽**。
  Qwen3-0.6B 的数据给出了悲观参照（1.2 GB 的权重只能跑到 75–81%），
  但我们要流的量化权重是 **4.4 GB**，处在 8.0 GB（91%）和 3.4 GB（92%）之间 → 风险可控。
* **判断**：**值得做，进 Phase 1。** 主收益门槛沿用 `B=1/4K decode tok/s ≥ +20%`，
  但**最终能不能算数取决于 Phase 2 的 kernel 实测**，不取决于这张上界表。

### 0.4 ★ 范围变更（用户裁定）：只量化 draft 的 FFN

原计划是量化 target 的 block 线性层。**改为：只量化 draft（Qwen3-0.6B）的 FFN
（gate/up/down），target 一个字节都不动。** 影响：

| | 量化 target（原计划） | 只量化 draft FFN（现方案） |
|---|---|---|
| 可量化字节 | 8.045 → 4.41 GB（0.548×，target 单次前向） | draft FFN 0.504 → 0.252 GiB（0.501×） |
| 有效收益 | Amdahl 上界 B=1/4K **+58.6%** | 见下（每轮只省 draft 侧的 ~22% 字节） |
| 无损性口径 | **必须改写**（target 是参考标准，动了 p 就变） | ★ **口径完全不用改** —— target 没动，`min(1,p/q)` 里的 p 原样，**「相对 BF16 target 无损」严格成立** |

draft 侧字节账（真实权重核实，非估算）：

```
Qwen3-0.6B 总权重 1.192 GB
  FFN（gate+up+down）   528 MB  = 44.3%   ← 只量化这三块
  Attention（q/k/v/o）  352 MB  = 29.6%
  embedding/lm_head     311 MB  = 26.1%
量化后 draft 权重 1.192 → 0.940 GB（−21.2%）
```
**★ 注意小模型与大模型的差别**：target 的 FFN 占 66%，draft 的 FFN 只占 44%
（词表一样大 → embedding 占比被抬高）。所以**预期收益只有个位数百分比**，
**很可能落在测量噪声边缘** —— 测量方法必须相应加强（空转噪声地板 + ≥7 组配对）。

## Phase 2 · 融合反量化 GEMM（W8A16）

### ★ 关键工程点：反量化必须融合

```
✗ 读 int8 → 反量化成 bf16 写回显存 → 调 cuBLAS 读 bf16
  每参数 = 读 1B + 写 2B + 读 2B = 5B，比原来的 2B 还多 → 完全白做
✓ 读 int8 + scale → 在【寄存器里】反量化 → 直接进 MMA
  每参数显存流量 = 1B（+ per-channel 的 2B/out）≈ 1.0002B
```
实现：Triton kernel，`w.to(bf16) * scale` 之后 `tl.dot`。

### ★ 两个真 bug（都是"只跑一个配置永远发现不了"那种）

1. **访存布局错了（这是第一版慢的真原因）**。W 是 `[N, K]` 行主序、**k 方向连续**；
   第一版把它读成 `[BLOCK_K, BLOCK_N]`，末轴是 stride=K 的 n → 访存完全散掉。
   症状：`o_proj` 只有 **1.08×**、`down_proj` 反而**慢 10%**（0.90×）。
   改成 `[BLOCK_N, BLOCK_K]`（末轴连续）+ `tl.trans` 后：**1.91× / 1.41×**。
2. **mask 轴写反**。沿用旧布局的 `k_mask[:, None]`；在 `BLOCK_N == BLOCK_K` 时**能编译通过**
   但语义是按 n 掩码 —— K 尾巴若不是整块就会读到脏数据。

### 微基准（draft FFN 形状，M=1，纯 kernel device time，`scripts/bench_int8_gemm.py`）

| 形状 [N,K] | cuBLAS bf16 | 本 kernel int8 | 加速比 | int8 有效带宽 |
|---|---:|---:|---:|---:|
| draft gate_up [6144, 1024] | 18.50 µs | **9.38 µs** | **1.973×** | 545 GB/s |
| draft down [1024, 3072] | 11.31 µs | **7.99 µs** | **1.416×** | 517 GB/s |
| 合计/层 | 29.81 µs | 17.37 µs | — | 每层省 12.44 µs |
| × 28 层 | — | — | — | **每次 draft 前向省 348 µs** |

### ★ 明确回答：这一刀到底有没有效果？

**有效果，但很小；而且没达到事前选的主收益门槛。**

- **每轮耗时**（最干净的度量）：**−3.6% ~ −4.5%（B=1）**，配对 **18/18 全胜**、
  B=4 合成档 22/24 全胜。合计 **40/42 配对一致**，符号检验 p ≈ 1e-10 → **效应是真的**。
- **预期端到端 tok/s**：因为接受率不变 ⇒ 每轮 token 数不变 ⇒ 端到端收益 ≈ 1/配对比值
  = **+3.8% ~ +4.7%（B=1）**。
  （直接看 tok/s 列会看到忽高忽低，那是**轮数的随机性**：自然采样下 9 组里轮数能在
  64~93 之间跳，±10~20% 的抖动把 4% 的效应整个盖住。所以必须按「每轮耗时」报，不能按 tok/s 报。）
- **接受率**：**不变**（Δα = −0.0025 ± 0.0035）。
- **精度**：draft 困惑度 +0.316%（整个 FFN）；**target 困惑度完全不变**，
  所以「相对 BF16 target 无损」这句话**严格成立**，一个字的口径都不用改。
- **B=4 结论**：本轮**分辨不出**。B=4 时批内请求陆续结束、批次规模在跑的过程中缩小，
  轮数与批构成的随机性把信号淹了（9~12 组噪声地板 43%–61%）。只能报"配对中位数为
  0.95–0.98 但区间跨过 1.0"。
- **没达到门槛**：事前选定的主收益门槛是 `B=1/4K decode tok/s ≥ +20%`
  （那是给 **target 全量化**定的）。**只量化 draft FFN 的实测是 +3.8~+4.7%，远低于 +20%。**
  按照"不达门槛就如实报负结论"的约定：**这一刀在性能上不划算**，
  除非它作为"无损口径不必改写"的示范有额外价值。

### 交付的配置开关验收（`scripts/check_quant_engine.py`，三个 case 各自独立进程）

| case | 结果 |
|---|---|
| `draft_model` = BF16 目录（无 quant_config.json） | **0** 个模块被量化；KV 池 174 块 / 44544 token ✓ 默认关 |
| `draft_model` = 带 quant_config.json 的目录 | **56** 个模块**自动**量化（无需逐层指定）；FFN 504.0→252.4 MiB；KV 池 171 块 |
| `draft_model` = 真·int8 checkpoint 目录 | **明确报错**（拒绝静默装错权重）✓ |

**★ KV 池是个负结论，如实报**。量化确实把权重内存降下来了
（`allocated_bytes.all.current` 8.683 → 8.438 GB，**−0.245 GB**，与 504→252 MiB 对得上），
但 `allocate_kv_cache` 的预算公式是

    budget = 0.9·total − used − peak + current

其中 `used` 取的是**驱动级**已用量（含 caching allocator 缓存），`peak` 是**进程历史峰值**。
实测这一次：`used` 反而多了 0.16 GB，把 `current` 省下的 0.245 GB 抵消掉还多，净 −3 块。

排查过程中抓到一个**真 bug 顺带修掉了**：split-K 的 partial buffer 是
`[SPLIT_K, M, N]` fp32，`warmup_model()` 的 prefill（M 大）会分配 200 MB+，
把 `peak` 顶高 1.285 GB → **KV 池少 11 块**。改成「split-K 只在 M ≤ 64（decode）用」后
peak 从 10.250 回到 9.719 GB，块数从 163 回到 171。
（prefill 本来也不需要 split-K —— 它不缺并行度，还白付一次归约 kernel。）

剩下那 3 块没有归因干净（`used` 多的 0.16 GB 在多次运行间很稳定，但我没找到来源）。
**要真正把显存挣回来，得直接加载预先量化好的 checkpoint（不做内存内转换），
或改 allocator 的预算口径 —— 本轮都没做。**

注：上面消融表里的 tok/s、ms/轮 是用 `install()` 就地换权重测的；
交付的**配置开关路径**另用 `check_quant_engine.py` 验收（见下）。

**做了什么**：在 nano-vllm 上给 **draft（Qwen3-0.6B）的 FFN** 做 W8A16 权重量化
（int8 存储 + bf16 计算），反量化**融合**进 Triton GEMM；引擎侧按 `quant_config.json`
**自动选层**、**默认关闭**、老路径**逐字节等价**。**target 一个字节没动。**

| 问题 | 答案 |
|---|---|
| 每轮耗时有没有降？ | **降了 −3.6% ~ −4.5%（B=1），配对 18/18 全胜**；B=4 合成档 22/24 全胜 |
| 端到端 tok/s？ | **≈ +3.8% ~ +4.7%（B=1）**（接受率不变 ⇒ 收益 ≈ 1/每轮耗时比） |

| 精度掉了吗？ | draft 困惑度 **+0.316%**（整个 FFN，wikitext-2）；**target 完全不变** |
| 无损性口径要改吗？ | **不要**。「相对 BF16 target 无损」严格成立 —— 这是选 draft 侧的最大好处 |
| 显存省了吗？ | **权重省了 0.245 GB（实测 current），但 KV 池反而少 3 块**（174→171），净负 |

② 微基准预测每次前向省 348 µs，实测只省 261 µs（**拿到 75%**）。
9.9% × 47% × 75% ≈ 每轮 −3.5%，与实测吻合。

## 没做 / 做不了 / 和预期矛盾的点

1. **B=4 分辨不出**。批内请求陆续结束、批次规模在跑的过程中缩小，
   轮数与批构成的随机性把 4% 的效应淹了（9~12 组的噪声地板 43%–61%）。
   只能报"配对中位 0.95–0.98，但区间跨过 1.0"。**要测准 B=4 需要固定轮数或几十组配对。**
2. **显存/ KV 池没拿到收益**（174→171 块）。权重确实省了 0.245 GB，
   但被 allocator 预算公式里多出来的 `used` 吃掉；最后 3 块**没归因干净**。
3. **`middle:6` 那一档没跑出来**（target 扫描时 eval_ppl 的 cfg 解析有 bug，已修但没重跑）；
   draft 的层位置扫描是**用修好的版本**跑的，数据完整。
4. **prefill 变慢这件事没能定量**。草稿的 prefill 在投机路径里也存在（前缀命中/补齐时要跑），
   本轮只测了 decode 侧的每轮耗时，**没有单独测 prefill 的 TTFT 回退**。
5. **和用户直觉相反的两条**（都如实报）：
   - 「FFN 损害较小」**不成立** —— 4B 上只 FFN +0.637% vs 只 attn −0.183%；
     0.6B 上 FFN +0.316% vs attn +0.132%。**attention 比 FFN 更耐量化。**
   - 「`down_proj` 最敏感」**只在 0.6B 上成立**（+0.228%，最敏感）；
     在 4B 上它反而是最不敏感的之一（+0.122%，低于 gate +0.213 / up +0.269）。
     **敏感度排序是模型相关的，不能跨模型套用。**
6. **额外发现**：draft FFN 的量化代价几乎全部来自**最前面 4 层**（+0.30%），
   中间 20 层只有 +0.02%、最后 4 层是 0。若要把代价压到 0，跳过前 4 层即可。
   本轮**没有**采用这个更细的配置（+0.32% 本来就小，不想把配置搞复杂）。

## 4.1 ★ 单层微基准：hidden=1024 也在 `LLM.int8()` 的陷阱区间里，但我们更快

文献警告：**hidden dim ≤ 2560 时朴素 int8 路径反而更慢**（LLM.int8() Table 5：d=1024 → 0.24×）。
draft 的 hidden 就是 1024。我们走的是「int8 只做存储 + 反量化融合进 BF16 GEMM」，
**理论上绕开**，但按规矩**先实测再说**（`SHAPESET=draft_all`，纯 kernel device time）：

| 形状 [N,K] | bf16 µs | int8 µs | 加速比 | 加速比 (M=4) | int8 有效带宽 |
|---|---:|---:|---:|---:|---:|
| draft_gate_up [6144,1024] | 18.46 | **9.41** | **1.96×** | 1.90× | 670 GB/s |
| draft_qkv [4096,1024] | 15.68 | **8.13** | **1.93×** | 1.70× | 517 GB/s |
| draft_down [1024,3072] | 11.23 | **7.98** | **1.41×** | 1.46× | 394 GB/s |
| **draft_o [1024,2048]** | 7.24 | 6.53 | **1.11×** | 1.43× | 321 GB/s |
| **整层组 ×28 层**（+lm_head 仍 bf16） | **1473.3** | **897.7** | **1.641×** | 1.649× | — |

**结论：四个形状在 M=1 与 M=4 上 int8 全部更快，闸门通过，不需要停下来。**
`hidden=1024` 那个坑属于「朴素 int8 matmul」，我们的融合路径不受影响。

**唯一的弱项如实报**：`o_proj` 在 M=1 只有 **1.11×**（它是 N=1024、K=2048，
输出方向小 → 并行度低、写入相对占比高）。M=4 时回到 1.43×。
它的字节只占 draft 的 8.8%，拖不动大局。
最大相对误差 0.40%–0.67%（就是 bf16 本身的精度量级）。
（M=16 时整层组掉到 1.442× —— 我们在 decode 上的 M 只有 1~4，不受影响。）

## 4.6 ★ 回答"量化 target 会削弱投机、量化 draft 会怎样"（本轮的核心叙事）

| | 普通解码 tok/s | 投机 tok/s | **投机 / 普通** |
|---|---:|---:|---:|
| draft **BF16** | 77.9 | 109.8 | **1.411×** |
| draft **INT8** | 77.9（同一个 U） | 124.7 | **1.601×** |

（自然 B=1/1K。另几档：1K 合成 2.355→2.540、4K 自然 0.927→0.954、
4K 合成 2.097→2.241、**B=4 合成/4K 1.548→1.624**。
注意 4K 自然档的比值 **< 1**（投机比普通解码还慢）—— 那是**既有的**长上下文现象，
不是本轮造成的，本轮只是把它从 0.927 抬到 0.954。）

**★ 结论与"量化 target"完全相反：量化 draft 让投机的相对优势【变大】而不是变小。**
机制很直白：普通解码 100% 是 target（一个字节没动 ⇒ 一分不变），
而投机一轮的权重流量里有 **6/7 是 draft**（6×1.110 GB vs 1×8.045 GB），
把 draft 砍掉 36.9% 相当于**给投机路径的成本打折**。
用最干净的口径说：`tok/s` 那两列有轮数噪声，但**因为接受率不变，
"投机/普通"这个比值就等于 1/配对比值**，即 **×1.069 ~ ×1.078**。

而这正是**选 draft 侧而不是 target 侧**的最大好处 ——
如果量化 target，普通解码（100% target）受益最大、投机（target 只占一半）受益小，
投机/普通 的比值会**掉**；量化 draft 则反过来。

## 4.10 ★ 无损性口径：**一个字都不用改**（这是选 draft 侧的核心好处）

上一轮文档 §Phase 3 写的是「相对 **BF16 target** 无损」—— 本轮**原样成立**，
因为 target 的权重一个字节没动：`min(1, p/q)` 里的 p 就是 BF16 target 的分布，
拒绝采样的数学前提完好。**不需要改成"相对同一个量化 target"那种弱化口径**
（那个改写只有在量化 target 时才被迫需要）。

量化 draft 为什么在数学上安全：draft 的 q 变了 → α 变小（或不变）→
**每一轮交付的 token 仍然服从 target 的分布**（拒绝采样的正确性只依赖 p 的正确性，
不依赖 q 有多准）。本轮实测 α 也没变（§4.3），所以连"每轮 token 数变少"这个代价都没有。

**怎么验的**（三档证据，沿用上一轮体系）：
1. **接受率的数学前提**：`α = 1 − TV(p,q)` 在 12282 个位置上算 → Δα 不显著（§4.3）；
2. **默认路径逐字节等价**：md5 逐字符复现（§4.9）；
3. **端到端无损性**：`scripts/check_lossless_engine.py` 的引擎级 token 频率分布检验
   （上一轮已建，本轮量化只改 draft，且 p 未动，故结论不受影响）。
