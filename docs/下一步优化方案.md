> 本次交付仅为方案；未修改代码、未运行 GPU 实验，下面的收益门槛都是拟定验收标准，不是实测结果。
> 基准版本：`v2-optimizations`，SHA `69fd2c3fa1892681db7386042da872afcf617362`。已用 `git ls-remote` 核验远端分支。本地当前分支名虽为 `main`，HEAD 与该远端分支完全相同；本方案依据这个 SHA 的材料与实现，不依赖分支名推断内容。

## 0. 修订：确实需要继续优化，测试伴随开发进行

上一版把测量前置、已有成果收尾和新功能开发放在同一推荐序列，导致计划偏向“把结果测全”。本版纠正这一点：**继续改变引擎执行路径；用测量确定瓶颈、检查每次改动的贡献，最后再统一验收组合效果。**

### 0.1 开发与测量的具体顺序

1. **做一轮最小基线。** 先拿当前版本在 B=1/4、输入 1K/4K、输出 256 下的完整生成时间和一个代表性 trace，约半天到一天。同时保存当前基准版本。此阶段不做完整长上下文/并发/P99 矩阵。
2. **实现第一项执行路径优化 P1。** 接入已有 attention，处理图兼容、工作区和不同形状配置。每完成一个可用版本，立即比较“同版本 flash-attn”与“同版本自写后端”。测不到整机收益时依据 profile 改或收尾，不能继续盲调。
3. **推进 P6 批量投机。** 将逐请求 draft 改成同位置批处理，扩展批量验证图，维护不同请求的确认长度和回滚。先 B=2/4，再扩展到 B=8/16；每个阶段都做前后对照。P2 扫描随开发进行，不要求先把所有配置测完。
4. **补混合调度 P12。** 先以普通 decode 开发，再接入已验证的批量投机路径，并计入 k+1 验证 token 与双 KV 预算。把批量状态处理与混合调度分阶段验收，减少同时改动两套执行逻辑造成的归因困难。
5. **P12 完成后，在收尾 trace 中决定是否追加 P11。** 在批量执行基础上，把候选、接受长度、bonus 与重采样尽量留在 GPU，批量返回最终结果；进一步融合实际占时的拒绝采样操作。这是有条件的代码优化，不能把“调用 profiler”写成这一项的成果。
6. **最后统一验收，再进入主流引擎阶段。** 对保留下来的单项与组合做相同输入/输出、模型、dtype、图和缓存状态的端到端对比，再扩展长上下文与有意义的并发点。完成本轮收尾条件后，再为 vLLM 选一个独立、范围明确的二次开发问题。

因此，不是“先测很多天再决定要不要优化”，也不是“全部写完才统一测”。应该是 **小规模定位 → 实现 → 测该改动 → 继续实现 → 单项消融与最终组合验收**。本轮仍只制定方案，不执行以上代码开发。

### 0.2 真正要改什么

| 开发项 | 当前执行路径 | 要实现的新路径 | 独立验收比较 |
|---|---|---|---|
| **P1：Paged decode 后端接入＋形状适配** | 引擎普通 decode 仍调用 flash-attn；已有 CUDA/Triton kernel 单独跑 | 在 `Attention.forward` 选择后端；预热/JIT 与图工作区复用；按 B/上下文桶选择已有 split 配置，适配 padded 空行；不匹配形状退回。选择形状用已有 CPU 元数据，避免新引入 GPU `.item()` 同步 | 同版本、图开启、普通 decode：flash-attn vs 接入版；另做“固定配置 vs 形状选择”的消融 |
| **P6：批量草稿与批量验证图** | B 个请求各自串行跑 k 次 B=1 draft；B>1 验证退回 eager | 同一候选位置的 B 个请求一起跑 draft，使模型调用结构从 B×k 次单序列前向变为 k 次批量前向；按 B=1/2/4/8 和固定 k 捕获验证图；补齐不同确认长度、拒绝回滚和 gate 后重启的 draft KV | 当前逐请求版 vs 批量 draft 版；再比批量验证 eager vs 批量验证 graph。batch 前向更贵、接受率和显存都要计，不承诺 B 倍提速 |
| **P11：GPU 拒绝采样与 CPU/GPU 往返削减** | proposer 末尾 `.tolist()` 将候选带回 CPU；runner 又造 GPU candidate tensor；逐请求取 `int(accepted)` 和 `int(bonus)` | 候选 ID 保留 GPU tensor，批量送验证；批量计算接受前缀和 bonus，最终按轮合并一次结果回传；先复用已有 GPU 张量运算做批量化，再对 trace 中实际占时操作做 Triton 融合，复用概率/临时缓冲区 | P6 批量版 vs P6＋往返削减；再比未融合 vs 融合。分别报同步/拷贝调用数、verify/sample 时间、临时显存和完整生成速度 |

这里 P1 是已有算子工作的工程落地，P6/P11 是当前项目仍未完成的执行优化。P11 不等于“把 CPU 算法搬到 GPU”：`verify_batch` 里的数值操作已经在 GPU，问题在调用粒度、候选往返、逐序列同步、临时张量和 kernel 启动。

源码依据：[单序列候选回传](</D:/学习/specdec/nanovllm/spec_decode/draft_proposer.py:172>)、[候选重新构造](</D:/学习/specdec/nanovllm/engine/model_runner.py:491>)、[逐请求读接受长度](</D:/学习/specdec/nanovllm/engine/model_runner.py:538>)。这些结构确实存在；它们在实际负载中占多少时间，尚未测量。

### 0.3 借鉴别人项目的层次，保留自己的主线

用户提供的简历有清楚的“访存瓶颈→改算子、prefill 阻塞→改调度、KV 容量→改存储”对应关系，这是值得借鉴的工程结构。我们同样需要明确瓶颈、真实代码改动和端到端数字；不必凑出与其相同的三个技术名。

- **算子融合值得有限范围实践。** 本项目两处已经使用 `torch.compile`，先查看实际生成 kernel，再自行实现一个 Triton 融合算子，与编译后基线对照。不要预设还能达到外部简历的 4–5×；P13 的价值是补融合与编译器对照经验，不能复制外部数字。
- **chunked prefill 是真实调度优化，建议作为 P12 开发。** vLLM 官方说明，decode 优先并利用剩余 token budget 处理 prefill，改变的是请求调度与 GPU 工作组合；不同 budget 会改变 ITL/TTFT。本项目当前仍 prefill/decode 互斥，因此有真实缺口；后续与投机的多 token 验证预算结合，形成自身实现范围。[vLLM 调优文档](https://docs.vllm.ai/en/latest/configuration/optimization/#chunked-prefill)
- **KV 量化作为 P14 容量专题保留。** 更大可容纳并发可能带来吞吐收益，但还要计写入/反量化/scale/长上下文误差；KV 字节减半不等于整机显存减半。sm_86 没有原生 FP8 Tensor Core，但这不等于不能进行低比特 KV 存储与反量化计算；优先评估 INT8 存储＋BF16 计算。需与现有无损投机的参考目标分开，见 §0.5。

本轮打开的成熟实现支持上述开发方向：[limei1221](https://github.com/limei1221/nano-vllm-speculative-decoding) 已有 B×(K+1) 验证图；[FlashInfer](https://docs.flashinfer.ai/generated/flashinfer.sampling.chain_speculative_sampling.html) 提供 GPU 融合 chain speculative sampling；[vLLM 拒绝采样源码](https://github.com/vllm-project/vllm/blob/main/vllm/v1/sample/rejection_sampler.py) 有 Triton 随机拒绝采样 kernel。它们证明这是有工程基础的优化入口，**不证明我们已经有收益，也不证明方法首创**。保留饱和方向的理由是当前实现存在具体未完成路径，并将实现、归因和容量边界做完整。

若 P11 之后 trace 仍显示 CPU 调度形成明显 GPU 空隙，才考虑下一阶段 CPU/GPU overlap；[mini-sglang 的 overlap_loop](https://github.com/sgl-project/mini-sglang/blob/main/python/minisgl/scheduler/scheduler.py) 是已打开的参考。重叠调度要处理上一轮结果依赖、EOS 和 KV 释放，不能把“加一个 stream”当作现成优化。

### 0.4 基准如何针对我们的实际改动

| 版本/对照 | 用途 |
|---|---|
| **U：同版本 target-only＋flash-attn＋普通 decode graph on** | 实用引擎基线；保留正确性修复，不为回到上游而重引入已知 bug |
| **C：当前逐请求 draft＋现有单请求图** | 当前项目状态，测未来新增优化相对 C 的增量 |
| **A：U＋P1** | 自写 attention 接入的独立引擎收益 |
| **S1：C＋批量 draft** | 单独识别批量草稿的贡献 |
| **S2：S1＋批量验证图** | 单独识别批量验证图的贡献 |
| **S3：S2＋P11** | 单独识别候选往返削减/融合拒绝采样的贡献 |
| **F：保留下来的优化组合** | 最终同负载下相对 U 的整体效果，同时保留与 C 的比较 |

至少回答两个不同问题：**“新增改动让当前版本快了多少？”以及“最终项目相对实用原路径快了多少？”** 不能只做 F vs U，省略失败或无效单项。普通单 query PA 不适用于多 query verify，F 未必从 P1 得到更多收益，不能将单项 speedup 相乘。

### 0.5 求职价值：三类方向值得做，但新增收益与投入不同

这三类是推理岗位的实际工作方向，不需要以“研究首创”作为实习项目的入场条件。本轮打开的 [百度 AI Infra 推理工程师校招要求](https://talent.baidu.com/jobs/detail/GRADUATE/7753cdb4-70b0-462b-a634-ee53818c7c9a) 明确涉及 CUDA/Triton、注意力/矩阵优化、批调度、Cache 池化和低比特量化；[快手招聘人员发布的推理引擎实习岗位](https://www.nowcoder.com/jobs/detail/438027?urlSource=sitemap) 也涉及算子/编译优化、量化与推理框架经验。前者是校招岗位，后者是实习岗位；它们支持技能相关性，不用于估计拿 offer 的概率。JD 相关性与所给 172 题里的具体考频分开记录。

**在混合调度、KV 量化、小算子融合三者中，本项目优先补混合调度。** 已有 attention/CUDA 经历已证明算子能力，调度能够拓宽引擎能力，量化能补数值与容量权衡。但技能相关不等于本轮必做：按最新范围，先完成 P1/P6/P12，P13/P14 仅在明确瓶颈或目标岗位需要时追加。面向算子内核岗时可改选一个融合实践；本方案主目标是推理引擎岗位。

**P12：decode-first＋token budget 的混合调度，估计 5–8 人天。** Scheduler 一轮返回 decode 与 prefill 两组工作；ModelRunner/主循环先执行 decode graph，再用剩余预算执行 eager prefill chunks，跨轮维护真实 KV 进度。先在投机关时跑通，再纳入 k+1 验证 token、草稿与双 KV 占用的预算。这与普通混合调度已有工作重合，保留理由是解决本项目真实缺口并完成投机路径集成，不能宣称新颖算法。

验收应使用短请求持续 decode、长 prompt 陆续到达的负载：相比原 prefill-priority，记录请求 ITL P99、TTFT、完整生成吞吐、长请求等待与抢占。预先选定代表性到达轨迹，拟定 ITL P99 降低至少 10%、吞吐回退不超过 3%，TTFT 权衡完整报告；数字是目标而非预测。只测所有请求同时到达的离线批次不足以证明在线 decode 阻塞改善。“同 step 先 decode 后 prefill”是两次顺序前向，不等于同一个 GPU batch 混算，也不证明 CPU/GPU 重叠。

**P13：先做一个 Add+RMSNorm 或 SiluAndMul 融合实现，估计 2–4 人天。** 检查 `torch.compile` 生成的实际 kernel 数、输入输出字节与临时张量，然后自行实现 Triton 版本，覆盖实际模型 shape、非整齐 token 数与 residual 输出语义。SiluAndMul 的 pointwise 计算可能已被编译器融合；Add+RMSNorm 也可能已获得高效代码，不能仅按 Python 运算数判断优化空间。至少与 eager 和编译后两套基线对照，算子指标和 graph-on 整机指标分开。若不能超过编译后基线，可以保留学习结论，避免把重复实现写成性能优化；不花额外数周凑两个算子。

**P14：INT8 KV 存储＋融合反量化 paged decode，估计 8–12 人天。** 先以 target-only 路径开发、对照 BF16；选定 token/KVHead 的缩放粒度，完成量化写入、scale 存储、decode 反量化与 prefill 兼容。Prefill 如使用 Gather＋反量化＋FA，则显式计入中间缓冲、拷贝与峰值，而不是只计压缩池。FP8 E4M3 是后续可比较格式，3090 上需要确认转换/反量化路径，不能预设原生 FP8 计算收益。[NVIDIA Ampere 类型说明](https://docs.nvidia.com/cuda/ampere-tuning-guide/index.html#improved-tensor-core-operations)

验收分别报告压缩 KV＋scale 的 bytes/token、24GB 中真实可用池大小、最大无抢占并发、decode/完整生成速度与真实长上下文输出质量。拟定 KV＋scale bytes/token 不超过 BF16 的 60%；确定性能主场景后至少 5 组成对生成测量。先看真实 checkpoint 上的逐层/logits 误差与长文检索/生成结果，再决定质量门槛；门槛在性能调优前固定，不只用一组随机 Q/K/V 或“logits 接近”证明质量不变。8bit 约减半的是 KV 主数据，权重和其他工作区不会因此减半。

**与投机无损性的关系：** target KV 量化会改变 target 的数值分布，不能继续说相对原 BF16 target 完全无损。可以单列量化 target 的质量结果，并要求投机相对同一量化 target 保持算法一致；或只量化 draft KV、保持 target 精度，只要验证所用 q 与草稿实际采样分布一致，仍满足拒绝采样的数学前提。draft-only 可作为与现有主线结合的扩展，但双池总容量不会自动提升两倍，接受率与草稿代价也要重新量化。

外部简历中的 4–5×、95%、37%、108% 均是对方特定配置的记录，本轮没有核验这些数字的原始日志。不能当作我们的验收结果或预期。也不能仅凭 172 题中 KV 量化直接题为 0，就推出该技能对推理岗位没有价值。

### 0.6 是否还需要进一步开发算子

**继续打磨已有 attention 算子的引擎适用性；新增算子按实际瓶颈决定。** 本轮不预设需要第三套 attention、两个小融合算子或一整套量化 kernel。现有 CUDA MMA 路径已经包含矩阵指令、访存流水、online softmax 和 split 归约，下一步可以在这套实现上完成必要修改。

| 工作 | 本轮定位 | 开发范围 |
|---|---|---|
| attention 接入、工作区/输出复用、合法形状与图配置 | P1 主线 | 多数属于算子接口及 C++/Python host 工程；需要时补 device kernel 的边界处理。已有代码支持 batch，不把“首次支持 B>1”记为新成果 |
| attention 的 split/block/warps/stages 与归约配置 | P1 内的有限优化 | 先比较已有配置；确有关键路径瓶颈再改加载、切分或归约实现。不匹配形状先退回，不承诺覆盖所有模型 |
| 拒绝采样/接受前缀/结果整理融合 | 条件 P11 | P6/P12 后的 trace 证明成本值得处理才开发；先减少候选往返和同步，再融合实际热点 |
| Add+RMSNorm、SiluAndMul | 选做 P13 | 两处已有 `torch.compile`，先比较编译后实现；最多选一个有限实践 |

批量 draft、批量验证图及顺序双前向混合调度的首版都可复用现有 attention 后端，不以新增算子为开工条件。**接入、形状选择、workspace 生命周期和 device kernel 改写在交付中分别列明**，避免将 host 调参包装成新的底层算法。可直接执行的开发拆分见 §12。

### 1.2 文档和代码之间有几处影响决策的差异

| 材料中的说法 | 本轮核对 | 对计划的影响 |
|---|---|---|
| “全部是 microbenchmark，没有端到端数字” | `bench_spec.py` 已在 warmup 后计时完整 `generate()`，计入生成阶段 prefill 与 decode，得到输出 tok/s；但只覆盖一个短代码 prompt、单请求，没有请求时间线或系统负载扫描 | 应补的是证据范围和口径，而不是从零证明投机能够跑完整生成。attention 的独立 kernel 数字仍不能代替引擎收益 |

## 3. 开发排序与“补新考点 vs 深挖已有”的论证

### 3.1 为什么先深挖，但不无限深挖

**第一，已有资产还有具体执行路径未完成。** C5/16/17 问亲手做过什么、瓶颈和流程，已有两版 attention 可以复用；但引擎仍未调用它们。投机已经跑通单请求，却仍有逐请求 draft、验证图退回和候选往返。继续优化这些路径，比另起一个 RMSNorm 或 KV 量化更连贯。K5 明问最终效果，K9/10 反馈数字和整体框架优化不足；新代码改动与完整负载结果要一起补齐。

**第二，少量测量用于选改动，完整验收跟随实现。** 首轮 trace 区分 attention、逐请求 draft、eager 验证和 host 同步，而不是先交付大规模测试报告。P1、P6、P11 各自拥有代码目标和前后对照；无效项收尾，有效项进入组合。新增 kernel 如果加速不在整机关键路径，就不能仅凭局部数字保留。

**第三，不能从桶大小推出“新考点都不值”。** H 的 19 题中有 OCR/关键词误分，真实 TP/NCCL 相关按本方案口径只有 4 条；不过它们确实暴露一个独立能力缺口。D 里 continuous batching 有 2 条、PD 有 4 条，也有真实新价值。P5 复用 TP 只需 3–5 人天，是值得保留的补课；P7 则要 12–20 人天与持续双卡机会，并且新增的简历收益高度依赖端到端验证。

**第四，求职技能价值与差异化要一起算。** 投机和 kernel 都已有 ≥3 个实现，1.61× 本身不独有。原方案把“社区/简历已有”用作过强的排除理由；实习项目应看独立实现、瓶颈解释、真实整机结果和覆盖的新能力。混合调度能补当前引擎缺口，KV 量化能补容量/精度权衡，小算子融合则与已证明的内核能力重叠较多。采用成熟机制可以有价值，复制整份项目与数字则没有。

因此，**近期深挖已有主线的边际收益更高，但“深挖”必须包含新的执行优化，不能等同于扩测试矩阵**。不是按桶占比选技术，而是将已有底层算子和投机算法发展成完整的批量执行路径，并测出每项改动的收益。新考点的代码开发仍可在核心主线完成或收益空间不足时接上。

**何时改变判断：** P1/P6 的核心实现和前后比较完成后，若 P11 的剩余成本很小，继续扩扫描或融合的价值就下降；若 P1 整机收益上界不足 5%、P6 小 batch 重构后仍无净收益，就停止该支扩展，保留结果和适用边界。随后完成 P12 的独立开发与验收，或据明确失败原因调整本轮范围；P5/P13/P14 不自动补入。不得把“再测一轮”或“再加一个功能”变成永不结束的前置。

## 4. P0：把测量前置做成可验证的交付

本节是共享测量协议：开工只需 §0.1 的少数基线点，其余字段和矩阵随实际开发补齐。完整协议通过不作为 P1/P6 开工条件。

### 4.1 固定基线和工作负载

主基线为同版本 nano-vllm、Qwen3-4B、真实 checkpoint dtype、flash-attn、普通 decode CUDA Graph 开启、投机关。eager 仅作为诊断消融；不将优化路径与 eager 基线的差包装成对当前最快基线的收益。

P2 的主组合固定为 **Qwen3-4B target＋Qwen3-0.6B draft、两模型 BF16、temperature=1.0、现有全词表采样（不加 top-k/top-p/penalty）**。执行前登记服务器上两份 checkpoint 的确切路径及已有 revision/版本标识、tokenizer 版本和 token-ID 映射，之后冻结；本轮未访问服务器，不能填写不存在的已核验 revision。若现有权重或实际模型 dtype 不符合这组条件，先明确选定另一组配置与成本，不能通过隐式转换混入主结果。接受率、容量和速度均按冻结后的同一组报告；仅 vocab_size 相等不能代替 tokenizer/token-ID 映射一致性检查。

最小单卡矩阵为 prompt token 长度 **1024/4096**、并发 **1/2/4/8/16**、固定输出 **256**；仅对已显示趋势的配置扩展到 prompt **8192/16384** 或 B=32。所有配置均需让 `max_model_len` 覆盖输入＋输出＋投机预留，4K 输入也不能沿用默认 4096；同一对照组使用相同长度上限。先限制 `max_num_seqs` 和捕获图的 batch 范围到本轮所需规模，避免默认 512 的初始化开销，另记图内存。采样统一 `temperature=1.0`，固定输出实验开启 `ignore_eos`；数值调试另用显式 argmax。`ctx=16K` 在本计划指 **16384 个输入 token**，生成期间 context 会增长，不能将整段生成写成恒定 16K。至少保存 12 条中文与 12 条代码 prompt 的 token IDs 及长度构造方式，别只用同一段代码前缀；明确这是工程负载，不据此声称回答质量提升。

测量时区分两种口径：

- **引擎端到端：** 已分词 token IDs 的请求入队→结果 token 可交付，覆盖排队、prefill、draft、verify、采样、调度和退回。主吞吐为所有实际交付 output tokens / 整批 wall time。不能拿 decode 阶段 tok/s 代替整段吞吐。
- **文本 API：** 字符串输入→最终文本结果，另计分词、反分词成本。引擎初始化、权重加载、JIT、图捕获单独计为启动成本，不混入稳态，不能称当前测试为 HTTP/线上服务性能。

每个配置先预热，再做至少 **5 组成对测量**，交替或随机 base/variant 顺序。主要结果计时与 profiler trace 分开跑，避免用带 profiling 开销的 wall time。报中位数及组间范围；5 组不用于估计可靠 P99。真实引擎测试不人为每步清 L2；独立探针若清 L2，明确属于另一实验口径。

### 4.2 时间与显存口径

| 指标 | 计算/记录方式 |
|---|---|
| TTFT | 请求进入引擎到首个结果 token 可交付；分解 queue wait 与运行 prefill，不能只取 prefill CUDA event |
| 请求 TPOT | `(最后 token 时间−首 token 时间)/(实际输出数−1)`，输出数≤1 时记不适用 |
| ITL | 相邻可交付 token 的时间差；投机一轮落地多个 token按真实可见时间记同批到达，不将轮时间除以 token 数伪造流式延迟；另报批间等待 |
| 完成时延/吞吐 | 请求到达→完成时延；整批吞吐按完成后的真实 token IDs 总数计，不用 `last_accepted` 进度条计数 |
| 接受率 | 真接受候选数 / 真提议候选数；bonus、拒绝重采样 token 不算接受候选；终止裁剪后的交付 token 另计 |
| 成本分解 | prefill、draft、verify、sample、输入准备、scheduler/postprocess、图/eager 次数；GPU device time 与 host wall time分栏，考虑重叠，不能机械相加 |
| 显存 | 权重、target/draft KV 池、图/workspace，`allocated/reserved` 峰值和设备总占用；预分配 KV 池与逻辑活跃块/尾页浪费分开 |
| 容量 | 固定 prompt/output 与页大小下，能完整完成且**无抢占**的最大 active B；另列有抢占时并发、重算和 OOM，不混称最大容量 |

关闭投机后的显存公平性需要两组对照：**实用 target-only 基线不加载 draft**；另用保留相同双模型/KV预算但禁用投机的运行隔离算法成本。两者都报，不用后一组冒充部署基线。预热不得让正式负载变成前缀 cache 热命中：需要正式测量 reset 缓存状态或使用不同前缀，并记录实际命中；故意测热缓存则单列。已有脚本在同一引擎重复相同 prompt 不能直接升级为公平基准。

### 4.3 完成判据

1. 至少 B=1 与 B=4、输入 1K 与 4K 的 baseline 得到上述字段，输出数与时间线最终累计一致；固定长度实验用 `ignore_eos=True` 恰好交付 256 token。另做开启 EOS 的终止检查，不把强制输出当自然完成。
2. 保留原 37 项测试，不重复造一套同义测试。新增检查只针对插桩计数、跨页、结束裁剪和后续真正改变的路径。
3. TTFT/ITL 的时间戳来自实际中间 token 可见点。当前 `step()` 只返回已完成请求，必须计划增加测量 hook；仅在 `generate()` 结束后填一个时间不能通过。
4. 报告注明 checkpoint、软件版本、输入 IDs、实际 max_model_len、k/batch、graph 开关、页大小、缓存状态、GPU 型号与资源占用；原始逐请求和逐组记录能复算汇总值。
5. 未达到尾部采样量时，P95/P99 标为探索性或不报；正式尾延迟至少 1000 个完成请求、10000 个有效 ITL 间隔，保留请求相关性和异常信息。只对值得比较的少数配置补足，不做全矩阵长压测。

P0 只要求测量真实一致，不要求“优化有提升”。

## 5. P2：当前投机并发边界与已有门控

本节随 P6/P11 开发运行并比较版本，不是要求先交付整张测试矩阵才能重构。首轮仅作小范围 pilot。

### 5.1 执行内容

先用 flash-attn 后端，保持 P1 独立，测 **B=1/2/4/8/16、k=2/6、输入 1K/4K、输出 256**。先做 B=1/2 的状态验证和 pilot；有意义且容量允许才扩到 B=32 或 8K。

逐条提议的成本和真正的批量模型成本必须分开说：当前是对 B 个请求循环跑 k 次单请求 draft，而验证 B>1 通常走 eager。报告草稿图 replay 数、验证图 replay/eager 数和每轮 active B。由此得出的交叉点只适用于当前实现，不能叫“投机解码固有并发上限”。

已有门控还需核对一次语义：scheduler 在 `popleft()` 后读取 `len(self.running)`，队列在本轮逐渐缩短，可能导致同一轮不同序列拿到不同投机决定。正式门控应按本轮开始时的 active B 做一致决定，并核对 scheduler、runner 和 `config.spec_k` 的同步关系，不能只修改配置字段假定已生效。高 batch 退回普通 decode 后再进入投机，还要确认 draft KV 已补齐中间已确认 token，而非沿用旧草稿状态。

用一半 prompt 测量数据选择阈值，另一半及一个 B 变化的到达轨迹作验证。比较三组：target-only、always-spec、已有门控校准后的 gated-spec；不训练复杂在线模型，不添加动态 k 作为第二个项目。

### 5.2 完成与收益判据

**正确性先过：** 覆盖 B=1/2/4、请求长度不齐、部分拒绝/全接受、跨 256 页边界、EOS/256 token 截断、门控开关及重新启用；核对 target/draft 的已确认上下文和 slot/block 有效性。用同一已确认前缀的完整重算 logits 对照增量路径，容差与实际 dtype 一致；小样本分布对比只能是补充，不能当整机无损证明。随机采样路径不能要求“同 seed 输出逐 token 一模一样”来证明无偏性。

**测量完成：** 所有可容纳配置都报实际 token 数、完整生成 speedup、TTFT/TPOT、接受率、token/round、draft/verify/host 时间、图退回、KV 容量；不可运行项报原因。必须有同 B、同输入长度、同输出数的完整比较，不拿 B=1 baseline 去比 B=8 spec。

**门控有收益才宣称优化：** 在保留 prompt 与动态 B 验证中，高负载退回后相对 always-spec 的完整生成吞吐至少提高 **5%**，且相对实用 target-only 同负载吞吐回退不超过 **3%**；低负载启用投机时完整生成 speedup 至少 **1.05×**。均需 5 组成对复测方向一致，TTFT/TPOT 同报。5%/3% 为本计划的工程筛选门槛，不是已测收益或显著性保证；跨 workload 不通过就只公布适用域。

**停止条件：** 若每个代表性配置净收益都未越过重复测量波动或 5% 门槛，就保留负曲线，不强行选阈值。短 pilot 后先完成 P6 的 B=2/4 最小重构与消融；若主要代价仍是额外 target 计算而非逐序列/eager 成本，停止向更大 batch 扩展并调整开发重心。门控关闭后 draft 权重/KV仍驻留、prefill 仍执行的实际成本必须留在结果中。

未来结果行应类似：`B=4, input=4096, output=256, k=6：target-only X tok/s；always-spec Y；gated Z；verify eager 比例 r；无抢占容量 C0/C1`。X/Y/Z/r/C 均待测；旧的 82.3/132.5 不能填进这个新配置。

## 6. P1：已有 attention 接入、长上下文与整机归因

### 6.1 接入范围和先测上界

P0 先用 baseline 的 torch.profiler/nsys 估计普通 decode 中 attention 占时间比例 `f`，结合**完整调用**的预计加速比 `s`，用 `S≈1/((1−f)+f/s)` 判断投入空间；将 attention 成本理想化为零时，上界为 `1/(1−f)`。这是“其他成本不变”的 Amdahl 估算，`f` 必须是时间占比，不能把历史 KV traffic 的 7%→38% 直接代进去。device profile 定位 GPU 成本，最终 `f` 要对应同一 decode critical path；不能直接将设备 kernel 时间之和除以含长 prefill 的完整生成时间。整段生成另按 decode 在全程 wall time 中的比例折算。

首版只接 **target 模型的普通单 query decode**。Prefill 与投机的多 query verify 保持 flash-attn；draft 和其他不匹配形状退回 flash-attn。这样可以解释“主 attention kernel 不会直接加速 verify”，不将 P1 与投机收益相乘。正式组合实验仅在两项各自通过后做。

后端比较为 `flash-attn / 已有 Triton v3 / 已有 CUDA mma`；主性能对照的图开关、KV 状态、dtype、页大小和生成长度一致。CUDA 入口目前按 BF16 指针解释，只支持 GQA=4、head_dim=128；接入时增加这些约束的明确检查。**不在每层偷偷将 FP16 转 BF16** 来跑 kernel，dtype 不匹配就退回或另立适配成本。

图路径要考虑固定地址的 partial/workspace、融合归约计数器复位，以及图 padding 产生的 ctx=0 空行。当前 C++ 使用 current stream，但每次仍有 contiguous 与临时工作区调用，不能据此宣布天然 graph-safe。先编译并预热，验证重复 replay、不同请求长度及融合/非融合归约；不使用已知错误的 warp-specialization 入口。静态图的块表宽度还参与 CUDA chunk 划分，必须记录，不能按实际 ctx 假定最佳 splits 自动成立。

### 6.2 长上下文不是把 4096 改成 16384 就完事

按 **1K→4K→8K→16K** 分阶段扩展。16K 输入加 256 输出应配置可覆盖总长度的 `max_model_len`（例如 20480，并核验 checkpoint 上限），还要覆盖投机预留槽位；重建普通/draft/verify 图的 block table 宽度。实际 KV 需求按 `2×层数×KV头数×head_dim×dtype字节×已缓存token数` 计算，再加页尾、workspace、图池与权重。模型标称支持长上下文不等于 24GB 中每个并发都能装下。

先跑真实模型 logits/生成，再测完整运行；随机 Q/K/V 正确不等于真实多层链路对齐。先 B=1，再 B=2/4；长上下文并发超过容量时记 NA 和所需预算，不能偷减输出或换小模型后仍声称原配置成功。

### 6.3 可验证的完成判据

1. **功能完成：** 真实 Qwen3-4B checkpoint 下，普通 decode 的后端命中与退回可观察；1K/4K/8K/16K、B=1 及可容纳的 B=2/4 完成 256 token，图/eager 对拍覆盖非整页长度、跨页、物理块不连续、图空行和连续 replay。只对改变路径做必要检查。
2. **数值完成：** 同真实前缀比较 attention 输出及 logits，输出容差暂定 `atol=2e-2, rtol=2e-2`（BF16），同时记录误差分布并与同 dtype flash-attn 相对 FP32 的误差尺度比较；若 baseline 本身超门槛，先调查而非事后任意放宽。另用显式 argmax 调试分支比较生成，不能直接传 `temperature=0`：当前 sampler 会除以温度，并未实现 greedy。浮点近似有边界 token 差异时回到 logits 定位，不能把稳定性替换成统计采样口径。
3. **性能完成：** 报每种后端完整 attention 调用延迟（含归约、必要数据准备）、逐层 attention 总 device time、完整生成 tok/s、TTFT/请求 TPOT、workspace/图显存。主 kernel partial 仅作解释，不进最终引擎 speedup 分子。
4. **收益成立：** 在预先指定主场景 `input=16384, B=1, output=256, 普通 decode graph on` 下，相对同配置 flash-attn，完整生成吞吐至少 **+5%** 或请求 TPOT 至少 **−5%**，5 组成对结果方向一致；另一项必须同报且无超过 3% 的回退，TTFT 回退不超过 3%。对主收益指标事前选定，不能事后挑较好的一项。若 16K 因预算不可执行，报失败/限制，不能悄悄改主场景。
5. **可用性成立：** 在非主场景通过后再决定保留后端；短 ctx/较大 B 的明显回退允许已有 flash-attn 退回，选择规则用一组测量确定，再以不同 prompt 验证。不能一组结果既调参又当最终验收。

第 4 条是拟定的“可以写整机提升”的门槛，而不是功能完成必须凭空达成的承诺。最终表保留 baseline X、CUDA Y、Triton Z 及变化率 `Y/X−1`，全部以同场景实测填入。本方案没有 X/Y/Z 的新测量值。

**停止条件：** 若 profile 给出的理想整机上界不足 5%，先不做复杂参数调优；可以做最小接入以验证上界，随后收尾。若接入超过 7 人天仍主要卡在 correctness/graph，就先交付已支持的 eager/短 ctx 范围，标明余项，保留默认 flash-attn。即使 kernel 更快但整机不快，也应写成“量化收益被其他成本稀释”，而不是造出显著数字。

### 6.4 P6：批量投机的开发范围与验收

**先改 draft，再改验证图，分别留版本。** 不将当前已支持多请求的 varlen target 验证前向误写成从零开发；新增的是同候选位置的 batch draft，以及目前缺失的 B>1 图路径。第一阶段只覆盖 k=2、B=2/4；正确且有收益空间后再扩 k=6 或 B=8/16，图形状按这些有限桶捕获，不捕获默认 512 的全范围。具体执行顺序见 §12。

核心实现工作：

1. proposer 接收批量 last tokens、context lengths、block tables 与 temperature；每个候选位置跑一次 batch 前向和采样。每请求的候选序列仍自回归，不能将时间维 k 个候选无条件并行。
2. 候选/候选 logits 与逐请求 ID、有效长度绑定；准备 B×(k+1) 或带显式有效 mask 的验证图输入。padding 不能贡献候选、采样结果或 KV 写入。
3. 按请求维护 target/draft 的已确认 KV 水位。门控禁用期间生成的真实 token、拒绝后的补采样 token，必须在重新提议之前补进 draft 的确认上下文；补齐成本计入速度。复用共同 block ID 不意味着两模型的 KV 内容天然同步。
4. 图、batch、有效长度和 gate 决定在本轮保持一致，结束请求与部分接受只更新真实确认前缀。P2 中已有门控的队列长度问题一并修正，不能在同轮随着 `popleft()` 改变决策。

**功能验收：** B=2/4、不同输入/完成长度、全接受/部分拒绝、EOS、跨页与重启投机均通过。注入相同候选和显式随机数时，批量与逐请求参考的接受前缀和 bonus 一致；真实模型用同一确认前缀对照增量 logits。随机生成最终序列不要求不同 RNG 消费顺序下逐 token 相同。

**结构验收：** trace/计数显示每个投机轮的 draft 模型调用是 k 次批量前向，B>1 的已覆盖验证形状实际 replay 图，不能只在配置里写 graph on；每个阶段单列新增图/概率/logits 显存和 draft 补齐量。

**性能验收：** 主场景选 `B=4,input=4096,output=256,k=6`，对照 C 与 S1/S2，5 组成对复测。拟定写成“优化提升”的门槛是完整生成吞吐 ≥+5%，同时报告 TTFT/请求 TPOT 和容量代价；对实用 U 是否加速另列，不能只赢过低效 C 就声称投机一定比普通解码快。未过门槛就报告功能完成与负结论，不扩 B=16，不用局部 graph 时延包装净收益。

### 6.5 P11：GPU 拒绝采样与往返削减的开发范围与验收

**第一步削减数据往返，第二步才融合占时操作。** GPU 上保存 `[B,k]` 候选，直接连接 proposer 与 verifier；验证结果组织成有效长度和 `[B,k+1]` token 缓冲区，在轮末合并回传用于当前 CPU scheduler。不承诺全引擎无同步，也不在这一步重写整个调度器。

批量化要先修正温度广播：当前 `_softmax_with_temp` 对三维 logits 构造 `[1,1,B]`，逐序列调用时 B=1 掩盖了这个问题；真正批量输入需要 temperature 沿请求维广播为 `[B,1,1]`。此项是批量路径正确性的前置，不是可报告的性能收益。

随机拒绝采样仍计算 `min(1,p/q)`，首拒绝位置从归一化的 `(p−q)+` 采样修正 token，全接受从最后一行 target 分布取 bonus。保留全词表校正，不能为了减少访存丢掉残差质量或用 argmax 替代随机采样。RNG 的 seed/offset 必须随轮推进，graph replay 不能重复使用同一份随机数。

用已有 `verify_batch` 作为数值参考。实现可以先对批量 GPU 操作编译/复用缓冲，再手写有依据的 Triton 接受前缀、残差采样或结果整理 kernel；FlashInfer 的 fused chain sampling 可作为接口和参考实现，是否能在当前 sm_86/依赖环境运行尚需执行时检查。若采用现成库，应如实写“后端接入”，不能称自研该库的 kernel。

**功能验收：** q=p 全接受、首位/中途拒绝、全接受 bonus、不同温度、padding、EOS 与终止裁剪通过；显式随机输入对拍，并保留分布测试。单位置独立 acceptance mask 为真不代表最终交付：首拒绝后的候选全部无效，接受率诊断与真实 emitted draft tokens 分开统计。

**结构验收：** 热路径无 proposer 候选 `.tolist()` 后又重造 GPU candidate tensor；无每请求单独读取 `int(accepted)`/`int(bonus)`；trace 验证回传/同步改成批量操作，临时概率、q_pad 和结果缓冲复用或消除的范围如实记录。主目标是必要结果的合并回传，不要求人为追求“只剩一个 kernel”。

**性能验收：** 沿用 P6 主场景，比较 S2/S3，报完整生成吞吐、verify/sample 时间、CPU 等待、显式回传次数和临时显存。主收益指标仍为完整生成吞吐 ≥+5%，5 组成对方向一致；如果 trace 中该部分的理想收益空间不足 5%，先交付数据流简化，不再投入 4–7 天写复杂 fused kernel。性能收益只能由新结果填写。

### 11.3 从 JD 得到的事实，与项目选择的推断

**直接得到的事实：** 多条实习要求涉及主流推理框架/后端、GPU 内核、性能分析和系统编程。百度 J104435/J100476 明确涉及投机推理。NVIDIA JR2019909 明确涉及 KV 分层卸载/复用。华为的大模型推理/软件研发涉及模型量化；这些措辞没有进一步明确“KV 量化”。现有强样本也不能将泛 GPU/集群调度解释成 mixed chunked prefill 的明文要求。

**据此给本项目的推荐：**

1. **先使已有 attention 与投机资产成为完整引擎成果。** 真实 checkpoint、graph-on、多个请求、不同 context 下的后端接入、批量执行和状态处理是具体代码工作；单项前后结果用于说明改动贡献。复用现有实现比另开一套热门功能更省求职准备时间。
2. **在 nano 内完成混合调度，再收尾本轮项目。** 它能补当前 prefill/decode 互斥的真实缺口，也有原面经的具体问句支持；本轮 JD 不足以将它说成实习招聘的最高频指定技术。与批量投机结合时要计 k+1 验证及双 KV 资源，并用长短请求交错到达验收。
3. **nano 本轮完成后，再做一次范围明确的 vLLM 二次开发。** 选择一个实际可读、可修改、可验证的后端或热路径问题，例如分页 attention 的形状配置选择、工作区/图 padding 处理或投机执行开销。届时核对主流框架现状、选定具体问题、再估实现成本；不把 nano 全套搬过去，也不默认现有框架缺少某个功能。SGLang/FlashInfer 可作为问题需要时的替代或后端。开源 PR 是可选呈现方式，是否合并由维护者决定；可复现的修改与性能归因本身也有展示价值。
4. **投量化/低比特岗位时，用 W4A16 或主流量化后端实践替代另开 KV 项目。** 它与用户已有算子学习路线衔接，不自动新增一条平行大项目。岗位说“量化”时，仍需看目标团队究竟做权重/激活、KV 或部署系统。
5. **小算子融合与独立 KV 压缩暂不作为核心必做。** 前者重复现有内核能力且可能已被 `torch.compile` 处理；后者在本轮实习 JD 中的具体支持较弱，并有较大的质量/后端工作。真实 profile 或明确目标岗位需要时再追加。

这是一组基于岗位要求与当前资产的**投入判断**，不能从少量 JD 推导 offer 概率。尤其不要为覆盖所有方向而同时开混合调度、W4A16、KV 卸载、KV 量化和两个融合 kernel；先完成一条能独立解释架构、瓶颈、正确性和整机效果的主线。

### 11.4 对“还能做什么”的最终收敛

推理引擎实习的方向池仍是 attention 接入、批量投机、混合调度、主流引擎二次开发，以及按岗位选做的低比特实践。**实际顺序固定为：nano 内 P1 → P6 → P12 → 单项消融与组合收尾 → 下一阶段 vLLM 二次开发。** P11 在 P12 后的收尾 trace 中根据批量路径的剩余同步/采样瓶颈决定是否追加；低比特权重、独立 KV 量化和小算子融合不作为 nano 本轮必做项。定位算子内核实习时，可以用形状覆盖、BF16/HGEMM 基本功替换部分调度工作；定位量化岗时，选择一项低比特权重/后端实践，替换相应分支，不全做。

这里的“nano 优化完”指本轮范围收尾：三条主线有可用实现或明确停止结论，改变的状态路径通过正确性检查，单项与组合具有同口径的端到端记录，已知退回/限制可复现，结果与简历陈述一致。它不指实现所有候选功能，也不要求每个改动都跑出正收益。未获收益的分支必须如实报告，不为凑数字继续无限调优；仍有正确性缺陷的功能不能作为完成成果。

本附录不新增代码，不报告未运行的优化收益，也不替用户投递职位。原 172 题数据、生态实现数量和本轮 JD 是三种不同证据，各自限定来源与用途。

### 12.3 阶段 0：最小基线与必要修复

预计首次可用半天到一天；完整 P0 工具合计 2–3 人天，随开发补齐。

1. 保存原始版本与工作负载配置，先核对缓存哈希前置问题：[scheduler.py](</D:/学习/specdec/nanovllm/engine/scheduler.py:118>) 先推进 `num_cached_tokens`，但 [hash_blocks](</D:/学习/specdec/nanovllm/engine/block_manager.py:155>) 又按 `cached` 到 `cached+scheduled` 计算登记范围。例：旧 cached=0、本次 scheduled=256，调用时 cached 已是 256，函数会算 start=1/end=2，跳过刚完成的第 0 页、尝试登记下一页。这是已读源码的语义矛盾，尚未运行复现；建立跨页最小复现，统一“旧有效缓存量→新有效缓存量”的契约后再跑正式基线。普通/分块/投机收尾都只登记已确认且确有有效 KV 的完整块，不能包含被拒候选或越界块。
2. 正式吞吐按实际交付 token IDs 计数；修复 `LLMEngine.step()` 中 `1+last_accepted` 与实际落地数不一致的口径。增加轻量 token 交付 hook，记录首 token、最后 token、投机一轮成批交付与请求结束；不要伪造逐 token 均匀到达。
3. 修复 `_softmax_with_temp` 的 batch 温度广播：输入 `[B,k,V]` 时温度应按 `[B,1,1]` 广播。先验证逐行结果，尤其 B>1 的不同温度；这是正确性修复，不包装成性能优化。
4. 门控使用本轮 active decode B 的一致快照，避免 `popleft()` 改变队列长度后同轮请求获得不同决定。首版 P6 性能比较可固定 always-spec；门控切换作为独立状态验收。
5. 在同一组必要正确性修复上建立 **U：target-only＋FA＋普通 decode 图**、**C：当前逐请求投机**，保存输入 token IDs 和完整生成记录。U 不加载 draft；另设保留双模型但禁用投机的诊断组，只在需要隔离驻留成本时运行。原始未修版本保留历史定位用途，不通过把正确性修复只放进优化组制造优势。
6. 获得一个普通 decode、一个投机代表性 trace，分清 attention、draft、verify、sample 和 host 等待。只用于决定改动范围，不先跑全矩阵长压测。

**阶段交付：** U/C 基线可复算，输出计数一致，缓存哈希、采样与门控语义明确。既有 37 项检查保持通过；新增检查只针对本次修改的哈希/跨页、温度、计数和门控路径。之后即进入 P1。

### 12.4 阶段 1 / P1：attention 接入与有限算子工程

预计 4–7 人天。首版只覆盖 **target 的普通单 query decode**，包括 batch 中每条请求一个 query。现有 kernel 已支持 batch；这项的新增成果是实际引擎接入与适配。

**任务 A：建立后端契约。** 在 attention 层接入 FA/已有 Triton v3/已有 CUDA MMA。将 q 归一到内核所需 `[B,H,D]`，返回形状与下游 reshape 保持一致。检查 BF16、GQA=4、D=128、页表和 KV layout；不匹配时明确退回 FA。保留 prefill、draft 及多 query verify 的现有 FA 路径，不为了命中 kernel 偷偷转换 dtype。

**任务 B：处理工作区与图。** 在 capture 外先触发扩展编译/加载和各拟捕获配置的 warmup，再捕获图；不让首次 JIT 发生在 capture 中。CUDA host 入口目前申请输出及 split scratch，并调用 `.contiguous()`。检查实际 stride，确认有没有复制；根据真实调用路径提供可复用的输出/scratch，维护捕获后的地址与生命周期。`.contiguous()` 在张量已连续时未必复制；捕获期间的 `torch.empty` 也不等于每次 replay 都重新分配，不能仅凭源码宣布开销。核对归约计数器复位、重复 replay 和 ctx=0 padding 行；有失败才修改对应 device 边界逻辑。[PyTorch CUDA Graph 约束与内存说明](https://docs.pytorch.org/docs/main/notes/cuda.html#cuda-graphs)

**任务 C：选择有限配置。** 比较已有 `splits/block_n/warps/stages/fused` 组合，在少量代表性 shape 上建立选择规则，不跑全笛卡尔网格。先调整已有配置；如果完整调用仍有清楚的加载/切分/归约瓶颈，才改内核主体。不要重开错误的 warp-specialization 分支。

图 replay 使用已捕获的 kernel 参数；Python 中换一个配置变量不会改变图。若采用 batch/context 配置桶，需捕获对应的有限图，或将确有必要的动态逻辑放在内核中；后者另算工作量。首版可以固定已验证配置，后端与配置选择均避免读取 GPU `.item()`。

**验收：**

- 数值覆盖 B=1/2/4、上下文不齐、跨页 255/256/257、图 padding、连续 replay。旧独立 attention 检查采用 vs FP32 最大绝对误差 2e-2、vs BF16 FA 1e-2；这些只作为同类探针的已有口径，不能直接套到模型 logits 或声称文本分布完全不变。
- 在真实 checkpoint 上逐层/最终 logits 对照 FA，先用小样本登记并固定容差，再调性能；出现 NaN、跨请求污染或 replay 后状态错误即停止性能扩展。
- 比较 **A：U＋P1 vs U**，图开关、dtype、页、输入/输出一致；再比较固定配置与选择规则。完整调用包含 wrapper、scratch/归约，不能只取 partial 主 kernel 时间。
- 预先选定一个主收益指标：完整生成吞吐至少 +5%，或请求 TPOT 至少降低 5%；至少五组成对方向一致，其余 TTFT/显存/退回完整报告。这是拟定门槛，不是预计收益。

**收尾条件：** 上界或实测不支持进一步调参，就交付最小可用接入与适用范围；不继续写第三套 attention 追数字。若七人天仍卡图/正确性，标记阶段未完成、保留 FA 默认，记录已支持范围与失败原因后调整投入。

### 12.5 阶段 2 / P6：真实批量 draft 与验证图

预计 7–12 人天。先 B=2/4、k=2，不扩动态 k。target 的多请求 varlen 验证输入已经存在，`verify_batch` 数值接口也已支持 batch；新增重点是 draft 的模型调用粒度和 B>1 图执行。

**任务 A：批量 draft eager。** 增加批量提议入口，同一候选位置将 B 条请求一起前向，k 个位置仍顺序生成。每步使用逐请求的 position/context/slot/block table，形成 `[B]` token 与 `[B,max_blocks]` 页表。目标是从 B×k 次单序列前向变为 k 次批量前向，不承诺 B 倍速度。

保存 `[B,k,V]` 的原始 draft logits 和 `[B,k]` 候选，温度与实际草稿采样一致。下一候选位置可以使用 GPU token；为兼容现有 Sequence/postprocess，首版允许在一轮结束后回传候选，但不在每个请求、每个位置上单独 `.item()`。不要误传 softmax 后概率，不让后续前向覆盖此前 logits。

**任务 B：批量 draft 图。** 扩展 `capture_draft_cudagraph()` 与 proposer 的图字典，捕获精确 B=2/4 的单步 decode 图，一轮 replay k 次。每行元数据独立更新；持久缓冲区保存各位置结果。图外采样可先保留，不把融合采样列为批量图的前置。

**任务 C：B>1 verify 图。** 扩展 `capture_verify_cudagraph()`/`run_verify_forward()`，以 `(B,k)` 选择图。固定 k=2 时 query 数为 `B×3`，实际 `cu_seqlens_q/k`、slot 和 block table 必须复制到静态输入；logits 按请求边界切分。首版可保留已有逐请求拒绝采样和 postprocess，P11 再优化这段数据流。

先只处理所有参与请求均有完整 k 个候选的图批次；B=3、候选变短或不支持形状走 eager，并记录原因。不通过补零 logits/概率强行凑图；之后有需求才设计合法 padding。

**任务 D：明确多轮状态。** 为每个请求明确记录已交付 token、target 有效 KV 范围、draft 有效 KV 范围以及待验证候选。草稿从最新已确认前缀继续；被拒候选不进入正式 `token_ids` 或前缀哈希，可由正确的 slot 覆写与可见长度屏蔽失效。bonus 往往还需要在后续前向写入 KV，不能把“已交付长度”直接当作两模型均已完整缓存的长度。

gate 关闭若干步再开启时，draft 必须补齐期间缺少的已确认 token，补齐费用计入运行时间；仅输入最后一个 token 不足以恢复缺失前缀。两套 KV 数据分开，但沿用现有逻辑块表/对应物理块编号约束，不把一条请求的 slot 写到另一条。

**验收：**

- B=1 回归；B=2/4 上下文不齐，比较批量 draft 与逐请求 draft 在相同已确认前缀上的逐步 logits；target eager/graph 也做相同输入对照。GPU RNG 消耗顺序可能变化，随机模式不要求同 seed 的输出逐 token 相同。
- 验证首位拒绝、中间拒绝、全接受＋bonus、EOS/输出长度裁剪、跨页、请求退出和新请求加入；至少跑两轮，以完整前缀重算核对增量 logits/KV 可见范围。新增测试应打到改变的状态路径。
- 校验本轮候选/logits 被正确清理、请求顺序一致；graph/eager 结果满足冻结容差，B=3/短候选确实退回，门控关闭后重启正确。
- 独立比较 **S1：C＋批量 draft vs C**；再比较 **S2：S1＋批量 verify 图 vs S1**。记录模型调用数、draft/verify wall/device 时间、完整生成吞吐、接受率和图/KV 显存；有限图带来的容量损失也报告。

**性能与停止：** 沿用预选完整生成吞吐 +5% 的门槛和五组成对检查。若 B=2/4 重构后额外 target 计算仍使净收益不足，保留边界/负结果，停止扩大 B/k 图集合；不将高接受率直接写成速度提升。k=6 或 B=8/16 只在这一版正确且有明确收益空间后追加。

### 12.6 阶段 3 / P12：顺序双前向混合调度

预计 5–8 人天。先关闭投机实现普通 decode，再接入已验证的 P6。首版含同一逻辑 step 内的两组工作：**先 decode，再 eager prefill chunks**；它不是一个 GPU batch 混算，也不是执行重叠。

**任务 A：改调度返回与执行协议。** 当前 `schedule()` 返回 `(seqs,is_prefill)`，有 prefill 就提前返回。改为明确的工作计划，分别包含 decode 和 prefill 工作、每条请求的执行长度和预算。`LLMEngine.step()` 分别执行与 postprocess 两组，runner 对每组重建 context；同一请求一轮只属于一个组。

先确定 decode 工作、锁定所需 block，再计算剩余预算和 prefill chunks。preemption 可能将 running 请求转为等待 prefill，工作计划要与最终队列/块所有权一致。两组之间的完成与释放由确定的顺序处理，不让后组引用已经失效或被重新分配的 block。

**任务 B：保持 chunk 增量语义。** prefill 使用该请求真正已缓存的前缀，从 `num_cached_tokens` 开始处理本 chunk，target/draft 都按各自状态完成对应 KV 写入；中途 chunk 不交付无效首 token。只有 prompt 完成后才转入正常 decode 并交付首 token。抢占后的重算、前缀命中和双模型缓存状态必须与现有块管理一致。

**任务 C：定义预算口径。** 首版的 `max_num_batched_tokens` 可作为本逻辑 step 的 **target 输入 token 预算**：普通 decode 按每请求 1，投机验证按实际 query 数（完整 k 时为 k+1），加上 prefill chunk token 数；按执行工作收费，不能按最后接受 token 数收费。draft forward/补齐的 token 数与耗时另列，不能把 target token budget 称为双模型总算力预算。

KV 分配继续按 target＋draft 的实际 bytes/block 计算，同时预留验证候选槽位；同一逻辑页号在两池中的有效性一致。无剩余预算或无可分配 KV 时就不调度该 chunk，记录等待原因，而不是越预算执行。

**任务 D：处理长请求等待。** 首版选择能给 prefill 留出预算的有限到达轨迹，记录等待和最大连续跳过轮数；持续 decode 饱和时，严格优先可能令 prefill 长期无预算，不能宣称天然公平。先据实际 active 上限与 budget 调整资源配置，仍有饥饿再单独设计预留/老化策略，并说明它改变的优先级与延迟权衡。

**验收：**

- 普通 decode 下覆盖仅 decode、仅 prefill、两组并存、长 prompt 跨多个 chunks、chunk/page 边界及请求结束。与完整 prefill 在相同前缀的 logits/KV 对照，中途 chunk 不多交付 token、不重复进入 running。
- 再开启 P6，覆盖不同接受长度、门控退回/重启、抢占后重新 prefill；目标预算和两池 block 计数逐轮可解释。
- 用同一长短请求交错到达轨迹，比较 **相同模型/后端/投机模式下，原调度 vs 新调度**。第一轮少量请求检查逻辑与曲线，正式尾延迟只对少数值得比较的配置补样本量。
- 拟定主目标为 ITL P99 至少降低 10%、完整生成吞吐回退不超过 3%；TTFT、长请求等待、抢占/重算同时报告。正式尾延迟需符合 §4.3 的样本要求，小 pilot 的 P99 只标探索性。若首 token/饥饿代价不合适，不能仅凭 ITL 达标默认开启。

### 12.7 条件 P11：何时新增一个真正的融合算子

在 P12 后收尾 trace 中，若批量路径的 verify/sample、候选回传和同步仍占有明显可优化成本，再投入额外 4–7 人天。先完成 GPU 候选保留、批量结果回传与缓冲复用，然后选择一段实际热点做 Triton/CUDA 融合，例如接受概率/首拒绝前缀/结果整理，或残差采样中的特定部分。全词表 softmax/归一化/随机采样不预设能高效塞入一个 kernel。

已有 [FlashInfer chain speculative sampling](https://docs.flashinfer.ai/generated/flashinfer.sampling.chain_speculative_sampling.html) 是成熟对照：其输入是 draft/target **概率**，本项目 `verify_batch` 接收 draft **原始 logits**，接入或比较时要计入相同的概率构造成本。它证明有实现参考，不证明我们这段已是瓶颈或能得到同样收益。

验收需保持温度、首拒绝后截断、全接受 bonus、残差分布与 RNG/graph 语义；比较 **S3：S2＋P11 vs S2** 的整段时间、同步/回传次数和临时显存。理想可省空间不足预定门槛时，只交付数据流简化，不开复杂 fused kernel 分支。

Add+RMSNorm/SiluAndMul 不自动替代这项；仅当编译后基线和真实 profile 显示缺口，或目标明确变为算子岗时，另选一个 2–4 人天的练习。FP8/INT8 KV 与 W4A16 仍不进入本轮必做范围。

### 12.8 单项消融、组合验收与交付

| 对照 | 要回答的问题 |
|---|---|
| A vs U | 已有 attention 接入让普通 decode/完整生成改变了多少 |
| S1 vs C | 真正批量 draft 的独立贡献 |
| S2 vs S1 | B>1 verify 图的独立贡献 |
| 相同 A 或 S2 下，新调度 vs 原调度 | 混合调度对长短请求干扰、吞吐与等待的贡献 |
| 有 P11 时 S3 vs S2 | 往返削减和采样融合的增量；融合前后再独立比较 |
| F vs U，以及 F vs C | 保留下来的组合相对实用普通路径和项目原版本的效果 |

F 只纳入实际可用、经过选择的改动。P1 普通单 query decode 不直接覆盖投机多 query verify；always-spec 下可能很少命中 P1。必须报告实际后端/图命中与退回，不能把各项局部 speedup 相乘。

每个阶段的交付统一为：实现版本与开关说明、实际配置与原始记录、改变路径的正确性证据、一张独立前后结果表、适用范围/失败原因。最终再给一张组合表，包含实际输出 tok/s、TTFT、TPOT、ITL（有样本时）、峰值/池/图显存、无抢占并发、接受率和退回。

性能计时与 profiler 分开；同配置至少五组成对，交替/随机顺序，冻结 prefix cache 冷热状态。初始化/JIT/捕获与稳态生成分栏。保存逐请求/逐组记录，不用进度条或 device 时间之和代替用户可见时间。

“nano 本轮完成”要求三条主线有可用实现或有证据的停止结论；实现正确性通过，结果口径一致，限制可复现，简历只写实际支持范围。某支停在实验阶段就写实验结论，未通过正确性的功能不能算完成。之后再启动 vLLM 的独立问题选择。
