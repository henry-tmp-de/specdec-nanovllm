# 调度优化：迭代过程、效果对比与思考方式

> 这份文档只讲**调度**这一条线（P12 → P13 → P15 → P14），是"**并行 / 并发 / 让路式**"这三个词的完整来龙去脉。
> 结果侧见 `优化报告.md` §c.3；行业对照见 `调度-行业现状调研.md`；时间线见 `优化过程复盘.md`。
> 日期：2026-10-13 · 代码版本：`v2-optimizations`（含 P15 `spec_overlap_mixed` 与 P14 `spec_prefill_rotate`，默认都关）

---

## 0. 一页速览

**要解决的问题**：一条长 prompt 到达时，正在解码的请求被"饿死"整个 prefill 时长。

| 阶段 | 做了什么 | 解码 ITL max | 长 prompt TTFT | 稳态吞吐 |
|---|---|---:|---:|---:|
| **0 原始** | prefill 独占（一轮只有一种路径）| **3836 ms** | **3756 ms** | 41.74 tok/s |
| **1 分块让路** | 切块 + 块间让一整轮给 decode | 580 ms | 7524 ms ❌ | 42.46 |
| **2 共批但串行** | 排进同一个 step，两个前向**串着跑** | 594 ms | 7529 ms ❌ | 42.46（**收益 0**）|
| **3 共批且并发** | 排进同一个 step，两个前向**并发跑** | **455 ms** | **5029 ms** | **45.45 tok/s** |
| （对照）**P14 轮转** | 多条长 prompt 轮转推进 | 不变 | 极差归零、**p50 变差** | 池满时 **−19.1%** ❌ |

★ **一句话结论**：**"把两件事排进同一个 step" 不省时间；"让它们同时跑" 才省时间。**
**而并发档让两边都变好了**（解码更快 + 长 prompt 也更快 + 吞吐更高）—— 它不再是"交换"。

# 第一部分：迭代过程

## 阶段 0：原始状态 —— prefill 独占（问题长什么样）

调度器每一轮只在"prefill"和"decode"里选一个：

```python
# 先跑 prefill 的 while 循环
if scheduled_seqs:
    return scheduled_seqs, True     # ← 只要有一条要 prefill，这一整轮就全是 prefill
# 才轮到 decode
```

**后果**（同进程探针实测，3 条请求在解码 + 突然来 1 条 16K）：

```
正常一轮解码：12.1 ms
长 prompt 到达那一轮：解码请求拿到的 token 数 = 【精确为 0】
                     它的下一个 token 要等【3836 ms】
                     尖刺 = 10.7×（1K 长 prompt）→ 310×（16K）
```

## 阶段 1：★ 先测上界，**不写一行代码**

这一步是整个迭代里最重要的一步 —— 因为**它决定了后面该不该做**。

**测了两笔账**（同进程多条件探针）：

```
账① draft prefill 是浪费：run() 里 `if self.draft_model is not None` 【不看 spec_k】
     ⇒ 只要进程加载了 draft，prefill 就白跑一遍 0.6B
     ⇒ 冷启动让 target prefill 多花 20%~26%（16K 时 +739 ms）
     ⇒ 热缓存下是恒定 +31.5 ms（与上下文无关）

账② 尖刺：10.7×(1K) → 310×(16K)，远超方案 §6.3 的"只有 2–3 倍就收手"停止线
```

**决策**：账② 远超停止线 ⇒ **立项**。（★ 同一条停止线，当年把 P1 否掉，这次放行 —— 判据一样，结论相反。）

## 阶段 2：分块让路（P12 / P13）—— 第一版解法

**做法**：把长 prefill 切成小块（C 个 token），**块与块之间让一整轮给解码**。

```python
budget = min(remaining, chunk) if chunk else remaining   # 每轮最多拼一块
...
yield_to_decode = (chunk > 0 and self._prefill_chunk_pending and bool(self.running))
#   ↑ 上一轮留下了没拼完的块，且此刻确实有请求在解码 ⇒ 这一轮跳过 prefill，整轮给 decode
```

★ **关键性质：一轮内仍然只有一种执行路径**（要么 prefill、要么 decode），只是轮与轮之间交替。
这是**有意选的**低风险路线 —— 因为这个项目被"一轮内混两条执行路径"坑过 3 次
（最典型：`spec_enabled` 门控快照 bug，有回归测试钉着）。

**结果**：16K 的尖刺 **310× → 16.9×（C=512）/ 24.4×（C=1024）**。
**代价**：prefill 墙钟 **+11.5%**；而且**长 prompt 自己的 TTFT 从 3756 翻倍到 7524 ms**。

★★ **所以这一步的本质是"交换"**：用 prefill 用户的延迟，去换 decode 用户的延迟。
（这一句话很关键，因为阶段 3 会把它彻底改写。）

## 阶段 3：把"真混合"的上界算出来 —— 当时算错了

当时的推理是：

```
让路式：解码请求的 ITL = 一个 prefill 块 + 一个解码轮 = T_chunk + 12.1 ms
真混合能做的，只是把"解码轮"和"chunk"叠在一起 ⇒ 最多省掉那 12.1 ms
⇒ 上界 = 一个解码轮 = 12.1 ms，占实测尾部 3.2%~10%
```

**结论：不做**（10% 的尾部改善，换不来把已知雷区搬进核心路径）。

★ **这个 12.1 ms 是错的** —— 见第二部分。**但它错得很有价值**（它引出了阶段 4 的实验设计）。

## 阶段 4：★ P15 —— 把"共批"和"重叠"拆开（认识的转折点）

**转折来自一个问题**：既然 decode 走图、prefill 走 eager 是可行的（行业做法），
那"排进同一个 step"到底省不省时间？

**把三种跑法分开测**：

```
让路式：        [解码轮 220][块 171] [解码轮 220][块 243] ...
P15-串行：      [解码 220 + 块 171 = 391] [解码 220 + 块 243 = 463] ...      ← 同一 step，但串着跑
P15-并发：      [解码 220 ∥ 块 171 → 298] [解码 220 ∥ 块 243 → 307] ...      ← 两条 stream
```

**实测（同进程、同一张卡、轮内交替，n=3，中位数）**：

| prefill 块深度 | t_decode | t_prefill | t_串行 | t_并发 | **重叠收益** | 上界 min | 收益/上界 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 第 0 块 | 220.2 | 171.4 | **391.5** | 298.1 | 93.4 | 171.4 | 54.5% |
| 第 5 块 | 220.4 | 242.9 | **462.8** | 306.8 | 156.0 | 220.4 | 70.8% |
| 第 10 块 | 219.0 | 319.2 | **537.9** | 338.9 | 199.1 | 219.0 | 90.9% |
| 第 14 块 | 218.8 | 381.4 | **600.7** | 396.9 | **203.8** | 218.8 | **93.1%** |

★★★ **第一列和第四列讲了两件事**：

1. **`t_串行 = t_decode + t_prefill`**，残差 **−0.1 ms** ⇒ **串行版一点重叠都没有**（这是诚实的对照）
2. **并发版把"相加"变成了"取大"** ⇒ 收益逼近 `min(t_decode, t_prefill)`

**端到端（场景 A：3 条解码 + 突来 1 条 16K）**：

| 指标 | 独占 | **让路式** | **P15-串行** | **P15-并发** | 并发 vs 让路 |
|---|---:|---:|---:|---:|---:|
| 解码 ITL 窗口 p50 | — | 475.1 | 498.8 | **316.5** | **−33.4%** |
| 解码 ITL 全程 p99 | 1089.8 | 570.4 | 581.5 | **409.3** | **−28.3%** |
| 解码 ITL 全程 max | **3836.2** | 580.3 | 594.4 | **455.3** | −21.5% |
| **长 prompt TTFT** | **3756** | 7524 | 7529 | **5029** | **−33.2%** |
| wall (s) | 21.62 | 21.05 | 22.32 | **18.66** | −11.4% |

**★ 请注意这张表的形状**：

```
独占      ：解码输（max 3836）、prefill 赢（TTFT 3756）
让路式    ：解码赢（max 580）、prefill 输（TTFT 7524）   ← 一笔交换
P15-并发  ：解码 max 455【而且】TTFT 5029                ← ★★ 两边都更好了
```

**它不再是交换** —— 因为两者吃的是**不同资源**，重叠让两边同时推进。

## 阶段 5：P14 —— 多序列轮转（一个诚实的负结论）

**另一个问题**：多条长 prompt 同时到达时，只有第一条在推进（`break` 掉），后面两条干等。

**做法**：把 waiting 当环，本轮让每条各拿一块、没拼完的移到队尾。

**结果（场景 B：1 条解码 + 3 条同时到达）**：

| ctx | off 三条 TTFT | on 三条 TTFT | 最大 TTFT | 极差 |
|---|---|---|---|---|
| 4096 | 952 / 1778 / 3013 | **2114 / 2114 / 2114** | **−29.8%** | 2061 → **0** |
| 8192 | 1963 / 3688 / 5636 | **4721 / 4721 / 4721** | **−16.2%** | 3673 → **0** |
| **16384** | 4248 / 8780 / **27390** | 8196 / 8196 / 30403 | **+11%（噪声内）** | 23142 → 22207 ❌ |
| 16384 **+ 池 253 块** | 3509 / 7300 / 12203 | **10049 / 10049 / 10049** | **−17.3%** | 8694 → **0** |

★★ **它自己纠正了任务书里的一个错误推断**：

> 任务书写的是"三条都在第 16 轮完成 ⇒ 等 3 倍时间变 1 倍"。
> **按【轮数】成立**（`[8,16,24] → [8,8,8]`），**但按【墙钟】不成立** ——
> 轮转把**每轮的工作量也放大了 N 倍**（off 每轮 1 块 vs on 每轮 3 块）。
> **"第 16 轮"是另一根尺子。**

**⇒ 它不是"让请求更快"，是"让请求一样快"**：极差归零，但 **p50 反而变差**（原本最快那条慢 2.4 倍）。

★★ **而且 16K × 3 条时它根本帮不上忙** —— 因为瓶颈是 **KV 准入**（每条 16K 要 64 块，池 174 块 ⇒ N_max=2），
**不是调度顺序**。把池子抬到 253 块，"没效果"立刻变成"max TTFT −17.3%、极差归零"。

**★ 2×2 分解**：`池子贡献 −55.4%`、`轮转再贡献 −17.3%` ⇒ **先要资源，再谈调度。**

**⇒ P14 交付为默认关闭的可选开关，不进入推荐配置。**

# 第二部分：效果对比 —— 为什么"并发"比"让路/串行"好这么多？

## 2.1 ★ 先把四个词分清楚（它们不是一回事）

| 词 | 含义 | 需要什么 | 我们的例子 |
|---|---|---|---|
| **串行（serial）** | 一个做完再做下一个 | —— | `run(decode)` 之后再 `run(prefill)` |
| **让路（yielding）** | A 主动**让出一整轮**给 B | 时间上**分离** | 块之间整轮给 decode |
| **并发（concurrent）** | 两件事在**同一时间段内都在推进** | **资源互补**（一个吃带宽、一个吃算力）| 两条 stream 同时跑 |
| **并行（parallel）** | 同一**时刻**真正同时执行 | **多份资源**（多卡 / 多 SM）| 4 张卡各跑一个配置 |

★ **你问的"并发比并行好" —— 实际是"并发（重叠）比让路/串行好"。**
**"并行"在我们这里指的是另一件事**（多卡同时跑不同配置做测量），跟这个问题的结论无关。
把这个区分讲清很重要，否则面试时会被绕进去。

## 2.2 ★ 为什么我原来只估计"好一点点"（12.1 ms）

**因为我把"解码轮"这个参数抄错了配置。**

```
我当时用的：一个解码轮 = 12.1 ms
   ★ 那是【普通 decode、无投机】的数字 —— 逐值复核确实是 12.04 ms ✓ 数字本身没错

但实际上（默认配置开了投机）：
   3 条请求 × (1 + k=6) = 21 个位置 + 6 次草稿前向
   一个解码轮 = 【220.2 ms】   ← 差了 18 倍
```

**⇒ 收益上界不是"一个解码轮"，而是 `min(解码轮, prefill 块)`。**

**用"相加变取大"直接推**：

```
串行/让路：解码和 prefill 的 GPU 时间【必须都花掉】 ⇒ 墙钟 ≈ t_decode + t_prefill
并发      ：两者重叠                                 ⇒ 墙钟 ≈ max(t_decode, t_prefill)
                                             收益 = t_dec + t_pf − max = 【min(t_dec, t_pf)】
```

**代入：`min(220, 171~381) = 171 ~ 220 ms`** ⇒ 这才对上实测的 93.4 → 203.8 ms。

★★★ **一个非直觉但很重要的后果**：
> **投机解码把"解码轮"从 12 ms 拉长到 220 ms（因为一轮里多了 6 次草稿前向 + 1 次 21 位置的验证），
> 于是"解码被 prefill 挡住"的代价也跟着变大了 —— 这反而让"重叠执行"更值钱。**
>
> **换句话说：越是用投机（每轮越重），越应该让 prefill 和 decode 重叠，而不是排队。**

## 2.3 ★ 为什么"把两件事排进同一个 step"收益是 0（这是理解的关键）

```
P15-串行实测：t_串行 = 391.5 ms，而 t_decode + t_prefill = 220.2 + 171.4 = 391.6 ms
                                                残差 = 【−0.1 ms】
```

**⇒ 只是"排进同一个 step"的话，一点都没省。** 因为：

```
总 GPU 工作量没变
两个前向都是【串行发到同一张卡】的（同一个 stream）
⇒ 时间就是加起来
```

**"共批"（把两件事放进同一个调度单位）和"重叠"（让它们在硬件上同时跑）是两个独立的自由度。**
我把它们混为一谈了 —— 这也是我最初反对混批时犯的第二个错误：

> ★ **我一度用"混批会让 CUDA Graph 失效 ⇒ 那些轮慢 3.6×"来反对它。**
> **那个论点针对的是"一个混合批走一次前向"的形态。**
> **P15 的做法是"拆成两个前向"：decode 那个照常吃图** ⇒ 图的问题**根本不存在**。**我错了两次。**

## 2.4 并发为什么能拿到上界的 93%

**因为两者吃的是不同资源**：

```
decode ：带宽型（3 个 token / 220 ms 里，主要成本是把 8 GB 权重读一遍）+ SM 占用低
prefill：算力型（4B 模型读一遍 8 GB 权重 / 171~381 ms ≈ 带宽的 3%）
⇒ 并发时带宽需求 ≈ 660 + 28 + KV 流量 ≈ 700 GB/s < 实测天花板 842 GB/s ✓ 放得下
```

**而且块越大，decode 越接近"免费搭车"**（收益/上界从第 0 块的 54.5% 涨到第 14 块的 93.1%）——
因为此时 `t_prefill > t_decode`，`min` 就等于 `t_decode`，**整轮解码被完全藏进 prefill 里**。

★ **但"免费"是相对的，它自己也承认了代价**：

```
并发时 decode 被拖慢 77.9 → 178.1 ms（资源竞争的真实代价，块越大拖得越多）
但"多跑一个 decode"的边际成本 = t_并发 − t_prefill = 126.7 → 63.9 → 19.7 → 15.5 ms
⇒ 两者确实互相拖慢，【但净账为正】
```

## 2.5 四个阶段的效果总表（同一套三场景）

| | **独占** | **让路式** | **P15-串行** | **P15-并发** | **P14-轮转** |
|---|---:|---:|---:|---:|---:|
| 解码 ITL max（场景 A）| 3836 ms | 580 | 594 | **455** | 不变 |
| 长 prompt TTFT（场景 A）| **3756** | 7524 | 7529 | **5029** | — |
| TTFT 极差（场景 B）| — | 大 | 大 | — | **归零**（但 p50 变差）|
| 稳态吞吐（场景 C）| 41.74 | 42.46 | 42.46 | **45.45** | 池满时 **−19.1%** |
| **本质** | 饿死解码 | **交换** | **零收益** | **双赢** | **只保公平** |

# 第三部分：思考方式（从简到详）

## 3.1 一句话版

> **先测上界 → 上界不够就收手；够，就找最便宜的等价实现 → 每次只动一个变量 →
> 并且一定要留一个"零收益对照"来证明收益是真的。**

## 3.2 五个步骤（简）

```
① 先建约束地图，别先优化
② 先测上界，再决定投不投
③ 先做最便宜的等价物
④ 每次只动一个变量，并留"零收益对照"
⑤ 结论必须连边界一起写
```

## 3.3 详细展开（每条配这一步的真实例子）

### ① 先建约束地图，别先优化

用 `torch.profiler` 把 decode 的 device time 分解：`GEMM 79.27% / attention 9.24% / elementwise 8.37% / 采样 0.81%`。
再确认"是不是到硬件极限"：权重流式 **763 GB/s = 峰值 81%**；prefill **≈65 TFLOPS（峰值约 71）**。

**⇒ 三条推论**：decode 想快只能让权重变小（量化）· prefill 没空间（只能靠调度）· 吞吐的杠杆是并发。

**这次的具体体现**：我们**没有**一上来就改调度，而是先确认"prefill 真的没有算力空间"
（≈65/71 TFLOPS）—— **如果 prefill 还有空间，那答案就是"把 prefill 做快"，而不是"重新排它"。**

### ② 先测上界，再决定投不投

```
P1（把自写 attention 接进引擎）：f = 8~9% ⇒ Amdahl 上界 +10%、代入实测 +3% ⇒ 【否掉】
这一次：尖刺 10.7× → 310× ⇒ 远超"2–3 倍就收手"的停止线 ⇒ 【立项】
```

**★ 同一条判据，两个相反的结论** —— 这就是"上界"这个工具的价值：它不带情绪。

### ③ 先做最便宜的等价物

**这次最典型的例子**：在决定"要不要写混批"之前，先问了一句
"**有没有更便宜的旋钮能达到同样目的？**"

```
❌ 混批（写代码、踩 3 次的雷区、前置条件 3 项）：上界 min(解码轮, 块)
✅ 切块大小（拧一个配置）：C=256 时解码 ITL 从 296 → 82 ms，代价 prefill 墙钟 +24.5%
```

**先拧旋钮，再考虑写代码** —— 因为拧旋钮是**可逆、可复算、零风险**的。

### ④ ★ 每次只动一个变量，并留"零收益对照"

**这是本文档最值钱的一条。** 两个例子：

```
P15：串行版 = 391.5 ms，而 t_decode + t_prefill = 391.6 ms（残差 −0.1 ms）
     ⇒ ★ 如果没有这个"零收益对照"，那个 −33.4% 就说不清是
       "重叠的功劳"还是"共批的功劳"

P14：N=1 时轮转退化成老行为 ⇒ 场景 A 逐项在噪声内相同（79.6 vs 79.8 ms）
     ⇒ ★ 这证明"轮转没把 decode 改坏"，是它后面所有结论的前提
```

**规则**：任何"改动带来了收益"的结论，都必须有一个"**改动退化成老行为时收益确实为 0**"的对照。

### ⑤ 结论必须连边界一起写

```
P15：只在"有请求在解码 + 有 pending 块"时生效；纯 decode step 图命中率不掉；
     spec_graph_bs 未含 B=3 时会退回 eager（既有配置边界，不是 P15 引入的）
P14：只在"池子有富余"时有效；16K×3 时 N_max=2 ⇒ 【那个 regime 下它没用】；
     它固有 max↔mean 交换（p50 变差）
```

## 3.4 ★★ 三条最值钱的方法论（这一轮新学到的）

### 3.4.1 "把两件事排在一起" ≠ "让它们同时跑"

**共批（放进同一个调度单位）和重叠（在硬件上同时执行）是两个独立的自由度。**
混批 + 串行 = 0 收益；混批 + 并发 = `min(t₁, t₂)` 的收益；让路 = 0 收益。

★ 我把这两件事混为一谈，**导致了两个错误判断**：
① 以为"混批没用"（其实"混批但不重叠"才没用）；
② 用"图会失效"反对它（那是"一个混合批走一次前向"的形态；拆成两个前向就不存在了）。

### 3.4.2 ★ "上界"这一项最容易抄错 —— 它也必须被实测检验

```
我把"解码轮"抄成了 12.1 ms（普通 decode 的读数），而默认配置开了投机 ⇒ 实际 220 ms
⇒ 上界算小了 18 倍 ⇒ 差点把一个真收益方向判死
```

**教训**：**"上界"是一个必须标口径、必须复核的量** —— 它来自哪个配置、哪个开关状态，要写清楚。
P15 用一个**深度扫描**（t_decode / t_prefill / t_串行 / t_并发 四列）把上界钉死了，
而且**它同时给出了"残差"**来证明串行档真的没有重叠。

### 3.4.3 ★ 先要资源，再谈调度

```
P14 的 2×2 分解：把池子从 174 抬到 253 块 ⇒ max TTFT −55.4%
                 在这个基础上再做轮转      ⇒ 再 −17.3%
⇒ 【容量的杠杆 >> 调度的杠杆】
```

**这解释了为什么 §d.5 引的那三个外部 issue（SGLang #32549、vLLM #57413）不能照搬**：
它们的 KV 都只用 15%~40%（**没满**），而我们 16K×3 的场景 KV 峰值已 **75%** ——
**不在同一个 regime**。**引用别人的结论前，先确认自己落在他的前提里。**

## 3.5 面试话术（可直接背）

> **问题**："长 prompt 把解码堵死怎么办？"
>
> "先测上界：3 条解码 + 突来一条 16K，解码请求那一轮拿到的 token 数是 **0**，
> ITL 尖刺 **310 倍**（3.8 秒）—— 远超我们事先定的'只有 2–3 倍就收手'的停止线，所以立项。
>
> 第一版做**分块让路**：把长 prefill 切块，块之间让一整轮给解码。尖刺 **310× → 16.9×**。
> 但它是**交换** —— 长 prompt 自己的 TTFT 从 3.7 秒翻倍到 7.5 秒。
>
> 第二版做**重叠执行**：同一个 step 里 decode 走 CUDA Graph、prefill 块走 eager，
> 用两条 stream **真正并发**。实测 ITL **−33%**、长 prompt TTFT **−33%**、稳态吞吐 **+8.9%**
> —— **两边都变好，不再是交换**。因为 decode 是带宽型、prefill 是算力型，资源互补。
>
> 关键是我把**串行版**也做了：`t_串行 = t_decode + t_prefill`（残差 0.1 ms）。
> **没有这个零收益对照，那个 −33% 就说不清是'重叠'还是'共批'的功劳。**
>
> 另外我一开始把上界算成 12 ms（那是**普通 decode** 的读数），实际开了投机之后一个解码轮是 220 ms ——
> **越是用投机，越应该让两者重叠，而不是排队。**"

## 附：术语对照（防混淆）

| 我们说的 | 英文 | 定义 | 本项目里的位置 |
|---|---|---|---|
| **prefill 独占** | exclusive / prefill-first | 一轮只有 prefill | 原始状态、SGLang 默认 |
| **分块让路** | chunked prefill + decode yielding | 块之间让一整轮给 decode，**轮间交替** | P12/P13（默认关）|
| **共批（混批）** | mixed batching / MB | 同一个 step 里既有 decode 又有 prefill | P15 的"串行档"就是它 |
| **重叠 / 并发** | overlap / concurrent execution | 两个前向在硬件上**同时**跑 | P15 的"并发档" |
| **多序列轮转** | multi-sequence prefill rotation | 一轮内在多条 prefill 序列间轮转 | P14（默认关）|
| **并行** | parallel | 多份资源同时用（多卡）| 只用于"多卡并行跑配置"做测量 |
| **EB vs MB** | Exclusive vs Mixed Batching | 论文给的名字（ICML 2026，arXiv 2606.00516）| 我们属于 EB 家族 + chunk 边界轮转 |
