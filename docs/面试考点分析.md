# AI Infra 面试考点分析（基于真实面经的机械抽取）

> 目的：**决定下一个优化做什么**，而不是"感觉什么重要"。
> 配套数据：`面试考点-逐题分桶.md`（每个考点的全部原题）
> 数据采集：2026-09-01，15 篇面经的 12 篇 OCR 原文

---

## ⚠️ 先读这一节：这份数据怎么用，怎么会被误用

**1. 分桶是关键词机械匹配，一题可落多桶 → 各桶占比相加 > 100%。**

**2. ★ 看占比之前必须先看每桶里的原题。**
大类占比会掩盖「这个大类里真正问某个具体技术的只有几道」。
**本项目已经两次栽在这上面**（见文末「反面教材」），所以：
每个考点下面都直接列出原题，**自己数，不要只看百分比**。

**3. 样本只有 12 篇面经、172 道题，不构成统计显著的大样本。**
只能看**量级和排序**，不要当精确分布。另有 24.4% 的题落不进任何桶（自我介绍、
场景题、LoRA 等），说明分桶本身也是不完备的。

**4. 「命中率」的分母是 172 道题，不是「面试总时长占比」。**
一道题被问到 ≠ 它和别的题一样重要，答不上来就挂的权重也不一样。

## 二、逐考点深挖：**桶里到底问了什么**

> 每节先给「原题摘录」（完整原题见 `面试考点-逐题分桶.md`），
> 再给「**这个桶的真实内容**」和「**我们能答什么**」。

### A. 模型结构 / Attention / 位置编码 —— 36 道（20.9%）

原题里出现的是：
```
MHA，MQA，GQA，MLA 有什么区别，谁更快，它们的 kvcache 怎么计算
讲解下 kvcache 的原理，以"我是小明"梳理下这个流程
Transformer 的 FFN 层作用是什么，intermediate_size 为什么通常是 hidden 的 4 倍
RoPE 位置编码的原理是什么，和传统 positional encoding 有什么区别
LayerNorm 和 RMSNorm 有什么区别，为什么 Llama 等模型大量使用 RMSNorm
Attention 为什么要除以 √d？如果不除会出现什么问题？
```

**桶的真实内容**：**纯八股**。问的是「知道不知道」，不是「做没做过」。
**这桶靠背，靠项目补不了。** 唯一和项目相关的是「kvcache 怎么计算」——
而那属于 E 桶。

**我们的位置**：✅ 强。写过两版 attention kernel 的人，讲 GQA / KV 显存公式
比背八股的人有体感（`Qwen3-0.6B ≈ 112KB/token` 这种数我们真算过）。

---

### B. prefill/decode 与性能指标 —— 17 道（9.9%）

```
prefill 和 decode 的区别？（计算密集 vs 带宽密集）
TTFT / TPOT 分别由什么决定，怎么优化
MFU / HFU 怎么算，有什么区别
attention 层的计算量和访存量怎么算，MLP 层呢
长文本推理时的 memory bottleneck 在哪里，如何优化
线上首 Token 响应时间从 1 秒变 3 秒，代码和模型都没改，你会从哪些方面排查
```

**桶的真实内容**：**「你会不会算账」**。不是背公式，是能不能对一个具体场景
给出「瓶颈在哪、为什么、怎么验证」。

**我们的位置**：✅✅ **最强的一块**。做过完整 roofline（算术密度 4.0 vs 拐点 38）、
实测带宽天花板（842 GB/s）、分离过「纯 kernel 时间 vs 墙钟时间」、
算过 attention 在不同 ctx 下占 memory traffic 的比例（7% → 38%）。
**这桶我们能答出别人答不出的深度。**

---

### C. CUDA / 算子 / kernel —— 18 道（10.5%）

```
写过 CUDA 算子、Triton 算子吗？讲讲最近写的一个算子
你实现一个算子的整个工作流程？
你实现的算子是什么瓶颈的？效率如何？
FlashAttention 为什么更快？有没有改变 O(n²) 复杂度？
推导一下 online-softmax 的伪代码
解释下 CUDA kernel launch overhead，如何减少
CUDA Graph 了解过吗 / vit 可以用 cuda graph 加速吗
Tensor Core 在大模型推理中的作用，FP16/BF16/FP8 如何利用它
手撕 MHA / 手撕 GQA（torch → CUDA）
GEMM 优化方法（tiling / 双缓冲 / swizzle / Tensor Core）
消除 shared memory bank conflict
TMA vs 旧数据搬运
```

**桶的真实内容**：**分两类**——
前半是「**你亲手做过吗**」（写好一个算子、讲瓶颈、讲效率），这是**门槛题**，
没做过就是零分；
后半是「**GEMM 阶梯**」（tiling / 双缓冲 / swizzle / bank conflict / TMA），
这是**深度题**。

**我们的位置**：
- 门槛题 ✅✅ **已经过了** —— Triton + CUDA 两版 paged decode attention，
  能报「纯 kernel 25.87µs，648 GB/s，占实测天花板 77%」这种数字
- 深度题 ⚠️ **只过了一半** —— 我们真的做了 shared memory 布局、`cp.async` 三级流水
  （一步值 1.43×）、swizzle。但 **TMA / TMEM / 2-SM cluster 在 sm_86 上物理跑不了**，
  只能讲原理。

### D. 调度 / batching / 引擎框架 —— 21 道（12.2%）

```
Continuous batching 和传统的 static batching 有什么区别，为什么更适合 LLM 推理
chunked prefill 是什么，如何平衡 prefill 和 decode 的调度
PD 分离的流程讲解下，单机/单卡/跨节点分别怎么通信
vLLM 支持的 PD 分离传输后端有哪些
vLLM 原理 / PagedAttention / prefix caching
```

**桶的真实内容**：**引擎机制**。注意这个桶 21 道里，
**「PD 分离」出现多次、「continuous vs static batching」出现多次**，
这两块是明确的重点。

**我们的位置**：⚠️ **弱**。
- continuous batching：nano-vllm 有实现，但我们**没做过对比实验**
- chunked prefill：nano-vllm **只有队首可切**（`scheduler.py` 里写死的），我们能讲这个缺陷
- PD 分离：**完全空白**，而且需要 2 张卡

### E. KV cache / 显存容量 —— 9 道（5.2%）

```
KVCache 是什么？为什么推理阶段需要 KV Cache？
MHA/MQA/GQA 的 kvcache 怎么计算
推理时如何处理 OOM，有哪些排查和优化方法
长文本推理时的 memory bottleneck 在哪里
```

**桶的真实内容**：**原理 + 容量**。**注意：这个桶里没有一道问「量化」，
也没有一道问「淘汰策略」**（见反面教材）。

**我们的位置**：⚠️ 会算，**但没有实测数据**。
我们的 `block_manager` 里写着「按字节反推块数」，这是能讲的；
`Qwen3-4B` 每 block 37.7 MB 这种数是真算过的。但没有「显存 vs 并发」的曲线。

### F. 前缀缓存 / 缓存复用 —— 4 道（2.3%）

### H. 分布式 / 并行 / 通信 —— 19 道（11.0%）

```
TP / PP / CP / EP 的通信方式和通信量
NCCL 的 allreduce / allgather / all-to-all 区别
ZeRO / FSDP / DeepEP / CPU offloading
MoE 推理的特点与挑战
TP8 部署时的 QKV 冗余问题，MLA / MHA 分别怎么样
```

**桶的真实内容**：**第三大桶，而且很硬**。

### I. 投机解码 —— 5 道（2.9%）

```
（这一桶在 172 道里只命中 5 道，具体原题见分桶文件）
```

## 三、★ 反面教材：我在这份数据上栽的两次

**两次都是同一个错：拿「自建大类的占比」去给一个具体技术背书。**

### 第一次：KV cache 量化

- 我说：「KV 量化踩中**显存KV 6.1%** + 算子 14.4%」
- 实际：那 6.1% 覆盖的是「显存/KV cache」**这个大话题**；
  G 桶（量化）的 8 道**全是权重/激活量化**，**没有一道问 KV 量化**
- 唯一出现「KV 量化」的地方是 **JD（岗位要求）**，不是面经题目

**教训：JD 提到 ≠ 面试考过。这两件事的权重完全不同。**

### 第二次：KV 生命周期（本篇要纠正的）

- 我说：「KV 生命周期打中**前缀缓存/调度 7.8%**，被列为高频第 2」
- 实际：那 7.8%（14 道）里 **10 道是调度/batching**，
  真正的**前缀缓存只有 4 道（2.3%）**，而且全是原理题
- 更直接的证据：**「淘汰 / LRU / 写时复制」在 172 道里命中 0 道**

**教训：大类占比会掩盖「这个大类里真正问 X 的只有几道」。**
**所以这份文档每个桶都列原题 —— 让你能自己数一遍。**

## 四、结论：我们该补什么

**先看事实**：
1. 172 道题里，**前四桶（A/D/H/C/B）占了 64.5%**，其余全部在 5% 上下
2. 我们**已经命中并做深**了其中两桶：**C（10.5%）和 B（9.9%）**
3. 我们**最强的两块**恰好是权重最高的两块之一
4. 我们**最缺的两块**是：**H 分布式（11.0%，完全空白）** 和 **K 项目效果（5.8%，没有端到端数字）**

**所以「再找一个新考点做」的边际收益很低。**

| 优先级 | 做什么 | 打哪桶 | 理由 |
|---|---|---|---|
| **1** | **端到端 harness + 长上下文**，把手里的 CUDA kernel 接进引擎 | **B 9.9% + K 5.8%** | 把已命中的 B 桶从「会算」升级成「量化过」；同时补 K 桶最缺的「最终效果」 |
| **2** | **投机解码 batch 扫描**（脚本已就绪） | **I 2.9% + B + E** | 独有资产，最快出数字 |
| **3** | **continuous vs static batching 对比 + chunked prefill 缺陷量化** | **D 12.2%** | 第二大桶，成本低，纯测量 |
| 4 | block_size / 内部碎片 | E 5.2% | 命中「PagedAttention 与碎片」这道最常问的原理题，改配置就行 |
| — | ~~前缀缓存 / RadixTree / 淘汰策略~~ | F 2.3%，**淘汰 0%** | **不做**，考频太低 |
| ? | 分布式 / TP 实测 | **H 11.0%** | 第三大桶且完全空白，但**需要 2 张卡**（服务器共享，得踩时间窗） |

## 五、和另一份简历的对照（避免撞车）

| | 对方 | 我们 |
|---|---|---|
| 算子 | 小算子融合（Add+RMSNorm / SiluAndMul） | **大算子**：paged decode attention，走到 CUDA 手写 |
| 显存 | **压缩** KV（FP8） | **量化瓶颈**（算清 attention 占比随 ctx 从 7% 涨到 38%） |
| 调度 | Chunked Prefill 混合调度 | **投机解码的 batch 门控** |
| 算法 | 无 | **投机解码（含无损性证明）** |
| 层次 | 优化已有路径的效率 | **改变要做的工作量本身** |

**四条线零重叠。**
