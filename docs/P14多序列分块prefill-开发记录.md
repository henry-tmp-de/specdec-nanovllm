## 0. 摘要（先看这七条）

1. **实现了**：同一轮预算内让**每条**待拼序列各拿一块（≤ `spec_prefill_chunk_tokens`），
   一条只服务一次；没拼完的序列**移到 waiting 队尾**（环状轮转）⇒ 队首永远是
   "最久没被服务"的那条（公平准入）。**默认关闭、老路径一行未改、可运行期翻转**。
2. **★★ 不变量守住了**：一轮内同一条序列只被调度一次（P13 那个"同一个 chunk 被拼 7 遍"
   的复现条件）。新增 51 项 CPU 断言把它钉死；全量 **412/412 通过，FAIL=0**（基线 361）。
3. **逐值等价**：把同一份 `p14_equiv.py` 指向**基线树**与**改动后的树**各跑一遍，
   8 组配置（chunk 0/2/4/8 × 预算宽/紧）下默认路径的**逐轮调度轨迹 md5 完全相同**。
4. **★★ 最重要的结论是一条【修正】**：§d.5 方向 1 说的"三条都在第 16 轮完成 ⇒ 等 3 倍
   时间变 1 倍"，**按【轮数】成立**（实测完成轮次 `[4,7,10] → [4,4,4]`），
   **但按【墙钟】不成立** —— 轮转把每轮的工作量也放大了 N 倍，所以
   **最大 TTFT 只降 16%（8K）/ 30%（4K）**，而**原来最快的那条变慢 2.4 倍**。
   它的真实收益是**把 TTFT 的极差压到 0**（公平），不是"总时间变短"。
5. **KV 代价（做完了）**：轮转**不会抬高池子峰值**（16K 下 132 → 133 块，8K 下 102 → 101），
   **不触发任何抢占**（8 组全 0）。真正的边界是**准入容量**：
   `N_max = floor(池块数 / ceil(ctx/块大小))` ⇒ ctx=16K 时 **N ≤ 2**（池 174 块 ÷ 64 块/条），
   N=3 出现 9~18 次"分配不到块"。
   ★ **判定性对照**：把池子抬到 **253 块**（开草稿滑窗，见 §4.6）后**同一个 16K × 3 场景**
   立刻兑现 —— 完成轮次 `[8,16,24] → [8,8,8]`、**最大 TTFT −17.3%**、准入被拒 0 次、
   极差 8.69 s → 0.05 s。⇒ **16K 那次的"没效果"全来自池子，不是机制。**
6. **代价侧**：轮转在"池子装得下"时**吞吐无损失**（全短 prompt：+2.5%，噪声内）；
   在"池子被顶满"时**稳态吞吐 −19%**（1819~2003 → 1486~1719 tok/s，两档范围不相交）。
   ★ 这 −19% 的**机理没归因**（批宽打点否掉了"解码批被压小"这个猜想，见 §4.5）。
7. **场景 A（对照组）**：3 条解码 + 突来 1 条 16K，开关两档**逐项在噪声内相同**
   （ITL p50 79.3~81.9 ms、p99 821~847 ms、max 868~872 ms）—— 轮转对只有 1 条
   partial 序列的场景**退化**成老行为（设计如此），没有把它改坏。

## 1. 出发点

### 1.1 要解决的问题（已量化）

`Scheduler.schedule()` 的 prefill 循环原来**只看队首**，且分块拼不完就 `break`：

```python
while self.waiting and len(scheduled_seqs) < self.max_num_seqs:
    seq = self.waiting[0]                       # ★ 永远只看队首
    ...
    if remaining < num_tokens and scheduled_seqs:
        break
    ...
    else:
        self._prefill_chunk_pending = True
        scheduled_seqs.append(seq)
        break                                   # ★ 直接收工，后面的请求没机会
```

⇒ 3 条长 prompt 同时到达时，只有第 1 条在推进（`docs/优化报告.md` §d.5 方向 1）。
**总工作量完全一样**，所以这是纯粹的调度损失。

### 1.2 外部依据（三个独立的生产 issue 指向同一个根因）

| 来源 | 现象 |
|---|---|
| **SGLang #32549** | 标题实测："Decode starved to ~1 batch per 24s under sustained chunked-prefill load" |
| **SGLang #35537** | 单槽卡住，KV 只用 ≤4% 也让请求等 4.5 分钟 |
| **vLLM #57413**（open） | TTFT p95 = 76 秒，而 KV < 40%、抢占 0 次 |
| **LMDeploy** | `_should_try_short_prefill_first()` 默认开；两个长 chunk 之间至少隔 3 轮（比我们保守） |

★ **本轮的实测给这条外部依据划了边界**（见 §5）：那三个 issue 的共同前提是
**"KV 没满"**。我们这台机器在 16K × 3 条时 KV 峰值是 **75%**，
**已经不在那个 regime 里了** —— 瓶颈换成了准入容量，轮转帮不上忙。

## 2. 机制与不变量

### 2.1 机制：把 waiting 队列当成一个环

```
每轮从环头起：给每条待拼序列最多 chunk 个 token，一条只服务一次；
              没拼完的把队首 rotate(-1) 到环尾。
```

* **轮转**：N 条 partial 在环上均分，每条每绕一圈拿到一次 chunk。
* **公平**：环头永远是"最久没被服务"的那条 ⇒ 预算不够时不会总从同一条开始（不饿死）。
* **总工作量不变**：只是把同一份 token 重新分配，一分不多
  （实测 `prefill_tokens_total` 两档逐值相同：16K→49152、8K→24576、4K→12288）。

### 2.2 ★★ 不变量：一轮内同一条序列只能被调度一次

P13 踩过的真 bug：分块拼不完的序列没被 `popleft()`、还留在 `waiting[0]`，
循环不 `break` 就会再取到**同一条**，把 `num_scheduled_tokens` 又覆盖一遍、再 append 一份
⇒ `scheduled_seqs` 里出现同一序列的多份副本 ⇒ **同一个 chunk 被拼 N 遍**
（实测 `round 0: step_tokens=14336`）。

**改成轮转之后循环必须继续往下走，这个坑更容易踩**，所以把"本轮已服务"做成
`PrefillRotation` 的**显式状态**（`_served: set[int]`），而不是靠调用方自觉：

* `next(waiting)` —— 环头若已服务过 ⇒ 返回 `None`（整环绕完一圈，本轮结束）；
* `mark(seq)` —— 拼完了（也要记，同一条不许再碰）；
* `yield_turn(waiting, seq)` —— 没拼完 ⇒ 记下 + `rotate(-1)` 让位；
* `skip(waiting, seq)` —— 分配不到块 ⇒ 记下 + 让位（**公平准入**：一条特别长的请求
  不该把整条队列堵死）。

`schedule()` 的六处最小改动：

1. `__init__`：`self.prefill_rotate = bool(getattr(config, "spec_prefill_rotate", False))` + `self._rotation = None`；
2. 循环前：`rot = None`，仅当 `chunk and prefill_rotate` 时建 `PrefillRotation` 并 `reset()`；
3. 取序列：`seq = rot.next(self.waiting) if rot is not None else self.waiting[0]`，`None` ⇒ `break`；
4. `can_allocate == -1`：轮转时 `rot.skip(...)` + `continue`（老路径仍 `break`）；
5. `remaining < num_tokens and scheduled_seqs` ⇒ 追加 `and rot is None`（轮转允许给"不足一整块"的剩余预算）；
6. 分块分支：`elif rot is not None:` 走 `rot.yield_turn(...)` + `continue`，老路径的 `else: break` **原样保留**。

★ `rot is None` ⇒ 老路径**一行未改**（这是默认值，也是 §4.2 对拍的依据）。

|---|---|---|---|
| off | **1867.8**（1819.0 ~ 2003.0） | **50.5**（49.2 ~ 54.1） | 9.85% |
| on | **1511.5**（1486.4 ~ 1718.7） | **40.9**（40.2 ~ 46.5） | 15.37% |
| **Δ(on − off)** | **−19.1%** | **−19.0%** | 噪声地板 15.4% |

★ 两档的**范围完全不相交**（off 最低 1819.0 > on 最高 1718.7）⇒ **这个回归是真的**，
不是"两组分歧大所以测不出"。3 遍版本的数是 −12.0%（1841.7 → 1620.2），方向一致。

**归因：把池子从方程里拿掉，差异就消失了**

| 条件 | off tok/s（中位） | on tok/s（中位） | Δ | 池子 |
|---|---|---|---|---|
| 4×16K + 4×2K（**池子被顶满**，峰值 165/174 = 95%） | 1443~1868 | 1419~1512 | **−19.1%** | 装不下 |
| 8×2K（**池子永远装得下**，峰值 40/174） | 1443.1 | 1478.9 | **+2.5%（噪声内，范围重叠）** | 装得下 |

⇒ **−19% 不是"轮转本身的开销"，而是"轮转 × KV 准入"的交互**：轮转让多条长序列
同时在环上，把池子顶到 95%，于是有请求反复拿不到块（准入被拒）。
**换句话说：P14 在这个场景里输给的不是老调度，是池子。**

**★ 但这个 -19% 的**机理**没归因出来（如实记录）**：探针加的"批有多宽"打点**否掉了**
最自然的那个猜想 —— 轮转**没有**把解码批压小，反而略大：

| 档 | tok/s（中位） | 平均解码批 | 平均 prefill 批（条） | 平均 prefill 批（token） | 解码轮数 | prefill 轮数 |
|---|---|---|---|---|---|---|
| off | 1820.6 | 2.48 | 1.12 | 2994 | 291 | 24 |
| on | 1573.5 | **2.64** | 1.16 | 3127 | 268 | 23 |

两档**总轮数几乎一样**（315 vs 291）、**批宽几乎一样**，但 on 档**每轮墙钟贵 ~24%**
（130 ms/轮 → 161 ms/轮）。**没查清**，两个待验的猜想（都未做隔离实验）：
① **物理块碎片化** —— 池子顶到 95% 且准入反复被拒时 `free_block_ids` 被打散，
   paged attention 的页局部性变差（两档的分配/释放**顺序**不同）；
② **解码批的"成分"不同** —— 轮转让长上下文序列更早/更久地留在解码批里，
   同样批宽下 attention 的 K/V 更长。

### 4.6 KV 代价：同时推进 N 条的池子占用（★ 任务书点名要量化的）

探针 `scripts/p14_kv_probe.py`：1 条解码请求在场（否则 P12 门控会把 `chunk` 压回 0）
+ N 条 16K 同时到达，用现成的池子打点（`block_manager.used_block_ids` / `free_block_ids`）
+ 包 `Scheduler.preempt` 数抢占 + 包 `can_allocate` 数"分配不到块"。

池子：`num_kvcache_blocks = 174`，`block_size = 256` ⇒ **总容量 44,544 token**；
一条 16K prompt = `ceil(16384/256) = 64` 块。

| N | 档 | KV 峰值(块) | 占池 | 最小空闲 | 抢占 | 准入被拒 | 完成轮次 | 轮内平均在场条数 |
|---|---|---|---|---|---|---|---|---|
| 1 | off | 66 | 37.9% | 108 | 0 | 0 | `[8]` | 1.00 |
| 1 | on | 66 | 37.9% | 108 | 0 | 0 | `[8]` | 1.00 |
| 2 | off | 130 | 74.7% | 44 | 0 | 0 | `[8,16]` | 1.00 |
| 2 | **on** | 131 | 75.3% | 43 | 0 | **0** | `[8,8]` | **2.00** |
| 3 | off | 130 | 74.7% | 44 | 0 | 0 | `[8,16,24]` | 1.00 |
| 3 | **on** | 131 | 75.3% | 43 | 0 | **9** | `[8,8,16]` | 1.50 |
| 4 | off | 130 | 74.7% | 44 | 0 | 0 | `[8,16,24,32]` | 1.00 |
| 4 | **on** | 131 | 75.3% | 43 | 0 | **19** | `[8,8,16,17]` | 1.88 |

**四条结论**：

1. ★ **轮转不抬高 KV 峰值**：N=2/3/4 时峰值都停在 130~131 块（±1 块 = 0.8%），
   因为**池子已经封顶**了 —— 峰值由容量决定，不是由调度顺序决定。
   （机理：本引擎的块是**首次调度时按整条序列一次性分配**的，所以"同时在场 N 条"
   在 old/on 两档下都受"池子能装几条整条序列"约束。）
2. ★ **不触发抢占**：`n_preempt = 0`（8 组全 0）。装不下时引擎的行为是
   **拒绝准入**（`can_allocate` 返回 -1），不是抢占 —— 所以代价体现为
   **等待**（TTFT 变长），不是抖动。
3. ★★ **推荐 N 与它的边界**：
   ```
   N_max = floor(pool_blocks / ceil(ctx / block_size))
   ```
   · ctx=16384 ⇒ `floor(174/64)` = **2**（N=3 起出现准入被拒：9 次 / 19 次）
   · ctx=8192 ⇒ `floor(174/32)` = **5**（3 条全装得下，实测零被拒、轮转收益完整）
   · 想在这个 ctx 下把 N 提到 3，需要 ≥ 192 块（3×64）⇒ 当前配置差 18 块。
   ★ **抬高边界的一条现成路子（已实测池子大小）**：日志里 draft KV cache =
   `28 层 × 174 块 × 28672 KB ≈ 4.87 GiB` —— **全上下文 draft 占的正是抬不起 N 的那块显存**。
   把 P7-B 的草稿滑窗打开（`spec_draft_window=4608`）后实测：

   | 配置 | draft 池 | **target 池** | 16K 下的 `N_max` |
   |---|---|---|---|
   | 全上下文 draft（默认） | 174 块 | **174 块** | **2** |
   | 草稿滑窗 W=4608 | 72 块 | **253 块（+79）** | **3** |

   ⇒ **开草稿滑窗正好把 16K × 3 条从"装不下"变成"装得下"**，这也解释了为什么
   §4.3(a) 的 16K 场景没有收益。★ **本轮没有跑"滑窗 + 轮转"的端到端**（只测了池子大小），
   所以这条是**线索 + 池子实测**，不是效果结论。
4. 轮内平均在场条数（`mean_batch`）：N=2 时 **2.00**（轮转真的让两条同时在跑），
   N=3 时 1.50、N=4 时 1.88 —— 数值 < N 正是"被准入卡住"的指纹。

## 5. ★★ 结论修正：**轮数收益 ≠ 墙钟收益**（本轮最值钱的一条）

§d.5 方向 1 的预言是：

> 改成"同一轮预算内多序列轮转"⇒ 三条都在第 16 轮完成。总工作量完全一样（48×1024 一分不多）。

**按轮数：完全成立。** 实测（B/8K/chunk=2048）完成轮次 `[4,7,10] → [4,4,4]`，
prefill 轮数 `10 → 4`，总 prefill token 两档**逐值相同**（24576）。

**按墙钟：不成立。** 因为轮转在把"轮数摊平"的同时，**把每一轮的墙钟也放大了 N 倍**：

```
off：每轮 1 块（2048 token）   → 10 轮 × ~0.5 s
on ：每轮 3 块（6144 token）   →  4 轮 × ~1.5 s
```

于是每条请求的完成时刻从"第 1 条快、第 3 条慢"变成"三条一样慢":

| ctx | off 三条 TTFT | on 三条 TTFT | 最大 TTFT | 极差 |
|---|---|---|---|---|
| 4K | 0.95 / 1.78 / 3.01 s | 2.11 / 2.11 / 2.11 s | −29.8% | 2.06 s → **0** |
| 8K | 1.96 / 3.69 / 5.64 s | 4.72 / 4.72 / 4.72 s | −16.2% | 3.67 s → **0** |
| 16K（池 174，装不下 3 条）| 4.25 / 8.78 / 27.4 s | 8.20 / 8.20 / 30.4 s | ~0%（KV 准入封顶）| 23.1 s → 22.2 s |
| **16K（池 253，装得下）** | **3.51 / 7.30 / 12.20 s** | **10.05 / 10.05 / 10.09 s** | **−17.3%** | **8.69 s → 0.05 s** |

★ 最后一行是本节的**判定性证据**：同一场景、同一 chunk，**只把池子从 174 抬到 253 块**，
"没效果"立刻变成"最大 TTFT −17.3%、极差归零"。
⇒ 轮转的收益**上限由准入容量决定**（`N_max = floor(池块数 / ceil(ctx/块大小))`），
在 `N ≤ N_max` 时它稳定地把"轮数收益"兑成"最大 TTFT 收益"（−16% ~ −30%），
在 `N > N_max` 时它什么也做不了（第三条根本不在环上）。

**16K × 3 条的 2×2 分解（★ 两笔收益谁大，一目了然）**

| 最大 TTFT / 极差 | 池 174 块（`N_max=2`） | 池 253 块（`N_max=3`，开滑窗） | **池子的贡献** |
|---|---|---|---|
| **轮转 off** | 27390 ms / 23.1 s | **12203 ms / 8.7 s** | **−55.4%** |
| **轮转 on** | 30403 ms / 22.2 s | **10093 ms / 0.05 s** | **−66.8%** |
| **轮转的贡献** | +11.0%（帮不上，反而略差）| **−17.3%** | |

★ 读法：**在 16K × 3 条这个场景上，"把池子做大"（−55%）比"改调度顺序"（−17%）有效得多**；
而轮转只有在池子够用之后才开始有正收益。**两者不冲突，是串联的**：
轮转负责把"排队不公"消掉（极差 → 0），池子决定它**能不能上场**。

★ **怎么读这个表**：P14 的收益**不是"让请求更快"**，而是**"让请求一样快"** ——
它消灭的是**队首独占造成的排队不公**（最快 vs 最慢差 2.9 倍）。对"每一条都要满足
TTFT SLA"的场景（p99 口径），这才是要的东西；对"总吞吐"没有直接收益（§4.5）。

★ **为什么任务书的算术会偏**：任务书的 `48×1024` 算的是**token 总量**（确实不变），
但"第 16 轮完成"里的"轮"是**被轮转重新定义过的** —— on 档的 1 轮 = off 档的 3 轮的工作量。
两边说的"轮"不是同一个时间单位。**这是本次实测最主要的一条修正。**
