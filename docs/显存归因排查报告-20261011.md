### 1.2 公式中每个量的定义

[model_runner.py 第 189～193 行](D:/学习/specdec/nanovllm/engine/model_runner.py:189)实际执行：

```python
free, total = torch.cuda.mem_get_info()
used = total - free
peak = torch.cuda.memory_stats()["allocated_bytes.all.peak"]
current = torch.cuda.memory_stats()["allocated_bytes.all.current"]
```

| 项目 | 获取位置 | 含义 |
|---|---|---|
| `total`、`free` | runner 第 189 行 | 当前设备 CUDA API 报告的总量和空闲量，不直接采用商品标称 24 GB |
| `used` | runner 第 190 行 | `total − free`，设备全局已用量，含本进程的 PyTorch 保留空间、框架外占用，也可能含其他进程 |
| `peak` | runner 第 191 行 | 最近一次 reset 后的 PyTorch allocator 已分配字节峰值 |
| `current` | runner 第 192 行 | 当前 PyTorch allocator 已分配字节，含模型及其他存活分配，不等同于纯权重 |
| 利用率 | [config.py 第 13 行](D:/学习/specdec/nanovllm/config.py:13) | 本次 harness 未覆盖默认值 0.9 |

`mem_get_info` 使用 `cudaMemGetInfo` 返回设备全局数据，不能把 `used` 理解成“只有驱动管理、PyTorch 管不到的占用”。PyTorch 保留的未使用内存同样会体现在设备已用量里。[PyTorch 2.10 API](https://docs.pytorch.org/docs/2.10/generated/torch.cuda.memory.mem_get_info.html)、[显存管理说明](https://docs.pytorch.org/docs/2.10/notes/cuda.html#memory-management)。

`warmup_model()` 先 `empty_cache()`，再 `reset_peak_memory_stats()`，运行 prefill，最后再次 `empty_cache()`：[runner 第 174～184 行](D:/学习/specdec/nanovllm/engine/model_runner.py:174)。草稿量化发生在这个 reset 之前：[第 88～104 行](D:/学习/specdec/nanovllm/engine/model_runner.py:88)。所以“加载期一次性峰值永久压缩 KV 池”的注释不符合当前调用顺序；加载过程仍可能通过留下分配布局或库状态间接影响预算。[reset API](https://docs.pytorch.org/docs/2.10/generated/torch.cuda.memory.reset_peak_memory_stats.html)。

两个 BF16 日志的预算数字一致。每个 target 块为 36 MiB，draft 块为 28 MiB，共 64 MiB；Q2 日志第 5～6、22～23 行直接报告了块大小。服务器原始 `config.json` 也给出 target/draft 层数 36/28、KV 头数均为 8、head_dim 均为 128、BF16；块大小默认 256，TP=1。计算位置为 [runner 第 195～212 行](D:/学习/specdec/nanovllm/engine/model_runner.py:195)，关闭滑窗时在 [第 239～240 行](D:/学习/specdec/nanovllm/engine/model_runner.py:239)整除。

**Q2 的差分账**，由原始日志舍入值推导：

```text
Δbudget = −Δused − Δpeak + Δcurrent
        = −0.190 − (−0.400) + (−0.399)
        ≈ −0.189 GiB
```

Q1 同理约为 `−0.159 GiB`。权重节省同时降低 `peak` 和 `current`，这两项几乎抵消；最终预算损失主要落在 `used`。不是“current 省下 0.399，再被 used 吃掉一半”的加减关系。

约 0.189 GiB 相当于 3.024 个块。整除的起点余数会影响块数差，再加上日志舍入，不能要求它恰好等于 4×64 MiB。直接用舍入值会把 Q2 算成 171 块；误差范围可以跨过 171 块的边界，并不构成代码与日志矛盾。要逐字节复算 170 块，需记录预算函数实际使用的未舍入变量；现有 wrapper 打印后还会调用原函数，再读一次显存。

## 3 最小补测与明确答案

### 3.1 目前为什么不能唯一确定

设 `C=current`、`R=reserved`、`U=used`、`P=peak`，定义：

```text
I = R − C                    分配器保留但未计入 current 的部分
O = U − R                    分配器之外的设备已用量，可能含其他进程
U = C + I + O
budget = 0.9T − P − I − O
```

这是指标的代数拆分，不把 I 自动等同于碎片，也不把 O 自动等同于 CUDA context。

Q2 的已知数字只能推出：

```text
ΔI + ΔO = ΔU − ΔC ≈ 0.190 − (−0.399) = +0.589 GiB
```

`ΔI≈0.589、ΔO≈0` 与 `ΔI≈0.399、ΔO≈0.190` 都能满足现有最终账目。预算阶段没有 R，不能区分这两种分配，更不能区分模块和库。加载阶段的 R 给出了支持分配器方向的证据，却没有补上另一个时刻的缺失观测。

**对“那 0.16～0.19 GiB 是什么”的回答：它是预算前设备全局 `used` 的净增量，不是已被确认的框架外额外开销。目前不能完整确定对象；已确认加载阶段有显著的分配器保留空闲增长，最值得优先验证的是这个增长如何延续到 warmup 后。**

### 3.2 第一对实验即可决定下一步

只需同一空闲卡、相同代码和环境，串行启动 BF16、qall 两个新进程，运行相同加载及 warmup，在 allocate 入口保存一次完整快照并停止，避免先分配十几 GiB KV 和捕获图。先做这一对，不运行生成基准、不同时启动两个引擎。

建议的诊断函数如下；它只作为实验设计附在本文中，尚未写入或运行生产代码：

```python
import json
import torch

def snap(tag):
    torch.cuda.synchronize()
    free, total = torch.cuda.mem_get_info()
    s = torch.cuda.memory_stats()
    c = s["allocated_bytes.all.current"]
    r = s["reserved_bytes.all.current"]
    p = s["allocated_bytes.all.peak"]
    rec = dict(tag=tag, free=free, total=total, used=total-free,
               current=c, reserved=r, peak=p,
               retained_idle=r-c, outside_allocator=total-free-r,
               inactive_split=s.get("inactive_split_bytes.all.current"),
               allocator=torch.cuda.memory.get_allocator_backend())
    print(json.dumps(rec), flush=True)
    return rec
```

在 [runner 第 186 行](D:/学习/specdec/nanovllm/engine/model_runner.py:186)的方法入口用外部 monkey patch 调用它，并抛出专用停止异常，在诊断 wrapper 中捕获退出。若与现有 harness 组合，注意 harness 还会再次包裹 allocate；不要让它继续调用原始分配函数。该停止方案只服务于预算前归因；最终显存收益还需完整构造引擎验证。

下一步按结果选择：

| 第一对观测 | 下一步 |
|---|---|
| `ΔI` 接近 +0.589 GiB、`ΔO` 很小 | 取一份预算前 allocator snapshot，检查权重、scale 与 inactive 空间共处情况 |
| `ΔO` 显著 | 再做 kernel 首次调用或 workspace 隔离，不先实现直载 |
| 二者都显著 | 分别报告各自字节数，再逐项干预，避免只找一个原因 |
| 外部进程占用变化 | 该对不能完成归因，换空闲卡后重新测一对 |

为了定位形成阶段，再将同一个 `snap` 插到量化后、warmup 的 reset 后、draft prefill 后、target prefill 后。reset 前的统计与 reset 后单独标记；不要把不同阶段相减当作最终 bf16/int8 差额。原生 allocator 的 snapshot 可用 `torch.cuda.memory_snapshot()`；若需要分配栈，再另启一次官方 memory-history 诊断，避免把这份有额外开销的运行当成性能基准。

现有 harness 的 `after load_model` 打点缺失还有一个代码原因：runner 提前 `from ...loader import load_model` 绑定了函数，harness 只改 `_ld.load_model`，未改 `_mr.load_model`：[runner 第 23 行](D:/学习/specdec/nanovllm/engine/model_runner.py:23)、[harness 第 75～78 行](D:/学习/specdec/scripts/check_quant_engine.py:75)。未来打加载点应同时替换已绑定入口。量化函数则已经正确同时 patch 了两个位置。

## 4 真正回收显存的做法与成本

### 4.1 先验证分配布局再选择实现

如果 I 解释主要差额，优先尝试紧凑 scale 存储、按最终 dtype 分配量化权重，或分离量化转换的临时分配。成本是一次诊断及小范围加载路径调整；风险是张量视图、存储生命周期或 packed 权重映射处理错误。验收以 **current 确实降低、retained_idle 不再反向增长、实际预算和块数增加** 为准，还要覆盖 CUDA Graph 捕获后的总占用。

直接预量化加载能避免 bf16 构造、GPU 量化临时量和交替替换造成的布局变化，因而是有针对性的工程方向。但如果最终 O 来自相同融合 kernel 的常驻模块，直载仍会执行这些 kernel；它不保证消除 O。

### 4.2 预量化直载需要做完整加载支持

现在不能仅切换到已有 int8 checkpoint：loader 在发现 `_scale` 键时明确拒绝，[loader.py 第 19～25 行](D:/学习/specdec/nanovllm/utils/loader.py:19)；Linear 构造仍统一分配浮点权重，[linear.py 第 27～33 行](D:/学习/specdec/nanovllm/layers/linear.py:27)。因此只删除拒绝分支会让 `copy_` 将 int8 整数直接转换进 BF16 参数，数值语义错误。

具体实现应包括：

1. 在构造前读量化层清单，为指定模块直接创建 int8 权重和 BF16 scale；未量化参数按原 BF16 路径构造。可用 meta 或量化构造分支，避免先在 GPU 分配整套 BF16。
2. 增加 scale 的形状及 dtype 校验、HF q/k/v→qkv 和 gate/up→gate_up 的加载映射。per-channel scale 要按输出行拼接；per-group 和 TP 分片不能直接假定与权重完全同规则。
3. 加载完成后跳过 `apply_int8_quant`，保留旧就地转换作为对照。对拍 int8 权重、scale、融合 GEMM 输出及完整生成行为。
4. 与旧路径同容量比较 capture 后和生成峰值；再比较自动预算产生的块数，避免“池小所以总用量小”的混淆。

成本为中等规模加载路径改造及数值回归，明显高于补两个指标；本次没有实现。离线脚本已经在 CPU 读取和转换权重并写入新目录：[quantize_int8.py 第 103～138 行](D:/学习/specdec/scripts/quantize_int8.py:103)。但离线与引擎是两份量化实现，不能仅凭注释宣称逐位等价；还要处理离线 scale 的二维存储形状与运行时 per-channel 一维参数的对应关系。

### 4.3 预算公式是否需要改

原公式可以写成 `0.9T − U − (P−C)`：以设备已用量为起点，再预留一次 warmup 的额外激活空间，具有合理的保守含义。它不是简单的“双扣权重”错误。

但它把 I 全部当作不可再用的开销。如果 I 中一部分能供后续激活或 KV 使用，确实可能低估容量。诊断性上界是 `budget + I = 0.9T − O − P`，**不能直接把这个上界用于生产分配**：inactive 小洞可能无法容纳当前的两个巨型连续 KV 张量，仍会 OOM。必须验证实际可复用性，或改变布局后重测。把 `used` 换成 `current` 则还会漏掉 O，依据不足。

增加几次 `empty_cache` 也没有针对性：warmup 开头、结尾本来就清缓存，INT8 还额外再清一次，[runner 第 104～112 行](D:/学习/specdec/nanovllm/engine/model_runner.py:104)。更不能删除 peak 余量来“挣块数”，那会把真实 prefill 的空间需求藏起来。

若 I 闭合，最合适的顺序是先修布局，再重测预算。若 O 闭合，则针对模块首次加载或具体 workspace；保留足够空间给预算后才出现的 decode kernel 和图捕获。NVIDIA 文档说明 lazy loading 可以把模块分配推迟到运行期，不能靠推迟加载把账面空间当成真实节省。
