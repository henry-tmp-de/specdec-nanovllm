# 第一部分 (a)：如何排查可优化的地方

## a.1 第一原则：先建"约束地图"，**不要先优化**

进项目时方案已经写好了一条主线。我们没有直接开工，而是**先花时间测清楚"瓶颈在哪"**：

```
用 torch.profiler 把 decode 的 device time 分解（B=1、ctx=4096、CUDA Graph 开、64 个 decode step）：

  GEMM / 线性层      79.27%   ← batch=1 时是【纯权重流式】：8 GB / 10.5 ms = 763 GB/s
  attention           9.24%         = 3090 峰值带宽（936）的 81%，基本跑满
  elementwise/norm    8.37%
  采样 + KV 写 + 其他  ~3%（采样仅 0.81%）
```

**这一张表决定了后面所有方向**，因为它把"哪里还有空间"变成了数量级问题。

## a.2 第二原则：用 Amdahl 把"上界"算出来，**上界不够就收手**

方案把「把自写 paged attention 接进引擎」排为**第一条开发主线**（4–7 人天）。我们没有直接做，而是先算上界：

```
attention 占比 f = 8.12% / 9.24% / 14.68%   @ ctx = 1024 / 4096 / 8192

Amdahl：S = 1 / ((1−f) + f/s)
代入我们自写 kernel 的实测加速比（比 flash-attn 快 1.31~1.47×）
⇒ 端到端上界只有约 +10%，代入实测 kernel 后【+3%】
⇒ 达不到方案自定的 +5% 门槛 ⇒ 【按方案 §6.3 停止条件降级】
```

★ **这是本项目最重要的一笔判断：用自己的测量否掉了自己方案里的第一条主线。**

## a.3 第三原则：用微基准验证"是不是真到硬件极限了"

只看占比不够，还要确认那 79% 里**有没有免费空间**：

```
权重流式实测 763 GB/s  = 3090 峰值带宽（936）的 81%   → 基本跑满，没有免费空间
prefill 实测 ≈65 TFLOPS（峰值约 71）                 → 也没有免费空间
draft 单次前向 2563.6 µs / 1.192 GB = 465 GB/s
   = 实测天花板（842）的 55.2%（对照 target 普通 decode 是 91.5%）→ 【这里有空间】
```

## a.4 从约束反推方向（而不是从"技术很酷"反推）

上面三条微基准直接推出三条可执行推论：

| 推论 | 由此立项 |
|---|---|
| decode 想显著变快，**只能让权重变小**（那 79% 是墙）| → **量化**（Q1/Q2/P9） |
| prefill 没空间 ⇒「长 prompt 堵 decode」**只能靠调度** | → **混合调度**（P12/P13） |
| 吞吐的杠杆是**并发**（B=1→4 效率涨 3.6×，而 B=4 时算力只用掉三十分之一）| → 批量投机（P6）、容量优化（P7/P9） |

## a.5 从"异常现象"里挖机会（四个真实实例）

很多时候机会不是从"约束地图"里读出来的，而是从**一个说不通的数字**里挖出来的：

| 异常 | 挖出了什么 |
|---|---|
| 投机**实现正确但只有 0.68×**（净亏）| 每步产出几乎没变（3.77→3.82 个 token），变的只有每步耗时（33.2→12.8 ms）⇒ **病根是固定开销不是算法** ⇒ CUDA Graph ⇒ 1.61× |
| **命中前缀缓存反而比不命中慢 3.6×** | 单步阻塞 17.3 秒、占端到端 85% ⇒ 这不是"缓存没用"，是**一个 bug 让一个功能变成负债** |
| 量化后权重省 0.4 GB，**KV 池反而少 4 块** | 把 `used` 拆成 `current + I + O` ⇒ **ΔO 逐字节为 0** ⇒ 不是"CUDA context 多了 kernel"，是分配器内不可回收碎片 |
| 滑窗 `P=0` **"第 1 轮正常、第 2 轮起崩"** | 轮次级退化不像"截断的固有代价" ⇒ 顺着查出一个 KV 对齐 bug |

## a.6 工具受限时怎么办（不许因此不测）

```
ncu 硬件计数器在机器上被禁（RmProfilingAdminOnly: 1 且无 sudo）
⇒ 改用 torch.profiler / CUDA event / 自写探针：
   · 同进程多条件探针（有 draft / 摘掉 draft / 窗口压回 0）
   · 逐轮打点（每一轮进了几个 token、墙钟多少）
   · 机制级判据（TV(q_eng, q_ideal)：引擎实际分布 vs 理想重算分布的 TV 距离）
```

## a.7 ★ 排查产出的三类东西（这才是"排查"的真正交付）

1. **一张约束地图**（哪块占多少、是否到硬件极限）
2. **一张"被否掉的方向"清单**（P1 attention、P11 拒绝采样融合、P13 小算子融合、P14 KV 量化）
   —— **这张清单和优化清单一样值钱**
3. **一批可复用的测量资产**（噪声地板口径、逐字节对拍脚本、同进程探针、一致性恒等式）

# 第二部分 (b)：遇到错误时如何分析

## b.1 八条手法（每条配一个真实实例）

**① 逐轮打点 —— 把"变慢"定位到"变了什么"的最短路径**

> 分块 prefill 第一版做完，`CHUNK=2048` 时尖刺**反而变大 3 倍**（642 → 2039 ms）。
> 第一版判断（★ 错的）：怀疑是 torch.compile 对新 chunk 形状付一次编译钱 —— 改了预热，**没修好**。
> 加了逐轮打点之后，一行输出就定案：`round 0: step_tokens=14336` = **同一个 chunk 被拼了 7 遍**
> （7×2048=14336，与打点逐字吻合）。根因是**我自己引入的** `budget = min(remaining, chunk)`
> 让循环得以继续，而那条序列本步拼不完、没被 `popleft()`，`while` 又取到同一条、再 append 一份。
> **修法：分块分支 append 后立刻 `break`。**

**② 同进程多条件探针 —— 把"跨进程对比的噪声"变成"闭合归因"**

> 验收表里 `U`（本该是 target-only 的零点）的 TTFT 在组与组之间差 **2.4 倍**（78.7 / 161.2 / 186.0 ms），
> 而噪声地板只有 0.12–0.5%。同一个进程内跑三个条件（① 有 draft ② 摘掉 draft ③ 有 draft 但窗口压回 0）：
> 77.8 / 45.7 / 77.5 ms ⇒ 归因**闭合**：`run()` 里 `if self.draft_model is not None` **不看 `spec_k`**，
> 只要进程加载了 draft，prefill 就白跑一遍 0.6B。

**③ 先排除最容易想到的解释**

> 上面那个 2.4 倍，第一反应是"4 卡并行争用"。**先把它做掉**：同配置并行 vs 串行 TTFT 差 ≤3.2% ⇒ 排除。
> 然后再找真因。**不先排除，就会在错误的方向上解释半天。**

**④ ★★ 换仪器，而不是加样本**

> 接受率用"自由生成 256 token 后统计"来测，跨批次漂移 **±4~13%**（0.7814 vs 0.6911），噪声压过效应。
> 于是写了一个"离线固定上下文重建"的确定性仪器 —— 它在 `w0` 上很准，但在 `P=0` 上**偏乐观 0.25**。
> 根因：**离线重建等价于"窗口永不滑动"这个理想极限**，它测的是另一个系统。
> **教训：换仪器必须换成"测同一个量的仪器"；判据是先在"已知答案"的格子上对一次**
> （本轮用的是"窗口盖住全序列 ⇒ 必须与全上下文一致"那格自检）。

**⑤ ★★★ 效应反号 = 判决性证据（本次最漂亮的一次判据）**

> 我们给滑窗加了一个"开头 P 块常驻"的设计，测到它把接受率从 0.404 救到 0.704（**+71%**）。
> 但后来发现滑窗的滑动路径有个 KV 对齐 bug。把它修掉之后重测：

```
              P=0      P=2      Δ(P2−P0)      显著性
ALIGN=0     0.3720   0.6517     +0.2797      23.6σ     ← P 看起来极其有效
ALIGN=1     0.6414   0.6226     −0.0188       3.0σ     ← 修完之后 P【更差】
```

> **效应反号（+0.28 ↔ −0.019）直接证明：P 的全部正收益 = 遮掩对齐 bug。** 结论：**P 从设计里砍掉**。
> **这条比任何统计检验都硬 —— "一个机制在修掉别的 bug 后失效了"，说明它从来就不是那个机制。**

**⑥ 对照的对照 —— 先把"是不是我改坏了"证伪**

> 一次"逐字节对拍不一致"出现后，没有立刻去改代码，而是**同一棵树重复跑 3 遍**：
> 它自己就产出两个不同的 md5 ⇒ 那是**环境噪声**，不是我们的改动。
> **在"我改坏了"和"这个东西本来就不确定"之间，先花 5 分钟把后者确认掉。**

**⑦ 承重性反证 —— 证明"这道守卫不可省"**

> 前缀缓存修复里加了一道"draft 块级有效性"守卫。为了证明它真的在挡东西，
> **故意绕过它直读脏 KV**：接受率从 0.9 **崩到 0.175–0.470**、argmax 一致率 0.333。
> 这比"我加了守卫"有力得多 —— 它给出了**守卫的承重证据**。

**⑧ 噪声地板 + 配对/交替 —— 让每个数字都自带"分辨力"**

> 每个判据都配地板（同配置跑两遍，用分歧当地板）。实测地板：`ms/轮` **0.05%–1.38%**，
> 但 B=4 的合成素材上**高达 43–61%** ⇒ 那一档直接写"**分辨不出**"，而不是硬报一个数。

## b.2 ★ 本项目最贵的三类坑

| 坑 | 表现 | 代价 |
|---|---|---|
| **静默 bug**（不报错、只静默出错）| prompt ≥384 token 直接崩；半满块被当满块登记；全接受时 draft 有位永不回头补；KV 对齐漂一格 | 最重的一个让**此前所有长上下文结论作废** |
| **假仪器** | 离线重建 = "窗口永不滑动"的理想极限；自写脚本打点位置不对 | 让我们相信了一个 +71% 的**不存在**的机制 |
| **口径混用** | 有的 B=1 有的 B=4；有的 device time 有的墙钟；接受率 0.84 / 0.99 | **招牌数字"B=4 提速 1.19×"在自然长文下其实是 0.71×** |

## b.3 一张"错误分析"决策树（可直接背）

```
出现异常
 ├─ 先问：这是【噪声】还是【真信号】？ → 跑同配置两遍，看分歧（噪声地板）
 ├─ 再问：是【我改坏的】还是【本来就不确定】？ → 同一棵树重复跑 N 遍
 ├─ 再问：是【算法】还是【开销】？ → 只翻 enforce_eager 一个开关对拍
 ├─ 再问：是【难想到的解释】还是【最容易想到的解释】？ → 先把最容易的做掉
 └─ 定位不到 → 上【逐轮打点】/【同进程多条件探针】/【机制级判据】，
              不要靠推理；并且【换仪器时要先在已知答案的格子上自检】
```

# 第三部分 (c)：具体是如何优化的

## c.1 正确性修复（价值在"发现了什么"，不在"快了多少"）

| 修什么 | 修复前的后果 | 证据 |
|---|---|---|
| 前缀缓存哈希契约（`hash_blocks()` 入参契约改为显式 `num_new_tokens`）| **prompt ≥384 或恰好 256 token 直接崩**；128–383 把半满块当满块登记（静默污染）；**从未登记过合法的 block 0**（缓存实际失效）| 边界表 255/256/257/383/384/385/1024/2048/4096/8192 全通 |
| 吞吐计数 | 用 `1+last_accepted` 计数，与实际交付 token 数不符 | 新口径严格等于 `len(output_tokens)` |
| 温度广播 | `_softmax_with_temp` 把长度 B 的温度塞进 vocab 维 | B=1 字节等价，为批量铺路 |
| 门控快照 | `spec_enabled()` 读会随 `popleft()` 变短的队列 → 同轮内决定不一致 | 一轮内混了两种执行路径 |
| 投机候选错位（Bug B）| 候选 j 被拿去和 target 第 j+1 行比 | 接受率被从应有的 0.84 打到 **0.16** |
| draft 侧传概率被二次 softmax（Bug A）| 151936 词表上被压成近似均匀分布 | 构造 `q≡p` 时正确实现必须全接受：实测 1.0000 vs 原实现 0.8895 |
| 全接受时丢掉 bonus（Bug C）| 每步恒定只出 1 个 token ⇒ 必然比 baseline 慢 | — |
| 终止判据 `==` 改 `>=`（Bug D）| 完成数跳过 `max_tokens` ⇒ 序列无限生成（64 跑到 572 token 还没停）| — |
| 跨 block 少分配一块（Bug E）| 位置正好是块整数倍时少分一块 ⇒ **CUDA 非法访存** | eager 静默读垃圾，拍图则崩 |
| 滑窗 KV 对齐（最新）| 窗口起点漂移 ⇒ 环里保留的块仍编码着"已被声明丢掉"的上下文 | 机制级 `TV(q_eng,q_ideal)` **0.685 → 0.016** |
| `spec_k` 0→正数时的水位（最新）| watermark **无条件推水位 = 盖了个没写过的章** ⇒ 拿未初始化 draft KV 提候选 | 每轮只交付 **1.21** 个 token（健康值 2.77）|

| 优化 | 效果 | 代价 |
|---|---|---|

## c.5 量化（draft INT8，target 一字节不动）

| | |
|---|---|
| 做了什么 | 对称 per-channel W8A16（融合反量化 GEMM），**不需要校准**（文献证实 8 位下换方法无差异 ±0.005）|
| 效果 | 每轮 **−6.4~7.1%**（B=1 四档 36/36 配对全胜，符号检验 p≈1.5e-11）；端到端 **+6.9~7.8%** |
| 精度 | **+0.455% PPL**；接受率**不变**（Δα = −0.00235 ± 0.00349，在 12282 个位置上用恒等式算）|
| ★ 口径 | **一个字都不用改** —— target 没动 ⇒「相对 BF16 target 无损」严格成立 |
| ★ 核心叙事 | **量化 draft 让投机的相对优势变大**（1.411× → 1.601×），与"量化 target"正好相反 |

## c.6 ★ 当前最终推荐配置

**滑窗侧**（三个都要显式开；只开 `align` 会在二次漂移上崩）：

```
spec_draft_window = 1280            # M = 5 块
spec_draft_head_blocks = 0          # ★ P 一律取 0（P 的收益已被证明是遮掩 bug）
spec_draft_win_align = True         # 必须显式开
spec_draft_win_realign = True       # 必须显式开
```

**调度侧**（★ 关键：**默认是 0 = 老行为 = prefill 独占、会把解码全堵死**）：

```
spec_prefill_chunk_tokens = 1024    # 推荐值；0（默认）= 你会在默认配置上看到的"长 prefill 阻塞"
```

实测：一个 16K 的 prefill 到达时，解码请求的 ITL 尖刺
**未分块 310.4×（≈ 阻塞 3.8 秒）→ C=1024 时 24.4×（≈ 296 ms）→ C=256 时 82 ms**；
8K 的 prefill 未分块时是 **120.8×（≈ 1.5 秒）**。
★ **代价与边界**：prefill 墙钟 +11.5%（C=1024）；**C≤512 有 p50 反向代价**（中位 ITL 12.2 → 60~76 ms），
所以不要一昧往下压；**"无人可让路时"（running 为空）不切块 ⇒ 那种情况下 +0% 代价**。

| 项 | 滑窗（新推荐） | 普通投机 |
|---|---:|---:|
| draft 池 | **20 块 / 0.55 GB** | 173 块 / 4.73 GB |
| target 池 | **293 块（+69%）** | 173 块 |
| 并发 @8K / @16K | **8 / 4 条** | 5 / **2 条** |
| α @8K / @16K | 0.6414 / 0.6165 | 0.6688 / 0.6559 |
| TTFT @8K/B=1 | **91.41 ms（+0.3）** | 91.13 ms |

**边界**：≤8K 直接用（α −4.1%）；16K 直接用（α −6.0%、并发 2→4）；对 α 敏感用 M=12（−4.3%，TTFT +42 ms）。
**★ 不是无损** —— 仍有 4%–6% 的**真截断代价**（这是修完 bug 之后才看清的数）。

# 第四部分 (d)：如何选择优化路径

## d.1 六条判据（每条都配一个"被否掉"的真实实例）

**判据一：上界够不够？不够就收手。**
> P1 自写 attention 接进引擎：f=8–9% ⇒ Amdahl 上界 +10%、代入实测 **+3%** ⇒ 达不到门槛 ⇒ **降级**。
> 真混合调度：上界 = 一个解码轮 = **12.1 ms**（占实测尾部 3.2%–10.0%）⇒ **不做**。

**判据二：边际收益是不是掉进噪声了？是就转去做整理。**
> `S5→S6`（直载 int8）速度 = **1.000–1.004×**，落在噪声地板内 ⇒ 据此判断
> "**新技术的边际收益已经低于把已有成果合成一组可复算数字**" ⇒ 把资源转向端到端统一验收。

**判据三：事先定好的停止条件，事后必须遵守。**
> "若长 prompt 的 ITL 尖刺只有 2–3 倍就收手"。**实测 10.7×→310×**，远超停止线 ⇒ 立项。
> （当年 P1 是在这条线上被否的，这次是同一条线放行的 —— **同一条判据，两个相反的结论**。）

**判据四：风险 vs 收益 —— 别把已知雷区搬进核心路径。**
> 真混合会让"一轮内同时跑 decode 和 prefill 两条路径"成为**常态**，而这个项目已经被
> "一轮内混两条路径"坑过 3 次（`spec_enabled` 门控快照 bug，有回归测试）。
> 10% 的尾部改善换不来这个风险 ⇒ 不做。
> **替代方案**：让路式分块（**一轮内仍只有一种执行路径**）—— 风险低得多，拿到 310× → 16.9×。

**判据五：★ 先修"确定的浪费"，再赌"重排"。**
> 我们测到 prefill 里有 **20%–26%（冷启动）** 是 draft prefill 的浪费，而"ITL 尖刺的高度 = prefill 的时长"。
> ⇒ **先修浪费，尖刺数字会跟着变小**；顺序反过来的话，你会**为一个被浪费撑大的数字去写一套复杂调度**。
> （实测：修掉之后 4K 下的尖刺会从 ~3.4× 降到 ~2.4× —— 更不值得做混合调度了。）

**判据六：★★ 结论必须在 bug 修完之后重新核一遍。**
> "推荐配置 (P=2, M=5)" 定了之后才发现滑窗有 KV 对齐 bug。修完重测，**P 的效应反号**
> ⇒ 推荐配置改回 `(P=0, M=5)`。**一个 bug 可以伪装成"机制收益"，而且会被写进推荐配置。**

## d.2 一张排序表（我们实际的排序依据）

```
优先级 ≈ (收益上界 × 确定性) ÷ (实现成本 × 风险)
```

| 进入排序的方向 | 上界 | 确定性 | 成本 | 结论 |
|---|---|---|---|---|
| CUDA Graph 覆盖 | 大（固定开销支配 batch=1）| 高（开关一翻就对拍出来）| 低 | **先做**（事后看是最大的一刀 2.4–3.6×）|
| 修静默 bug | 大（有些直接让结论作废）| 高 | 低 | **先做** |
| 批量投机（P6）| 中（B>1 从净亏翻正）| 高 | 中 | 做 |
| 量化 draft | 中（−6~7%）| 高（纯字节账）| 中 | 做 |
| 混合调度 | **中（12.1 ms 封顶）** | 高（先测了上界）| **中高** | ★ **只做低风险的让路式** |
| 真混合 | 小（10% 尾部）| 高 | 高 + 高风险 | **不做** |
| P1 attention 接入 | **+3%** | 高 | 4–7 人天 | **不做** |
| P11/P13/P14 小算子融合等 | ~3–8% | 高 | 中 | **不做** |
| 量化 target | 会**削弱**投机的相对优势 | 高 | 中 | **不做**（用户决策）|

## d.3 ★ 五次"主动不做"的决策（和做了什么一样值钱）

1. **不做 P1**（attention 接入）：上界 +3%
2. **不做真混合调度**：上界 12.1 ms = 3.2–10% 的尾部，代价是把已知雷区搬进核心路径
3. **不做 P11（拒绝采样融合）**：采样只占 **0.81%**
4. **不做 P14（KV 量化）**：我们**没有 KV 带宽瓶颈，只有容量问题**（面经直接题 0 道）
5. **不做 target 量化**：会让普通解码也变快 ⇒ **削弱投机的相对优势**（实测 1.601× → 1.411×）

## d.4 教训清单（都是花代价换来的）

| 教训 | 代价 |
|---|---|
| **"为了测 A 而改的配置，会污染 A 自己的结论"** | 为了给一个**最后没被采用**的对照留块号空间，把 `max_num_seqs` 撑到 12 ⇒ 白占 4 GB ⇒ **把滑窗判成了负的** |
| **"一个 bug 可以伪装成一个机制"** | P 轴的 +71% 全是对齐 bug 的补偿，还写进了推荐配置 |
| **百分比比绝对值更容易骗人** | 同一个 31.5 ms，分母是"整条 4K prompt"时是 6%，分母是"未命中的尾巴"时是 70% |

## 附：这套流程的可迁移版本（一段话）

> 先测清楚瓶颈在哪（profiler + 微基准 + Amdahl 上界），**上界不够就当场收手**；
> 每个判据都配噪声地板，主结果配对/交替、报中位数 + 范围；
> 异常出现时先分清"噪声 / 我改坏了 / 真信号"，定位不到就上逐轮打点与同进程探针；
> 换了仪器先在**已知答案**的格子上自检；
> 结论必须在**相关 bug 修完之后**重新核一遍；
> 一句话总结**永远连边界一起写**，并且**敢报负结论**。
