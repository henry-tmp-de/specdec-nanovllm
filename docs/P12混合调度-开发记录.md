## 0. 摘要（先看这六条）

1. ★ **真混合：不做。** 上界被量死了 —— 让路式分块后，解码请求的 ITL 尖刺
   = `一个 chunk 的 prefill 墙钟 + 一个解码轮`；真混合最多把**后面那一项**（12.1 ms）
   从尖刺里去掉。实测尖刺 173.8 ms（C=512）里，这一项只占 10.3%（C=256 只占 4.3%）。
   而"压尖刺"这件事 chunk 大小一个旋钮就能做。论证见 §2。
2. ★ **分块档不是逐字节无损**（这是任务书点名要补的）：只要真的拆过，prefill 的
   last-token logits **一定**不同；但差异是 **bf16 的 1~2 个 ULP**（max|Δ| 0.125~0.34），
   且 `L == chunk`（没真的拆）时**逐位相同**。机制用微基准钉死：flashattn 的
   **paged varlen 核**（第 2 块起走这条）与**本地 varlen 核**本身差 ~1 ULP。见 §3。
3. ★ **判"无损"的仪器要换**：本轮实测发现 **解码路径本身跨进程不可复现**
   （同配置跑两遍，解码 logits 最大差 20~29；而 prefill 4/4 逐位相同）。
   所以只有 **prefill 的 logits** 能当判据，token 序列不能。见 §3.1。
4. ★ **chunk 选择规则**给了可复现的三步法（标定一个点 → 线性外推 → 对齐块大小）
   并验证（四条目标值上偏差 ≤6.5%）。★ 同时发现**小 chunk 会把 p50 也抬起来**
   （C≤512 时中位数 60~76 ms，C≥1024 回到稳态 12.2 ms）—— KPI 含 p50 时规则要选 C≥1024。见 §4。
5. **顺手修掉一个真 bug**：P13 的"跳过 draft prefill"会**盖一个没写过的章**
   （`advance_draft_watermark` 无条件推进水位）⇒ 运行期把 `spec_k` 从 0 翻回正数后，
   proposer 拿未初始化的 draft KV 提候选，每轮交付 2.77 → **1.21** 个 token（比不投机还慢）。
   修后回到 **2.46**（健康值 2.47）。另把 `spec_batch_threshold` 的"打架"也修了
   （白跑的 draft prefill 16384 → 0）。见 §5。
6. **验证**：CPU 测试 **355 PASS / 0 FAIL** (基线 336 + 新增 19)；
   默认路径与基线树**逐字节等价**（`core_w0` / `core_w0_b4` / `win4608` 三组 md5 全同）；
   两张模型指纹开工/收工各查一次，**逐行未变**。

## 2. ★ 判断题：真混合做不做 —— 用算术回答，不凭感觉

### 2.1 先把"让路式还剩多少"量成绝对毫秒

让路式的尖刺结构（`p12_sched_probe.py`，ctx=16384，3 条解码，3 遍取中位数）：

```
round 序列：  [decode 轮: 解码请求拿到 1 个 token] → [prefill 块轮: 解码请求拿到 0 个 token] → [decode 轮] → ...
⇒ 解码请求的 ITL 尖刺 = 一个 prefill 块轮  +  一个 decode 轮
```

实测逐格验证（`prefill_max_ms` = 一个块轮的墙钟，`steady_round_ms` = 稳态解码轮）：

| C | prefill 块轮 | 稳态解码轮 | 两者之和 | 实测 itl_max | itl_max ÷ steady |
|---|---:|---:|---:|---:|---:|
| 256 | 78.9 | 12.14 | 91.0 | **82.3** | 6.8× |
| 512 | 153.6 | 12.14 | 165.7 | **170.7** | 14.1× |
| 1024 | 279.3 | 12.14 | 291.4 | **296.5** | 24.4× |
| 2048 | 517.7 | 12.16 | 529.9 | **535.0** | 44.0× |
| 不分块 | 2877.9 | 12.13 | 2890 | **2895.6** | 238.4× |

（差 `itl_max − prefill块轮` = 3.4 / 17.1 / 17.2 / 17.3 / 17.7 ms，即恒等于一个解码轮到
一个解码轮零头。）

### 2.2 真混合最多还能削掉多少

真混合 = 一轮内同时跑 decode 子批与 prefill 子批 ⇒ 解码请求**每一轮**都拿到 token ⇒
ITL = 混合轮的墙钟。混合轮里 prefill 那一份工作跑不掉（除非给 prefill 更小的预算，
那就等价于用更小的 C —— 见 2.3），所以：

```
混合轮墙钟 = T_pre(C) + δ          δ = 把 decode 子批塞进 prefill 轮的边际代价，0 ≤ δ ≤ T_dec
⇒ 相对让路式的绝对节省 = T_dec − δ ≤ T_dec = 12.1 ms     ← 【上界是硬的】
```

| C | 让路式 itl_max | 真混合的下界（δ=0） | 绝对节省上界 | 占尾部 |
|---|---:|---:|---:|---:|
| 256 | 82.3 | 78.9 | **3.4 ms** | **4.1%** |
| 512 | 170.7 | 153.6 | **17.1 ms** | **10.0%** |
| 1024 | 296.5 | 279.3 | 17.2 ms | 5.8% |
| 2048 | 535.0 | 517.7 | 17.3 ms | 3.2% |

★ **上界 = 一个解码轮 = 12.1 ms**，且这只是 δ=0 的乐观界；真实 δ > 0
（混合批丢了精确形状的 CUDA 图、退化成逐 kernel eager 发射），节省只会更小。

### 2.3 而且"压尖刺"本来就是一个旋钮，不是"能不能做到"

让路式已经能用 chunk 大小把尖刺压到任意值。真混合不能把这个曲线整体下移超过
12.1 ms，它只是"同一个 T* 可以用更大的 C 达到"，而更大的 C 对吞吐更友好 ——
**这是一次小幅的 Pareto 平移，不是开/关**：

| 目标 T* | 规则给的 C | 实测 itl_max | prefill 吞吐代价 |
|---|---:|---:|---:|
| 50 ms | 128 | 51.3 | **+70.4%** |
| 100 ms | 256 | 82.3 | +24.5% |
| 200 ms | 512 | 170.7 | +20.3% |
| 400 ms | 1024 | 296.5 | **+11.5%** |

### 2.4 代价清单

| 代价 | 分量 |
|---|---|
| ① 一轮内混两条执行路径 | ★★ 本项目**踩过 3 次**。最典型是 `spec_enabled` 门控快照 bug：decode 分支逐条 `popleft()`，同一轮里靠后的请求按变短的队列长度重新判定，一轮内混着"开投机/关投机"两种路径，后处理形状与 KV 预算全对不上（复现见 `tests/test_spec_gate.py`，已加护栏）。真混合等于**主动**把两条路径塞进一轮。 |
| ② decode 预算被分走 | 混合轮的形状不固定 ⇒ ③ |
| ③ CUDA Graph 命中率下降 | decode 图按**精确 B** 捕获（`spec_graph_bs=(1,2,4)`）。decode 是**带宽 bound**（3 token / 12.1 ms ≈ 660 GB/s ≈ 峰值 82%），prefill 是**算力 bound**（65/71 TFLOPS）—— 资源不同、理论上可重叠，但混合批的 kernel 形状逐轮不同，图退化成 eager，launch 开销按轮数放大。 |
| ④ 工作量 | scheduler 维护两个子批的 KV 槽位/预算、`prepare_mixed`、`postprocess` 的交付语义、图捕获重做。 |

### 2.5 结论

**不做。** 理由三条，按分量排序：

1. **上界太小且是硬上界**：≤ 12.1 ms 绝对，占实测尾部 3.2%~10.0%。
2. **不是"能不能做到"的开关**：尖刺由 chunk 大小这一个旋钮控制，真混合只是小幅 Pareto 平移。
3. **把已知雷区搬进核心路径**：① 是本项目唯一被证明过 3 次的失效模式；
   收益 10% 的尾部改善换不来这个风险。

★ 这与 P1（自写 attention kernel）当年被否是同一套做法：**先量上界，上界不够就明确写"不做"，并留下数据。**

## 3. ★ 分块的分布级无损性

### 3.0 为什么会不一样（代码事实）

`prepare_prefill` 里：

```python
if cu_seqlens_k[-1] > cu_seqlens_q[-1]:    # prefix cache
    block_tables = self.prepare_block_tables(seqs)
```

- **不分块**：`start=0` ⇒ `seqlen_k == seqlen_q` ⇒ `block_tables is None`
  ⇒ `flash_attn_varlen_func` 走**本地** k/v 的因果路径。
- **分块**：第 1 块 `start=0` 同上；**第 2 块起 `start>0`** ⇒ `seqlen_k > seqlen_q`
  ⇒ 置 `block_tables` ⇒ 走 **paged** varlen 路径（从 KV cache 里读 K/V）。

两条核的浮点归约顺序不同 ⇒ 预期 ULP 级差异。**探针就是去量它有多大。**

### 3.1 ★ 先换仪器：解码路径跨进程不可复现

第一版把"生成的 token 序列"当判据，结果出现自相矛盾的现象（prefill 的 argmax 相同、
第一个 token 却不同）。**加了一个"同配置跑两遍"的对照**，真相出来了：

| 对比 | prefill last-token logits 逐位相同 | 解码 logits 最大差 | 解码 argmax 翻转 |
|---|---|---|---|
| **同配置、同代码、两个进程** | **4/4** | 20.2 / 29.0 | 22 / 60 步 |
| 分块 vs 不分块 | 0/16 | — | — |

⇒ **解码路径本身跨进程不可复现**（与 `优化过程复盘[16]` 记的"同一棵树跑三遍 `out_md5` 都不同"同源）。
**结论：判"分块是否无损"只能用 prefill 的 logits**；token 序列/解码 logits 都被这个抖动污染，
不能当证据。这条是任务书没提、但不定下来整张表就不能下结论的前提。

### 3.2 结果（判据 = prefill 的 last-token logits，float32 逐字节）

| 对比 | 样本 | 逐位相同 | max\|Δ\| | argmax 翻转 | 最小 top1−top2 间距 |
|---|---|---:|---:|---:|---:|
| **同配置跑两遍**（噪声地板） | 4 | **4/4** | **0** | 0/4 | 6.0 |
| **分块 C=256 vs 不分块** | 8 | **0/8** | 0.125 ~ 0.336 | **0/8** | 1.125 |
| **分块 C=512 vs 不分块** | 8 | **0/8** | 0.141 ~ 0.266 | **0/8** | 0.625 |
| **对照：`L ≤ chunk`（没真的拆）** | 2 | **2/2** | **0** | 0/2 | 6.0 |

`L` 取值：512 / 1024 / 1500 / 3000 / 4096 / 5000 / 9216 / 12345（含多个与 chunk、与块大小不对齐的值）。

三条结论：

1. **分块档不是逐字节无损。** 只要真的拆过（≥2 块），prefill 的 logits 一定不同。
   `L=512 & C=512`、`L=1024 & C=1024` 这两格**逐位相同** —— 这证明差异来自
   **"真的拆开了"**，不是"翻了个开关"。（这两格是本轮最值钱的对照。）
2. **差异是 bf16 的 1~2 个 ULP 级**：max|Δ| 0.125~0.34，对应 logits 量级（10~50）
   的 1~2 个 ULP；且**不随 chunk 数增长**（L=512 两块 max|Δ|=0.25；L=12345 四十九块 max|Δ|=0.188）。
3. **argmax（=贪婪会吐的 token）在 16/16 个 prefill 步上全部一致**，
   8 条 prompt 的 prefill 最小间距 0.625，全部大于 max|Δ|。

### 3.3 机制（微基准直接钉）

`flash_attn 2.8.3.post1`，L=1024、随机 bf16 张量、同一份 K/V：

```
本地核  vs  把 K/V 放进 paged 缓存 + block_table（cu_seqlens_k == cu_seqlens_q）
⇒ attention 输出 max|Δ| = 0.0039（输出量级 ~1 ⇒ ≈1 个 ULP），逐位不同
```

attention 输出的 1 ULP 经 28 层放大到 logits 的 1~2 ULP，与 §3.2 实测吻合。
⇒ **机制 = "paged varlen 核 vs 本地 varlen 核"，不是分块引入的其他副作用。**

（诚实挂账：我另外试过一个"把不分块的 prefill 也强制成 paged"的对照，结果
注意力明显算错（输出退化成重复 token，max|Δ| 16~38）。这说明 `block_tables` 在
`cu_seqlens_k == cu_seqlens_q` 时不能这么用 —— 但**不能**用它来反推机制，
它本身是个非法配置。见 §8。）

### 3.4 交付前必须写进口径的一句话

> **分块档的无损性是"到 bf16 ULP 为止"，不是逐字节。**
> 需要逐字节复现的场景（与 BF16 基线的 `out_md5` 对拍）**必须关掉分块**
> （`spec_prefill_chunk_tokens=0`，也正是默认值）。

## 4. chunk 选择规则（可复现）+ 验证

### 4.1 代价函数 T_pre(C)（无解码请求，ctx=16384，2 遍取中位数）

| C | prefill 总墙钟 ms | tok/s | 相对不分块 | 每块墙钟 ms | 每 token ms |
|---|---:|---:|---:|---:|---:|
| 0（不分块） | 2880.5 | 5688 | — | 2880 | 0.176 |
| 128 | 4908.1 | 3338 | **+70.4%** | 38.6 | 0.299 |
| 256 | 3587.3 | 4567 | +24.5% | 56.6 | 0.219 |
| 512 | 3463.8 | 4730 | +20.3% | 108.2 | 0.211 |
| 1024 | 3210.2 | 5104 | +11.5% | 200.6 | 0.196 |
| 2048 | 3018.5 | 5428 | +4.8% | 377.3 | 0.184 |
| 4096 | 3003.8 | 5455 | **+4.3%** | 750.9 | 0.183 |

噪声地板：同条件两遍的极差 ≤ 0.5%（±0.2% 量级）。
⇒ **C ≥ 2048 时代价几乎免费；C ≤ 512 开始显著；C=128 代价翻倍。**

### 4.2 规则（三步，可复现）

```
① 标定一个点：在目标 ctx 上跑一次 C0 的分块 prefill，取逐轮打点里
   prefill 轮的【最大墙钟】 T_pre(C0)（= p12_sched_probe 的 prefill_max_ms）。
② 线性外推：C ≥ 256 时 T_pre(C) ≈ 每 token 边际成本随 C 缓降，
   用 T_pre(C) ≈ T_pre(C0) / C0 × C 外推（±15% 足够选档）。
③ 按目标 ITL 上限 T* 反推：
       C* = C0 × (T* − T_dec) / T_pre(C0)        T_dec = 稳态解码轮（≈12.1 ms）
   向下取到 kvcache_block_size（256）的整数倍。
```

**验证**（B=4，ctx=16384，3 遍中位数）：

| 目标 T* | 规则给的 C | 预测区间 | 实测 itl_max | 偏差 |
|---:|---:|---|---:|---:|
| 50 | 128 | ~50 | 51.3 | +2.6% |
| 100 | 256 | ~88 | 82.3 | −6.5% |
| 200 | 512 | ~172 | 170.7 | −0.8% |
| 400 | 1024 | ~296 | 296.5 | +0.2% |
| 800 | 2048 | ~530 | 535.0 | +0.9% |

### 4.3 ★ 规则的两条硬边界

**(a) 没有解码请求可让路时不要分块**（本轮新增门控，见 §5 改动清单）。
让路这一步本来就门控在 `bool(self.running)` 上 —— running 空时分块**只有代价、没有收益**。
实测（无解码请求、ctx=16384）：

| C | 门控前 prefill 墙钟 | 门控后 prefill 墙钟 | 门控后 prefill 轮数 |
|---:|---:|---:|---:|
| 0 | 2880.5 | 2868.0 | 1 |
| 256 | 3587.3 (+24.5%) | 2870.2 (**+0.1%**) | 1 |
| 512 | 3463.8 (+20.3%) | 2881.2 (**+0.4%**) | 1 |
| 1024 | 3210.2 (+11.5%) | — | 1 |

⇒ **门控把"没人可让路"这一档的代价清零。**

**(b) `T*` 已经大于不分块的 prefill 总墙钟时不要分块** —— 分块只是把一次长阻塞摊成多次。

### 4.4 ★★ p50 的反向代价（本轮新发现，KPI 含 p50 时必须看）

小 chunk 压的是**最大值**，但会把**中位数**也抬起来。实测（B=4，ctx=16384，
长 prompt 期间 3~4 条解码请求**全部** ITL 的 p50）：

| C | itl_p50 | itl_max | 说明 |
|---:|---:|---:|---|
| 0 | 12.17 | 2895.6 | 一次长阻塞 |
| 128 | 49.2 | 51.3 | 整个 prefill 期间每轮都被拖 |
| 256 | 60.6 | 82.3 | 同上 |
| 512 | 75.4 | 170.7 | 同上 |
| 1024 | **12.21** | 296.5 | p50 回到稳态 |
| 2048 | **12.21** | 535.0 | 同上 |

（p50 = 长 prompt 的 prefill 时长相对解码请求剩余寿命的占比决定：prefill 越"细长"，
落在 prefill 窗口内的 ITL 样本越多，p50 就越等于"窗口内 ITL"。）

⇒ ★ **KPI 里 p50 算数的话，规则应额外加一条 `C ≥ 1024`**（否则换来的是
"最大值变小、中位数从 12 ms 涨到 60~76 ms"）。

### 4.5 推荐

| 场景 | 建议 C | 代价 | 拿到什么 |
|---|---:|---|---|
| 只要 p99/max、不管 p50 | 256 | +24.5% prefill | 尖刺 238× → **6.8×** |
| **默认推荐** | **1024** | **+11.5%** | 尖刺 → **24.4×**，p50 保持稳态 |
| 长 prompt 很少、想省到底 | 2048 | +4.8% | 尖刺 → 44× |

## 5. 吞吐 / B=4 / 与投机联动

### 5.1 B=4 并发下的尖刺

同场景把解码请求从 3 条加到 4 条（各 3 遍中位数）：

| C | B=3 itl_max | B=4 itl_max | 差 | B=3 p50 | B=4 p50 | B=3 TTFT | B=4 TTFT |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 0 | 2961.3 | 2895.6 | −2.2% | 12.22 | 12.17 | 2942.9 | 2877.7 |
| 256 | 83.7 | 82.3 | −1.7% | 60.6 | 59.4 | 4288.5 | 4224.1 |
| 512 | 173.8 | 170.7 | −1.8% | 76.4 | 75.4 | 3905.1 | 3842.9 |
| 1024 | 301.0 | 296.5 | −1.5% | 12.21 | 12.18 | 3455.4 | 3399.5 |
| 2048 | 542.2 | 535.0 | −1.3% | 12.23 | 12.17 | 3165.9 | 3118.3 |

⇒ ★ **尖刺与解码批大小基本无关**（差异 ≤3%，且方向是 B 越大略快）。
原因：尖刺 = 一个 prefill 块轮 + 一个解码轮，解码轮从 B=3 到 B=4 只从 12.14 → 12.14 ms
（decode 是带宽 bound，B=3/4 都要把权重读一遍）。**这条把"B=4 会不会更糟"的担心直接否掉了。**

### 5.2 与投机路径的两条交互（都发现真问题）

**(1) `spec_batch_threshold` 与"跳过 draft prefill"打架** —— P13 挂账的那条。

场景：`spec_k=6`、`spec_batch_threshold=2`、3 条解码请求。prefill 时刻
`_draft_prefill_needed()` 只看 `spec_k>0` ⇒ 照跑；而"这一刻的解码批"已经是 3 > 2
⇒ 下一步解码**一定**关投机。实测（`p12_spec_probe.py TEST=threshold`）：

| 配置 | 此刻解码批 | 下一步开投机？ | 白跑的 draft prefill token 数 |
|---|---:|---|---:|
| 开关关（老行为） | 3 | 否 | **16384** |
| 开关开（P13 版） | 3 | 否 | **16384** ← 开关帮不上忙 |
| 开关开（本轮修后） | 3 | 否 | **0** ✅ |
| 开关开、阈值 5 | 3 | 是 | 16564（正确：不跳） |

**修法**（不猜未来、只用现在）：`Scheduler` 每轮把"此刻已经在解码的批大小"写进
`config._sched_running_decode_b`；`_draft_prefill_needed()` 里若它已经 > 阈值就返回 False。
边界（诚实）：抢占可能让解码批临时缩回阈值以内 —— 那只是"少跳过一趟"，
draft KV 由 proposer 正常 catchup 补齐（见下一条的修），不会出错。

**(2) ★★ 运行期把 `spec_k` 从 0 翻回正数：draft KV 的补齐路径「不」通（真 bug）**

P13 的跳过开关让 draft 前向不跑，但 `prepare_prefill` 里的 `advance_draft_watermark(start, end)`
**无条件**把 draft KV 的"有效水位"推到 chunk 末尾 —— 相当于**盖了一个没写过的章**。
之后把 `spec_k` 翻回 6，proposer 相信水位、不做补齐，拿**未初始化**的 draft KV 提候选。

指标：每个解码轮**实际交付**几个 token（`llm.step()` 的返回；k=6 且草稿健康时 >1）：

| 配置 | 翻回前的 draft 水位 | 翻转时缺口 | 全部解码轮平均 | 翻转后平均 |
|---|---:|---:|---:|---:|
| A 对照：开关关、spec 从头开（draft prefill 跑了） | 8192 | 0 | **2.765** | 2.765 |
| B 修前：开关开、第 16 轮翻回 | 8192（假的） | 15 | 1.205 | **1.333** |
| C 修前：开关开、第 32 轮翻回 | 8192（假的） | 31 | 1.068 | **1.143** |
| B 修后：同上 | **0**（不盖章） | 8207 | 1.679 | **2.462** ✅ |
| C 修后：同上 | **0** | 8223 | 1.432 | **2.462** ✅ |

⇒ 修前：翻转后每轮只交付 1.07~1.33 个 token —— **投机等于没开，而 verify 前向照付，
比不投机还慢**。修后回到 **2.462 ≈ 健康值 2.765 的 89%**（差的是补齐那一趟的一次性成本），
且 89% 的分母含"没落地的候选"，按接受率口径已恢复。

**修法**：`prepare_prefill(seqs, advance_draft=True)` 加一个默认 True 的参数；
`run()` 里先算 `draft_needed = self._draft_prefill_needed()`，跳过时传 False ⇒
**不盖章**，水位留在 0，之后由 proposer 的正常 `catchup` 路径补齐。

**正确性说明**（重要）：这个 bug **不影响输出**。验证用的是 **target** 的 logits，
草稿分布被建模成单点分布（见 `model_runner.run_verify` 的说明），所以
**草稿 KV 对不对只影响接受率、不影响输出的分布**。这条 bug 是"静默性能损失"，
不是"静默错误输出"。

## 8. 没做 / 测不出 / 挂账

1. **真混合没做** —— 这是结论不是挂账，论证在 §2。
2. **`FORCE_PAGED` 那个机制对照失败了**（见 §3.3）：把不分块的 prefill 也强制成 paged
   会让注意力明显算错。**原因没查清**（怀疑 `flash_attn_varlen_func` 在
   `cu_seqlens_k == cu_seqlens_q` 且带 `block_table` 时不是"无前缀 paged"的合法用法）。
   机制结论改由**微基准 + `L≤C` 对照**支撑，两条证据合起来已经足够，但这条悬案如实记录。
3. **分块会多消费 sampler 的 RNG**：中间块不交付 token，但 `run()` 里 sampler 照调
   （实测 `n_sampler_calls = 块数 + 解码轮数`，不分块时是 `1 + 解码轮数`）。
   影响：temperature>0 时，分块档的随机流与不分块档**不同** ⇒ 同一 seed 下采样结果不同。
   **这不是分布级的损失**（同分布、只是抽到不同样本），本轮**没改**（改 `run()` 的
   热路径风险大于收益），如实挂账。
4. **滑窗 + 分块的交互只做了 sanity**（`LENS` 那批都是 `window=0`）。
   滑窗档的 draft prefill 是整窗重算，与分块的叠加没系统测。
5. **长 prompt 的 TTFT 代价只测到"分块让它变长"**（C=128 时 +92%），
   没做"同时有多个长 prompt 时谁先谁后"的公平性实验。
6. **`spec_batch_threshold` 修复的边界**：抢占导致解码批临时缩回阈值以内时，
   投机会重新打开，此时 draft KV 靠 catchup 补 —— 这条路径**没单独压测**。
7. **chunk 规则只在本机（RTX 3090 x1、ctx=16384）标定过**；换 ctx/换卡要重标一次（规则里写了步骤）。
