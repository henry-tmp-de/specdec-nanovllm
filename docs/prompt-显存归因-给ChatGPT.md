## 二、现象与已知事实（先说清楚，别重复查）

### 2.1 显存账是怎么算的

```
KV 池块数 ≈ ( 总显存 × 0.9 − used − peak + current ) / 每块字节

  总显存   = 24 GB（RTX 3090）
  used     = 【驱动级】占用（不是 PyTorch 缓存分配器管的那些）
  peak     = 加载/预热期间的【峰值】分配
  current  = 当前 PyTorch 已分配
```

**关键性质：KV 池是"剩余量"，不是"分配量"。**
所以省下来的权重显存**不会自动变成 KV 池** —— 只要另外三项里任何一项涨了，省下的就被吃掉。
**这是一个零和的账。**

### 2.2 实测数字（两次独立复现）

```
Q1（只量化草稿的 FFN，84 个模块）：
    权重 current  −0.245 GB
    但 used 多出 0.16 GB → KV 池 174 → 171 块（−3）

Q2（量化草稿的全部线性层，196 个模块）：
    权重 current  −0.399 GB（8.683 → 8.284 GB）
    但 used 多出 0.19 GB → KV 池 174 → 170 块（−4）
```

两次都**权重省了、但可用池反而少了**，而且 `used` 的增量**稳定、可复现**。

### 2.3 已经确认并修掉的主因（★ 不要重复查这条）

```
量化路径的 split-K 会把 [SPLIT_K, M, N] 的 fp32 scratch 全量分配
  → 在 warmup 的 prefill 阶段（M 很大）吃掉 200 MB+
  → 把 peak 顶高 【1.285 GB】
  → 直接让 KV 池少了 【11 块】

修法：限制「split-K 只在 M ≤ 64 时使用」
效果：KV 池从 −11 块回到【−3 块】（找回 8 块）
```

**这条已经修了、已验证。你要查的是剩下的部分。**

### 2.4 还没归因的部分

`used` 稳定多出的 **0.16 ~ 0.19 GB**。**两次复现、数值稳定，但来源没找到。**

**存疑的候选（都是猜测，没有被验证过，不要直接当结论）**：

| 候选 | 支持它的理由 | 反驳/存疑 |
|---|---|---|
| **CUDA context 里多了量化 GEMM 的 kernel 模块** | 每个 Triton kernel 编译出的 cubin + 启动元数据都要常驻 context；Triton 常为不同 shape 编多份。**这类占用只出现在 `nvidia-smi` 的 used 里、不出现在 `torch.cuda.memory_allocated()` 里**，正好符合"只在 used 上看得见"的现象 | 量级是否真有 0.16~0.19 GB，没测 |
| 量化路径调了不同的库、预留了更多 workspace | 换了 GEMM 实现就可能换 workspace 需求 | 没测 |
| 载入期的瞬时重叠（bf16 与 int8 权重同时存在）被算进 `peak` | 我们是"载入 bf16 → 在内存里量化 → 留 int8" | **若为真，量级应远大于 0.19 GB**，与实测不符 —— 优先排除 |
| 分配尺寸变化导致落址/碎片变化 | 分配尺寸确实变了 | 没测 |
