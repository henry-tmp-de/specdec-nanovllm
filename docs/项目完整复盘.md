## 1. 一页速览

**一句话**：在 [nano-vllm](https://github.com/GeeeekExplorer/nano-vllm)（1385 行教学版 vLLM 复现）
上做**线性链投机解码 + 量化 + 调度**，并且**用测量回答了"投机解码到底在什么条件下才真加速"**。

**硬件**：单张 RTX 3090（24 GB，sm_86）· Qwen3-4B（target）+ Qwen3-0.6B（draft）· BF16 · temperature=1.0。

**最终数字**（8 档消融，同一份代码 / 同一组负载 / 同一套口径）：

| 负载 | 普通解码（eager） | 全优化后 | 整体提升 |
|---|---:|---:|---:|
| B=1 / 1K | 21.7 tok/s | 126.5 tok/s | **5.82×** |
| B=1 / 4K | 21.7 | 86.3 | **3.97×** |
| B=4 / 1K | 100.7 | 279.2 | **2.77×** |
| B=4 / 4K | 100.9 | 175.1 | **1.74×** |

**★ 但最大的一截不是投机，是 CUDA Graph（2.4–3.6×）。**
把投机那一截单独拎出来（`G → S6`）：**1.60×（B=1/1K）→ 0.71×（B=4/4K，也就是 batch 大时净亏）**。

**最值钱的三件事**：

1. **用自己的测量否掉了自己方案里的第一条主线。** 方案把"把自写 attention 接进引擎"排为
   第一条开发主线（4–7 人天）。先算 Amdahl 上界：attention 只占 device 时间 8–9%
   ⇒ 上界 +10%，代入实测 kernel 加速比后**只有 +3%** ⇒ 达不到门槛 ⇒ 收手。
2. **抓出十多个"静默 bug"**（不报错、只悄悄出错）。最重的一个让 **prompt ≥ 384 token 直接崩** ——
   意味着**此前所有引擎级长上下文结论都无效**。
3. **给每个数字都配了口径和边界**，并且**敢报负结论**。项目里有一张"被自己推翻的结论"清单
   （见第 10 节），里面包括：招牌数字 `B=4 提速 1.19×`、一个被当成"机制收益"的 bug、
   一个算小了 18 倍的收益上界。

## 2. 起点：接手时是什么状态

上一轮已经把投机解码**实现对了**（无损性单测全过），但**速度是负的**：

```
baseline（普通 decode，eager）   30.6 tok/s
draft k=6（投机，eager）         20.8 tok/s   ← 0.68×，净亏 32%
```

上一轮给出的解释是：

> 「每步 decode 要读全部权重，baseline 读 8.0 GB，draft k=2 要读 10.2 GB，
> 读取量涨 27% → 净亏损 34%。」

**这个模型解释不了实测。** 算一笔账：

```
4B 模型 fp16 权重 8 GB，3090 显存带宽 936 GB/s
读一遍只需要 8.5 ms —— 而实测每步要 33 ms
多出来的 24 ms 跟权重一个字节的关系都没有
```

同一个模型、同一次前向，**只差一个开关**：

| | 每步耗时 | tok/s |
|---|---:|---:|
| `enforce_eager=True`（不拍图） | 33.2 ms | 30.6 |
| 开 CUDA Graph（拍图） | **12.8 ms** | **79.6** |

**差 2.6 倍，这 20 ms 里没有一个字节是权重读取，全是 kernel launch + Python dispatch。**
draft 侧更极端：0.6B 只有 1.2 GB 权重（理论 1.3 ms 读完），eager 下一次前向要 **24.8 ms —— 19 倍**。
而 draft 要串行跑 k 次，这笔开销要乘以 k。

```
旧模型（错）：加速比 ≈ f(权重比)
新模型（对）：加速比 ≈ f(每步固定开销)     ← batch=1 时的主导项
```

**★ 这就是整个项目的起点判断：batch=1 的推理引擎，先把 per-step 固定开销压掉，再谈投机解码。**

## 3. 约束地图：先测瓶颈，再谈优化

进项目时方案已经写好了一条主线。我们**没有直接开工**，而是先花时间测清楚"瓶颈在哪"。

### 3.1 普通 decode 的 GPU 时间分解

用 `torch.profiler` 把 **device time**（纯 kernel 时间，不含 Python 开销）分解
（B=1、ctx=4096、CUDA Graph 开、64 个 decode step）：

| 类别 | 占 device 时间 | 说明 |
|---|---:|---|
| **GEMM / 线性层** | **79.27%** | batch=1 时是**纯权重流式**：8 GB 权重 / 10.5 ms = **763 GB/s = 3090 峰值带宽（936）的 81%**，基本跑满 |
| attention | 9.24% | 随上下文上升：**8.12% / 9.24% / 14.68%** @ ctx 1024 / 4096 / 8192 |
| elementwise / norm / rope | 8.37% | 采样器已被 torch.compile 融合成 1 个 kernel |
| 采样 / KV 写入 / memcpy / 其他 | 合计 ~3% | **采样只占 0.81%** |

### 3.2 另外两处也贴着硬件极限

```
权重流式    实测 763 GB/s  = 峰值带宽（936）的 81%    → 没有免费空间
prefill     B=4 的 TTFT 是 B=1 的 4.09 倍（完全线性、不摊薄）
            反推 ≈ 65 TFLOPS（3090 bf16 峰值约 71）   → 也没有空间
draft 单次前向  2563.6 µs / 1.192 GB = 465 GB/s
            = 实测流式天花板（842）的 55.2%（对照 target 普通 decode 是 91.5%）→ ★ 这里有空间
```

（注：842 GB/s 是**实测**的流式天花板，用纯 copy 512 MB 测出来的；936 是规格值。
下文所有百分比都用 842 算 —— 用 936 会低估自己的效率。）

### 3.3 ★ 三条推论（后面所有决策都建立在这上面）

| 推论 | 由此立项 |
|---|---|
| **decode 想显著变快，只能让权重变小**（那 79% 是墙） | → **量化**（Q1 / Q2 / P9） |
| **prefill 没空间** ⇒「长 prompt 堵住 decode」只能靠**调度**解决 | → **混合调度**（P12 / P13 / P15 / P14） |
| **吞吐的杠杆是并发**：B=1→B=4 时效率涨 **3.6 倍**（0.082 → 0.295 token/ms），而 B=4 时算力只用掉峰值的三十分之一 | → **批量投机**（P6）、**容量优化**（P7 / P9） |

**★ 这一张表决定了后面所有方向**，因为它把"哪里还有空间"从感觉变成了数量级问题。

## 4. 主线一：把符号翻正（CUDA Graph）

### 4.1 为什么是它，不是算法

诊断路径只有一步：**先看"每步产出"有没有变。**

```
draft k=6，eager : 20.8 tok/s    ← 每步 3.77 个 token，仍然是【净亏损】
draft k=6，拍图  : 132.5 tok/s   ← 每步 3.82 个 token，加速 1.61×
   ↑ 每步产出几乎没变（3.77 → 3.82），变的只有 per-step 固定开销
```

**每步产出的 token 数几乎没变，说明算法本身没问题；变的只有每步耗时。**
⇒ 病根是固定开销，不是算法效率。⇒ 解法是 CUDA Graph。

### 4.2 做了什么

给**两条前向**各拍一张**静态形状**的 CUDA graph：

| 图 | 形状 | 收益 |
|---|---|---|
| draft 前向 | bs=1、每次 1 token | 24.8 ms → **~2 ms** |
| 验证前向 | bs=1、query 恒 1+k、varlen | 36 ms → **~14 ms** |

验证前向走 varlen，`run_model` 里 `is_prefill=True` 会强制走 eager 分支，
**但它的形状是固定的**（batch=1、query 恒等于 1+k、块表宽度固定），所以照样能拍图。
形状不匹配时自动退回 eager。

★ 还有一个细节：**图路径里采样结果留在 GPU 上**。draft 的 k 步自回归中间不做 `.item()`，
直接把 token 写回静态输入缓冲区，只在最后 stack 成 list 时同步一次 ——
否则 k 步就是 k 次 pipeline stall。

### 4.3 结果与边界

| | |
|---|---|
| **效果** | 普通 decode **30.6 → 79.6 tok/s（2.6×）**（每步 33.2 → 12.8 ms）；单请求投机 **1.61×**（82.3 → 132.5 tok/s） |
| **条件** | B=1、单条 256 token 生成的**自然代码 prompt**、`enforce_eager=False`、α=0.77 |
| **★ 边界** | 这个 1.61× **不是**"投机解码的功劳"，而是"投机 + 拍图"的联合结果。同一配置不拍图只有 **0.68×**。加速比**强依赖接受率**，必须连报 |

★ **同一个规律在 kernel 层重现了**（见 4.4）：这不是两个巧合，是同一个规律 ——
**"小尺寸下，固定开销支配一切"**。

### 4.4 附带：手写 paged decode attention（Triton 三版 + CUDA 版）

这条线**没有被接进引擎**（因为 Amdahl 上界只有 +3%，见第 9 节），但本身是硬资产。

**先证明它是访存瓶颈**：

```
ctx=1024 时：
  要搬的字节 = 1024 × 2 × 8头 × 128 × 2B  = 4.19 MB
  要算的浮点 = 4 × 32头 × 128 × 1024       = 16.78 MFLOP
  算术密度 = 16.78e6 / 4.19e6              = 4.0 FLOP/Byte
3090 的 roofline 拐点 = 35.6 TFLOP/s ÷ 936 GB/s ≈ 38 FLOP/Byte
⇒ 算术密度只有拐点的 1/10 ⇒ 铁定的访存瓶颈
```

**三个版本，每一步的动因都来自上一步的实测数据**（纯 kernel 时间，ctx=4096）：

| 变体 | 纯 kernel 时间 | 搬的字节 | 实测带宽 | 占实测天花板 842 |
|---|---:|---:|---:|---:|
| v1 每 (序列, q头) 一个 program | 191.4 µs | 67.1 MB（4× 冗余） | 86 GB/s | 10.3% |
| v2 按 kv 头分组，共用 K/V | 111.2 µs | 16.8 MB | 150 GB/s | 17.8% |
| **v3 split-K**（把 context 切开并行） | **31.4 µs** | 16.8 MB | **523.8 GB/s** | **62.2%** |
| （对照）flash-attn | 41.2 µs | 16.8 MB | 410 GB/s | 48.7% |

- **v1 → v2**：GQA 是 32 q头 : 8 kv头 = 4:1，v1 把同一份 K/V 读了 4 次。
  证据最漂亮的一条：v1 和 flash-attn 的**实测带宽几乎一样**（348 vs 400 GB/s），
  但 v1 搬了 4 倍的字节、慢 4.6 倍 ⇒ **v1 不是"带宽用不满"，是"搬了不该搬的字节"**。
- **v2 → v3**：v2 字节少了 4 倍却只快 1.7 倍，因为带宽利用率掉到 17.7% ——
  v2 只启动 8 个 program，而 3090 有 82 个 SM。v3 把 context 方向也切开。

**CUDA 版**（Ampere 深度实现）：`mma.sync` + `ldmatrix` + **`cp.async` 三级流水** + 手写 XOR swizzle
+ `__threadfence()`/`atomicAdd` 融合归约。

| | 纯 kernel 时间 | 带宽 | 占实测天花板 |
|---|---:|---:|---:|
| Triton v3（partial + combine 两个 kernel） | 30.66 µs | — | — |
| flash-attn（对照） | 40.80 µs | 411 GB/s | 48.8% |
| **CUDA 只读探针**（访存逐字节相同、mma 全删） | **23.08 µs** | **727 GB/s** | **86.4%** |
| CUDA 主 kernel st1（不用 cp.async） | 36.91 µs | 455 GB/s | 54.0% |
| **CUDA 主 kernel st3（三级流水）** | **25.87 µs** | **648 GB/s** | **77.0%** |
| **CUDA 完整（st3，融合归约）** | **28.03 µs** | — | 1.094× vs Triton v3 |

**每一步值多少**：

```
不用 cp.async → 三级流水 cp.async     36.91 → 25.87 µs   1.43×   ← 最大的一步
双缓冲       → 三级流水               27.63 → 25.87 µs   1.07×
combine 另起 → threadfence 融合归约   28.27 → 28.03 µs   1.009×  ← 几乎白干
```

**★ 两个被自己的数据证伪的假设**（这两条比"赢了多少"更值钱）：

1. **"Triton 的 M 补到 16，GQA 只有 4，所以 75% 的 MMA 行白算" —— 错。**
   真写了一个"正好算 4 行"的 FFMA 版（完全不用张量核），结果 **47.73 µs，比 mma 版慢 1.84 倍**。
   机制：张量核的价值不在算力，在于**它把 head_dim 方向的归约做掉了**（FFMA 版要自己用 shuffle 归约）。
2. **只读探针给出了上界**：把 mma 和 softmax 全删掉、只留访存，跑 **23.08 µs** ——
   也就是说**整个张量核 + softmax + 同步加起来只值 2.79 µs（10.8%）**。
   ⇒ warp specialization 的上限本来就只有 ~10%，是个低价值目标（所以试了 4 轮停手）。

**边界**：

- 所有时间都是 `torch.profiler` 的 **device time，不是墙钟**。Triton 一次启动的 Python 开销 ~20 µs，
  两个 kernel 就 46 µs，**能把 31 µs 的 kernel 盖成 76 µs**（这个坑踩了整整一轮）。
- 带宽分母用**实测天花板 842 GB/s**，不是规格值 936。
- **本机 ncu 被禁**（`ERR_NVGPUCTRPERM`，无 sudo），拿不到 `dram__bytes_read` ——
  所有带宽都是"字节数 ÷ 时间"反推的，**不要说成"ncu 量的"**。
- 只用随机数据测过，**未接进引擎**。
- sm_86 物理不支持 TMA / TMEM / 2-SM cluster，只讲得了原理。

## 5. 主线二：批量与容量

### 5.1 P6：批量投机（把 B=4 从 0.77× 翻到 1.19×）

**问题**：B=4 时投机**输给普通解码**（`C/U = 0.77`）。结构证据两条：

- **验证图只有单请求形状** ⇒ B>1 整条验证**退回 eager**（命中 3–7 次、退回 48–72 次）。
- **draft 是逐请求串行的** ⇒ B=4、k=6 时每轮 **24 次**独立前向，每次重读 1.2 GB 草稿权重。

**判断**：两处开销都随 batch **线性增长** ⇒ 改成批量 draft + 按 `(B,k)` 捕获验证图。

**做了什么**：

1. **批量 draft**：同一候选位置把 B 条请求**一起**前向（k 个位置仍顺序，因为候选是自回归的）。
2. 按精确 B∈{1,2,4} 捕获 draft 图。
3. **按 `(B,k)` 捕获验证图**（query = B·(k+1)）。
4. 每请求的 draft KV 水位与补齐。

**效果**（B=4 / 4K / k=6 / 输出 256，output tok/s）：

| 档 | 说明 | tok/s |
|---|---|---:|
| `U` | 普通解码 | 169.9 |
| `C` | 改之前（旧投机） | 131.2 |
| `S1` | + 批量 draft | 176.0 |
| `S2` | + 验证图 | **201.8** |

**消融**：`S1/C = 1.34×`（批量 draft 的独立贡献）· `S2/S1 = 1.15×`（验证图的独立贡献）
· `S2/C = 1.54×` · **`C/U` 0.77 → `S2/U` 1.19**。
结构证据：验证图 **37/37 全命中、0 退回**（改前命中 3–7、退回 48–72）；draft 前向/轮 **24 → 6**。

**★ 顺带修掉的第 3 个静默 bug**：全接受时 draft KV 有位**从没写过且永不回头补**，污染会**累积**。
对照实验（关补齐 vs 开补齐）：接受率 **0.866 → 0.987**、同负载 **152.3 → 201.8 tok/s（×1.32）**。

**其他档**：B=2/4K `S2/U = 1.45×`（最漂亮的一档）· B=1 **无变化**（116.68 → 116.76，没东西可批）
· B=4/1K **0.93×U 仍略输** · B=4/4K/k=2 **0.88×U 仍略输**。

**★ 边界（必须一起写）**：

1. **那个 1.19× 依赖接受率**：本负载 α≈0.99，把接受率还原到 0.87 → **152.3 tok/s = 0.897×U，仍低于普通解码**。
   自然代码 prompt 的 α 只有 0.745–0.842，那一档大概在 0.9× 附近。
2. **代价**：加载草稿把主模型可用 KV 容量从 **88,832 → 45,312 token（−49%）**，TTFT 也变差。

### 5.2 前缀缓存是"负优化"（P7-A）

**现象**：4 条请求共享 4096-token 前缀时，**单个 decode step 阻塞 17.3 秒、占端到端墙钟 85%**；
吞吐只有 12.53 tok/s，而**冷缓存（不命中）有 45.5 tok/s**。

**判断**：命中 target 的前缀缓存 ≠ draft 那把 KV 也有效。
但**正确修法不是"假设有效"**（那会静默输出垃圾），而是给 draft 做**它自己的**块级有效性追踪。

**做了什么**：给 `Block` 加 `draft_hash` / `mark_draft_valid` / `draft_valid_cached_blocks`
（只认连续前缀）；并做**承重性反证 NEGX**（故意绕过守卫直读脏 KV）。

**效果**：

```
补齐 16660–16665 token  →  22–31 token（−99.8%）
吞吐     12.53 tok/s    →  76.63 tok/s（6.1×）
★ 修复前：前缀缓存是净亏的（12.5 < 冷缓存 45.5）—— 命中了比不命中还慢 3.6 倍
★ 修复后：净赚 1.68×（76.6 > 45.5）
```

**正确性证据（正反两面）**：复用路径输出 == 全量补齐路径输出，**3/3 输出 md5 完全一致**；
负对照 NEG（target 命中但 draft 没写过）仍正确回退；
★ **承重性反证 NEGX**（朴素修法跳过守卫直读脏 KV）→ **接受率 0.9 崩到 0.175–0.470、
logits argmax 一致率 0.333** ⇒ 证明那道守卫真在挡东西。

**★ 边界**：这一节的价值在"发现了一个让功能变成负债的 bug"，
不在于"我加了一个缓存"—— 缓存本来就在，是我们把它从负债修成了资产。

### 5.3 草稿滑窗 + 解耦分配（P7-B/C → P7-D → 最终推荐）

**问题**：draft 与 target **共用块号**（`Sequence.block_table`）⇒ 块数必须相等、无法缩小 ⇒
target 可用容量被 draft 吃掉近一半。

**做了什么**：

1. **草稿只保留最近 M 个 token 的 KV**（块级环形缓冲，块表旋转成递增以保因果正确，RoPE 用绝对位置）。
2. **解耦草稿的显存分配**：draft 有自己的独立编号，不再共用 target 的块号。

**★ 过程中修掉 3 个静默 bug**，其中最有教育意义的一个：
**"补齐那一趟前向硬传 `valid_from=base`"** ⇒ **那个前向的可见上下文从 1031 个 token 被砍到 7 个**，
而它恰是草稿下一步最需要的 ⇒ 每轮全接受就往环里写一格坏 KV。
定位方法是**逐次前向逐位对拍**，钉到**第 7 次前向**（ctx 1031 vs 7）。

**效果①：容量**

| | 普通投机 | 滑窗（M=5） |
|---|---:|---:|
| draft 池 | 173 块 / **4.73 GiB** | **20 块 / 0.55 GiB（−88%）** |
| target 池 | 173 块 = 44,288 token | **293 块 = 75,008 token（+69%）** |
| 并发 @8K / @16K | 5 / **2** 条 | **8 / 4** 条 |

**★ 判据（一条式子，可先算后测）**：

```
滑窗省显存  ⟺  M × max_num_seqs  <  普通投机的池块数（本机 173）
```

四个实测点全部对上：M=33 → target **206**（+19%）· M=18 → **252**（+46%）· M=5 → **293**（+69%）；
**反面也测到了**：M=65（16K 下"不截断"的窗口）→ **106（−39%）**。

**★ 长上下文才是滑窗的主场**：16K 下请求 4 并发时，**普通投机只能真正跑 2 条**
（第 3、4 条排队到 **TTFT 13.6 秒**）；M=5 能跑满 4 条。
理论值 `floor(池块数 / ceil((ctx+out)/256))` = 2/3/3/4 **与实测逐格相同**。

**效果②：解耦草稿分配本身**：每轮耗时 **0.79–0.86×**、吞吐 **+16~21%**，
且**逐位相同、零接受率代价**、**与窗口大小解耦**。

**效果③：接受率的真实代价（修完 bug 之后才看清）**

| 配置 | ctx | α | 相对普通投机 | 显著性 |
|---|---|---:|---:|---|
| `(P=0, M=5)` | 8192 | 0.6414 | **−4.1%** | 5.6σ |
| `(P=0, M=5)` | 16384 | 0.6165 | **−6.0%** | 5.4σ |

**★ 不是无损** —— 纯滑窗仍有 **4%–6% 的真实截断代价**。

**效果④：代价的另一面 —— TTFT**

保住接受率的窗口 **prefill 很贵**（滑窗路径按 `token_ids` 重算整个窗口，**不认前缀缓存**）：

```
8K/B=1 下 W=8448 的 draft prefill = 273.9 ms、占 prefill 的 82.8%
TTFT 90.9 → 336.9 ms（3.7×）
而 W=1280 只花 33.5 ms，代价是接受率 0.7814 → 0.4190（−46%）
```

**★ 最终推荐配置**（三个开关，两个修复必须同时开）：

```
spec_draft_window    = 1280     # M = 5 块
spec_draft_head_blocks = 0      # ★ P 一律取 0
spec_draft_win_align   = True   # 必须显式开
spec_draft_win_realign = True   # 必须显式开（只开 align 会在第二次漂移上崩）
```

新推荐下的实测：α@8K **0.6414 ±0.0042**、α@16K **0.6165 ±0.0050**；
TTFT@8K/B=1 **91.41 ms（+0.3）**、@16K **116.04 ms（+2.2）**。

**★ 归因未钉死（诚实挂账）**：解耦分配那 **+20%** **不是**来自"读的 key 变少"（已否）、
**也不是**来自块表宽度（已否）。隔离实验同时改变了整套 KV 的分配布局，
**具体环节尚未隔离**。**不要写"来自滑窗省上下文"或"连续块"。**

**★ 还挂着的一条**：B=4 下 `ms/轮(maxB)` 大致随 draft 读的块数 `(P+M)` 上升（平均 **+1.1 ms/块**，
散布 ±6 ms，28 格）⇒ **"滑窗只换容量、不换速度"在 B=1 成立、在 B=4 不成立**（机制未隔离）。

### 5.4 P9：把量化的显存账从负翻正 —— 构造期直载 int8

**问题**：量化后权重真省了 0.4 GB，但 **KV 池反而 174 → 170 块**（见 6.2）。

**第一版判断（★ 错的）**：怀疑 CUDA context 里多了量化 GEMM 的 **kernel 模块**。

**做了什么**：在**预算时刻**补打点，把设备已用量 `used` 拆成三项：

```
used = current + I + O
  current = PyTorch 分配器已分配给张量的字节
  I       = reserved − current   （分配器【内部】保留的空闲）
  O       = used − reserved      （分配器【之外】）
```

**根因：第一次被钉死（三个量逐字节对齐）**

| | used | current | reserved | **I** | **O** | 块数 |
|---|---:|---:|---:|---:|---:|---:|
| BF16 基线 | 9,721,872,384 | 9,323,314,176 | 9,370,075,136 | 46,760,960 | 351,797,248 | **174** |
| INT8 就地 | 9,925,296,128 | 8,894,348,288 | 9,573,498,880 | **679,150,592** | 351,797,248 | **170** |
| **INT8 直载** | 9,319,219,200 | 8,885,697,536 | 8,967,421,952 | **81,724,416** | 351,797,248 | **180** |

1. ★★ **`ΔO` 逐字节精确为 0**（三档 `O` 全是 351,797,248）
   ⇒ **"CUDA context 多了 kernel 模块"这个猜测被实测直接否掉**（该涨的是 `O`，而 `O` 一分没动）。
2. ★ **`ΔI = +632,389,632 B = 0.589 GiB`**，且**逐字节等于** `Δused − Δcurrent`
   ⇒ 损失**全部**在 PyTorch 分配器内部。
3. ★★ **`I` 恒等于 `inactive_split`** ⇒ 这些保留空间**全是不可回收的 split 残块**，
   **不是可复用的缓存**。所以 warmup 头尾两次 `empty_cache()` **一分钱没还回去**。

**修法**：把量化从"载入 BF16 全模型 → 在 GPU 上就地量化"改成**构造期直载**：

```
meta 构造整个模型
  → 未量化参数（embed_tokens / lm_head / norm）单独 materialize 成 bf16
  → 量化层【完全不 materialize bf16】，直接建 nn.Parameter(int8) + weight_scale
     （逐层把【那一层】的 bf16 搬上卡算一次量化，算完即弃 —— 整模型 bf16 从未在显存里存在过）
```

**结果**：`I` 从 679 MB 打回 **82 MB**；**KV 池 170 → 180 块（+5.9%），并反超 BF16 基线的 174 块**。

**★ 同容量对照**（两档都锁 `FORCE_BLOCKS=170`，`after_capture` 设备全局 `used`）：

```
BF16     21,522,546,688
INT8 就地 21,707,096,064
INT8 直载 21,101,019,136
   直载 vs 就地  −606,076,928 B = −0.564 GiB
   直载 vs BF16  −421,527,552 B = −0.393 GiB
```

⇒ **排除了"池子小所以总占用小"这个混淆**：容量锁死时直载仍然更省。

**★ 口径陷阱**：这里**必须用 `after_capture` 的设备全局 `used`**；
脚手架里的 `used_MB` 取的是 `max_memory_allocated()`，**只统计已分配字节、看不到 reserved 里的收益** ——
三档几乎相同，会误判成"没省"。

**验收**：直载权重与就地量化**逐位相同**（112/112 模块、scale 0 处不同）；融合 GEMM 输出逐位相同 20/20；
生成 md5 一致；**251 项 CPU 测试全过**；默认路径逐字节等价；负数对照（真 int8 checkpoint 但不直载 → 必须报错）✅。

**★ 一个反直觉的发现**：**离线的 int8 checkpoint 与引擎就地量化不是逐位相同** ——
量化算法在 **CPU 上逐位相同**（196/196 张量），但在 **GPU 上** 112/112 层都有约 **0.006%** 的元素差 **1 LSB**
（scale 逐位相同；GEMM 输出最大差 0.0078~0.0156，**一个 bf16 ULP 量级**）。
根因**未定位**（怀疑 CPU/GPU 的 fp32 除法或取整在 .5 边界差 1 ULP，**这只是怀疑**）。
⇒ 据此把**默认**量化来源定成 **GPU 侧逐层算**（逐位性成立），离线 int8 兜底为另一档。

**★ 没做 / 未解**：`per_group` 粒度、`TP>1`（被显式 assert 挡住，是有意不做）；
**target 侧没接直载**；直载路径下 `I` = 82 MB（比 BF16 基线的 47 MB 还多 35 MB）**这 35 MB 没查清来源**；
碎片的具体形成序列**没做 allocator snapshot 验证**。

## 6. 主线三：量化（只量化 draft，target 一个字节不动）

### 6.1 ★ 核心叙事：量化 draft 让投机的**相对优势变大**

| | 普通解码 tok/s | 投机 tok/s | **投机 / 普通** |
|---|---:|---:|---:|
| draft BF16 | 77.9 | 109.8 | **1.411×** |
| draft INT8 | 77.9（同一个 U） | 124.7 | **1.601×** |

普通解码 100% 是 target（没动 ⇒ 一分不变），而投机一轮的权重流量里 **6/7 是 draft**
（6×1.110 GB vs 1×8.045 GB）⇒ 给投机路径的成本打折。
**所以：量化 draft 会放大投机的相对优势；量化 target 正好相反**（会让普通解码也变快）。
这是选 draft 侧而不是 target 侧的最大好处。

**★ 口径最干净的一句话**：接受率不变 ⇒ **"投机 / 普通"就是 1/配对比值 = ×1.069 ~ ×1.078**。

### 6.2 Q1：只量化 draft 的 FFN —— **未达门槛，如实记录**

**做了什么**：对称 per-channel 量化草稿（Qwen3-0.6B）的 FFN（gate/up/down，84 个模块），
配一版**融合反量化**的 GEMM（"先解压再算"会变成读 1B + 写 2B + 读 2B = 5B/参数，比原来更糟）。

**★ 一个副产品是本项目最强的一条证据**：GEMM 时间在 `B=1/4 × ctx=1K/4K` 四种组合下是
**10.46 / 10.52 / 10.65 / 10.70 ms —— 只差 2.3%**
⇒ **直接证明 decode 的 GEMM 是纯权重流式，与 batch 多大、上下文多长几乎无关。**

**效果（配对、交替、含空转噪声地板，用每轮耗时）**：B=1 四档 **0.9548–0.9638**（即 **+3.8% ~ +4.7%**），
**9/9 全胜**。**没达到事前门槛（`B=1/4K ≥ +20%`）。**

**机制解释**：draft FFN 只占 draft 权重 **44.3%**，draft 又只占一轮权重流量 **47%**
⇒ 一轮总字节只降 **9.9%**；再乘草稿前向的带宽效率折损 → 每轮 ≈ **−3.5%**，与实测吻合。

**精度**（wikitext-2，122760 token，每次只量化一类）：只 FFN **+0.316% PPL**（噪声地板 [0.317, 0.316]）。

**★ 接受率不变**：引擎只有 384 样本（SE 2.2%）分不出，改用恒等式 `α = 1 − TV(p,q)`
在 **12,282** 个 wikitext 位置上算 → **Δα = −0.00251 ± 0.00349，不显著**。

**★ 显存是负的**：权重 −0.245 GB，但 **KV 池 174 → 171 块（−1.7%）**（后来由 P9 解决）。

**★★ 两条反直觉的发现（都推翻了事前假设）**：

1. **「FFN 比 attention 更耐量化」不成立。**

   | | draft（0.6B） | target（4B） |
   |---|---:|---:|
   | 只量化 FFN | **+0.316%** | **+0.637%** |
   | 只量化 attention | **+0.132%** | **−0.183%**（负值即噪声） |

   **attention 反而更耐量化。** 事前"只量化 FFN 因为 FFN 损害小"这个切法**既漏掉了更耐量化的 attention，
   又包含了最敏感的首尾层 —— 切错了维度。**
2. **「`down_proj` 最敏感」只在 0.6B 上成立。** draft 上它 +0.228%（三类里最高）；
   **4B 上它最不敏感**（+0.122% < gate +0.213 / up +0.269）
   ⇒ **敏感度排序是模型相关的，不能跨模型外推。**

**★★ 两个新机会（本次测量挖出来的）**：

- **机会 A：按「层位置」切，而不是按「FFN / attention」切。**
  draft 的 FFN 按位置拆：**前 4 层 +0.304% / 中间 20 层 +0.021% / 后 4 层 −0.002%**
  （三段和 +0.325 ≈ 整块实测 +0.316，**可加性成立**）
  ⇒ **量化中间 20 层（71% 的层）代价几乎为零。** 这条对 **target 更重要**（上界 1.42–1.60×）。
- **机会 B：draft 前向只有 55.2% 的带宽效率。**
  draft 单次前向 **2563.6 µs / 1.192 GB = 465 GB/s = 实测天花板（842）的 55.2%**
  （对照 target 普通 decode：770 GB/s = **91.5%**）。拟合出**每步约 1.2 ms 固定开销**
  ⇒ 6 次草稿前向/轮 ≈ **7.2 ms ≈ 一轮（约 38 ms）的 19%**。
  **零精度代价、比量化那一刀更大**，且可能与「解耦草稿分配白拿 +20%」是**同一现象**。

**★ 方法（这一节本身就是资产）**：

1. **逐模块消融**：每次**只量化一类**，其余全部保持 BF16。
2. **★ 噪声地板**：同一配置在语料**两半**上各算一次 ΔPPL，用两半**分歧**当地板。
   这一步抓出了假效果 —— `up_proj` 报 **−0.078%**（字面即"量化让它变好了"），
   而两半分歧 [−0.059, −0.096] 说明整条落在噪声里。**没有地板就会把它当结论。**
3. **可加性检验**：位置维度三段和 ≈ 整块实测 ⇒ 证明分解有意义。
4. **接受率不信任引擎的少量样本**：改用恒等式在 12k 位置上算。
5. **在第二个模型上交叉验证**（4B）→ 才发现敏感度排序是模型相关的。

### 6.3 Q2：扩到 draft 的全部线性层 —— **有效，−6.4% ~ −7.1%**

**动机**：Q1 只值 −3.6% ~ −4.5%，因为动的字节太少。这一轮把 draft 的
**q/k/v/o + gate/up/down 全量化**（196 个模块，字节 −21.2% → **−36.9%**）。
**target 依旧一个字节不动** ⇒ **「相对 BF16 target 无损」这句口径一个字都不用改**。

★ **本轮对 `nanovllm/` 是零生产代码改动**（`git diff` 为空）——
上一轮交付的配置开关原样够用，换个 `quant_config.json` 就完成范围扩大。

**闸门（单层微基准）**：四形状在 M=1/M=4 上**全部更快**（1.96× gate_up · 1.93× qkv · 1.41× down · 1.11× o），
整层组×28 **1.641×**，max rel err 0.40%–0.67%（bf16 天然精度量级）。
⇒ 陷阱属于"朴素 int8 matmul"，融合反量化路径绕开了。

**精度**（协议与 Q1 完全对齐）：

| 配置 | 模块 | ΔPPL% | 占线性层字节 | 省下字节 |
|---|---:|---:|---:|---:|
| **全量化（本轮）** | 196 | **+0.455** | 73.9% | **36.9%** |
| 只 FFN（Q1） | 84 | +0.337 | 44.3% | 22.1% |
| 只 attention | 112 | +0.116 | 29.6% | 14.8% |

**代价只从 +0.337% 涨到 +0.455%，省下的字节翻倍** —— 因为 draft 的 attention 比 FFN 更耐量化。

**★ 接受率没变**（12282 个位置）：Δα = **−0.00235 ± 0.00349**（不显著）。
Q1 是 −0.00251 ± 0.00349 —— **从 FFN 扩到全部线性层，Δα 一点没动**。

**性能**（配对 / 交替 / 含空转噪声地板；按每轮耗时报）：
**B=1 四档 36/36 全胜**（符号检验 p≈1.5e-11）→ **每轮 −6.4% ~ −7.1%**，
接受率不变 ⇒ **端到端 tok/s +6.9% ~ +7.8%**。**比 Q1 翻了一倍。**

**★ 内部一致性（这一轮最有说服力的一条）**：用**同一把尺子**回归重跑了 Q1 的 FFN 配置，
复现上一轮。然后看"每 100 MB 省多少 µs"：

| 范围 | 每次前向省下的字节 | 实测省 µs/前向 | 每 100 MB |
|---|---:|---:|---:|
| 只 FFN | 264 MB | 229.7 / 252.2 | 87 / 96 |
| 全部线性层 | 441 MB | 393.2 / 425.2 | **89 / 96** |

**两档完全一样 → 这一刀就是纯字节账，没有别的机制。** 也因此可以外推。

**★ 为什么是 −7% 而不是估的 −10%（逐条对账，两个输入都偏乐观）**：

1. 省下的字节：估的是每次前向 0.57 GB，**实测 0.409 GB**（draft 权重 1.192 → **0.752** GB）。
2. 字节→时间的捕获率：微基准预测 575.6 µs，**实测 393–465 µs = 68%–81%**
   （与 Q1 实测的 **75% 一致**，是同一现象的第二次测量）。

**★ 显存（负结论，与 Q1 同一个坑，第二次复现）**：权重真省了（`current` 8.683 → 8.284 GB），
**但 KV 池 174 → 170 块（−2.3%）**。→ **由 P9 解决（见 5.4）**。

**★ 没做 / 测不出**：B=4 自然档仍分辨不出（地板 58%–60%）；
B=4 的"每次前向省多少"折算对不上（实测 127–149 µs vs 预测 602 µs，未归因）；
draft 的 embedding/lm_head 没量化（占 26%）；prefill 侧代价仍未测。

## 7. 主线四：调度（"排在一起" ≠ "同时跑"）

### 7.1 问题长什么样

调度器每一轮只在"prefill"和"decode"里选一个：

```python
# 先跑 prefill 的 while 循环
if scheduled_seqs:
    return scheduled_seqs, True     # ← 只要有一条要 prefill，这一整轮就全是 prefill
# 才轮到 decode
```

**后果**（同进程探针，3 条请求在解码 + 突然来 1 条 16K）：

```
正常一轮解码：12.1 ms（普通 decode）
长 prompt 到达那一轮：解码请求拿到的 token 数 = 【精确为 0】
                     它的下一个 token 要等【3836 ms】
                     尖刺 = 10.7×（1K 长 prompt）→ 310×（16K）
```

### 7.2 ★ 先测上界，不写一行代码

这一步是整个迭代里最重要的一步 —— 因为它决定了后面该不该做。

```
账① draft prefill 是浪费：run() 里 `if self.draft_model is not None` 【不看 spec_k】
     ⇒ 只要进程加载了 draft，prefill 就白跑一遍 0.6B
     ⇒ 冷启动让 target prefill 多花 20%~26%（16K 时 +739 ms）
     ⇒ 热缓存下是恒定 +31.5 ms（与上下文无关）
账② 尖刺：10.7×（1K）→ 310×（16K），远超方案 §6.3 的"只有 2–3 倍就收手"停止线
```

**决策**：账② 远超停止线 ⇒ **立项**。
★ **同一条停止线，当年把 P1 否掉，这次放行 —— 判据一样，结论相反。**

### 7.3 四个阶段（效果总表）

| | **独占**（原始） | **让路式**（P12/P13） | **P15-串行** | **P15-并发** | **P14-轮转** |
|---|---:|---:|---:|---:|---:|
| 解码 ITL max（场景 A） | 3836 ms | 580 | 594 | **455** | 不变 |
| 长 prompt TTFT（场景 A） | **3756** | 7524 | 7529 | **5029** | — |
| TTFT 极差（场景 B） | — | 大 | 大 | — | **归零**（但 p50 变差） |
| 稳态吞吐（场景 C） | 41.74 | 42.46 | 42.46 | **45.45** | 池满时 **−19.1%** ❌ |
| **本质** | 饿死解码 | **交换** | **零收益** | **双赢** | **只保公平** |

**★ 一句话结论：把两件事排进同一个 step 不省时间；让它们同时跑才省时间。**

### 7.4 阶段 1：分块让路 —— 它是一笔交换

**做法**：把长 prefill 切成小块（C 个 token），**块与块之间让一整轮给解码**。

```python
budget = min(remaining, chunk) if chunk else remaining   # 每轮最多拼一块
yield_to_decode = (chunk > 0 and self._prefill_chunk_pending and bool(self.running))
```

★ **关键性质：一轮内仍然只有一种执行路径**（要么 prefill、要么 decode），只是轮与轮之间交替。
这是**有意选的**低风险路线 —— 因为这个项目被"一轮内混两条执行路径"坑过 3 次。

**结果**：16K 的尖刺 **310× → 16.9×（C=512）/ 24.4×（C=1024）**；8K 未分块是 120.8×。
**代价**：prefill 墙钟 **+11.5%（C=1024）**；而且**长 prompt 自己的 TTFT 从 3756 翻倍到 7524 ms**。

**★★ 所以这一步的本质是"交换"**：用 prefill 用户的延迟，去换 decode 用户的延迟。

**★ 还有一条反向代价**：**C≤512 时中位 ITL 反而被抬起来**（12.2 → 60~76 ms），
只有 C≥1024 才回到稳态 ⇒ 规则里得多一条约束：**不要一昧往下压 C**。

**★ 一个自己埋的 bug**：第一版做完，`CHUNK=2048` 时尖刺**反而变大 3 倍**（642 → 2039 ms）。
第一版判断（★ 错的）是"torch.compile 对新 chunk 形状付一次编译钱"，改了预热没修好。
加了**逐轮打点**之后一行输出就定案：`round 0: step_tokens=14336` = **同一个 chunk 被拼了 7 遍**
（7×2048=14336）。根因是**我自己引入的** `budget = min(remaining, chunk)` 让循环得以继续，
而那条序列本步拼不完、没被 `popleft()`。**修法：分块分支 append 后立刻 break。**

### 7.5 阶段 2：算"真混合"的上界 —— 当时算错了

当时的推理是：

```
让路式：解码请求的 ITL = 一个 prefill 块 + 一个解码轮 = T_chunk + 12.1 ms
真混合能做的，只是把"解码轮"和"chunk"叠在一起 ⇒ 最多省掉那 12.1 ms
⇒ 上界 = 一个解码轮 = 12.1 ms，占实测尾部 3.2%~10%  ⇒ 【不做】
```

★ **这个 12.1 ms 是错的** —— 见下一节。**但它错得很有价值**（它引出了后面的实验设计）。

### 7.6 阶段 3：★ P15 —— 把"共批"和"重叠"拆开（认识的转折点）

**把三种跑法分开测**（同进程、同一张卡、轮内交替，n=3，中位数）：

| prefill 块深度 | t_decode | t_prefill | t_串行 | t_并发 | **重叠收益** | 上界 min | 收益/上界 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 第 0 块 | 220.2 | 171.4 | **391.5** | 298.1 | 93.4 | 171.4 | 54.5% |
| 第 5 块 | 220.4 | 242.9 | **462.8** | 306.8 | 156.0 | 220.4 | 70.8% |
| 第 10 块 | 219.0 | 319.2 | **537.9** | 338.9 | 199.1 | 219.0 | 90.9% |
| 第 14 块 | 218.8 | 381.4 | **600.7** | 396.9 | **203.8** | 218.8 | **93.1%** |

★★★ **两件事**：

1. **`t_串行 = t_decode + t_prefill`**，残差 **−0.1 ms** ⇒ **串行版一点重叠都没有**（这是诚实的零收益对照）。
2. **并发版把"相加"变成了"取大"** ⇒ 收益逼近 `min(t_decode, t_prefill)`。

**端到端（场景 A：3 条解码 + 突来 1 条 16K）**：

| 指标 | 独占 | **让路式** | **P15-串行** | **P15-并发** | 并发 vs 让路 |
|---|---:|---:|---:|---:|---:|
| 解码 ITL 窗口 p50 | — | 475.1 | 498.8 | **316.5** | **−33.4%** |
| 解码 ITL 全程 max | **3836.2** | 580.3 | 594.4 | **455.3** | −21.5% |
| **长 prompt TTFT** | **3756** | 7524 | 7529 | **5029** | **−33.2%** |
| 稳态吞吐 | 41.74 | 42.46 | 42.46 | **45.45** | **+8.9%** |

**★ 这张表的形状**：

```
独占      ：解码输（max 3836）、prefill 赢（TTFT 3756）
让路式    ：解码赢（max 580）、prefill 输（TTFT 7524）   ← 一笔交换
P15-并发  ：解码 max 455【而且】TTFT 5029                ← ★★ 两边都更好了
```

**它不再是交换** —— 因为两者吃的是**不同资源**，重叠让两边同时推进：

```
decode ：带宽型（3 个 token / 220 ms 里，主要成本是把 8 GB 权重读一遍）+ SM 占用低
prefill：算力型（4B 模型读一遍 8 GB 权重 / 171~381 ms ≈ 带宽的 3%）
⇒ 并发时带宽需求 ≈ 660 + 28 + KV 流量 ≈ 700 GB/s < 实测天花板 842 GB/s ✓ 放得下
```

★ **但"免费"是相对的**：并发时 decode 被拖慢 77.9 → 178.1 ms（资源竞争的真实代价，块越大拖得越多），
但"多跑一个 decode"的边际成本 = t_并发 − t_prefill = 126.7 → 63.9 → 19.7 → 15.5 ms
⇒ **两者确实互相拖慢，但净账为正。**

**★ 上界算错在哪里（18 倍）**：

```
我当时用的：一个解码轮 = 12.1 ms
   ★ 那是【普通 decode、无投机】的数字 —— 逐值复核确实是 12.04 ms ✓ 数字本身没错
但实际上（默认配置开了投机）：
   3 条请求 × (1 + k=6) = 21 个位置 + 6 次草稿前向
   一个解码轮 = 【220.2 ms】   ← 差了 18 倍
⇒ 收益上界不是"一个解码轮"，而是 min(解码轮, prefill 块)
```

**★★ 一个非直觉但很重要的后果**：

> **投机解码把"解码轮"从 12 ms 拉长到 220 ms，于是"解码被 prefill 挡住"的代价也跟着变大了
> —— 这反而让"重叠执行"更值钱。越是用投机（每轮越重），越应该让 prefill 和 decode 重叠，而不是排队。**

**★ 另一个反直觉的观测**：场景 B（只有 1 条解码 ⇒ 解码轮仅 32 ms）只 **−5.7%** ——
**同一个机制、同一个 CHUNK，收益从 −33% 掉到 −5.7%，只因为被藏的那个前向变小了**。
实测每块省 34.6 ms，与 32 ms 的预测吻合。

**★ 实现成本**：新模块 1 个（168 行）+ 4 个文件局部改动（净 +185 / −32 行）+ 新测试 1 个（43 项）+ 探针 4 个。
**没有动 KV 分配、没有动投机路径、`run()` 的 decode 分支零改动。**
5 条显式不变量（I1–I5）写进模块头与代码守卫。

**★ 遗留边界**：默认 `spec_graph_bs=(1,2,4)` 下，**3 条请求的混合 step 拿不到 B=3 的验证图**
（实测退回 22 次）—— 这是既有配置边界，不是 P15 引入的（后来由 P16 解决）。

### 7.7 阶段 4：P14 多序列轮转 —— 一个诚实的负结论

**问题**：多条长 prompt 同时到达时，只有第一条在推进（`break` 掉），后面两条干等。

**结果**（场景 B：1 条解码 + 3 条同时到达）：

| ctx | off 三条 TTFT | on 三条 TTFT | 最大 TTFT | 极差 |
|---|---|---|---|---|
| 4096 | 0.95 / 1.78 / 3.01 s | 2.11 / 2.11 / 2.11 s | **−29.8%** | 2.06 s → **0** |
| 8192 | 1.96 / 3.69 / 5.64 s | 4.72 / 4.72 / 4.72 s | **−16.2%** | 3.67 s → **0** |
| **16384** | 4.25 / 8.78 / **27.4 s** | 8.20 / 8.20 / 30.4 s | **+11%（噪声内）** | 23.1 s → 22.2 s ❌ |
| 16384 **+ 池 253 块** | 3.51 / 7.30 / 12.20 s | **10.05 / 10.05 / 10.05 s** | **−17.3%** | 8.69 s → **0** |

**★★ 它自己纠正了任务书里的一个错误推断**：

> 任务书写的是"三条都在第 16 轮完成 ⇒ 等 3 倍时间变 1 倍"。
> **按【轮数】成立**（`[4,7,10] → [4,4,4]`，总 prefill token 两档逐值相同），
> **但按【墙钟】不成立** —— 轮转把**每轮的工作量也放大了 N 倍**（off 每轮 1 块 vs on 每轮 3 块）。
> **"第 16 轮"是另一根尺子。**

**⇒ 它不是"让请求更快"，是"让请求一样快"**：极差归零，但 **p50 反而变差**（原本最快那条慢 2.4 倍）。

**★★ 而且 16K × 3 条时它根本帮不上忙** —— 因为瓶颈是 **KV 准入**
（每条 16K 要 64 块，池 174 块 ⇒ N_max = 2），**不是调度顺序**。
把池子抬到 253 块，"没效果"立刻变成"max TTFT −17.3%、极差归零"。

**★ 2×2 分解**：`池子贡献 −55.4%`、`轮转再贡献 −17.3%` ⇒ **先要资源，再谈调度。**

**★ 代价**：轮转**不抬高 KV 峰值**（132 → 133 块）、**零抢占**（8 组全 0），
但**场景 C 稳态吞吐 −12%**（当档噪声地板 3.7% / 8.0%）。

**⇒ P14 交付为默认关闭的可选开关，不进入推荐配置。**

## 8. 主线五：图的形状（P16 + 行业对照）

### 8.1 问题

投机路径的两张 CUDA Graph 都是**精确匹配** batch 的
（验证图 `verify_graphs[(B,k)]`、draft 图 `draft_graphs[B]`），
而 `config.spec_graph_bs = (1, 2, 4)` 只捕获这三个桶
⇒ **B=3 的混合 step 整个退回 eager**。

```
实测（3 条 decode + 1 条 16K prefill 的混合批）：
verify_graph_fallbacks = {"shape_not_captured(B=3,k=6)": 18~23}
draft 前向退回 eager    = 108 ~ 138 次
```

★ 这不是 P15 引入的，是 `spec_graph_bs` 这条**既有配置边界**。
原版 decode 早就用同一套办法绕开了它（`next(x for x in self.graph_bs if x >= bs)`），
投机路径当时没跟上。

### 8.2 做法

**桶选择：向上取整，正好命中就用自己**（`graph_pad.pick_bucket`）：

```
buckets=(1,2,4):  B=1→1(pad 0)  B=2→2(pad 0)  B=3→4(pad 1)  B=4→4(pad 0)  B=5→None(退回 eager)
```

**★ 空行不是"什么都不做"，它会被真的算一遍** —— 四个位置，四个不变量：

| 位置 | 填什么 | 为什么 |
|---|---|---|
| `slot_mapping` | **−1** | `store_kvcache_kernel` 见到 −1 直接 return，一个字节都不写 |
| `block_table` | **0**（块 0） | 块 0 永远落在预分配的 KV cache 张量里 ⇒ 读它合法；留 −1 会读第 −1 页 |
| `cu_seqlens_k` / `context_lens` | **0** | 空行读不到任何 key（与 vLLM 的 `seq_lens=0` 一致） |
| `input_ids` / `positions` | **0** | 合法值；算出来的 logits 丢弃 |

★ 硬约束：`cu_seqlens` 是**前缀和**，必须**单调不减**（flash-attn 的硬要求）。

**★ 「空行长度归零」是实测过的，不是照抄**：三种形状（`q=nq,k=1` / `k=0` / `q=0,k=0`）
**互相对拍逐位相同**，都不崩 ⇒ 采用 `k=0`（与 vLLM 对齐），q 侧保留 `nq` 以保住
「query 表总长 = q 行数」这条不变量。

### 8.3 结果

| 口径 | pad 关（默认） | pad 开 |
|---|---:|---:|
| `shape_not_captured(B=3,k=6)` | **18 ~ 23** | **0** |
| draft 前向退回 eager | 108 ~ 138 | **0** |

**★ 单次验证前向耗时（轻档，批里全是短上下文 ctx ≈ 120~130）**：

| B | 用的桶 | eager | 补进图后 | 加速 | 其中 padding |
|---:|---:|---:|---:|---:|---:|
| 1 | 1（精确） | 40.53 ms | **13.73 ms** | 2.95× | 0 |
| 2 | 2（精确） | 40.46 ms | **14.83 ms** | 2.73× | 0 |
| **3** | **4（补 1 行）** | **40.86 ms** | **15.55 ms** | **2.63×** | **23** |
| 4 | 4（精确） | 40.55 ms | **15.51 ms** | 2.61× | 0 |

★ **补 1 行的 B=3（15.55 ms）与精确命中的 B=4（15.51 ms）只差 0.04 ms（0.3%）**
⇒ **padding 的代价可以忽略**，而 B=3 从 40.86 降到 15.55 ms（**省 25.3 ms/次**）。

**★ 重档（批里混进一条 ~16K 的长序列）—— 一个必须一起写的边界**：

| B | 桶 | 是否补 | ctx_lens | eager | 图 | 加速 |
|---:|---:|---|---|---:|---:|---:|
| 2 | 2 | **精确命中（padded 0）** | [128, 16392] | 49.07 ms | 46.88 ms | **1.05×** |
| **3** | **4** | **补 1 行** | [132, 127, 16391] | **50.29 ms** | **47.51 ms** | **1.06×** |

⇒ **当批里有一条长上下文序列时，验证前向变成 GPU 工作主导，图能省的固定开销从 25 ms 缩到 ~2 ms。**
★★ **但这不是 padding 造成的**：`B=2` 那一行是**精确命中、`padded=0`**，同样掉到 1.05×。
而且把空行换成别的形状再量一遍，三种形状**完全一样**（47.51 / 47.67 / 47.52 ms）。
⇒ 是**既有的验证图**在长上下文下的固有性质，P16 只是继承它；
**即便如此，补进图仍严格优于 eager**，方向没变，只是幅度小了。

### 8.4 三条独立证据证明"默认关 = 老行为"

1. **精确桶上 `off ≡ on` 逐位相同**（verify 1+3=4 次、draft 1+3=4 次全部逐位）
   ⇒ **padding 的代码完全没有扰动原有的精确匹配路径。这是最强的证据。**
2. **B=3 的 `off` 就是纯 eager**（`off vs eager = 0.0000`，逐位）。
3. 补进图的 B=3 与 eager 的差（0.5625 / 0.1875）**落在既有「图 vs eager」地板（0.72~0.81 / 0.16~0.22）之内**，
   而且 argmax 一致率 100% ⇒ 这点差异是 flash-attn 分块累加顺序的固有差异。

另外：全量 CPU 测试 **514/514**；与干净 `main` 树逐文件对拍 stdout，14/16 完全一致，
另 2 个只差墙钟 / 对象地址。

### 8.5 ★ 行业对照：vLLM / SGLang 也是这么做的

（依据 `docs/投机解码显存与图-行业调研.md`，直读源码，带版本号 + 文件行号。）

| 问题 | vLLM | SGLang |
|---|---|---|
| **没精确捕获的 batch 怎么办** | `_compute_bs_to_padded_graph_size` 建 `bs → padded` 查表，落在两档之间就映射到上面那档；**只有 `num_tokens > max_size` 才退 eager** | `_pad_to_bucket` 用 `bisect_left` 向上取最近 bucket |
| **正好命中怎么办** | **映射到自己，零浪费**（只有落在缝隙才上取整） | 同上 |
| **padding 行怎么保安全** | `slot_mapping=-1` + kernel 早退（**完全不写 KV**）；`block_table=0`（NULL_BLOCK_ID）；`seq_lens=0`；`query_start_loc` 拍平 | `out_cache_loc=0` 指向保留槽（**写进一个会被丢弃的草稿槽**）；`seq_lens` 填 1 |
| **大 batch 怎么办** | **降 K 到 0**（`num_speculative_tokens_per_batch_size`，官方推荐 [1,64]→K=3 / [65,128]→K=1 / [129,512]→**K=0**） | `--speculative-adaptive` 默认配置 **bs ≥ 64 强制 0 步 = 投机关闭** |
| **怎么省 target 显存** | draft 复用 target 的 **KV cache group**（不开独立池）+ **共享 target 的 embedding 与 LM head 权重** | draft 有独立 KV，但新的 `UnifiedKVPool` 把 draft 的 lane **融进 target 同一块物理 buffer**（"same pages, same slot ids, same v2p table"） |
| **capture 表怎么排** | 投机场景把捕获尺寸**整体向上取整到 (1+K) 的倍数**；改按"请求数网格 × query 长度"生成 | ★ **spec 与非 spec 两张不同的表**：投机专用表小 batch 段 **1..8 每个都捕**（`less padding for smaller batch sizes`） |

**★ 我们和行业的差距（这是"下一步"的明确依据）**：

| 项 | 我们 | 行业 |
|---|---|---|
| 捕获表 | `{1,2,4}` 三个 | 小 batch 段 1..8 全捕 |
| 匹配不上 | ~~退回 eager~~ → **P16 已改成向上取整 padding** | 向上取整 padding |
| spec 专用表 | 无（和非 spec 共用） | 两张不同的表 |
| draft 显存 | **draft 有自己独立的 KV 池**，加载 draft 让 target 容量 88,832 → 45,312 token（−49%） | **KV 池与权重共享**（我们**还没做**） |

★ **vLLM 文档里那段话，正是我们实测出来的规律**：

> SD methods need to verify K tokens for each sequence during decoding.
> As BS increases, the effective BS becomes BS×K which increases the compute requirement during verification.
> When this BS×K goes beyond a critical BS then SD negatively impacts the decode speed (TPOT).

**翻成大白话：batch 大了以后，验证要算的 token 数是 BS×K，这个乘积超过某个临界点，投机就开始拖慢 decode。**
—— 这正是我们 P10 验收表里 `G→S6 = 0.71×`（B=4/4K）在行业里的说法。

## 9. 被否掉的方向（★ 这张清单和优化清单一样值钱）

| 方向 | 方案里的预期 | 实测 | 结论 |
|---|---|---|---|
| **P1：把自写 attention 接进引擎** | 方案排为**第一条开发主线**，4–7 人天 | f 只有 8–9%（ctx≤4096）→ Amdahl 上界 **+10%**，代入实测 kernel 加速比只有 **+3%** | **达不到方案自定的 +5% 门槛 → 按方案 §6.3 停止条件降级** |
| **真混合调度**（一轮内同时跑 decode 与 prefill 两个子批，串行版） | 直觉是"还能再压一个量级" | 上界 = **min(解码轮, prefill 块)**；而**串行版实测 `t_串行 = t_decode + t_prefill`，残差 −0.1 ms ⇒ 收益 0** | ★ **只做低风险的让路式 + 重叠执行**，不做"混进同一个 step"这个形态本身 |
| **P11：拒绝采样融合** | 「trace 证明成本值得才做」 | 采样只占 **0.81%** | 不做 |
| **P13：小算子融合（Add+RMSNorm / SiluAndMul）** | 2–4 人天 | elementwise 合计 **8.37%**，上限就这么多；采样器已被 torch.compile 融合成 1 个 kernel | 性价比过低 |
| **P14：KV 量化** | 8–12 人天 | 面经直接题 **0 道**；且我们**没有 KV 带宽瓶颈，只有容量问题** | 不立项 |
| **target 侧量化** | 会让普通解码也变快 | **会让普通解码也变快 ⇒ 削弱投机的相对优势**（实测 1.601× → 1.411×） | 不做（用户决策） |
| **P14 多序列轮转** | 任务书算的是"等 3 倍时间 ⇒ 变 1 倍、几乎免费" | 按轮数成立；**按墙钟只有最大 TTFT −16%（8K）/−30%（4K），而 p50 反而 +141%**；16K×3 被 KV 准入卡死；稳态吞吐 −12% | ★ **默认关闭的可选开关，不进推荐配置** |
| **warp specialization（CUDA kernel）** | 生产者/消费者分离，理论能再压一点 | 跑得起来但结果不对（竞态），修 4 轮停手；**只读探针给出上界 —— 整个计算侧只值 2.79 µs（10.8%）** | 低价值目标，停手 |

★ **还有一批"工具受限，所以不测"的**：ncu 硬件计数器在本机被禁（`RmProfilingAdminOnly: 1` 且无 sudo）
⇒ 改用 torch.profiler / CUDA event / 自写探针 / 机制级判据（TV(q_eng, q_ideal)）。
**不许因为工具受限就不测。**

## 10. ★★ 我自己推翻过的结论（面试官最想听这一节）

**"我做过什么"不难讲；"我被数据打过脸、并且承认了"才是可信度的来源。**

### 10.1 效应反号：一个 bug 伪装成了「机制收益」（最漂亮的一次）

**背景**：滑窗只留最近 M 块，把序列**最开头**的块全丢了，小窗口下接受率掉。
于是加了一个设计 P：**开头 P 块常驻（永不轮转）**。测出来效果惊人：

```
M=5 时：P=0 → α 0.404     P=1 → α 0.679     P=2 → α 0.704
```

**它被写进了推荐配置**（`(P=2, M=5)`）。

**后来发现滑窗的滑动路径有个 KV 对齐 bug。把它修掉之后重测**（32 格 × 3–9 遍）：

| | ctx | P=0 | P=2 | Δ(P2−P0) | 显著性 |
|---|---|---:|---:|---:|---:|
| `ALIGN=0`（老口径） | 8192 | 0.3720 | **0.6517** | **+0.2797** | **23.6σ** |
| `ALIGN=0` | 16384 | 0.3816 | **0.6016** | **+0.2200** | **9.6σ** |
| **`ALIGN=1`**（修好之后） | 8192 | **0.6414** | 0.6226 | **−0.0188** | **3.0σ（P 更差）** |
| **`ALIGN=1`** | 16384 | **0.6165** | 0.6031 | **−0.0134** | **2.1σ（P 更差）** |

**★ 效应反号（+0.28 ↔ −0.019）直接证明：P 的全部正收益 = 遮掩对齐 bug。**
⇒ **推荐配置从 `(P=2, M=5)` 砍成 `(P=0, M=5)`** —— 从 2 个旋钮砍到 0 个。

**★★ 这条比任何统计检验都硬 —— "一个机制在修掉别的 bug 后失效了"，说明它从来就不是那个机制。**
**连带结论：凡是写着"推荐配置 / 参数旋钮 / 经验规则"的结论，只要它是在已知 bug 未修的状态下定标的，
就必须在 bug 修完之后整张重核一遍。**

### 10.2 收益上界算错了 18 倍

**当时写的**：重叠执行的收益上界 = **一个解码轮 = 12.1 ms**（占实测尾部 3.2%–10.0%）⇒ 据此"有依据地暂不做"。

**问题**：12.1 ms 是**普通 decode（`spec_k=0`）**的解码轮读数（P15 逐值复核 **12.04 ms** ✓ 数字本身没错），
而基准场景写的是 **`k=6`**。同一个探针在 `k=6 + draft` 下量到 **220.2 ms（18 倍）**。

**修后**：上界 = **`min(解码轮, prefill 块)`**，实测每轮可省 **93.4 → 203.8 ms**（占上界 0.545 → 0.931）。

**★ 教训：「收益上界的量级」比「收益是否正确」更容易错，而且更难被发现。**
写"上界 = X ms"时，**必须同时写下 X 是在什么配置下量的**，并检查它与本场景的配置逐项对得上
（batch / k / 是否开投机 / ctx）。本轮对不上的地方正是 `k`。

### 10.3 假对照：测出「图跟 eager 一样快」

**第一版计时**测出 B=3 的验证前向「图 39.8 ms、eager 39.7 ms —— 图没用」。

**真因**：计时循环没按每个 B 重设 `_verify_extra`，**两边都走了 eager**（`static_shape_mismatch`）。
修好后真值是 **13.7 ~ 15.6 ms vs 40 ms（2.6~2.9×）**。

**★ 教训：任何 A/B 耗时对照都要有一条独立的「对照组真的生效了吗」的证据**（这里是 hits / fallbacks 计数）。

### 10.4 一次"逐字节对拍不一致"差点被当成自己的 bug

**现象**：P7-D 的逐字节对拍里，**默认路径**（代码上一行都没改的那条分支）两棵树 `out_md5` 不一致。

**做法**：不猜，**让同一棵树的同一个 CASE 重复跑 3 遍**。
结果：两棵树**都同时产出两个值** ⇒ 抖动是**环境噪声**（全上下文 draft 路径本来就跨进程不可复现）。

**★ 教训：「对拍不一致」要先排除"这条路径本来就不可复现"，再怀疑自己。
判据现成、成本极低：同一侧重复跑，看它自己是否稳定。**
（这条在本项目里**踩了三次**。）

### 10.5 "换一个更干净的仪器" —— 但必须换成"测同一个量的仪器"

**现象**：接受率用"自由生成 256 token 后统计"来测，跨批次漂移 **±4~13%**（0.7814 vs 0.6911），噪声压过效应。

**做法**：写了一个"离线固定上下文重建"的确定性仪器。它在 `w0` 上很准，
但在 `P=0` 上**偏乐观 0.25**（0.621 vs 引擎的 0.366）。

**根因**：**离线重建等价于"窗口永不滑动"这个理想极限**，它测的是**另一个系统**。

**★ 教训：换仪器必须换成"测同一个量的仪器"；判据是先在"已知答案"的格子上对一次**
（本轮用的是"窗口盖住全序列 ⇒ 必须与全上下文一致"那格自检）。

## 11. 方法论沉淀（这一节是可以直接背的）

### 11.1 找瓶颈的顺序

```
① 先建"约束地图"，别先优化
   profiler 把 decode 的 device time 分解 → GEMM 79.27% / attn 9.24% / elementwise 8.37% / 采样 0.81%
② 用 Amdahl 算上界，上界不够就收手
   attn 占 8–9% ⇒ 上界 +10%、代入实测 +3% ⇒ 直接降级整个方向
③ 用微基准验证"是不是真到硬件极限了"
   权重流式 763 GB/s = 峰值 81%；prefill ≈65 TFLOPS（峰值约 71）⇒ 两处都没有免费空间
④ 从约束反推该做什么（而不是从"技术很酷"反推）
⑤ 从"异常现象"里挖机会 —— 一个说不通的数字往往比约束地图更值钱
```

**★ 排查真正的交付物是三样东西**：
**一张约束地图** + **一张"被否掉的方向"清单**（和优化清单一样值钱）+ **一批可复用的测量资产**。

### 11.2 数字怎么才可信

| 手法 | 怎么做 | 本项目的例子 |
|---|---|---|
| **噪声地板** | 同一配置跑两遍，用分歧当地板 | 实测地板 `ms/轮` **0.05%–1.38%**；但 B=4 的合成素材上**高达 43–61%** ⇒ 那一档直接写"**分辨不出**"，而不是硬报一个数 |
| **配对 / 交替** | 同进程内 A/B/A/B 交替，报中位数 | `C`/`S1`/`S2` 是运行期开关翻转，**真配对** |
| **符号检验** | 数"更快"的配对占多少 | Q2 量化 B=1 四档 **36/36 全胜**，p≈1.5e-11 |
| **逐字节对拍** | 把基线单独放一份，用**同一个**脚本指过去跑，比每次前向的 `(tokens, positions, ctx, block_table, slot) + logits 的 bitwise md5` | P7 严格层：226 次草稿前向 **0 条不同** |
| **承重性反证** | 故意绕过守卫 / 关掉补齐，看指标会不会崩 | 绕过 draft 有效性守卫 ⇒ 接受率 **0.9 → 0.175–0.470** |
| **零收益对照** | 改动退化成老行为时，收益必须真的是 0 | P15 串行档 **`t_串行 = t_decode + t_prefill`，残差 −0.1 ms**；P14 的 N=1 退化档逐项在噪声内相同 |
| **对照的对照** | 先证明"两次相同的运行是相同的" | 同一棵树跑 3 遍，它自己产出两个 md5 ⇒ 是环境噪声 |
| **机制级判据** | 引擎实际分布 vs 理想重算分布的 TV 距离 | `TV(q_eng, q_ideal)` **0.685 → 0.016**（对齐修复前后） |

### 11.3 换仪器 / 换对照物

- **换仪器必须换成"测同一个量的仪器"**；判据是**先在"已知答案"的格子上自检**。
- **换对照物要换到"能看见机制"的那一层**：同一个疑点，拿离线重算当对照只能证伪"写坏了值"；
  拿**引擎自己声明的窗口**当对照，才看得见"写的上下文不对"。
- **"理想值"有两个意思**：物理上不可达的上限 vs 当前实现没做到的事。
  分辨方法只有一个 —— **把差异项解耦出来单独测**（这里是"同样截断、但让窗口起点不漂移"）。

### 11.4 结论怎么写

- **一句话总结永远连边界一起写**。
- **口径不一致的数字合集 = 没有数字**：`device time ≠ 墙钟`；`tok/s` 必须连报接受率；`B=1 ≠ B=4`。
- **百分比比绝对值更容易骗人**：同一个 31.5 ms，分母是"整条 4K prompt"时是 6%，
  分母是"未命中的尾巴"时是 70% ⇒ **凡是"占比"都要先问分母是什么状态**。
- **拿到收益 ≠ 理解了收益**：解耦分配那 +16~21% 的具体环节至今未隔离，就明确写"未隔离"。
- **"新功能没提速"不一定是坏消息** —— 要能判断它是"没效果"还是"测不出 / 本来就不该有效果"。
- **一条优化"没用"的时候，先问它被什么前置条件挡着**（P14：先要资源，再谈调度）。

### 11.5 错误分析决策树（可直接背）

```
出现异常
 ├─ 先问：这是【噪声】还是【真信号】？        → 跑同配置两遍，看分歧（噪声地板）
 ├─ 再问：是【我改坏的】还是【本来就不确定】？ → 同一棵树重复跑 N 遍
 ├─ 再问：是【算法】还是【开销】？            → 只翻 enforce_eager 一个开关对拍
 ├─ 再问：是【难想到的解释】还是【最容易想到的】？ → 先把最容易的做掉
 └─ 定位不到 → 上【逐轮打点】/【同进程多条件探针】/【机制级判据】，
              不要靠推理；并且【换仪器时要先在已知答案的格子上自检】
```

★ 三条**最贵的坑**：**静默 bug**（不报错、只悄悄出错）、**假仪器**（让我们相信了一个不存在的 +71% 机制）、
**口径混用**（招牌数字"B=4 提速 1.19×"在自然长文下其实是 0.71×）。
