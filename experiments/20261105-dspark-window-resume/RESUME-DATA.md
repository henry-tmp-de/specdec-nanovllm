# 本轮简历数据与建议写法

新增实现与实测发生于2026年11月，采用这些成果时，项目结束日期建议更新至2026.11。框架基于nano-vLLM，草稿权重来自官方DSpark；不写从零编写引擎骨架或自行训练草稿模型。

## 可以引用的数据

| 结论 | 必须连同保留的条件 |
|---|---|
| B1完整请求吞吐相对普通Graph解码2.34–3.39x | 单3090、Qwen3-4B BF16、DSpark block7、W512、1K输入/256输出、三个固定长度面板、各3次 |
| B8代码/数学相对普通Graph解码1.575/1.562x | 1K输入，其余同上 |
| B16代码/数学相对普通Graph解码+14.4%/+13.4% | 1K输入；通用文本同条件为-25.4%，不是普遍大batch收益 |
| B16相对0.6B AR窗口512为1.18–1.34x | 同一新源码的AR k6、块对齐W512；不能称所有原AR参数下最优基线 |
| 4K输入/B1、2、4时窗口相对DSpark全历史+4.4%–38.8% | 九个条件各3次；窗口还改变feature/投影；1K部分条件会回退 |

| target KV池槽数67,328→76,544，+13.7% | 同0.85初始化预算系数，分配池槽数，不是最大并发提升 |

完整请求吞吐与稳态decode口径不同。本轮是固定批量引擎基准，4K成功请求96.34%–99.54%为Wiki填充，不写成生产在线压测或长任务质量验证。详细定义见METHODS.md与FINAL_REPORT.md。

## 建议替换投机与滑窗两条

以下文本需与保留的旧混批/kernel条目分开条件，不把新DSpark与双流并发说成已联合验证。

```latex
\item \textbf{DSpark 投机解码与 CUDA Graph}：基于 nano-vLLM 接入官方 DSpark block-7 草稿模型，
  实现并行草稿 backbone、Markov 条件采样与批量拒绝验证，为 draft、target decode/verify 捕获精确形状 CUDA Graph。
  在单张 RTX 3090、Qwen3-4B BF16、1K 输入/256-token 输出的固定批量基准中，
  B=1 三类负载的完整请求吞吐相对普通 Graph 解码达到 \textbf{2.34--3.39$\times$}；
  B=16 的代码/数学负载分别提升 \textbf{14.4\%/13.4\%}。
\item \textbf{草稿 KV 滑窗与确认提交}：以独立块级环池保留 draft 最近 512 个历史位置，
  验证结果先暂存、仅提交确认前缀，target 保持完整上下文。
  在 16K/B=4 容量测试中，窗口版本完成四请求，DSpark KV 加验证暂存约
  \textbf{1.284 GiB $\rightarrow$ 40.64 MiB（$-$96.9\%）}，
  target KV 池槽数 \textbf{67,328 $\rightarrow$ 76,544（+13.7\%）}
  （全历史侧按已分配块数复算，非总显存峰值）。
```

显存条目的全历史侧没有成功的完整run：KV张量字节按日志实际分配块数和BF16尺寸复算，不能答成NVML或进程峰值测到1.284GiB。想要最少歧义，可以删去该百分比，仅保留“独立W512环池、16K四请求跑通、target池槽数+13.7%”，并在面试时解释全量侧预热OOM。

## 必须能说明的边界

- B16通用文本相对普通解码下降25.4%；4K/B16五种主方案均未满足本轮容量条件。
- DSpark环池目前要求prefix关闭、TP1、不开mixed overlap；原双流混批属于另外的target-only测试。
- 原0.6B的1.39x、82.3→132.5、PPL+0.455%、W8A16收益都不能改名迁给DSpark。旧量化若保留，明确是AR路径独立成果；本轮DSpark未量化。
- kernel旧数据属于独立算子基准，不能说已集成到此次推理路径。
- 本轮代码/数值验收通过不等于所有负载都更快；主分支未自动合并，保留实验分支和负结果。

原始条件、逐次值、输出hash、图/内存记录与最终账均可沿FINAL_REPORT.md链接核对；不使用论文加速倍数代替本机数据。
